第 1 课 · 技能机制

一次 /命令 的完整链路

你已经用过 /teach 这类技能，但不知道点下回车后机器做了什么。这一课给你一个能自己复述的五步链路——而且证据全部来自本课备课时的真实会话。

学完你能做到：别人问「技能到底是什么、跑在哪、用什么工具」时，不看资料讲出五步链路；并能指出技能在你仓库里的生效落点。

先立三个地基事实

① 技能不是程序，是指令文本。本机技能包是 25 个目录，每个目录一份 SKILL.md（外加若干格式说明文件），没有任何可执行逻辑。执行者永远是模型，技能只决定「模型读到什么」。实测：bundled-skills 下 25 个目录，teach/ 内 6 个文件

② 会话开始时你只拿到名册。harness 把技能名单（名字 + 一句话摘要）注入上下文，并明说「这只是摘要，未加载前不要推断其指令」。全文在点名那一刻才进入。出处：本会话系统提示 available_skills 段

③ 工具属于 harness，不属于技能。技能说「读这个文件、跑那条命令」，真正能读能跑的是模型手里那套工具；沙箱与审批策略随时可以否决它。这就是你第一个心结（代码不可控）的伏笔：技能文本 ≠ 能力许可。

五步链路（每步都有本课实证）

1

名册注入 — 会话启动，available_skills 名单进上下文。实证：本次会话开始时列出 30+ 技能名与摘要。

2

点名加载 — 你输入 /teach，harness 扫描技能根、按名命中，把 SKILL.md 全文作为 skill_content 块放进对话。实证：你这条消息下方紧跟一整块 skill_instructions。

3

按图施工 — 模型按指令调用工具。实证：本课备课依次用了 glob（找工作区文件）、read（读 4 个 FORMAT 文件）、pwsh（列技能包、验扫描根）、web_fetch（读上游 README）、ask_user_question（访谈你四问）。

4

落盘成状态 — 产出写进工作区文件（MISSION.md、RESOURCES.md、learning-records/），技能的「记忆」是文件，不是聊天记录。实证：你刚看到这 4 个文件被创建。

5

下次续读 — 新会话里模型先读这些文件，才知道教到哪了。会话可以断，状态在盘上。

生效面：技能从哪里被加载

扫描根是一张优先级表（数字小的赢），每层都「现测、不按记忆」：

rank位置本机现测（本课验证）
100项目根/.dsh/skills目录存在但无 skills 子目录 —— 且本仓裁定不放（它会改掉所有会话的生效版本）
200项目根/.agents/skills不存在
400~/.dsh/skills不存在
500~/.agents/skills存在（用户级技能落点）
600插件 bundled存在，25 个 = 你点名的 mattpocock 全家桶（pin v1.2.3）

直接推论（出自你仓的 skills.md，原始实测在 ADR-0024）：在移动端子树里放技能副本不生效——子树不在任何扫描根下，放了也是死文件，还会在将来某次路径调整后静默改变全会话版本。

你的第三问：在 uniapp-x 项目里怎么用？

答案一句话：技能跑在开发机的 harness 里，作用对象是 training-app/ 的代码——它不跑在手机上，也不需要跑在手机上。

  • 你在 D:\FL 开会话、敲 /grill-me 或 /tdd，加载与执行全程发生在本机；技能指令里的「读票 → 动手术 → 跑 npm run test:unit」操作的是移动端代码库。
  • 移动端自己那套会话纪律（grilling→to-spec→to-tickets 连做、一票一会话）写在移动端 AGENTS.md，与技能机制是两层：技能给流程骨架，AGENTS.md 给本仓规则，后者优先。
  • 「用户触发」与「模型自取」有别（上游 Reference 分法）：/teach、/grill-me 是 user-invoked（只有你能点名）；tdd、diagnosing-bugs 是 model-invoked（任务匹配时模型自己会拿）。
