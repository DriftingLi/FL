## 0. 结论（先看这五行）

1. **测试全部本机可跑**：233 个套件（行为 104 + 接线 129）都是 node 上的 jest，**不需要**真机 / 微信开发者工具 / HBuilderX；单套件现测 0.5–0.8 s（§1.3 实测）。
2. **覆盖极不均衡**：按键名反查，行为腿触达 **85/256 源文件（33.2%）**、接线腿 **229/256（89.5%）**、任一触达 **242/256（94.5%）**、**零触达仅 5 个**（`components/app-{badge,button,card,list-item,tabs}` 各 1 个 `.uvue`）。
3. **真正薄的是"页面级逻辑"**：61 条路由页里只有 **10 条**有任何行为套件触达（16.4%）；49 个页面级组件（`pages/*/components/*.uvue`）行为触达 **0**，19 个 `components/*` 行为触达 **0**。承重的覆盖集中在 `utils`（26/38）、`api`（22/29）、`types`（12/20）、`composables`（6/12）。
4. **② 能只跑 `changed:N`——但它不是模块级的**：`-Pages auto` 已是缺省（`scripts/mp-weixin-check.ps1:301`、`scripts/pr-gates.ps1:87`），三态语义在 `scripts/lib/mp-weixin-pages.ps1:105-122`。判据只认 `pages/**/*.uvue` 的**路径**，**不做路由过滤**（页面级组件也被算成"改动页"，§3.1 实测），**不做模块→页反向展开**（§3.2 给出扇出实测：改 `api/request.uts` 影响 67 页、`components/app-nav-bar` 55 页 ⇒ 展开在成本上不成立）。
   > **2026-11-05 补记（#2320）**：② 已整门退役，本条描述的是它退役前的选页能力；`scripts/pr-gates.ps1` 因此不再跑 ②，
   > 文中引用的 `pr-gates.ps1:87` 行号也随之失效（`-Pages` 降为兼容位）。
5. **对 `logicLiteTierOpen` 的事实输入（不裁定）**：以「模块级覆盖」作前置，则**前置今天不成立**——页面级逻辑几乎没有行为套件；且 `.uvue` 的组件导入不在任何依赖图里（`behavior-suite-deps.mjs` 的 `importGraph` 只收 `.uts`，94 节点）。转正 / 退役由后续决议票裁定。

### 1.2 分类口径（照 `docs/agents/guards.md` 的定义，不另立）

- **行为腿**（`jest.config.behavior.js`，`npm run test:behavior`）：文件里有代码级执行调用（`child_process` / `execFileSync` / `spawnSync` / `loadUts(` / `import(`）⇒ **承重**，是 ③ 门唯一回答得了「改坏它会不会红」的一腿。
- **接线腿**（`jest.config.unit.js`，`npm run test:unit`）：只读源码文本断言 ⇒ **不构成 ③ 证据**（算法坏了字面量还在时照样绿）。
- 两腿的 `testMatch` 由 `guard-split.js` 现算，**写死套件数是被 ADR-0046 明确禁掉的事**——本文件所有计数都是 2026-11-02 的读数，不是常量。

### 1.3 本机可跑性（实测，不是推断）

## 3. ② 能只跑 `changed:N` 吗

### 3.1 机制：已经默认开、且只认"页路径"

`scripts/lib/mp-weixin-pages.ps1:79-84` 对 `git diff --name-only origin/master...HEAD` 的每一行做 `(^|/)pages/.+\.uvue$` 匹配，命中就把路径换算成路由（剥 `pages/` 前缀与 `.uvue` 后缀），**没有拿 `pages.json` 的路由集过滤**。`Resolve-MpWeixinDirectCoverage` 三值互斥穷尽：

| 分支 | 判据 | `coverage=` | 取证页清单 |
| --- | --- | --- | --- |
| git 判据不可用 | `Ok=false`（git-unavailable / -timeout / -exit-N） | `none` | 空，**不退化冒烟集**（#2101：不把"不可知"包装成"已覆盖"） |
| 改动页为空 | `Ok=true` 且清单空 | `smoke:2` | `pages/dashboard/dashboard` + `pages/profile/profile`（门计划 `directPages.smokePages`） |
| 改动页非空 | `Ok=true` 且清单非空 | `changed:N` | 改动页（不含入口页） |

**实测边界（本次真执行判据库，不是读代码猜）**：

```
Range=408a891f~1...408a891f  coverage=changed:5
  pages/forum/components/forum-topic-card | pages/forum/forum | pages/forum/my-forum
  | pages/profile/components/activity-topic-card | pages/profile/personal-activity
```

⇒ 5 条里有 **2 条是页面级组件、不是路由**。它们会被拼进 `directList`（`scripts/mp-weixin-check.ps1:2397`）并逐条冷启动取证；落到别处就记 `landed-elsewhere`（同文件 `:2531`）、进 `missPages` ⇒ 组级 `partial`/`skip`（`:2571-2573`）。**读数被抬高、N 不实**——这是「② 的 `changed:N` 不能直接当模块级覆盖读」的第一条硬理由。

### 3.2 扇出：为什么"模块级定向"在 ② 上不成立

按 `.uvue`/`.uts` 的 import 逐层求闭包，反向数"有多少路由页会因此页受影响"：

| 改动落在 | 影响路由页数 | 占 61 条路由 |
| --- | ---: | ---: |
| `types` | 79 | — （跨页共享，单页不可切） |
| `utils` | 77 | — |
| `config` | 71 | — |
| `constants` | 68 | — |
| `api` | 67 | — |
| `components/app-nav-bar` | 55 | 90% |
| `stores` | 21 | 34% |
| `composables` | 12 | 20% |
| `utils/format.uts`（单文件） | 21 | 34% |
| `api/request.uts`（单文件） | 67 | — |

> 「影响页数 > 61」是因为闭包里也含页面级组件与被嵌套的共享文件；这里只用来看**量级**。结论：公共目录的改动扇出到几十页，**"按模块只跑受影响页"在 ② 上无从瘦身**——这也正是 `mobile-gate-core-list.json` 把 `api|stores|composables|utils|components|uni_modules|config|constants|i18n|types` 全列进 `alwaysFullGateDirPrefixes` 的合理性所在（不是漏了粒度，是粒度在此不成立）。

### 3.3 与 ③ 的分工（别把 `changed:N` 当测试子集）

- ② 的 `changed:N` = **取证哪些页**（截图/日志/元素探针），与测试无关。
- ③ 的"受影响子集" = 行为腿按改动路径算子集（`behavior-suite-deps.mjs`），入口 `npm run test:unit:changed`（接线腿**全量** + 行为腿子集，`scripts/dev-finish.ps1:1313`），且明写**不是门的证据**（同文件 `:1317`）。
- ADR-0052 决策 6 的 `planned=0` 双证链要的是「改动文件→套件映射机器算得为空」+ `discovered>0`，即 **③ 侧**的机器，不是 ② 的 `changed:N`。

## 5. 覆盖缺口（按对 `logicLiteTierOpen` 的影响排序）

1. **页面级逻辑的行为覆盖近乎为零**：61 条路由页只有 10 条被行为套件触达；49 个页面级组件与 19 个公共组件**均为 0**。页面里的 `<script>` 逻辑今天只被接线套件读文本守着——按 `docs/agents/guards.md` 判据，这不构成 ③ 证据。
2. **`.uvue` 组件导入不在任何依赖图里**：`behavior-suite-deps.mjs` 的 `importGraph` 只收 `.uts`（94 节点：api 27 / utils 27 / pages 17 / composables 9 / types 3 / uni_modules 3 / stores 2 / 其他 4），`components/**` 为 0 节点。⇒ "改 `app-nav-bar` 会影响哪些套件"这类问题，今天**算不出来**（§3.2 的扇出表是本票一次性现算的，不是仓内机器）。
3. **零触达的 5 个通用组件**：`app-badge` `app-button` `app-card` `app-list-item` `app-tabs`——纯展示、无逻辑，缺测试的代价低，但它们是"改了就没人看"的形态（② 也不直接取证）。
4. **② 的 N 不实**（§3.1）：页面级组件被计成改动页，读数偏高 + 可能 `partial`。属判据层，**本票不改**（票面明确"不动判据"）。

## 6. 限制与未核（明写）

- 「触达」是**键名反查的上界**：同名夹具会命中（§2 表头已注）。要"这个文件被断言了"的证据得看套件本体，本文件不替代逐个断言审计。
- 扇出表（§3.2）用相对 import + `@/` 别名解析，**不解析 UTS 条件编译分支**；`uni_modules` 内部实现未展开。
- 未核：`pages.json` 之外的动态路由（`navigateTo` 拼串）是否产生额外取证面；② 在本机实测中是否真的因页面级组件条目落 `partial`（本票只证到"判据把它算进 `want`"这一步，未跑一整轮 ②）。
- 计数会漂：套件数、触达数随 master 前进而变，**以 §1.1 的命令现测为准**。
