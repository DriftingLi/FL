## 1. 结论（维护者可直接据此裁 P0 实施票）

1. **落盘不是当前瓶颈，样本流才是。** 影子分支（SHADOW-0052 注记）进入默认分支的时刻实测为 **2026-10-31T15:38:07Z**（提交 7b1a331f，#2172；判据与 workflow 同一提交）。此后到最新一条 run（2026-11-02T02:13:47Z）共 **34.6 小时**，其间 pr-evidence 跑了 **13 次，命中运行时面 0 次 ⇒ 实时影子样本 = 0**。对照影子落地前 84.1 小时（10-28T03:22:29Z → 10-31T05:26:26Z）：**99 次 run / 命中 18 次 = 18.2%，约 5.14 命中/天**。先建载体不会凭空产生数据；先要的是「命中流是否恢复」这个观测结论。
2. **写入面已经存在两条落点，且都带影子行——但各缺一半。** pr-evidence.yml L117-121 把全部 notes（含 SHADOW-0052 行）写进 step summary；L127 用 core.info 把同一批 notes 打进 CI 日志。缺口：step summary **无任何 REST 端点可读**（workflow-runs 端点只有 run / attempt / jobs / logs / artifacts）；日志则在**判红路径下不含影子行**（L125 只 setFailed 打 errors，notes 不进日志），恰好漏掉最该看的失败样本。
3. **寿命天花板是 90 天，而且落在 run 记录本身。** 官方：workflow 运行记录（2026-10-01 起含 checks / runs / statuses / artifacts / logs）默认保留 90 天，公开仓可配 **1–90 天**，私有仓 1–400 天，变更**不追溯**。upload-artifact README 原文同样锁死「Artifacts are retained for 90 days by default」「The retention period must be between 1 and 90 inclusive」。⇒ 任何「只存在 GitHub 侧」的载体（summary / artifact / check run / 日志）都不能承诺超过 90 天的历史窗口；要长窗口只能把数据搬到仓外或仓内。本仓实测印证「不追溯」：可见 run 总数 10,655，最早一条 **2026-07-10T05:39:55Z（115 天前 > 90）**，即 2026-10-01 前的老记录未被追删。
4. **推荐载体 = 复算器侧「原始档 + manifest 版本戳」（E），保留 step summary 作人读面（A），本轮不引入 CI 写权限。** 硬理由三条：(a) pr-evidence.yml L26 明文承诺「本 job 不 checkout、不读评论、不写任何东西、不碰 actions/secrets」，任何 artifact / 台账 / check run 载体都要破这条不变式并新增写权限；(b) ruleset「protect master」实测 enforcement=active、**current_user_can_bypass=never**、必检项 ci-summary + ensure-testing-smoke、require PR 且 **require_extra_approval_for_unattributed_changes=true** ⇒ CI 直写仓内台账不可行，机器人提交还要额外批准；(c) GitHub 侧四种载体全部同受 90 天天花板，换了载体也没换来历史窗口。E 的实测成本极低：112 次 logs 调用全部成功（串行 + 0.15s 间隔，0 次限流失败），单包 **3,694 / 5,141 / 5,408 / 8,743 B**（min/p50/p95/max），全窗口 112 包合计 **530,061 B**。
5. **P0 若要成立，完整性判据必须先补，否则落的是「无法自证正确的数据」。** 现测缺口四处：复算器 L65 盲用缓存（只看文件存在，不看判据版本）；产物无版本戳（不记 validator 提交、不记名单哈希、不记取数时刻）；样本窗口依赖 gh pr list 默认排序（L108 未显式 --sort）；判红样本不进日志（上一条）。ADR-0053 P2 原文「复算器必须独立验证输入完整性，不得只是重复生成相同的错误结果」正是针对这一族风险。

**Q1 谁写、写到哪**：写入者是 pr-evidence 这一个既有 job，无新增执行体；影子行已同时进 step summary 与 CI 日志（成功路径）。**P0 真正要补的不是「新写入面」，而是「带版本戳、可在判红时也成立、能被机器读的持久档」**。

**Q2 谁读、多久读一次、成本**：唯一读者是复算器，人工、按波次触发（3a 一次）。若把「读 CI 日志」纳入常态：单 run 一趟 logs 调用取回约 5 KB，112 次串行实测 0 失败；200 PR 回放约 1.0 MB / 400 次调用。对照门本体 4–6 秒/趟，这条读路径的成本量级完全可接受，**成本不在 API，在人的触发频率**——所以 P0 该定的是采集节奏（见 §6 判据 5），不是采集工具。

**Q3 怎么证明输入数据没被篡改或缺失**：见 §6 五条可执行判据。核心思路是把「同一份数 = 同一套判据 + 同一个窗口 + 同一时刻」写成 manifest 字段，并让缓存命中条件依赖它，而不是依赖文件是否存在。

## 6. 完整性判据（可直接写进 P0 实施票的验收条款）

1. **manifest 必含字段**：validatorBlobSha（判据模块在默认分支上的 blob 提交短哈希，现测样例 7b1a331f）、coreListHash（mobile-gate-core-list.json 内容 sha256 前 12 位）、switches（两开关原值，本窗口现测 false/false）、capturedAtUtc、sourceCommand（逐条原样，含 --sort / --limit）、window（首末 PR 号 + 首末 mergedAt）、prCount、runtimeHitCount、shadowLineCount、patchMissingCount、anomalyCount（含 0）、cacheHitCount、cacheRebuiltCount。
2. **缓存键换掉**：L65 现在的判据是 fs.existsSync(cacheFile)，改为 (validatorBlobSha, coreListHash, prNumber) 三元组匹配才复用；不匹配就重拉并记 cacheRebuiltCount。堵住「判据改了还在用旧档」——这正是 P2 原文要防的「重复生成相同的错误结果」。
3. **窗口显式闭合**：L108 的 gh pr list 加 --sort merged --direction desc（现测默认序不保证），并把 window 首末两端写进 manifest；样本范围从此可复核、可复现。
4. **「0」必须显式**：anomalyCount=0、shadowLineCount=0、patchMissingCount=N 一律落盘。理由：判据 L222/L226/L227 只在特定条件下产出注记，缺行与产 0 行在文本上不可区分。
5. **CI 与复算器交叉验证（命中流恢复后启用）**：同一样本集，复算器给出的分档必须能在对应 run 的 notes 里找到同一行；找不到即判「落盘不可信」，停止扩大采集。这是 P0 与 P2 之间唯一必需的握手，成本一趟 grep。
6. **载体持久化动作**：复算器把 raw JSON + manifest + replay.json 一并落 .scratch/3a/（不入仓，沿 L14 既有约定），并在每次运行时**先拉后算**，确保原料在 90 天天花板内被搬离 GitHub 侧。若日后要多机/多人复算，再走 §4 的 B，届时前提「命中流已恢复」必须先成立。
