# 真链路吊销取证 · #1387（2026-09-29）

**结论先行**：`logoutApi()` 带上 `refresh_token` 之后，登出**确实吊销**手上那支长效凭证；
不带（改动前的形态）**照样能续**。本票判据 1 成立，不是「代码发出去了所以大概有效」。

## 环境与对象

- 后端：**production**（`https://www.gccsmile.com/api`）——也正是移动端 `API_BASE_URL` 打的那一个
  （`config/env.uts:20-22`，开发与生产同值），所以这一次验的是**真链路**而非本地替身。
- 账号：学员真实账号（凭据不入本文件、不入仓）。
- 方式：直接对三个端点发 HTTPS 请求（`logout` 带 / 不带 body 两组对照）。
  与客户端实现同一条服务端代码路径，因此它对「带 rt 是否生效」的判定是**等价**的。

## 读数（原始输出，未加工）

| # | 动作 | 期望 | 实际 |
| --- | --- | --- | --- |
| 1 | `POST /auth/login` | 200 | `HTTP=200 code=200 msg=登录成功`，`rt0.len=317` |
| 2 | `POST /auth/logout`（**body 带 rt0**） | 200 | `HTTP=200 code=200 msg=已登出` |
| 3 | `POST /auth/refresh`（用 rt0） | **401** | `HTTP=401 code=401 msg=登录已过期，请重新登录` ✅ |
| 4 | 重新登录 | 200 | `HTTP=200`，`rt1.len=317` |
| 5 | 对照：新 rt1 直接刷新 | 200 | `HTTP=200 code=200` |
| 6 | 对照：rt1 被轮换后再用一次 | 401 | `HTTP=401 code=401`（原子单次使用语义未被本改动破坏） |
| 7 | 对照：用轮换出的新 rt 再刷新 | 200 | `HTTP=200 code=200` |
| 8 | 对照：`POST /auth/logout` **不带 body**（改动前的移动端形态） | 200 | `HTTP=200 code=200`（服务端「静默成功」） |
| 9 | 对照：接着用那支 rt 刷新 | —— | **`HTTP=200 code=200 msg=success`** ← 登出没吊销，仍可续 |

## 这三条读数为什么一起才算证完

- **3 vs 9** 是本票的**主判据**：同一台后端、同一类账号，唯一差别是登出请求**带不带 body**。
  带 ⇒ 旧凭证被拉黑；不带 ⇒ 服务端照样回「已登出」，而凭证**仍可继续续期**。
  ⇒ 缺口 2 是真的，且这次改动确实修掉了它。
- **5 / 7** 排除了最容易被误读的一种假象：**「401 不是端点坏了，是那一支被专门吊销了」**——
  同一时刻别的合法凭证仍返回 200。
- **6** 顺带确认 ADR-0016 的**原子单次使用**语义没有被本次改动波及（轮换过的旧凭证照旧被拒）。

## 复现

对 `/auth/login → /auth/logout(带 rt) → /auth/refresh(同一 rt)` 三步发 HTTPS 请求即可，
期望序列 `200 → 200 → 401`；对照组把第 2 步的 body 去掉，期望 `200 → 200 → 200`。

## 未覆盖（照实写，别当成验过了）

- **App 进程内的实际发包形态**（logcat 里那条 `[request] >>> POST …/auth/logout data:{refresh_token=…}`）：
  本次是**服务端等价验证**，未跑真机 UI 全链路；真机侧的逐页取证见本 PR 的 ① 行口径
  （低风险运行时面：改动仅 `.uts`，按 `pr-evidence.yml` 的 `isLowRiskUtChange` 免 ①②）。
- **招聘者侧**：`logoutRecruiter()` 目前完全不打后端（本地身份槽复位），因此上面这套
  200→401 的效果**在招聘者态不成立** —— 已记在 ADR-0030 与本 PR 正文的遗留段，另立票。
