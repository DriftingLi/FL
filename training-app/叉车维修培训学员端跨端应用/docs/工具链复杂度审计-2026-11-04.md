# FL 移动端工程工具链复杂度审计与收敛方案（2026-11-04）

> **性质**：只读审计。**本轮不修改任何业务代码 / 脚本 / npm scripts / CI，不删除文件，不创建 Issue / PR，不改 ADR 或验收规则。**
> 本文是一次性盘点产出的新增文档（先例：`docs/门资产清算-2026-10-28.md`），不触达任何既有资产。
> **口径**：所有数字当场现测，命令记在 §11。跨版本失效的数字不写。

## 0. 一句话结论

**问题不是"脚本太多"，是"退役的概念还活着"。**

75 个 tracked 工具文件 / 25,428 行，对着 237 个测试文件 / 64,922 行 —— 这个比例本身在移动端是合理的（工程工具服务于跨端构建、真机取证、双门链，这些是 UniApp + HBuilderX + Android + 微信开发者工具带来的**必要成本**）。

真正可减的是三类：

1. **已退役但仍被 7 个脚本的参数面和 6 个守护的 34 条断言钉住的评论投递链**（A1 / #2100 后已不再 POST 任何评论）——这是**唯一"删掉净减代码且不降覆盖率"**的面；
2. **5 个仅参数不同的 npm 入口**，其中 2 个文档引用为 0；
3. **三份同形 adb 薄封装**（`Invoke-AdbTierCall`）与三份同形 adb 解析器。

结论：**不存在"过度设计"的整体判断，存在"局部沉积"**。整体加机制不是问题，问题是机制退役后判据不退场。

## 3. 大型脚本复杂度分析

**方法**：不以行数判拆分。判据是三条 —— ① 是否存在**多个互不依赖的退出契约**；② 是否存在**只靠参数区分的多种运行模式**；③ 是否**把业务判据、环境操作、证据生成混在一个进程里**。

### 3.1 `mp-weixin-check.ps1`（2835 行 / 34 函数 / 17 参数 / **62 处 `exit 2`**）

| 判据 | 读数 | 判读 |
| --- | --- | --- |
| 单一职责 | 是：只做 ② 门 | ✅ |
| 参数模式分支 | 4 组：`-SkipBuild` / `-BuildOnly` / `-Doctor` / 正常跑 | ⚠️ 3 个是**别人的活** |
| 职责混合 | 编译（`mp-weixin-build-fingerprint`）→ 发布 → 就绪 → 探测 → 导航 → 截图 → 归档 → 证据 | ❌ **五件事一个进程** |
| 收敛能力 | 已 dot-source 11 个 lib | ✅ 收敛度不低 |

**判断（2026-11-04 修订）**：**原判「应拆分」已被 ADR-0008 否决，现撤回。** 复杂度判断成立（五件事一个进程、17 参数、62 条 `exit 2`），但**拆分不是允许的解法**。

`docs/adr/0008-移动端验收门与证据.md:339`（2026-10-28 二次裁定，推翻首版"抽 `lib/mp-weixin-publish.ps1` + 新薄壳"）逐字写着 **「不抽库、不建薄壳」**，理由是四条「必须继承」：① `publishArgs` 唯一构造点（#2048 血账的复发形态）；② `finally` 里的 `devtools-close`（publish 尾段 5–6 ms 内必自启微信开发者工具）；③ 退出码三分 0/1/2 与结果行构造器；④ `HX_BUSY` 单实例锁 + `finally` 释放。`-Doctor` 与 `-BuildOnly` 与 `-SkipBuild` **同族**（ADR 原文），按同一裁定**一并不得拆出**。

**原报告「收益：17 → ~12 / 语义不再靠读头注释」作废** —— 该收益以拆走两个模式为前提，前提不成立。

**ADR 允许的降复杂度路子**：**计划数据化 + 判据抽纯函数**。同 ADR `:38` 的先例（`scripts/lib/screenshot-gate.ps1` 的 `Get-PngDiffVerdict`，"判定抽成可被真跑的纯函数，根因是判定散在 I/O 里 ⇒ 没人能真跑它"）；同 ADR `:910` 的先例（`Get-PublishStageVerdict`，"门与守护共用同一段裁决"）。**这条路本轮不设计**（该文件正被 #2254 改）。

**风险不变**：`utils/mpWeixinGateContract.test.js`（1685 行）有大量源码字面量锚点，任何结构性改动都会触发失配 —— 这也是 ADR 选择"不拆"的旁证之一。

### 3.2 `dev-finish.ps1`（1981 行 / 8 函数 / 19 参数 / 九步管线）

| 判据 | 读数 | 判读 |
| --- | --- | --- |
| 单一职责 | 否：九步管线 = 一个**编排器** | ⚠️ 但编排器本来就是它的职责 |
| 参数模式分支 | `-UnitGate` / `-UnitLocal` / `-Changed` 三条互斥出口 + `-DryRun` / `-Distribute` / `-Compile` | ❌ **6 种运行形态** |
| 函数粒度 | 只有 8 个函数管 1981 行 —— 主流程是**一条 1800 行的直线** | ❌ 可读性瓶颈 |
| 职责混合 | 编译 + 两腿测试 + 设备 + 截图 + 像素比 + 证据 | ❌ |

**判断**：**不应拆成多个文件，应把主流程切成有名字的阶段函数**。它已经是全仓的"完整验收入口"，拆成多进程会让 `dev:finish` 失去"一条命令拿到全部读数行"的价值。真实收益在**同文件内的阶段化**（现 8 函数 → 每步一个函数），使 `-Changed` / `-UnitLocal` 分支不必与设备步骤共处一个 1800 行直线。

**关键约束**：`devFinishContract.test.js`（1613 行）有一条断言判"本文件里每个步骤串的首次出现位置单调递增"（`dev-finish.ps1:213-215` 注释原文自述），重构时必须保持该不变式。

### 3.3 `wireless-debug.ps1`（803 行 / 27 函数 / 8 个子命令）——**最该拆的一个**

```
-Action 取值：status | ensure | keep | watch | stop | pair | on | probe   （8 个）
退出码：0 ×10 / 1 ×1 / 2 ×3 / 3 ×4 / 4 ×3 / 5 ×1                  （6 种语义）
```

**判读**：这是全仓**唯一**靠一个 `-Action` 参数承载 8 种互不相关运行形态的脚本。`watch`（常驻轮询，`-MaxHours 8`）与 `pair`（一次性配对）**没有共享状态**，`status`（只读）与 `on`（开无线调试）**没有共享判据**。

**结论：拆分**。至少切成「查询类（status/probe）」+「配对类（pair/on/ensure）」+「常驻类（keep/watch/stop）」三块。**收益**：退出码从 6 种降到每块 2–3 种；`connect:device` 的默认 `ensure` 语义不再需要读者先理解另外 7 个模式。
**风险**：`utils/wirelessDebugContract.test.js` + `wirelessDebugEnsureBehavior.test.js` + `wirelessDebugKeepRecoverBehavior.test.js` + `wirelessDebugBoundedTextBehavior.test.js` 四个守护覆盖它，拆分是**四改一**，成本真实。

### 3.4 不该拆但值得记的两个

- **`lib/auto-screenshot.ps1`（1636 行 / 21 函数）**：它被 4 个脚本复用，是**唯一**的"有界 adb 调用"真源。它的体积是"收敛"的代价而不是"膨胀"的证据 —— 拆它等于把已被收敛的重复再散出去。**保留。**
- **`lib/gate-common.ps1`（46 行）**：全仓最小的 lib 之一，因为它的**准入门槛极严**（文件头自述："各副本逐字节相同" + "没有被任何 `utils/*Contract.test.js` 作为字面量锚点 pin 住"）。46 行不是因为没东西可放，是因为**契约守护把门脚本源码字面量钉死了，搬进去就失配**。这是"测试守护在阻止收敛"的最直接证据，见 §4.3。

## 4. 职责重复分析

### 4.1 真实重复（可证实）

**(1) `Invoke-AdbTierCall` 三份同形**

| 落点 | 形态 |
| --- | --- |
| `scripts/device-capture.ps1:342` | 计数 → serial 取舍 → 委托 `Invoke-BoundedAdbText` → 超时点名 |
| `scripts/emulator-smoke.ps1:227` | 同上（注释几乎逐字相同） |
| `scripts/hx-run.ps1:232` | 同上 + `$script:TargetSerial` |

三份都**不重写执行核**，只做三件事：档位、超时点名、serial 取舍。这是**薄封装重复**，不是判据重复 —— 合并收益 = 少维护两份 20 行，风险 = 三个守护（`deviceCaptureBoundedShotBehavior` / `emulatorSmokeBoundedTextBehavior` / 相关契约）都要核。

**(2) `Get-AdbOutput` / `Resolve-AdbExe` 三份**

`scripts/emulator-smoke.ps1:251/266`、`scripts/hx-run.ps1:261/340`、`scripts/lib/env-check.ps1:28/36`。**`env-check.ps1` 已经是真源**（`auto-screenshot.ps1:1134` 注释明写"解析器的唯一真源在 `lib/env-check.ps1`……本文件**不得**再自带候选集"），但 `emulator-smoke` 与 `hx-run` 仍各自持有一份。

**这是本审计认为性价比最高的一处合并**：真源已存在、已被文档认定、合并方向明确。

**(3) adb 超时参数四面重复**

`AdbCallTimeoutSeconds` / `AdbTextCallTimeoutSeconds` 在 4 个文件里重复声明，引用密度：

```
device-capture.ps1   38 处
emulator-smoke.ps1   33 处
wireless-debug.ps1   17 处
lib/auto-screenshot.ps1  8 处
```

**判读**：这是"一次有界 adb 调用只有一个口径"这条正确原则的**实现代价**，不是设计错误。四个脚本各自暴露同名参数是为了可调，但默认值必须一致。**建议：不合并参数，改为 lib 里导出常量默认值，四个脚本引用它。** 收益小、风险极低。

**(4) 证据链路四模块叠加**

```
gate-commit.ps1      (266 行)  sha 绑定 + Send-GateComment（A1 起只打印）
gate-evidence.ps1    (117 行)  证据"形状"读取器（与 node 同源）
evidence-gen.ps1     (123 行)  A1 证据段生成
evidence-selfcheck.ps1 (127 行) ④c 出口自查
```

**判读**：**职责确实不同**（绑定 / 形状 / 填充 / 自查），不构成重复。但 `gate-commit.ps1:194-206` 的 `Send-GateComment` 已自述"A1 起只打印可粘贴的证据块，不再投递任何评论"—— 它现在与 `evidence-gen.ps1` 的**输出面重叠**。这是**候选合并点**，但两个都有调用方，需先证伪再动。

### 4.2 必要职责分离（**不是**重复，禁止合并）

| 看似重复 | 为何必须分开 |
| --- | --- |
| `screenshot-diff.ps1` / `screenshot-gate.ps1` / `png-diff.mjs` | 三层三职责：**I/O 对比** / **纯判定**（可被 pwsh 真跑成对断言）/ **像素算法**（纯 Node，CI ubuntu 可跑）。`png-diff.mjs` 头部明写"不用 System.Drawing：CI 跑在 ubuntu，.NET 6 起仅 Windows 可用" |
| `device-capture.ps1`（①a 真机）vs `emulator-smoke.ps1`（仿真机） | 两者都自述**非门**，但抓得到/抓不到的能力面**互补且不重叠**（仿真机抓不到生物识别 / content:// 上传 / 厂商 ROM） |
| `compile-check.ps1`（④a）vs `kotlin-all-check.ps1`（④c） | ④a 是"仅编译代码"（止于 `.class` + `dex`），④c 是整模块 kotlin 全量。945 秒里 71.9% 是后者的 kotlinc + dex 化 |
| `style-loop.ps1`（入口）vs `lib/style-loop.ps1`（纯判定） | 与 `wt-bootstrap.ps1` / `lib/wt-bootstrap.ps1` 同款分法：**纯逻辑必须能在 ubuntu CI 上 dot-source 断言**，副作用留入口。这是本仓被反复验证的最佳形态，不是重复 |
| `jest.config.unit.js` / `.behavior.js` / `.all.js` | 三腿分离是 ADR-0042 的裁定；`.all.js` 只服务 `--testPathPattern` 收窄跑法 |

### 4.3 测试守护重复保护同一实现细节

**这是本轮最实质的发现。**

`gate-common.ps1` 文件头自述：契约守护仍在**文本面**断言门脚本源码字面量，例如 `mpWeixinGateContract` 曾直接 pin 住 `Invoke-Process -FilePath $devTools -Arguments @('auto'`、`Write-Log "`n>>> devtools-open`、`$ProbeTimeoutMs = ` 等原文。后果：

> "把这类代码搬进共享库，守护会立刻失配，而唯一的「修法」是放宽守护 —— 那等于把防护拆掉。"

**这就是"改一处冒三处"的机制本体**：收敛动作会撞上钉死实现细节的文本断言，而放宽断言等于放弃防护 ⇒ 收敛被系统性地阻止。

量化：`utils/` 下 120 个 `*Contract.test.js`。至少 3 个明确以"源码字面量"为判据源（`mpWeixinGateContract` / `deviceCaptureContract` / `gateCommitBindingContract`），合计 3,460 行。**这些不是重复测试，是"以源码文本为契约"这一形态本身在阻碍重构。**

### 4. 哪些现有 Issue 需要修正目标或验收标准？

**结论：A、C 两条线本身不需要修正目标。需要修正的是它们与"退役残留"的关系边界。**

- **#2235 的 A-4「npm 层去留」**：建议在票面明确纳入本审计 §6 的 5 组"仅参数不同"表，避免 A-4 只做性能视角的去留判断而漏掉语义重复的 5 组。**这是补充范围，不是改目标。**
- **#2234 的验收标准第 5 条**（"`TEST_*_RESULT` 字段集 diff = 空"）：本审计建议**保留不动**。**但需注意（2026-11-04 校准）：** 原版本处写"若阶段 1 与 C 线同批落地，6 个守护文件的改动会让 #2234 的『73 → 0 逐文件核对表』失真"。实测后需拆成两句：
  1. **计数不会失真** —— C 线的归零对象是裸编码点 30（已归零），阶段 1 删的是 `-PostTo*` 参数与相关断言，两者不共享计数。
  2. **文件快照会错位** —— 阶段 1 要动的 `utils/devFinishContract.test.js`（6 条断言）与 `utils/mpWeixinGateContract.test.js`（9 条断言）**正是 #2254 冻结集成员**，其源码正被 #2254 修改。若同批落地，核对表的行号与文件状态会与 #2254 落票时的快照不符。
  ⇒ **这是顺序约束，不是验收标准缺陷。结论仍成立：阶段 1 在 #2254 收口后做。**
- **#2256（C-4 棘轮）的判据定义需要修正**（2026-11-04 新增）：现票面写"扫描裸 `execFileSync('pwsh'|'powershell'|powershellExe(...))` 形态调用，出现即判红；基线写死为 0"，**照字面实现必红约 20 处**——迁移后仍保留 `-File` 4 处 + `-EncodedCommand` 16 处调用壳（只换编码入口，未换调用壳）。建议判据改为「裸 UTF-16LE 编码字面量 / 未走 `encodeCommand`·`withUtf8Discipline` 的编码点」，基线 0 才可达。实测证据见报告 B §1.5。**这是本审计唯一建议修改验收口径的票。**

### 5. 是否需要新增独立的 D 线治理专项？

**不建议现在开 D 线。理由是 ADR-0053 自己的总成本尺。**

ADR-0053 决策 3 原文：

> "总开发成本 = 开发 + 验收 + 维护 + 返工……**为省少量验收时间而引入大量规则、Shadow 逻辑与工具维护，即得不偿失。**"

新开一条 D 线 = 新增：
- 1 个 spec 票 + N 个子票（B 线是 1+5，C 线是 1+4，A 线是 1+5）
- 每条线的阶段报告、验收表、状态同步
- 一条新的"治理线"概念本身要进 `AGENTS.md` 并长期维护

而本审计识别的问题总量是 **1 个净减项 + 4 个收敛项 + 1 个归档项**，全部可在 A/B/C 的现有边界内以 ≤3 张一次性小票完成。

**替代方案**：把阶段 1 作为**独立小票**（不属于 A/B/C 任何一条），阶段 2–5 按归属挂到 A（npm 层 / 性能读数）与"工具链维护"常规改动。**若之后仍反复出现"改一处冒三处"，再考虑 D 线 —— 那时它就有实测依据，而不是先建线再找问题。**

### 6. 最终建议的移动端工具体系应该是什么样子？

**一句话：四入口 + 双门链 + 一次性工具归档，且退役的东西必须退场。**

> **2026-11-04 修订**：本图「按需层 9 条」与「内部实现 5 条」已按 §6 的三层口径更正 —— 原内部实现里的 `test` / `test:unit` / `test:behavior` / `test:unit:local` / `test:unit:gate:local` **不是内部实现**（它们可直调、有文档、且按腿排障是刚需），属**层 2 专项公开**。层 3 只剩 2 条。

┌─ 层 2 专项公开（可直调、有文档、稳定契约，不要求日常记忆）┐
│  测试：test / test:unit / test:behavior /            │
│        test:unit:local / test:unit:gate /            │
│        test:unit:gate:local                          │
│  构建：build:compile / build:kotlin-all /            │
│        build:mp-weixin-check /                       │
│        build:mp-weixin-doctor /                      │

│  门与迭代：gates:pr / style:loop / dev:finish:dry    │

│        connect:device / setup:android-sdk            │
└──────────────────────────────────────────────────────┘
┌─ 层 3 内部实现（仅被其他命令调用，不作为稳定入口）──────┐
│  test:behavior:local（退役归 #2235 A-4）             │
│  dev:finish:distribute（0 引用）                     │
└──────────────────────────────────────────────────────┘
┌─ 归档（不删，移入 docs/verification/_tools/）────────┐

**条数核对**：层 1 **4** + 层 2 **14** + 层 3 **2** + 按需专项 **5** = **25** ✅ 一条不多一条不少。权威逐条表见修订文档 §2.7。

> 注：上图中「层 2」框内的「按需」小节是**并列的第 4 组**（5 条），不是层 2 的成员 —— 分列展示只为让读者在一个框里看全"可直调但不必日常记忆"的面。严格计数时 层 2 = 14 条、按需 = 5 条，两组相加 19。

**三条判据**（供后续任何新增工具对照）：

1. **有一件事，才有一个脚本**。一个脚本承载 ≥3 种"只靠参数区分、无共享状态"的形态时，它已经是多个工具（`wireless-debug.ps1` 的 8 模式）。**但例外必须先查 ADR**：`mp-weixin-check.ps1` 的 `-Doctor`/`-BuildOnly` 看似符合本条，却被 ADR-0008 `:339` 以「四条必须继承」明确否决拆分 —— **判据不能覆盖已裁定的架构决定**。
2. **判据与 I/O 分离**。纯判定必须能 dot-source 并在 ubuntu CI 上真跑（`screenshot-gate.ps1` / `lib/style-loop.ps1` / `lib/wt-bootstrap.ps1` 是本仓已验证的形态）。这也是 ADR-0008 允许的降复杂度唯一路子（`Get-PublishStageVerdict` 先例）。
3. **退役即退场**。一条裁定退役时，它的参数、分支、断言必须在同一批或明确的下一批里消失。否则就是 10-28 §4 和本审计 §5.1 的重复。

## 12. 复算命令

```bash
# 基线
git log -1 --format='%h %ad %s' --date=iso
git ls-files scripts | wc -l
git ls-files scripts | grep -E '\.(ps1|mjs|cjs|js)$' | xargs cat | wc -l
ls utils/*.test.js | wc -l && cat utils/*.test.js | wc -l

# 引用数（五面口径：package.json + .github/ + docs/ + utils/ + scripts/）
for f in $(git ls-files scripts); do
  b=$(basename "$f")
  n=$(git grep -l -F "$b" -- . ':!node_modules' ':!.opencode' | grep -v "^$f$" | wc -l)
  echo -e "$n\t$f"
done | sort -n

# 退役参数残留
grep -rn "PostToIssue\|PostToPr" scripts/ | wc -l
grep -rln "PostToIssue\|PostToPr" utils/*.test.js
grep -rn "gh api\|gh pr comment\|gh issue comment" scripts/ | wc -l   # 期望 0

# 脚本结构
for f in scripts/*.ps1 scripts/lib/*.ps1; do
  echo -n "$f funcs="; grep -cE '^\s*function ' "$f"
done

# 趋势
git log --since=2026-10-28 --diff-filter=A --format="" --name-only -- scripts/
git log --since=2026-10-28 --diff-filter=D --format="" --name-only -- scripts/

# npm 文档引用
for c in $(node -e "console.log(Object.keys(require('./package.json').scripts).join(' '))"); do
  n=$(grep -ro "npm run $c\b" AGENTS.md docs/ ../../AGENTS.md ../../docs/agents/ | wc -l)
  echo -e "$n\t$c"
done | sort -rn
```
