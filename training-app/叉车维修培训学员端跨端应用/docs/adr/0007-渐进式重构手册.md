# 0007 - 渐进式重构手册：页面层手术 + api 契约收紧

**状态**：定稿（T02 mall + T03 profile 两模块复盘收束；T04 forum 术后补录与 600 预算第三复评结论见文末，2026-09-08；决策清单见 `docs/refactor-decisions.md`）
**来源**：重构 epic #638（四轮 grilling 收束），试点工单 #640

## 背景与目标

学员端（uni-app-x，约 4.2 万行、53 页）随迭代出现巨型文件（20 个源文件超 600 行）、页面层重复无沉淀、api 契约不一致（请求基座裸 `any`、部分域无 DTO）。目标：治类型/编译痛点 + 可维护性 + 为功能迭代提速。**性能与 UI 重设计不在目标内。**

## 决策

### 形态：渐进绞杀，非大爆炸

- 每模块 1 分支（`refactor/<module>`）+ 1 PR + 1 专注会话；每 PR 合并即直发 production（squash revert 即回滚），不改 CD 流水线
- 模块级冻结：手术期间该模块冻结新功能；**纯机械 import 迁移不算破坏冻结**
- 手术顺序按体量降序（mall 试点先行）；login 单独 pin 在生物识别线合并后

### 靶子：页面层手术，骨架不动

- `pages/ components/ api/ stores/ utils/` 顶层保留，不做 `features/` 迁移（pages.json 53 路径 churn + easycom 约束 + UTS import 脆弱，负收益）
- 巨型页面拆 section 组件/composable；不拆子路由（除非产品本就是多页）
- **单文件软预算 ≤600 行**（全文件计），模块目录 ≤2 层。试点起以契约测试机检锁定已达标模块（防回潮），未达标模块不强制全库扫描
- **UI 像素级冻结**：界面必须与手术前一致，UI 问题记 issue 不顺手改。冒烟基线 = 前后逐页截图对比

### api 契约收紧：requestMapped / getMapped 出口家族

- 出口形态 = mapper-callback（与 ADR-0003 手动 JSON 映射同构）：`requestMapped<T>(opts, map)`；GET 走便捷面 `getMapped<T>(url, params, map)`——**params 沿用手动 query 序列化，不交平台自动序列化**（试点发现：跨端序列化行为有漂移风险，`get()` 的手动拼接是实证安全的行为，收紧不得改变请求形态）
- 每域 api 导出显式 DTO + build* 映射函数；页面层只 import 域 api（2026-09 探针实测页面层直接 `uni.request` 为 0，暂无独立守护规则；若新增违例在 #654 收尾票立项）
- 既有 `request/get/post` 原样保留（expand–contract），页面接线迁移按票推进

### 拆出物安置与晋升

- 模块私有组件/composable 放 `pages/<module>/components|composables/`，**显式 import**（PascalCase 标签 + kebab-case 事件绑定，同 ai-chat 先例；easycom 仅全局件）
- 全局 `components/`、`composables/` 只放已确认跨模块复用件；**第二个模块需要时晋升全局**，晋升 PR 允许机械改使用方 import
- 手术 PR 内允许增量式抽取（新建共享件 + 当前模块采用），不碰其他模块行为代码

### 静态守护与契约测试纪律

- `utsAndroidCompile.test.js` 沿用「纯函数扫描 + 注入违规自检 + 全工程断言」模式按遭遇增量扩规则；存量违例走 `GUARD_ALLOWLIST`（expand 侧），各手术票清自己范围，epic 收尾票删机制
- 手术 PR 内契约测试可更新文件路径指向，**禁删/弱化断言**（弱化须引用 issue）
- 不新增组件级测试（uvue 无生态）；行为回归靠四门冒烟

### 每手术 PR 四门验收

1. Android 真机逐页截图前后对比（人工签收）
2. 微信开发者工具逐页打开无报错（人工）
3. `npm run test:unit` 全绿（既有失败须可指认到独立 issue）
4. HBuilderX 真机运行全量编译无新增 error（人工）

**push 前先 `git merge origin/master`**（试点教训：分支基点过期会同时触发 ruleset up-to-date 门禁与迁移版本预检两道拦截）。

**四门的现行口径以 ADR-0008（移动端验收门与证据）为准**——门的分级判据（运行时面）、证据四字段、`pr-evidence` 必检与 ruleset `approve=1`、dev 编译门与 release 云打包门的拆分，见 0008；本节只保留「有哪几道门」的历史叙述。

## 试点复盘（keep–adjust）

- **keep**：拆纯展示/纯动作段（排序栏、悬浮组）成本低收益高；业务数据区（商品列表+必买清单+分页加载）留主文件不硬拆；600 预算 442 行达标且未过度碎片化
- **keep**：契约测试机检组件接线（防"import 了但没用"与静默回退）
- **adjust**：出口家族需 GET 便捷面（getMapped）——spec 只写了 requestMapped，试点第一步即暴露 GET 参数序列化的形态保持问题

**删除禁区型工单：三向归一化 diff 审计（T05 verbatim 审核的细化）**
「不删既有实现」与「拆文件」同时成立时，「搬」与「改」的边界必须有证据。本票把 T05 的归一化 diff 拆成三向（临时脚本，收口即删、不进仓）：
① **CSS 规则集**（selector → 归一化声明集）：旧 56/49 条 → 新 56/49 条，零声明漂移；
② **模板 token 级 LCS**：组件模板按页面用法展开、prop 名反代回旧表达式后与旧模板对齐，漂移清单只剩刻意项（`.action-area` 单根包层、retry handler 薄包装改名、结果页行别名 `detail`→`row`）；
③ **脚本行级 LCS**：删行只允许出现「import / 显式结果类型 / 被 utils 接管的纯函数 / 合并的 computed」，加行只允许「composable 骨架 + 页面薄包装」。

- **新坑位（审计工具自身）**：token 切分**不能按裸 `>` 切** —— `:is-last="currentIndex >= questions.length - 1"` 里的 `>=` 会把标签切碎，导致组件展开失败并**误报 20+ token 漂移**；正确切法是「引号外首个 `>` 才收尾」。**一般教训：审计器用正则扫模板属性前，先问「属性值里会出现我要找的分隔符吗」。**
- **新增判据：单根包层可接受**。页面里两个同级块（`.action-bar` + `.submit-section`）搬进单个组件时，uvue 单根要求多一层 column 容器（`.action-area`）。判据 = 包装层无 padding/背景/尺寸且不翻转 flex 方向 → 视觉零漂移。这是 T05「模板留壳层」的**同一问题在相反条件下的结论**：那里状态所有权在页面（v-if 重挂载会重置态）故留壳，这里只是布局容器故可搬。
- **静默回退去留按「是否掩盖面」+ 本票禁区双判**：`getMockExamHistoryApi` 的空表回退**保留**（既有行为、无幻影路由、两个消费方各自另有 try/catch 与可见错误态），并在契约里显式钉死「api 层唯一一处 `.catch` 且落在 history」——**保留是决策，不是惯性**；是否退役并入 #652/#653 域 api 批量收尾。

### 「未解锁 / 不存在」判定口径（#1204 → #1268 第二例，2026-09-22）

- **HTTP 状态码只有一个承载通道**：`api/request.uts` 的 `handleStatus` 把 404/403 折成消息前缀常量（`NOT_FOUND_MESSAGE_PREFIX = '404:'` / `FORBIDDEN_MESSAGE_PREFIX`）再 `reject(new Error(prefix + msg))` —— UTS 侧不能 `extends Error`、也没有 Error 子类先例，前缀是**唯一**能把状态码送出 request 层的形态。调用方判 404 只能比前缀，**不许按后端中文文案匹配**（文案一改语义就静默改变，#1204 的成因）。

  - ① **显式** `key: fn` —— `use-dashboard-credential.uts` / `use-dashboard-feeds.uts`（T05 #763），8 处，随 **#800** 修
  - ② **速记** `{ fn }` —— practice 的 4 个 composable（T06），36 处，随 **#802** 修

- **落锁**：守护规则 T（`scanBareFnRefInReturn`）扫「return 对象字面量内、值为同文件函数名的成员」，**显式与速记两种形态都判**、不设类型标注前提；带注入违规自检（两形态各一）+ 箭头反向自检 + Ref 速记放行自检。全工程零命中。

### 缺口三（守护侧）：同名异形类型让规则 L 误报

- **现场**：规则 L 报 `dashboard-menu-grid.uvue` 三处「参数 item : MenuItem 访问未声明字段 path/available」，但该文件**本地就声明了含 `path`/`available` 的 `MenuItem`**，Kotlin 侧完全合法——是守护误报。

### 缺口四：返回函数的 composable 缺显式结果类型（Kotlin error18）

- **现场**：#803 给 practice 的 4 个 composable 补了箭头（缺口二）后，下一轮 HBuilderX 改报 `找不到名称 "onNext"` / `找不到名称 "value"`——`practice-do.uvue` 对 `session.onNext` / `session.currentQuestion.value` 的成员访问全部解析不出。原因是 return 对象**无显式类型**，UTS 在消费侧还原不出它的成员。
- **关键区分**：箭头与显式类型是**两件独立的事** —— 箭头治 error17（函数字段被当调用），显式类型治 error18（成员解析不出）。**只补其一都不够**；合法形态 = 两者同时具备。先例 `composables/useTopicDetail.uts`（显式 `UseTopicDetailResult` + 全部箭头字段）。

- **教训（第二次同类）**：**只按「日志里报了什么」下刀不够**。#803 修完 error17 就收手，没去核对「本仓同类文件都长什么样」——而先例比对（14/14 同款写法）本可以一次性给出完整形态，省掉一整轮编译。**修一类问题前，先看这一类在仓里的既定写法。**
- **另一条流程教训**：本轮日志夹杂了差量编译读到的**过期文件**（16:51 那条打印的是上一版单行内容），把已修好的问题又报了一遍。看到日志与磁盘不一致时，先怀疑编译缓存，要求一次干净重建再判定。
### 缺口五：async 函数缺返回类型标注（Kotlin 推不出 UTSPromise 的 T）

- **现场**（**云打包 release 编译**，`compileReleaseKotlin`）：
  `wrong-questions.kt:49` 报 `Cannot infer type for this parameter. Specify it explicitly.` / `Not enough information to infer type argument for 'T'.` / `Return type mismatch: expected 'Unit', actual 'UTSPromise<uninferred ERROR CLASS: Cannot infer argument for type parameter T>'`。

- **与规则 R 的关系**：规则 R 覆盖的是 `async fn() : void`（**写错**的标注）；**不写标注**是另一个子类——Kotlin 生成 `UTSPromise<T>` 而 `T` 推不出来。两者都归「UTSPromise 类型参数不可推断」这一族。

### 缺口六：模板裸 handler 未定义（error18 找不到名称）

- **现场**：`practice-do.uvue:5` 模板 `<view class="nav-left" @click="onBack">`，但 script 里**没有 `onBack`** —— 重写该文件时只保留了 `onExit`，漏带了导航返回按钮的 handler。Kotlin 报 `找不到名称 "onBack"`。

## types 域拆分两个坑位（2026-09-11，PR #830）

types 域拆分的独立重构（把 1,151 行的 `types/index.uts` 按域拆成 15 个文件 + barrel re-export 壳），不属 T01–T13 工单序列，但产出两条守护/选型教训，按「新决策回写纪律」落此。

### 坑位一：UTS 编译器不支持 `export type { X } from './y'`

- **现场**：barrel 壳先写成 `export type { ForumTopic, … } from './forum'`，HBuilderX 编译报
  `Cannot create property 'code' on string 'load_transformed failed … failed to resolve ./common from …/types/index.uts … index not found'`。
- **结论**：UTS（编译到 Kotlin）**不支持** `export type { … } from` 形态。合法形态 = `export { type X, type Y } from './y'`（inline type modifier），已编译签收。
- **旁证**：同仓 `stores/index.uts:5` 早有值形态 `export { useAuthStore } from './auth'` 且长期可用 —— 所以「barrel 不可用」的说法不成立，**只有 `export type {…} from` 这一形态不可用**。
- **教训**：UTS 的重导出语法是子集，选型前先找**仓内既有先例**（同 T06 缺口四的教训）；「值可重导出」不能推广为「类型也可」。

### 缺口七：规则 K/L 的字段表被 barrel re-export 行污染（本机绿 / CI 红）

- **现场**：barrel 壳落地后 **CI 的 `mobile-test` 红、本机全绿** —— 规则 K/L 对 `NotificationItem` / `SearchItem` / `ExamQuestion` 报「访问未声明字段」共 21 处，而这 3 个类型的字段在域文件里一个不少。
- **根因（双因叠加，缺一不炸）**：
  1. `buildTypeFieldMap` 的类型头正则 `[^{]*\{` **可跨行**。barrel 行 `export { type X, type Y } from './y'` 被当作类型头 —— 正则里的 `{` 取自**下一行**的 `export {`，于是 X 以「零字段」入表。
  2. 入表判据是 `!fields.has()`（**先到先得**）。谁先被读到谁胜出，而 `readdirSync` 顺序 **NTFS 与 ext4 不同** —— 同一份代码两端结论相反。
- **性质**：**「本机绿 ≠ CI 绿」的第二形态**。第一形态是「jest 绿 ≠ 能编译」（T03/T06 已录）；这一形态是「本地守护绿 ≠ CI 守护绿」，根因是**判定依赖文件系统枚举顺序**。二者都指向同一条：**本地单测全绿不构成合并依据**。
- **落锁**：
  - 类型头与 `{` 收紧为**必须同行**（`[^{}\n]*\{`）。已逐一核对全仓 `.uts` 无「`{` 在类型头下一行」的声明，收紧不丢类型；barrel 的四种写法（`export type {X} from` / `export { type X } from` / `export * from` / `export { X } from`）收紧后**均不命中**。
  - 新增**「字段表与文件遍历顺序无关」自检**（`utsAndroidCompile.test.js` 守护自检段）：对同一份 `.uts` 清单**正序 / 逆序两次构建，结果必须完全一致**，并对曾受害的 3 个类型断言其字段集非空且含真实字段。已实测**旧正则下该锁必红**（`authenticate` / `checkSupport` / `isSupported` 正序有字段、逆序为空），新正则下绿 —— 锁具备 red-capable，符合「注入违规自检」的既有范式。
- **一般教训**：**任何「先到先得」的全局表，都必须显式锁「与遍历顺序无关」**——跨文件系统的 `readdir` 顺序不可假定。写守护规则时先问：「这个判定的结果，依赖文件被读到的顺序吗？」；跨端项目里还要再问一句：「两端文件系统枚举顺序一致吗？」

## 门脚本守护改口径：断言行为而不是源码文本（2026-09-13，#914，属「手术 vs 收束」的**前置收束**）

**现场**：门脚本守护（`utils/*Contract.test.js`）断言的是门脚本的**源码字面量**，而实测被 pin 的锚点里有几条正好是**调用点原文**（`Invoke-Process -FilePath $devTools -Arguments @('auto'`、`@('open', '--project', $dist)`、`Write-Log "…>>> devtools-open`、`$ProbeTimeoutMs = `）。后果：任何把进程调用/日志/证据行抽进共享库的重构都会让守护立刻失配，而唯一的「修法」是放宽守护 —— 等于把防护拆掉。于是门脚本家族（9 个脚本约 4,600 行 + 只有 169 行的 `scripts/lib/hx-busy.ps1`）事实上**冻结在重复状态**。

**决策（#914）**：把「步骤序列 / 每步参数与判据 / 超时预算与 exit 2 归属 / 结果行字段清单」四类不变量从调用点原文收成**一份数据**（`scripts/mp-weixin-check.ps1` 的 `New-GatePlan` → `-DryRun` 输出单行 `GATE_PLAN {json}`），执行路径按 id 取用（`Get-GateStep`），守护改为**跑 `-DryRun` 并断言这份 JSON**。决策的理由与代价记在 ADR-0008「门脚本共享载体」节（该票的 ADR 触发条件：决定**做**收束 ⇒ 必须补 ADR）。

**同族的三类脆弱（本票一并处置，逐条实测）**：

1. **在注释/帮助文本上误报**：C14 的规则是「行首 `-Word` 的行，上一行必须以续行反引号结尾」，它在 `device-capture.ps1` 上误报 **3 条** —— 命中的全是 `<# .DESCRIPTION #>` 里的 help bullet（`-Pages` / `-AllowAppStart`），那本来就不是续行参数。**处置**：规则收窄为**只对代码行判**（剥离 `<# … #>` 块注释与 `#` 行注释，**行号保持不变**），并加对 `device-capture.ps1` 的零命中用例 + 合成样本（help bullet 不报 / 代码里的真断链要报）。
2. **子串遮蔽**：`s.includes('[switch]$Doctor')` 会被 `[switch]$DoctorX` 这类改名蒙过去（子串仍在），注入用例因此抓不到（已修为 `/[switch]\$Doctor,/`）。**本票又踩了一次同族的坑**：C12 的位置判据原本拿裸 `no-dist` 当锚点，注入用例把 `reason=no-dist` 改成 `reason=no-dist-X` 时**判据依然为真**（子串还在）—— 换成整条字面量 `'MP_WEIXIN_RESULT errors=env reason=no-dist'` 才 red-capable。**教训**：位置/顺序类判据的锚点必须是**整条字面量**，且要真跑一次「把锚点改坏」的注入确认它能红。
3. **用 `indexOf` 比先后顺序**：断言「`open` 出现在某锚点之后」靠的是字符串位置而非结构 —— 插到前面的代码可能悄悄改变判据含义，且锚点消失时会**静默放行**（旧写法 `if (a !== -1 && b !== -1) must(...)` 就是 fail-open）。**处置**：顺序判据搬到计划的步骤序列上（那份数据**就是**执行顺序）；仍留在文本面的位置判据（`open` 的执行点晚于构建分支的 `no-dist` 兜底）改成**锚点找不到即判红**的 fail-closed 形态。

**一般教训**：守护的判据面应当落在**行为输出**上；非要在文本上判时，① 只判代码行、不判注释；② 锚点用整条字面量、不用裸词；③ 锚点缺失必须判红、不得静默放行。三条都由本仓既有的「注入违规自检」范式覆盖 —— 本票新增的注入用例里，**每一条**都是先写注入确认能红，再对真实文件断言零命中。

## 图标字形遗留缺陷收口与字符级落锁（#1071，2026-09-17）

T08 复盘只把「图标字形只能机检、不能目测」记成坑位、未落锁，缺陷本身按「发现的 UI 问题记 issue，不顺手改」另立了 #1071。本票是那笔债的收口：**全仓 29 处空槽归零 + 4 处孤立 U+FE0F 归零 + 字符级守护落锁**。

### 坑位一：非 BMP 字形在批量改写中被静默吃掉

- **根因确证到提交级**：`f1ab2648`（PR #361，2026-08-31）批量改写移动端源文件时把**非 BMP（星形面）字符**成片吃掉，**BMP 字符原样幸存**。12 个文件的删除行含非 BMP 字形、9 个文件的非 BMP 数量在该提交后净下降，合计 28 个字符。
- **判别特征极干净**：幸存的是 `⚠️`(U+26A0)、`⚙️`(U+2699)、`☁️`(U+2601) 这类 **BMP 基字符 + U+FE0F**；被吃的是 `📖`(U+1F4D6)、`🎬`(U+1F3AC)、`🖼`(U+1F5BC) 这类**代理对**字符 ⇒ 典型的**代理对不感知的编码往返**。
- **指纹 = 孤立变体选择符**：跟在代理对后面的 **U+FE0F 是 BMP，因此幸存** —— 于是 `return '🏗️'` 变成 `return '️'`（**引号之间只剩一个 U+FE0F**）。坏点形态恒为两种：`''`（空串）或**长度 1 且码位为 U+FE0F**。
- **订正原票假设**：原票推测是「私有区（PUA）图标字形被有损保存」—— **不成立**。原字形是**标准 Unicode emoji**（`f1ab2648^` 逐字形在白）⇒「需先确认用的是哪套图标字体」这个前置问题**不存在**。
- **不会自愈，只会随重构搬迁**：同批被吃的还有 `constants/app.uts`（5 个导航图标）、`dashboard.uvue`、`profile.uvue`、`practice.uvue` 等处；这些页面其后被重做，损伤仍在但已无可指认的空图标位。#1071 实测的两处 `action-icon` 空槽就是**从已丢字的 `forum.uvue` 板块搬进组件**时带走的（`4284ffd1a` / PR #713）——**搬迁不修字，只搬空**。

### 坑位二：「出生即空」是另一族，必须一起收口

- 29 处里 **12 处并非丢失**，而是**新建时就空**：这些文件/板块**生于 `f1ab2648` 本身**（`my-forum.uvue` / `notifications.uvue` / `forum-resource-panel.uvue`），历史里**没有完整版可抄**。同批第 4 张资源卡当年就写了 `☁️`，可证「新建时人真的会写字，只是这几处没写」。
- **为什么这条必须记**：只修「能 git 恢复」的那 17 处，守护测试**上线即红** —— 这一族没有原文可抄，必须先**取一套字形**（本票由维护者按语义拍板：`💬 🚩 🗑️ 🗑️ 📝 🔔` / `🔔` / `💬 💬` / `🛒 🛍️ 📤`）。
- **两族唯一的硬佐证**：删除类两处留有**孤立 U+FE0F** ⇒ 原基字符必为非 BMP 且后接 FE0F ⇒ `🗑️`(U+1F5D1+FE0F) 是**唯一自然解**；其余 10 处是按事件语义取的。
- **写回字形时的形态要求**：`🏗️` / `🖼️` / `🗑️` 必须整对写回「**非 BMP 基字符 + U+FE0F**」两码位，**不能只留 `️`**。验收只能靠**码位直方图/逐码点比对**，目测会把「本来就是空的」和「搬丢了」互相误判。

### 坑位三：守护规则上线前必须逐条核实命中（本次又抓出两个误报）

按既有范式写了「图标函数返回空字形」的字符级扫描，**上线前先跑全量**，抓到两处**误报**，均收窄而非加 allowlist：

- `utils/pointsDisplay.uts` 的 `ledgerIconGlyph` 返回 `◆ ✓ ★ ✎ ! ·` —— 这是**刻意**的非 emoji 图标集（几何符号 + 一个 ASCII `'!'`），与 emoji 字形集**并存且正常工作**。原判据「必须是非 ASCII 码点」会把它判红 ⇒ 删掉该判据，只禁**ASCII 字母降级**（`'v'` 这类「把 emoji 改成字母」的真回归）。
- 同文件的 `ledgerIconClass` **函数名也含 `Icon`**，但返回的是 class 名（`'icon-task'`）⇒ 原判据「去掉 U+FE0F 后必须恰好一个码点」会把它判红 ⇒ 删掉该判据。

判据最终只覆盖**本票的两种坏点形态**（空串 / 孤立 U+FE0F）**加** ASCII 字母降级，**不钉死具体码位**——日后要换某一处字形，改字面量即可，不必改测试。

### 决策：字符级守护落锁

- **载体**：`utils/iconGlyphContract.test.js`（照 `uvueEntityLiteralContract` / `gradientSyntaxContract` 范式：先对注入违规样本断言检测有效，再对真实文件断言零命中），并入既有契约测试族、随 `npm run test:unit` 跑。
- **两道锁**：① **字符级** —— 图标函数的 `return` 不得为空串、不得为孤立 U+FE0F；② **结构级** —— 模板里 `class` 含 `icon` 的 `<text>` 不得为空（带绑定的槽由①那一半守，两半合起来覆盖两种坏点形态）。
- **`EXPECTED_SLOTS`（20 函数坏分支 + 9 模板空槽 = 29）是故意的口径锚点**：增删图标位必须同时改这张表 —— 静默改变「有多少图标位要守」等于静默改变守护范围，必须留痕。修复前本守护实测**恰好红在这 29 处**，修复后 26 用例全绿；注入一个空槽即判红（red-capable 实测）。
- **扫描面切准（与 #957 同款教训）**：只判**函数名含 `Icon` 的函数**与 **class 含 `icon` 的 `<text>`**。切宽了会把 `fileSizeText`（`if (size <= 0) return ''` 是数字格式化）这类合法空串判红；切窄了会漏掉 `getTypeIcon` 这种**名字不含 `XxxIcon` 形态**的图标函数。本票按前者收口、按后者核对过全仓命中。

### 坑位四（真机复核发现）：坏点是**三**形态，而首版守护只覆盖了两形态

- **现场**：维护者真机复核 #1071 时发现**帖子详情页的「浏览量」没有图标**。原文（`f1ab2648^` 的 `forum-detail.uvue`）是
  `<text class="stat-text">👁 {{ topic.views_count }}</text>`，现树成了 `<text class="stat-text"> {{ viewsCount }}</text>`
  —— `👁` 被吃掉，**只剩前导空格**。（同票另一处，`my-forum.uvue` 的 `meta-item` 也留着同样的前导空格 + `margin-right` 图标间距。）
- **为什么守护没抓到**：首版把坏点定义成两形态（`''` 空串 / 长度 1 且为 `U+FE0F`），可**结构级判据的扫描面是「`class` 含 `icon`」**，而该槽 class 是 **`stat-text`**（不含 icon）⇒ 不在面内。更根本的是它属**第三形态**：
  **绑定还在、字形没了** —— 三种里唯一既不是空串、也不是孤立 FE0F 的一种。
  ⚠️ 注意 `stat-text` 这处**没有** U+FE0F：`👁`(U+1F441) 后面本来就**不跟**变体选择符 ⇒「孤立 FE0F」这个指纹**在该形态下不存在**，不能靠它兜。
- **一般教训（本条的落锁价值）**：**「按名字切靶」的守护天然漏掉「名字不像图标槽、但语义上是图标槽」的位**。
  `stat-text` / `meta-item` / `meta-like-icon` 这类名字里没有 `icon` 的槽，只要丢了字形就完全静默。
- **为什么没有顺手把判据放宽到「任意 `<text>`」**：实测该信号在本仓误报率极高 —— 「`<text>` 内容以空白开头」粗扫出 **44 处**，绝大多数是**合法的**（`{{ value }}` 前留空格的排版习惯、以及 `<text>` 开标签换行的多行内容）。定一条会误报成灾的规则，等于逼后续会话把它加进 allowlist 而废掉守护（本 ADR 的既有教训）。
- **本轮的处置（写实，不假装已闭环）**：按术前原文**逐字形恢复**该槽（码位 `1F441`，已机检与 `f1ab2648^` 一致），并把本条记为**已知边界**：守护覆盖的是「空字形」两形态；**「绑定还在、字形没了」这一形态仍需人工/真机复核兜**。若日后要机检它，判据面应落在**真实源码结构**（如「统计槽是否配了图标」的白名单/表格），而不是空白字符这类高误报信号。

## 导航 query 键契约与「静默失效」缺陷族（#1071 牵出，2026-09-17）

维护者真机复核 #1071 时追问「课程下面已完成的课程，那些也点不开吗？」—— 牵出一族**与本票图标无关**的独立缺陷，并落锁一道新守护。

### 坑位：页面入参与调用方**各自合法**，只有对起来才不成立

- **现场**：`pages/profile/records.uvue` 跳课程详情传 `?course_id=<n>`，而
  `pages/courses/course-detail.uvue` 的 `onLoad` 读 **`options['id']`**
  （实测 `ea2baba8` / `f1ab2648^` / `f1ab2648` / `origin/master` **每个版本都是 `id`**，
  即 `?course_id=` **从来不是**合法键）。同理 `favorites.uvue` 传 camelCase `chapterId`，
  而 `chapter-view` 读 `course_id` + `chapter_id`（键名由 **ADR-0014** 明载：章节落点）。
- **为什么难发现**：① 编译期**无任何检查**（query 键是字符串，页面读不到就是 `null`）；
  ② 失败**静默** —— `onLoad` 普遍写成 `if (x != null) { … } else { loading = false }`，
  于是「没传参」表现为**空页**而不是报错；③ 两端分别看都正常，只有交叉比对才暴露。
- **必经而非边缘**：后端 `StudyRecordDTO.ChapterID` 是可空 `*int`，前端映射为 `0`
  ⇒ **课程级记录必然**走那条错键分支。**一般教训**：**「数据可空」会让某条分支从「边缘」变成「必经」**，
  判影响面时不能只看代码形状。
- **落锁**：`utils/navQueryKeyContract.test.js` —— 对每个导航的**字面量** URL，把 query 键集合与
  目标页 `onLoad` 实际读到的键集合求差，非空即红。判据**刻意只做一个方向**（传了没读）；
  「该读没传」需每页的必填参数声明，而仓里没有（普遍 `if (x != null)` 兜底），硬判会误报。

### 坑位：写「解析源码」的守护时，五种假阳性形态（本轮逐一踩过）

写这道守护的过程中，首版**误报 19 处**，全部来自解析器自身。逐条留痕（同 ADR-0009「守护规则上线前必须先跑全量、逐条核实命中」）：

1. **锚点命中导入行**：`onLoad` 匹配到了 `import { onLoad } from '@dcloudio/uni-app'` ⇒ 目标页被解析成「只读 []」。
2. **用 `replace` 去预处理会移动字符位置**：为绕开①而去掉 import 行，而取函数体用的是**原串**偏移
   ⇒ index 错位、body 为空。**一般教训**：任何「先 replace 再按 index 取子串」的写法都是错的，
   除非替换**等长**（保长度掩码）。
3. **按变量名匹配**：`options['x']` 在本仓至少四种写法（`options` / `_options` 再别名成 `opts` /
   `onLoad((options : OnLoadOptions) => …)` / 委托给 composable）。改为按「`onLoad` 内的 `['键']`」收，
   与命名无关。**一般教训**：解析源码要盯**语法位置**，不要盯**标识符名字**。
4. **缩进/行尾假设**：取函数体写成「找下一个行首 `}`」（四空格），而本仓**空格与 tab 混用**
   （`ai-feature.uvue` 用 tab）⇒ 永远找不到、函数体一路延伸到文件尾。改为**括号与花括号配平**，
   与缩进风格、CRLF/LF 无关。**一般教训**：本仓缩进不统一，任何依赖缩进的解析都不成立。
5. **取体函数用错种类**：对**函数声明**误用了**调用表达式**版的取体函数，
   把 `function f(options : T) : void {` 的**参数表**当成了函数体 ⇒ 派生表全空、连带误报。
   声明与调用是两种形态，需两个取体函数。

**共同点**：五条都不是「业务判据错了」，而是**解析器自己错了**，且**方向全是假阳性**（把合法写法判红）。
按本 ADR 既有纪律，这类规则若不先在全量上逐条核实命中，最终只会被 allowlist 废掉。

### 坑位：读者不归一 EOL ⇒ 注入自检**静默假绿**（与上条相反的一极）

紧接上一条的判据面 —— 上面五条**全是假阳性**（把合法写法判红），这一条是**反方向**：变异没生效、断言照跑（**假绿**）。同一棵树上两个方向都会坏，纪律要成对写。

- **现场**：`utils/contributionStatusContract.test.js` 的「锁自检」（把源里 `archived` 那一行删掉，再断言解析结果不含
  `archived`）在 **Windows 工作树恒红**、CI（Linux）恒绿 —— 即这条守护的红能力**只在 Linux 上被验证过**（#1134 全量
  95/96 时才暴露，见 **#1143**）。
- **根因**：守护**直读工作树文本且不归一 EOL**，而 `*.uts` / `*.uvue` **没有**被 `.gitattributes` 钉 LF（`git ls-files --eol`
  → `i/lf w/crlf attr/`，`core.autocrlf=true`；治本票 **#1137**）。注入锚点 `^ *\{ status: 'archived'.*\n` 里
  **`.` 不匹配 `\r`**、`\n` 又必须紧跟其后 ⇒ 在 CRLF 行上**匹配 0 次** ⇒ 变异根本没发生，而「删掉后不应再含」这条断言
  **照样通过**（源没变，当然还含）。
- **为什么长期没人看见**：失败方向是**假绿**，而唯一能暴露它的判据（EOL 差异）**在 CI 上看不到** —— LF 检出上真源本来就是
  LF，归一与否都一样。**一般教训**：**注入自检的判据必须与检出平台无关**，否则守护的红能力只在作者那台机器上成立。
- **修法（读者层归一，不逐处放宽锚点）**：`normalizeEol` + `readText`，`read` / `readRepo` / 零内联扫描的 `walk()` 统一走它。
  把锚点改成 `\r?\n` 只治当前一条，下一条同类锚点还会踩；归一摆在读者处，对**任何原因**导致的 CRLF 都成立。
- **落锁**：新增 2 例读者自检 —— ① **合成 CRLF 源**经 `readText` 后不含 `\r`（**唯一与检出平台无关**：删掉归一，LF 检出上也红）；
  ② 真源（`.uts` / `.uvue` / 仓外对账源）经读者后不含 `\r`。红能力实测：删掉 `archived` 行 ⇒ 3 例判红（修复前该守护在
  Windows 为 1 红 / 17 绿，修复后 20/20）。

### 未修项（如实登记，禁静默删）

`favorites.uvue` 的章节收藏**仍打不开**，登记在 `GUARD_ALLOWLIST`：`FavoriteItem` / 后端 `FavoriteDTO`

### 决策一：域 DTO 归位 `types/<域>.uts` 的判据是「本批五域里唯一没归队的」，不是审美

⚠️ **本节是被代码审查打回后重写的**。首版写的是「`api/job.uts` 是**全仓唯一**一个把响应 DTO 内联声明在
api 文件里的域 api」+「70 处 / 8 处」两个度量 —— **两条都不成立**（按下面的命令重测即否），
照错的度量做决策比不做决策更糟，故把正确的数与正确的理由一起留在这儿。

可复现度量（`training-app/叉车维修培训学员端跨端应用/` 下；术术前 = `b07491b4`，术后 = 本分支）：

**所以真正的理由有两条，都比「全仓唯一」弱但都是真的**：

1. **本批口径的一致性**：票面点名的五域（guide 无 api 文件）里，四条在前序票已按 ADR-0003
   把 DTO 放进 `types/<域>.uts`，只有 `api/job.uts` 还留着 4 个内联声明。而 ADR-0003 的落锁形态是
   **整目录不变式**（`api/<域>.uts` 零内联 `export type`）—— job 一留，这条批量锁就只能对五域之一开口，
   「批量收紧」的锁当场退化。
2. **本票要动的就是这个文件的映射**：既然详情/列表两份同形映射必须去重、出口签名必须带 DTO，
   「顺手让类型留在原地」才是最小的额外改动 —— 但那等于把不一致**锁死**成批量票的先例。

**必须如实登记的反证**：术术后仍有 **7 个** api 文件在原地声明类型，其中 `recruit` / `contribution` 是
地地道道的**响应 DTO**（不是请求参数）⇒ **「响应 DTO 一律住 `types/`」在全仓范围内并不成立**，
它是本批五域的域内不变式，不是仓规。首版拿 `api/*` 那 8 处页面 type import 当「全是请求参数类型」的证据
是**错的**（`RecruitResumeCard` / `ContributionItem` 等就是响应 DTO）。
⇒ 真正的存量归位是 **#653（批量收尾 B）** 与后续 recruit/contribution 票的活，本票不 claim。

本票动作：`JobPosting` / `JobListParams` / `JobListResult` / `ReportReason` 逐字节搬进新建
`types/job.uts`（51 行），`types/index.uts` 加一行 barrel re-export，两个 job 页面各改**一行**
type import 指向（页面行数不变，见决策二）。api/job.uts 155→**110** 行。

**barrel 行的形态必须用 `export { type X, type Y } from './job'`**（inline type modifier）。
写成 `export type { X } from './job'` 会让 UTS 编译器报 `load_transformed failed … index not found`
—— 见上节「types 域拆分两个坑位 · 坑位一」，本票照既有先例走，未重踩。

### 决策二：这次的真实代价 = 门 ①a 从「免」变「必过」（② 仍免），登记而不回避

`api/search.uts` 单独收紧是纯 `.uts` 改动 ⇒ 命中「低风险运行时面」豁免 ⇒ ①a 免。
但**决策一那两个页面的 type import 一动，整个 PR 就被降级为常规运行时面**——
判据（`.github/workflows/pr-evidence.yml` 的 `isLowRiskUtChange`）是**逐文件**的：改动集里
每一个文件都得落在 `*.uts` / `*test.js` / `*.md` / `jest.config*.js` 白名单内，一行 `.uvue` 就破功。

⚠️ **代价的精确边界（本地跑校验器实测，别凭印象写）**：把本 PR 的十个文件与 patch 喂给抽取出的
`validatePrEvidence`，输出是 `runtime=6 / lowRiskRuntime=false / needs4b=false`，而
**`needs2` 为 false** —— ② 的触发面是「MP-WEIXIN 面」（`manifest.json` / `platformConfig.json`，
或运行时面文件里**增删一条真的 `#ifdef` 指令行**），本票两样都没有 ⇒ **② 仍免**，
校验器还会主动注一条 `未命中 MP-WEIXIN 面 → 第②门免`。
所以本票的**净门成本只有一道：①a**。（初稿此处写「①a + ② 双双必过」，是把
「常规运行时面」误当成「①② 全亮」——见本节末「度量口径」：**门的必过性由校验器判，不由作者叙述**。）

这正是根 `AGENTS.md` 那条「不看源码读不出来」的硬口径的又一例。**为什么仍然做**：

- 反向做法（让 `api/job.uts` 用 `export { type JobPosting, … } from '../types/job'` 把类型再导出，
  页面 import 一个字都不动）**技术上成立**、且能省下 ①a 这道门；
- 但它会造出**仓内唯一「api 层 re-export 类型」的异类**——即把「不一致」从「DTO 声明位置不一致」
  换成「DTO 导出路径不一致」，与本票所属 epic 的目标（治 `api 契约不一致`，见「背景」）**反向**。
- ⇒ 结论：**门成本不是把结构留在错位的理由**。成本如实登记在此，由本票 PR 的 ①a 兑现。
  （度量补一句：两个 `.uvue` 各只改一行，改后**行数逐字不变**——`job-detail.uvue` 573→573、
  `job-list.uvue` 513→513 ⇒ 页面渲染面零改动，①a 的实质风险极低。）
- **度量口径（可迁移的手法）**：门要不要过，别按 ADR 叙述推——`sed -n '/VALIDATOR-START/,/VALIDATOR-END/p'`
  把校验器抽出来、用 `git diff --name-only -z` + 每文件 patch 造 `files` 喂进去，一次跑出
  `runtime / lowRiskRuntime / needs4b / needs2` 与全部 errors。**写 ADR 的「门」节前必须跑一次**；
  本票正是靠它抓出了「② 必过」这个虚报（虚报方向还不利于自己 ⇒ 不是激励问题，是没跑）。

### 决策三：收紧后的目标形态 = 「出口一行委托，出口体内零字段读取」

对齐 T05 #643 已收紧域的既有形态（`featured.uts` / `notification.uts` 都是这个形状）：

```ts
export function searchAllApi(keyword : string, credentialId : number = 0) : Promise<SearchResult> {
    const params : UTSJSONObject = withCredential({ keyword: keyword } as UTSJSONObject, credentialId)
    return getMapped<SearchResult>('/search', params, (data : UTSJSONObject) : SearchResult => buildSearchResult(data, keyword))
}
```

- **`keyword` / `type` 是回退缺省值，只能由出口注入映射**（`toStr(data['keyword'], keyword)`）。
  这决定了 `buildSearchResult` 不能是纯单参函数——写成单参会静默丢掉回退，是一处会改变行为的假等价。
- **job 详情与列表此前各有一份 15 行同形映射**（`apply_state` / `cooldown_days` 那组 #488 字段）⇒
  去重为 `buildJobPosting`，列表经 `buildJobListResult` 复用它。`jobApplyStateContract` 的旧锁
  C1 原本断言「两处映射点各写了这两个字段（计数 ≥ 2）」，收紧后只剩一处 ⇒ 判据**升级为结构锁**：
  两端点必须都路由进同一个 `buildJobPosting`。**这是强化不是弱化**——旧判据容忍两份会各自漂移的复制品，
  新判据让「补了详情漏列表」在结构上不可能发生。
- **规则 M**（`*Mapped` 出口不得收裸 `build*` 函数引用，Kotlin error17）：一律箭头包裹。
- **请求形态锁**：`getJobListApi` 保留手动 query 拼接 + `params` 传 `null`。`getMapped` 内部
  `url + (url.includes('?') ? '&' : '?') + pairs.join('&')` 与旧拼接逐字节同解，
  「顺手改成传 params 对象」属另一件事（会换掉序列化通路），故钉住现状不改。
- **void 透传仍留裸 `post`**（`reportJobApi` / `applyJobApi` / `viewFeaturedContentApi` / `mark*`）：
  按「两问判据」①无载荷可 DTO 化 ②消费方全在手，硬套 identity map 属过度设计。

### 落锁：`utils/apiBatchAContract.test.js`（353 行 / 49 用例）+ 五条判据各带注入自检

批量票的契约不重复前序票的主体锁（points / featured / notification 的域锁在
`pointsRealApiContract` / `dashboardContract`），本票只钉**批次一致性**与**不回潮**：

| 判据 | 抓什么 | 为什么需要它 |
| --- | --- | --- |
| `RAW_THEN_TO_DTO` | `return get/post/patch(...).then((data : UTSJSONObject) : DTO …` | 「未收紧」的标准形态 |
| `RAW_GET` | 域 api 里任何裸 `get(` | **比上条更严**：`get(url).then(x => x)`、`.then((d : any) => …)` 这类没标注 `data : UTSJSONObject` 的回潮从上一条的缝里过去。实测五域该判据零命中，而 `getMapped` / `getJobListApi` / `getUnreadCountApi` 不误伤（`get` 后紧跟字母而非 `(`） |
| `FIELD_READ` | 出口体内出现 `data['…']` | 映射一旦回到出口里，就意味着又开始按出口复制映射（job 域收紧前正是这个病） |
| `TYPES_INDEX_IMPORT` | api 文件的 DTO 是否真从 `types/index` 进来 | 票面「导出显式 DTO」的单一来源面 |
| `guideApiHits` / `apiEntryRe` | guide 页面回潮出 api 面；五域被塞进豁免名单 | 两条「登记事实」型锁的判据本体 |

**首版只有前三条带注入自检**（自检块当时就叫「三条判据」），后两条与 `guide 零 api` /
`allowlist 不回潮` 是**裸 `not.toMatch` / 裸 `filter(...)` === []** —— 代码审查按
`docs/agents/guards.md` 判据 ①「改坏它会不会红」逐条问，问出来的两个**真缺陷**（不是措辞问题）：

1. **空花括号假绿**：原判据 `import\s+type\s*\{[^}]+\}` 里 `[^}]+` 能被一个空格满足 ⇒
   `import type { } from '../types/index'` **也算命中**，锁在「类型被搬空但 import 行还在」时不红。
   修法 = 要求花括号内至少一个非空白字符（`TYPES_INDEX_IMPORT`）。**这条是补自检的当场抓到的**，
   不是补完自检才发现的第二例。
2. **无界 `[\s\S]*` 可被注释凑满足**：`jobApplyStateContract` C1 的
   `/getMapped<JobPosting>[\s\S]*buildJobPosting\(data\)/` 跨全文件匹配，而 `api/job.uts`
   **文件头注释里就写着**「映射…收敛到 `buildJobPosting`」⇒ 把出口改坏、注释留着，照样绿。
   修法 = 改按 `between(jobSrc, 'export function getJobDetailApi', '\n}')` **切函数体**再判。

⇒ 一般化两条，写进这里而不是只留在测试里：
**① 判据本体只能有一份** —— 锁与它的注入自检必须引用**同一个** const / 同一个函数；自检里另写一遍
正则，自检绿只证明自检那份没坏，证明不了锁没坏（本票两条新锁就是这么写的）。
**② `filter` / 循环型判据要有下限断言** —— `allowlistPaths()` 若为空、`sourceFilesIn('pages/guide')`
若目录改名，`toEqual([])` 都**恒真**；故各补一条 `length > 0` 的存活断言，把「读者没读到东西」与
「读到了但不违规」分开。

变异实测（改坏被测物看锁会不会红，两次都用 `cp` 还原并 `git status` 确认干净）：
把 `buildJobListResult` 里的 `buildJobPosting(obj)` 换成 `obj` ⇒ `jobApplyStateContract` **1 failed**；
把详情出口的 `buildJobPosting(data)` 换成别的 builder ⇒ 两套件合计 **2 failed**。
**两条锁均判据 ① 成立**。

另钉：五域 import 含 `getMapped`、DTO 一律来自 `types/index` 且 api 层零 `export type`、
guide 零 api + 页面零 api import、五域永不出现在 GUARD_ALLOWLIST。

### 缺口七的第三面：新搬进 barrel 的类型族要进反向自检清单

「types 域拆分两个坑位 · 缺口七」（规则 K/L 字段表被 barrel 行以零字段先占 → **本机绿 / CI 红**，
根因是 `readdir` 顺序 NTFS≠ext4）对本票是**直接命中**——决策一正是往 barrel 里加一族新类型。
正则已收紧为「类型头与 `{` 同行」，barrel 四形态均不命中，且「正序 / 逆序两次构建结果必须一致」
的通用锁会抓住任何回归。**本票补的是它的反向断言面**：`utsAndroidCompile.test.js` 那份

`JobPosting`（含 #488 的 `apply_state` / `cooldown_days`）——**每往 barrel 归位一族，清单就加一族**，
否则新家族只被通用顺序锁覆盖、不被「字段真在表里」这条具体断言覆盖。
