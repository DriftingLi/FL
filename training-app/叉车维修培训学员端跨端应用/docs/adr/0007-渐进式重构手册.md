# 0007 - 渐进式重构手册：页面层手术 + api 契约收紧

**状态**：定稿（T02 mall + T03 profile 两模块复盘收束；T04 forum 术后补录与 600 预算第三复评结论见文末，2026-09-08；决策清单见 `docs/refactor-decisions.md`）
**来源**：重构 epic #638（四轮 grilling 收束），试点工单 #640

## 背景与目标

学员端（uni-app-x，约 4.2 万行、53 页）随迭代出现巨型文件（20 个源文件超 600 行）、页面层重复无沉淀、api 契约不一致（请求基座裸 `any`、部分域无 DTO）。目标：治类型/编译痛点 + 可维护性 + 为功能迭代提速。**性能与 UI 重设计不在目标内。**

## 决策

### 形态：渐进绞杀，非大爆炸

- 每模块 1 分支（`refactor/<module>`）+ 1 PR + 1 专注会话；每 PR 合并即直发 production（squash revert 即回滚），不改 CD 流水线
- 模块级冻结：手术期间该模块冻结新功能；**纯机械 import 迁移不算破坏冻结**
- 手术顺序按体量降序（mall 试点先行）；login 单独 pin 在生物识别线合并后

### 靶子：页面层手术，骨架不动

- `pages/ components/ api/ stores/ utils/` 顶层保留，不做 `features/` 迁移（pages.json 53 路径 churn + easycom 约束 + UTS import 脆弱，负收益）
- 巨型页面拆 section 组件/composable；不拆子路由（除非产品本就是多页）
- **单文件软预算 ≤600 行**（全文件计），模块目录 ≤2 层。试点起以契约测试机检锁定已达标模块（防回潮），未达标模块不强制全库扫描
- **UI 像素级冻结**：界面必须与手术前一致，UI 问题记 issue 不顺手改。冒烟基线 = 前后逐页截图对比

### api 契约收紧：requestMapped / getMapped 出口家族

- 出口形态 = mapper-callback（与 ADR-0003 手动 JSON 映射同构）：`requestMapped<T>(opts, map)`；GET 走便捷面 `getMapped<T>(url, params, map)`——**params 沿用手动 query 序列化，不交平台自动序列化**（试点发现：跨端序列化行为有漂移风险，`get()` 的手动拼接是实证安全的行为，收紧不得改变请求形态）
- 每域 api 导出显式 DTO + build* 映射函数；页面层只 import 域 api（2026-09 探针实测页面层直接 `uni.request` 为 0，暂无独立守护规则；若新增违例在 #654 收尾票立项）
- 既有 `request/get/post` 原样保留（expand–contract），页面接线迁移按票推进

### 拆出物安置与晋升

- 模块私有组件/composable 放 `pages/<module>/components|composables/`，**显式 import**（PascalCase 标签 + kebab-case 事件绑定，同 ai-chat 先例；easycom 仅全局件）
- 全局 `components/`、`composables/` 只放已确认跨模块复用件；**第二个模块需要时晋升全局**，晋升 PR 允许机械改使用方 import
- 手术 PR 内允许增量式抽取（新建共享件 + 当前模块采用），不碰其他模块行为代码

### 静态守护与契约测试纪律

- `utsAndroidCompile.test.js` 沿用「纯函数扫描 + 注入违规自检 + 全工程断言」模式按遭遇增量扩规则；存量违例走 `GUARD_ALLOWLIST`（expand 侧），各手术票清自己范围，epic 收尾票删机制
- 手术 PR 内契约测试可更新文件路径指向，**禁删/弱化断言**（弱化须引用 issue）
- 不新增组件级测试（uvue 无生态）；行为回归靠四门冒烟

### 每手术 PR 四门验收

1. Android 真机逐页截图前后对比（人工签收）
2. 微信开发者工具逐页打开无报错（人工）
3. `npm run test:unit` 全绿（既有失败须可指认到独立 issue）
4. HBuilderX 真机运行全量编译无新增 error（人工）

**push 前先 `git merge origin/master`**（试点教训：分支基点过期会同时触发 ruleset up-to-date 门禁与迁移版本预检两道拦截）。

**四门的现行口径以 ADR-0008（移动端验收门与证据）为准**——门的分级判据（运行时面）、证据四字段、`pr-evidence` 必检与 ruleset `approve=1`、dev 编译门与 release 云打包门的拆分，见 0008；本节只保留「有哪几道门」的历史叙述。

## 试点复盘（keep–adjust）

- **keep**：拆纯展示/纯动作段（排序栏、悬浮组）成本低收益高；业务数据区（商品列表+必买清单+分页加载）留主文件不硬拆；600 预算 442 行达标且未过度碎片化
- **keep**：契约测试机检组件接线（防"import 了但没用"与静默回退）
- **adjust**：出口家族需 GET 便捷面（getMapped）——spec 只写了 requestMapped，试点第一步即暴露 GET 参数序列化的形态保持问题

**删除禁区型工单：三向归一化 diff 审计（T05 verbatim 审核的细化）**
「不删既有实现」与「拆文件」同时成立时，「搬」与「改」的边界必须有证据。本票把 T05 的归一化 diff 拆成三向（临时脚本，收口即删、不进仓）：
① **CSS 规则集**（selector → 归一化声明集）：旧 56/49 条 → 新 56/49 条，零声明漂移；
② **模板 token 级 LCS**：组件模板按页面用法展开、prop 名反代回旧表达式后与旧模板对齐，漂移清单只剩刻意项（`.action-area` 单根包层、retry handler 薄包装改名、结果页行别名 `detail`→`row`）；
③ **脚本行级 LCS**：删行只允许出现「import / 显式结果类型 / 被 utils 接管的纯函数 / 合并的 computed」，加行只允许「composable 骨架 + 页面薄包装」。

- **新坑位（审计工具自身）**：token 切分**不能按裸 `>` 切** —— `:is-last="currentIndex >= questions.length - 1"` 里的 `>=` 会把标签切碎，导致组件展开失败并**误报 20+ token 漂移**；正确切法是「引号外首个 `>` 才收尾」。**一般教训：审计器用正则扫模板属性前，先问「属性值里会出现我要找的分隔符吗」。**
- **新增判据：单根包层可接受**。页面里两个同级块（`.action-bar` + `.submit-section`）搬进单个组件时，uvue 单根要求多一层 column 容器（`.action-area`）。判据 = 包装层无 padding/背景/尺寸且不翻转 flex 方向 → 视觉零漂移。这是 T05「模板留壳层」的**同一问题在相反条件下的结论**：那里状态所有权在页面（v-if 重挂载会重置态）故留壳，这里只是布局容器故可搬。
- **静默回退去留按「是否掩盖面」+ 本票禁区双判**：`getMockExamHistoryApi` 的空表回退**保留**（既有行为、无幻影路由、两个消费方各自另有 try/catch 与可见错误态），并在契约里显式钉死「api 层唯一一处 `.catch` 且落在 history」——**保留是决策，不是惯性**；是否退役并入 #652/#653 域 api 批量收尾。

## api 收紧的失败可见口径与幻影路由锁（#709，2026-09-09）

points 域接真接口时与 #652 T14 撞同一文件，本票先行完成 points 收紧，顺带把 api 层的两条隐含口径钉明：

- **catch-mock 静默回退按「掩盖面」处理，不按「降级」处理**：api 层 `.catch()` 回落占位数据会把后端未注册路由（404）、网络故障一律伪装成正常首屏——points 域三条假流水就是这么盖了三个月（#662 实测）。收紧一个域时若该域回退曾掩盖真实缺口，回退须随本域一并退役，失败上抛、由页面呈现可见错误态 + 重试（request 层 toast 只算瞬时提示，不足以承载「可见」）。纯体验型降级（如 mall 列表离线可看）要保留必须有 issue 依据，不能凭惯性沿用。
- **反转旧锁属于改口径，不属于弱化断言**：上文「禁删/弱化断言（弱化须引用 issue）」在此的落地形态是把 `profileContract` 的「points 域 mock 降级保持」改写为「points 域零回退」，测试注释与被引用 issue（#709）双向可追。后续 #652 批次遇到同类旧锁照此办理，不得默默删掉。
- **幻影路由可机检**：`utils/pointsRealApiContract.test.js` 把「api 层出现的每个路由字面量都必须落在后端已注册清单内」做成断言——这是 #662 整类问题（前端调后端从未注册的路由）的第一道回归锁。其他域收紧时照抄这条断言，后端路由清单以 `backend/internal/api/<域>.go` 的 `Register*Routes` 为唯一事实源。
- **展示纯函数与文案表落 `utils/<域>Display.uts`**（先例 wrongQuestionDisplay / checkinCalendar），配镜像单测；两端同源文案表（Web `pointsReason.ts` ↔ 移动端 `pointsDisplay.uts`）是**已知债不是终态**——根因是后端流水条目只给 `reason` 键不给展示标题，已记 #709 待后端清单，后端补 `display_title` 后两端表一起删。

## 编译门六道缺口与机械化落锁（#787 / #800 / #803 / #805 / #806，2026-09-10）

T06 practice 与 T05 dashboard 接连在 master 上编译不过，暴露两类 playbook 未覆盖的坑位，以及**验收面本身的结构性缺口**。

### 缺口一：孤儿 import（组件 import 了但文件不存在）

- **现场**：#779 把 `practice.uvue` 的横幅/统计栏/功能网格/模块列表四段改成组件 `import`，但 `pages/practice/components/` 目录从未创建——全仓搜索该组件名只有一处引用，指向不存在的文件。HBuilderX 报 `Could not resolve "./components/practice-banner-card.uvue"`。
- **为什么 jest 全绿**：彼时 `practiceContract` 只断言 composable 接线，**没有断言「页面 import 的组件文件必须存在」**。再次印证「jest 全绿 ≠ 能编译」。
- **落锁**：`utils/practiceContract.test.js` 增「组件接线零孤儿」两条断言——① 页面 import 的每个 `./components/*.uvue` 必须真实存在；② 组件目录不得有孤儿文件。**每个模块手术照建这两条**（并入该模块的 `<module>Contract.test.js` 汇总票）。

### 缺口二：return 对象里裸传同文件函数引用（Kotlin error17）

- **现场**：UTS 把 return 字段位置上的函数名解析为**调用**，实际类型成了返回值类型，与期望的 `Function0<...>` 不匹配：
  `error: Function invocation 'loadOverview()' expected.` /
  `参数类型不匹配：实际类型为 'UTSPromise<Unit>'，预期类型为 'Function0<UTSPromise<Unit>>'`。
- **两种形态都触发**（两轮编译各证一次，共 44 处）：
  - ① **显式** `key: fn` —— `use-dashboard-credential.uts` / `use-dashboard-feeds.uts`（T05 #763），8 处，随 **#800** 修
  - ② **速记** `{ fn }` —— practice 的 4 个 composable（T06），36 处，随 **#802** 修
- **重要更正**：#800 当时据「首轮日志只列了 dashboard」推断「触发条件是 return 字面量带显式类型（`as XxxResult`），速记形态不带类型标注故不被调用」，并据此给规则 T 加了「推断形态不判定」豁免 —— **该推断被 #802 的编译现场证伪**：速记形态**无需任何类型标注**同样触发。教训：**编译器日志是分批/截断输出的，不能把「没出现在日志里」当作「不会触发」**；推断应写成「未证实」并选择宁误勿漏的判定方向。
- **合法形态（先例 `composables/useTopicDetail.uts`，同一 #779 PR 里就是对的）**：
  `loadDetail: () => loadDetail(),` / `canDeleteReply: (reply : ForumReply) => canDeleteReply(reply),`
  —— 与规则 M 同类：**裸引用 → 箭头包裹才合法**，带参函数在箭头里补显式形参类型。Ref 等非函数值用速记不受影响。
- **落锁**：守护规则 T（`scanBareFnRefInReturn`）扫「return 对象字面量内、值为同文件函数名的成员」，**显式与速记两种形态都判**、不设类型标注前提；带注入违规自检（两形态各一）+ 箭头反向自检 + Ref 速记放行自检。全工程零命中。

### 缺口三（守护侧）：同名异形类型让规则 L 误报

- **现场**：规则 L 报 `dashboard-menu-grid.uvue` 三处「参数 item : MenuItem 访问未声明字段 path/available」，但该文件**本地就声明了含 `path`/`available` 的 `MenuItem`**，Kotlin 侧完全合法——是守护误报。
- **根因**：`buildTypeFieldMap()` 只收 **`.uts`** 且以**裸类型名**键控（首次优先）。全仓有三个异形 `MenuItem`：`ai-assistant-constants.uts` 的 `{key,label}` 先入表，于是 `.uvue` 本地那个更宽的同名类型被顶掉。规则 K 早已按「页面本地类型声明优先于全局表」做过遮蔽处理（先例注释就写着 dashboard 的 `CourseItem`），**规则 L 漏了同一处理**。
- **落锁**：`scanTypedParamFieldAccess` 补本地优先（与 K 同构：拷全局表 → 用同文件 `type/interface` 声明覆盖同名项）。修后全工程 161 文件 0 命中；反向自检（本地声明确无该字段）仍能抓到，遮蔽放行也通过。
- **一般教训**：**守护表按裸名键控时，必须实现「本文件声明优先」**，否则新增同名类型就会污染既有判定。写新规则时先问「这个类型的名字在全仓唯一吗」。
### 缺口四：返回函数的 composable 缺显式结果类型（Kotlin error18）

- **现场**：#803 给 practice 的 4 个 composable 补了箭头（缺口二）后，下一轮 HBuilderX 改报 `找不到名称 "onNext"` / `找不到名称 "value"`——`practice-do.uvue` 对 `session.onNext` / `session.currentQuestion.value` 的成员访问全部解析不出。原因是 return 对象**无显式类型**，UTS 在消费侧还原不出它的成员。
- **关键区分**：箭头与显式类型是**两件独立的事** —— 箭头治 error17（函数字段被当调用），显式类型治 error18（成员解析不出）。**只补其一都不够**；合法形态 = 两者同时具备。先例 `composables/useTopicDetail.uts`（显式 `UseTopicDetailResult` + 全部箭头字段）。
- **仓内早有记录**：`composables/useAiChat.uts` 第 233 行自己写着「整体以显式类型 UseAiChatResult 强转（与 stores/auth.uts 同款写法规避类型推断问题）」。核对全仓：**14/14** 个返回函数的 composable 都满足该约定（签名标注或 `as T` 强转），practice 是唯一例外。
- **落锁**：新增**规则 U**（`scanComposableMissingResultType`）—— `export function useX(...)` 的 return 对象含函数成员时，须有签名标注 `: T` 或 return 后 `as T`。自检四条：缺类型必抓 / 签名标注放行 / `as` 强转放行 / 纯状态 composable 不判定。
- **教训（第二次同类）**：**只按「日志里报了什么」下刀不够**。#803 修完 error17 就收手，没去核对「本仓同类文件都长什么样」——而先例比对（14/14 同款写法）本可以一次性给出完整形态，省掉一整轮编译。**修一类问题前，先看这一类在仓里的既定写法。**
- **另一条流程教训**：本轮日志夹杂了差量编译读到的**过期文件**（16:51 那条打印的是上一版单行内容），把已修好的问题又报了一遍。看到日志与磁盘不一致时，先怀疑编译缓存，要求一次干净重建再判定。
### 缺口五：async 函数缺返回类型标注（Kotlin 推不出 UTSPromise 的 T）

- **现场**（**云打包 release 编译**，`compileReleaseKotlin`）：
  `wrong-questions.kt:49` 报 `Cannot infer type for this parameter. Specify it explicitly.` / `Not enough information to infer type argument for 'T'.` / `Return type mismatch: expected 'Unit', actual 'UTSPromise<uninferred ERROR CLASS: Cannot infer argument for type parameter T>'`。
  源码是 `pages/profile/wrong-questions.uvue` 的 `async function loadRecords(reset : boolean = false) {` —— **完全没写返回类型**。
- **与规则 R 的关系**：规则 R 覆盖的是 `async fn() : void`（**写错**的标注）；**不写标注**是另一个子类——Kotlin 生成 `UTSPromise<T>` 而 `T` 推不出来。两者都归「UTSPromise 类型参数不可推断」这一族。
- **规模**：全仓 11 处（practice 1 + profile 8 + courses 1 + …），全部补 `: Promise<void>`（逐个核对过函数体只有裸 `return`，无带值返回）。
- **落锁**：新增**规则 V**（`scanAsyncMissingReturnType`）——扫 `async function` 声明是否带返回类型。自检四条：缺标注必抓 / `Promise<void>` 放行 / `Promise<T>` 放行 / 非 async 不判定。
- **注意**：这是**云打包（release）才暴露**的门 —— dev 编译那一轮没报。ADR 上文「云打包跟发布节奏走，不按 PR 打」的结论需要打个补丁：**release 编译门比 dev 严**，涉及 async/Kotlin 类型推断的改动，收口前应至少跑一次云打包或 release 编译。

### 缺口六：模板裸 handler 未定义（error18 找不到名称）

- **现场**：`practice-do.uvue:5` 模板 `<view class="nav-left" @click="onBack">`，但 script 里**没有 `onBack`** —— 重写该文件时只保留了 `onExit`，漏带了导航返回按钮的 handler。Kotlin 报 `找不到名称 "onBack"`。
- **性质**：属「重写时逐符号核对消费面」的老教训（T02 mall 的 `mustBuyList`、T04 的 `useAccept` 幻影块）**第三次复发**，只不过这次漏的是被模板消费的符号，而模板不在 jest 覆盖范围内。
- **落锁**：新增**规则 W**（`scanUndefinedTemplateHandler`）——扫模板里**整体为裸标识符**的 `@event="name"`，要求 script 侧有四类定义之一：`function`/`const|let` 声明、`import` 绑定、解构绑定（先例 dashboard/practice 从 composable 取 handler）、Options API `methods` 条目（先例 `pages/index/index.uvue`）。带参调用与对象成员不在靶内。
- **写规则时的教训**：初版检测只认 `function`/`const`，误报了 30 处（全是解构与 import 绑定）。**守护规则上线前必须先跑全量、逐条核实命中**，否则要么误报成灾、要么被迫加 allowlist 把规则废掉。
### 结构性教训：跨模块夹带让验收面失效

T06 的改动是随 **#779（标题为 ai-assistant 拆分）** 合入 master 的，没走 `refactor/practice` 分支、没按 #644 的四门验收签收；T05 标称「三门人工签收 2026-09-09 确认」的产物却编译不过。两条合起来说明：

1. **一票一模块：手术改动不得夹带进标题无关的 PR**。夹带使该模块的验收面（四门 checklist）无人执行——断链正是在这里漏过去的。
2. **四门之「HBuilderX 全量编译无新增 error」须留可核验产物**（编译日志或截图）；口头/勾选式「签收」不构成证据。
3. 跨模块必然要动同一文件时（先例 #652 撞文件），在 PR 描述里显式写明「本 PR 同时覆盖 X 模块，已按 X 的四门自查」，把验收面显式带过来。

## types 域拆分两个坑位（2026-09-11，PR #830）

types 域拆分的独立重构（把 1,151 行的 `types/index.uts` 按域拆成 15 个文件 + barrel re-export 壳），不属 T01–T13 工单序列，但产出两条守护/选型教训，按「新决策回写纪律」落此。

### 坑位一：UTS 编译器不支持 `export type { X } from './y'`

- **现场**：barrel 壳先写成 `export type { ForumTopic, … } from './forum'`，HBuilderX 编译报
  `Cannot create property 'code' on string 'load_transformed failed … failed to resolve ./common from …/types/index.uts … index not found'`。
- **结论**：UTS（编译到 Kotlin）**不支持** `export type { … } from` 形态。合法形态 = `export { type X, type Y } from './y'`（inline type modifier），已编译签收。
- **旁证**：同仓 `stores/index.uts:5` 早有值形态 `export { useAuthStore } from './auth'` 且长期可用 —— 所以「barrel 不可用」的说法不成立，**只有 `export type {…} from` 这一形态不可用**。
- **教训**：UTS 的重导出语法是子集，选型前先找**仓内既有先例**（同 T06 缺口四的教训）；「值可重导出」不能推广为「类型也可」。

### 缺口七：规则 K/L 的字段表被 barrel re-export 行污染（本机绿 / CI 红）

- **现场**：barrel 壳落地后 **CI 的 `mobile-test` 红、本机全绿** —— 规则 K/L 对 `NotificationItem` / `SearchItem` / `ExamQuestion` 报「访问未声明字段」共 21 处，而这 3 个类型的字段在域文件里一个不少。
- **根因（双因叠加，缺一不炸）**：
  1. `buildTypeFieldMap` 的类型头正则 `[^{]*\{` **可跨行**。barrel 行 `export { type X, type Y } from './y'` 被当作类型头 —— 正则里的 `{` 取自**下一行**的 `export {`，于是 X 以「零字段」入表。
  2. 入表判据是 `!fields.has()`（**先到先得**）。谁先被读到谁胜出，而 `readdirSync` 顺序 **NTFS 与 ext4 不同** —— 同一份代码两端结论相反。
- **性质**：**「本机绿 ≠ CI 绿」的第二形态**。第一形态是「jest 绿 ≠ 能编译」（T03/T06 已录）；这一形态是「本地守护绿 ≠ CI 守护绿」，根因是**判定依赖文件系统枚举顺序**。二者都指向同一条：**本地单测全绿不构成合并依据**。
- **落锁**：
  - 类型头与 `{` 收紧为**必须同行**（`[^{}\n]*\{`）。已逐一核对全仓 `.uts` 无「`{` 在类型头下一行」的声明，收紧不丢类型；barrel 的四种写法（`export type {X} from` / `export { type X } from` / `export * from` / `export { X } from`）收紧后**均不命中**。
  - 新增**「字段表与文件遍历顺序无关」自检**（`utsAndroidCompile.test.js` 守护自检段）：对同一份 `.uts` 清单**正序 / 逆序两次构建，结果必须完全一致**，并对曾受害的 3 个类型断言其字段集非空且含真实字段。已实测**旧正则下该锁必红**（`authenticate` / `checkSupport` / `isSupported` 正序有字段、逆序为空），新正则下绿 —— 锁具备 red-capable，符合「注入违规自检」的既有范式。
- **一般教训**：**任何「先到先得」的全局表，都必须显式锁「与遍历顺序无关」**——跨文件系统的 `readdir` 顺序不可假定。写守护规则时先问：「这个判定的结果，依赖文件被读到的顺序吗？」；跨端项目里还要再问一句：「两端文件系统枚举顺序一致吗？」
