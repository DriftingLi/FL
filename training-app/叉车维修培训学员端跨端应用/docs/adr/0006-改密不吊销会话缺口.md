# 0006 - 已知安全缺口：修改密码不吊销既有会话

**状态**：已确认（记录在案，暂不处理）

## 缺口描述

修改密码后（`AuthService.UpdatePassword`，`internal/service/auth_service.go`），仅更新密码 hash，**不吊销任何已签发的 JWT**。Redis 黑名单（`jwt:blacklist:<sha256>`）只在登出（`Revoke`/`RevokeRefresh`）与 refresh 轮换（`RotateRefresh`）时写入，改密路径不经过它。

后果：攻击者若已持有某用户的有效 token（如设备被盗、token 泄露），即使用户立即修改密码，该 token 在剩余有效期内（access 默认 2 小时，refresh 默认 7 天，`JWT_REFRESH_EXPIRES_DAYS=7`）依然可用。密码修改无法作为"踢出所有设备"的应急手段。注意 refresh 轮换是滑动续期（`RotateRefresh` 每次签发全新 7 天窗口），持续使用的会话链不会自然过期。

## 影响

- 改密后其他设备的登录态继续存活，最长可达 refresh 有效期
- "记住密码"类客户端功能回填的旧凭据在改密后仍可用于登录尝试（会被服务端密码校验拒绝，不构成凭据绕过，但已存数据不失效）
- 与「改密后所有设备强制下线」的用户直觉不符
- **快捷登录（ADR-0004 增补）放大影响面**：生物识别门控的快捷登录直接用 refresh_token 静默续登，绕过"旧密码被服务端拒绝→被迫重登→覆盖新凭据"的自愈路径——改密后被记住的设备最长 7 天内（滑动续期下更久）仍可静默进入。决策：起步阶段接受，收口依赖下述后端修复方向。

## 可能的修复方向（未决策，仅列举）

1. JWT 增加 `pwd_version` claim，用户表存版本号，改密自增；鉴权时比对不符即拒绝（需查库或缓存版本号）
2. 改密时按用户维度写入吊销标记（如 `jwt:pwd_revoked:<userID>` + 时间戳），鉴权时签发时间早于该时间戳的 token 全部拒绝
3. 改密时枚举吊销该用户全部 refresh token（需维护 user→jti 索引，复杂度最高）

## 关联

- 发现场：Spec《安全记住密码（凭据门控回填）与自研安全存储落地》（Issue #542）核对后端生命周期假设时确认
- ADR-0004（生物识别门控）中"改密时后端使旧 token 失效，间接实现凭据失效"的表述**与现状不符**，实际语义为"客户端凭据仅用于填表单，改密后旧凭据在下次登录被拒绝，用户重新登录时覆盖更新（自愈式）"
