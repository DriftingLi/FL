# 0003 - 手动 build*() 函数做 JSON→类型映射

每个 API 模块都编写 `build*()` 函数，将后端返回的 `UTSJSONObject` 逐字段手动赋值给前端类型定义，而非使用 `as` 类型断言或运行时类型映射。

选择此方案的原因：UTS（uni-app-x 的 TypeScript 变体）编译到 Kotlin 后，`as` 类型断言仅是编译时检查，不做运行时类型转换。直接将 `UTSJSONObject` 强转为自定义类型会导致 Android/iOS 原生端崩溃。因此只能手动逐字段赋值，确保每个字段都经过类型安全的处理。

> **2026-09-20 补正（#1195 真机取证）**：上一段「`as` 类型断言仅是编译时检查」这句**读起来像「`as` 在 Kotlin 侧什么也不做」，那个推论是错的**。准确的口径是两条，不要混：① **不转换值** —— `UTSJSONObject` 不会被转成自定义类型，这就是本 ADR 要手动逐字段赋值的原因（结论不变）；② **但 `as` 编到 Kotlin 后确实是运行时的非空断言** —— 目标键缺席时**先抛** `NullPointerException`，`??` / `?:` 兜不住。②是 #1195 真机抓到的那个缺陷的成因，展开见下一节。

此模式的代价是代码量较大（每个 API 响应都需要一个 `build*()` 函数），但保证了原生端的类型安全。Web 端（H5）虽然支持动态类型，但为保持代码一致性，统一使用此模式。

## 可缺省键（`omitempty`）的读法纪律（2026-09-20，#1195 真机 ①a 抓获）

**现象**：招聘者「职位」段**恒显示「暂无职位」**，而后端确实回了 `200` + 正常列表 —— 取数异常被页面 `catch` 后当成空列表吞掉，屏上与事实相反的**假空态**。

**事实（全部可核验）**：

- 后端 `JobPostingDTO.OfflineReason` 带 `json:"offline_reason,omitempty"`（`backend/internal/service/job_posting_service.go:74`）⇒ **未强制下架时该键不出现在 JSON 里**（是「键缺席」，不是「值为 `null`」）。
- 客户端原写法 `offline_reason: (obj['offline_reason'] as string) ?? ''`（`api/recruit.uts`）—— 按上面补正的②，`as string` 是运行时的**非空断言**。缺键时先抛 `NullPointerException`，**`?? ''` 根本轮不到**（抛的是异常，不是 `null`）。
- 真机 `logcat`：`GET /api/recruit/jobs?page=1&page_size=20` → `<<< 200`，紧接着 `[recruiter-jobs] load jobs failed: java.lang.NullPointerException: null cannot be cast to non-null type kotlin.String`，栈顶 `IndexKt.getRecruitJobsApi$lambda$79(index.kt:10674)`（取证归档 `docs/verification/recruiter-workspace/1208/README.md` 第三节）。
- 生成代码对照（同目录 `unpackage/cache/.app-android/src/index.kt`）：修复前 `:10674` 为 `offline_reason = (obj["offline_reason"] as String) ?: ""`；修复后 `:10675-10680` 为 `val offlineReasonRaw = obj["offline_reason"]` + `if (offlineReasonRaw == null) { "" } else { offlineReasonRaw as String }`。**后者才是运行时不再抛的形态**。
- 为什么只有真机能抓：**jest 复现不了** —— JS 里 `undefined ?? ''` 永不抛。这一族缺陷**只存在于 Kotlin 一侧**。

**纪律**（读 `omitempty` 字段、或任何后端可能不下发的键时必须）：

1. **先取值、再判空、最后才强转**：`const raw = obj['x']` → `raw == null ? <默认> : raw as <T>`。**禁止**裸强转（`obj['x'] as T`）与「裸强转 + `??` / `?:` 兜底」两种写法 —— 兜底运算符在 Kotlin 侧不是兜底。
2. **对齐既有先例**：`api/auth.uts:20-21` 的 `nameRaw` 已是这个形状（`const nameRaw = obj['name']` → `nameRaw == null ? username : nameRaw as string`）。新代码照抄这个形状，不另立新写法。
3. **同族核查要落到「该键会不会真缺」**：`omitempty` 只说明「可能不下发」，还要看赋值侧是否恒赋值。本轮核查结论：`offline_reason` 是 `RecruitJob` 读到的**唯一「既 `omitempty` 又真会缺」**字段；`CompanyName` / `ContactRequestDTO.Source` / `ApplicationDTO.JobTitle` 同样带 `omitempty` 但 `toDTO` 恒赋值 ⇒ **现状不会缺键，故不做无依据的连带改动**。
4. **缺键时的默认值必须与展示判定一致**：走空串分支后，页面侧「是否强制下架」的判定读的是 `forced_offline`（布尔、无 `omitempty`），不得改成靠 `offline_reason != ''` 反推。

**落锁**：`utils/recruitWorkspaceContract.test.js` 的 **J 组**（`describe('J. 可缺省键先判空再强转（真机 NPE「假空态」缺陷的回归锁）')`）—— 5 例：① 读法形态（必须先落中间变量再判空）；② 旧写法（裸强转 + `??`）绝迹；③ **锁自检**（好/坏两种合成样本各跑一次，且交叉不互中，否则本组是空跑）；④ **跨语言对账**（直读 `backend/internal/service/job_posting_service.go` 断言 `OfflineReason` 确实带 `omitempty`，读不到后端源码即 fail-closed 判红 —— 后端改掉这个 tag 就该重估本锁）；⑤ 同族扫描（`api/recruit.uts` 里裸强转形态按出现次数归零，防止有人加第二个消费点绕过）。

**守护的已知边界（写实）**：J 组是**源码文本断言**，它挡得住写法回退，**挡不住**「新增了另一个 `omitempty` 字段又忘了先判空」—— 每新增一个 `omitempty` 消费点都应同步在同族扫描里加一条，或在 ①a 真机取证时按「列表页渲染真数据」判（假空态的判据不是「没报错」，而是「渲染出真列表」）。

**为什么落在这篇 ADR（取舍说清）**：本仓移动端**没有**「UTS 类型系统坑位」的独立 ADR（`0003` 是这个主题在编号体系里的最近一篇；`0015` 讲的是 uvue **实体解码**边界，不是 Kotlin 强转语义）。新建一篇会与 `0003` 的主题重叠，且 `0003` 原文那句「仅是编译时检查」正是**这次误读的源头** —— 把纪律写回源头处，比另开一篇更能拦住下一个人。故选择扩写本篇并就地补正。（`AGENTS.md` 那条「决策/重构清单固定六段结构、≤25 行」约束的是**新建决策/重构清单**的形态；本节是坑位回写，沿用 `0008` / `0017` 已有的「现象 → 事实 → 结论 → 落锁」写法。）
