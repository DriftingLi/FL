# 0041 - 三层门分离与云上证据管家

> 状态：已生效 ｜ 2026-10-16 立 ｜ 来源：/grill-with-docs 会话（触发材料 `handoff-1666-prf.md` §3「5 小时全耗在门执行」的时间账）
> **职责边界**：裁定「门在**哪台机器**上执行、**谁**回答证据是否有效」——把门分成三层（云上纯逻辑 / 本机运行时 / 真机取证），并新增一个**只读证据、不判红**的云上管家。
> 不动门的**判据**（`0008-移动端验收门与证据.md`）、不动 ② 门三条硬前提、不动 `-i` 串行语义（`jest.config.unit.js` 文件头，#1410）、不动窗口口径（`0039` / `0040`）、不动证据格式（`pr-evidence.yml`）。

**① 目标与范围**

起因是一笔时间账：一次「本机把四道门串行跑完」的会话里，代码与测试只占 ~2h40，剩下 5h+ 全花在**门不可稳定执行**上（③ 门 in-band 连挂 3 次 2h03、② 微信门全量 2 次 1h28、④ 等 HBuilderX 锁 40m、② 因子集白跑 21m）。

先纠一处事实，因为它决定了这次改动的形状：**`ci.yml` 的 `mobile-test` 里现在没有任何真门**——它只跑 `npm run test:unit` 与「读取层归一」守卫。所以「把 ②④ 从 `mobile-test` 剥离」在现状里**没有对应物**：这不是一次搬迁，而是**新增一层**。而「新增在哪」必须先问「跑不跑得动」。

本 ADR 的范围：三层门的归属、云上那一层能做什么与不能做什么、以及新增 `mobile-gates.yml` 的边界。**不在范围**：改门判据、改证据格式、扩门触发面、把真门搬上云。

**② 决策 + 一句理由**

**决策 1（真门不上云）**：② 微信开发者工具门与 ④ 编译门**继续留在本机/真机**，不做 CI 化。理由是实测证伪，不是保守：

2026-10-16 在 `windows-latest` 上跑了两轮一次性探针（workflow 用完即删，未进任何 PR）：

| 环节 | 实测结果 |
| --- | --- |
| HBuilderX 安装 | `HBuilderX.5.26.2026091802.zip` 93,908,502 B，CDN 3.2 s；7-Zip 解压 18.4 s / 8081 文件（**`Expand-Archive` 会静默残缺**，只剩插件目录、大量 `package.json` 缺失） |
| 主程序启动 | `cli.exe open` 退出 0，`HBuilderX_processes=1` ⇒ **托管 runner 上主程序能起** |
| 项目导入 | `cli.exe project open --path <项目>` → `Project imported successfully` |
| 插件补装（④ 的 kotlinc） | `installPlugin uniapp-runextension` 恒报 `Command'installPlugin …' does not exist or is missing parameters`，三个插件目录均 0 文件 ⇒ **kotlinc 装不上** |
| ④ publish | `cli.exe publish app-android --type appResource` ~30 s 返回、退出码 0、**stdout 只有 `Please Login in!`**，`.kt` 数 0 ⇒ **卡在 DCloud 账号登录态** |
| 微信开发者工具安装 | `/S` 静默安装成功 29.9 s，`cli.bat -v` 命令表完整（含 `open/login/islogin/auto/preview`） |
| ② 登录态 | `cli.bat islogin` → `[error] Please ensure that the IDE has been properly installed` + `ENOENT …\微信开发者工具\UserData\<hash>\Default\.cli` ⇒ **UserData 首次初始化 + 微信扫码登录态**，托管 VM 上没有 |

结论：**工具装得上、主程序起得来、项目导得进，但两道门都卡在「账号登录态」这一层**。这不是工程能用「多试几次」绕过的，是账号与扫码的物理约束。⇒ ADR-0008「不把 HBuilderX 搬进 CI……若日后证实可无头，再议」这一条**至今仍然成立**，本次只是把「未证实」换成了「已证伪」，并把口子写死。

**决策 2（云上只做纯逻辑，且分片）**：`ci.yml` 的 `mobile-test` 改成 **4 片 matrix 并行**（`npm run test:unit -- --shard=k/4`），契约守卫与其自测只在第 1 片跑。

理由有两半，缺一不可：

- **墙钟**：全量实测 189 套件 / 3579 用例 / **423.5 s**，且最慢单套件 `utils/wirelessDebugBehavior.test.js` 独占 **108.6 s**（其余除 5 个外都 <1 s）⇒ 单进程串行是唯一主因，4 片后单机约 3 分钟。
- **分片≠把 `-i` 改并行**：`jest.config.unit.js` 文件头记着 #1410 的评估——套件**无跨套件共享面**（temp 全落 `mkdtempSync` 唯一目录、端口 `listen(0)`、git 只读），`-i` 真正在挡的是**同机 CPU 争抢下的 5 s 默认超时抖动**（`loadUts` 系套件同步转译 .uts）。分片是**分机器**，每片内部仍 `-i` 串行 ⇒ 墙钟减半而 #1410 怕的抖动一点没引入。无共享面这一条同时就是「分机器切分安全」的依据。

`ci-summary` 的 `needs` / `check` 清单**一字不改**（matrix 的多个子 job 仍满足 `needs.mobile-test`），ruleset 唯一必检的诚实性不变（`scripts/ci-summary-needs.test.mjs` 的依赖闭包断言照旧通过）。

**决策 3（云上当证据管家，不当判官）**：新增 `.github/workflows/mobile-gates.yml`，把「**这个 PR 的门证据是不是对当前 head 有效**」渲染成 PR 上**一条常驻评论**。四条硬边界：

1. **不执行任何真门**（决策 1 的直接后果）。它只读 PR 改动集与评论，回答「有没有、绑没绑上」。
2. **不判红、不阻断合并**（整 job `continue-on-error`）。本仓的门是人工/agent 执行、agent 签齐即合并（ADR-0008）；再加一个会变红的机器人检查，只会逼人绕过它。管家自身故障时**不改评论**，只在跑摘要留痕——绝不把「没算出来」渲染成「没有证据」。
3. **判据同源，不另写一套**：从 PR head 取 `.github/workflows/pr-evidence.yml`，把 `PR-EVIDENCE-VALIDATOR` 标记块原样抽出来跑（同一个 `validatePrEvidence`，同一份 `MP_WEIXIN_DIRECTIVE`、同一套 sha 绑定判据）。为此给校验器加了一个**纯增量**的 `gates` 字段（`②`/`④` 各自的 `required`/`bound`/`commit`/`reason`），由 `.github/scripts/pr-evidence-check.test.mjs` 的抽取式单测守住（成对取证：该 true 与该 false 各有用例）。于是「管家说绿、pr-evidence 说红」在结构上不可能出现。
4. **常驻一条评论、三个入口**：`pull_request [opened, synchronize, reopened]` / `issue_comment [created]` / `workflow_dispatch`。评论用固定 MARKER 原地更新，不刷屏；`issue_comment` 那一入口是承重的——**贴门证据的人不会再去点一次重跑**。防自锁：含 MARKER 的评论与任何机器人评论一律早退。

**沉默边界**（噪音成本提前定死，这是本决策最容易被事后改坏的部分）：非运行时面 PR **一句话都不发**；但若该 PR 之前发过（改动集变过），就把那条改写成「已无需门证据」而不是留着过期结论；草稿 PR **照发**（草稿阶段正需要知道还缺哪条）。

**决策 4（三层门的名字与归属）**：本 ADR 说「三层」时指——

| 层 | 在哪跑 | 内容 | 谁判 |
| --- | --- | --- | --- |
| 云上纯逻辑 | `ubuntu-latest`（4 片并行） | ③ 门 `test:unit` + 静态守卫 | CI（`ci-summary`） |
| 本机运行时门 | 开发机 / 真机 | ② 微信开发者工具门、④ 编译门（含 ④b 云打包） | 人/agent 执行 + sha 绑定评论 |
| 真机取证 | 真机 | ① 逐页截图 + 能力面人工签收 | 人 |
| （横切）证据管家 | `ubuntu-latest` | 只核对上面三层的证据是否绑当前 head | 不判，只呈现 |

⚠️ **术语撞车提醒**：② 门脚本 `-Doctor` 里已有一套 `L1 工具链 / L2 登录态 / L3 进程端口 … L7 会话就绪` 的**自检分层**（见 ADR-0008 对应节）。本 ADR 的「三层门」是**门的执行位置分层**，与 `-Doctor` 的 L 系列**不是同一套**——文档里一律写「云上纯逻辑 / 本机运行时门 / 真机取证」，不写 L1/L2/L3，免得两套编号互相污染。

**③ 明确不做的事**

- **不把 ②④ 搬上云**（决策 1），也不做「自托管 Windows runner + 常驻登录态」——那是另一件事，且它要推翻 ADR-0008 与 ADR-0019「全仓零 Windows 基建」两条，收益（省掉本机排队）与成本（常驻带账号的 Windows 机器）不成比例。真要做，另立 ADR。
- **不让管家判红、不让它进 ruleset 必检**（决策 3 第 2 条）。它是**可见性**设施，不是门。
- **不在管家侧复制判据**（决策 3 第 3 条）：哪怕「顺便看一眼 MP-WEIXIN 面」也不行，那是同一条判据的第二个副本。
- **不改 `-i`、不改 `test:unit` 脚本本体、不改本地 `test:unit:local` 的定位**：分片只发生在 CI 的调用行。
- **不做 E2E**（`0020` 已裁决）。
- **不追溯已合并 PR**：管家只对事件发生时的 open PR 生效。

**④ 落地步骤与载体**

1. `.github/workflows/ci.yml` 的 `mobile-test`：`strategy.matrix.shard=[1,2,3,4]` + `fail-fast: false`，单测步改 `npm run test:unit -- --shard=${{ matrix.shard }}/4`，契约守卫与其自测加 `if: matrix.shard == 1`；`ci-summary` 不动。
2. `.github/workflows/pr-evidence.yml`：校验器加 `gates` 字段（4 个 return 位点，纯增量）。
3. `.github/scripts/pr-evidence-check.test.mjs`：加 4 条 `gates` 断言（非运行时面 / 无评论 / 已绑回填 commit / ② 触发面与低风险面成对）。
4. 新增 `.github/workflows/mobile-gates.yml`（证据管家，三入口，单条常驻评论）。

**⑤ 约束**

- 这些文件都在**根仓库面**（`.github/**`），不属于移动端「不在宿主树改 `training-app/**`」的射程，可在主树直接改。
- 管家写评论需要 `pull-requests: write` + `issues: write`；**fork PR 的 token 是只读的** ⇒ 对外来 PR 管家会静默失败（不判红、不发评论），这是既有边界，不是缺陷。
- `-PostToPr` 贴评论用的是人的 token，管家不代贴证据、不冒充执行人。
- 分片只换执行拓扑，不换判据：③ 门的「改坏它会不会红」成对取证要求（`docs/agents/guards.md`）不受影响，CI 绿永远只是「必不红」那一侧。

**⑥ 验收标准**

1. 分片在真实链路绿一次：一次性分支推上去，`mobile-test (1..4)` 四片全绿、`ci-summary` 仍绿，且单 job 墙钟显著低于改前的 7:04（基线 run 39090642299）。
2. 管家在 `pull_request` 路径验一次：一次性 PR 上看到**一条**常驻评论，且缺证据 / 已绑两种状态都渲染正确（用一条临时门评论触发状态翻转，验完删评论）。**验完关 PR、删分支**；仓库会短暂留一条机器人评论。
3. `issue_comment` 入口**无法在合并前验完**（`issue_comment` 与 `workflow_dispatch` 只认默认分支上的 workflow 文件）⇒ 该入口的验收顺延到合并后第一个真 PR：贴一条 `-PostToPr` 证据评论，确认管家自动刷新。
4. `node --test .github/scripts/pr-evidence-check.test.mjs` 全绿（含新增 `gates` 用例）。
