# 0044 - 官方自动化测试路线选型裁定

**状态**：已接受（2026-10-26，来源：issue #1925 —— GitCode 博文《uni-app x 自动化测试指南》的一手回溯调研（`/research`）+ 追问收敛（`/grill-with-docs`）；本 ADR 把裁定落到仓库面）

> **部分被取代**（2026-10-29，地图 #2098 调研）：两处前提被推翻——HBuilderX 实为 5.26、官方测试环境自带 `jest-image-snapshot`；仍**不是 headless**（单实例铁律不变）。「不引入」的结论未变，接管 ② 驱动层的残余收益随 ② 降本而收窄。执行以 `AGENTS.md` 执行单为准；本文件只作来路。

> **一句话**：官方 uni-automation-test 路线（`@dcloudio/uni-automator` + DCloud 测试平台）**不引入**，现有 ②（微信开发者工具截图门）③（契约门两腿）保持不动；唯一保留的兴趣点（App 端自动截图作 ①a 采集层）挂起为开放候选、**痛点触发**才做实验；6 项需实测与 3 项 ② 门增强候选登记在附录，防丢防漂移。

## ① 目标与范围

**要回答的是选型问题**：在 ADR-0043 把 ② 升为常态主门、①a 降为发版前一次的格局下，官方 uni-automation-test 能否、是否值得补进本仓验收门体系，替代或叠加 ②③ 门。

**范围**：选型裁定 + 两份附录登记。一手回溯全过程（博客逐条核对、六轴对比表、26 条来源清单）在调研文档 `docs/design/20261026-uniappx官方自动化测试选型调研.md`（根仓库路径，与本 ADR 同 PR 收进），本 ADR 不复抄。

**不含**：不重开 ADR-0020 的 E2E 通道裁决；不动 ②③ 门的脚本与配置；不评估 DCloud 闭源测试平台的内部机制（无一手来源，调研文档已标注）。

## ② 选型 + 一句理由

| 决策 | 一句话理由 |
| --- | --- |
| **① 不引入官方 uni-automation-test 路线，②③ 门原样** | 官方开源侧只有「截图保存」没有「对比」（`toSaveImageSnapshot` 无条件覆盖、恒 pass），对比与基准管理在闭源测试平台；且本仓 2026-09-19 已实测清退过整套装配（ADR-0020），引入 = 重开已关闭的裁决 |
| **② 「App 端 program.screenshot + Element 作 ①a 发版冒烟采集层」挂起为开放候选，不现在 prototype** | 这是官方路线唯一未被旧实测覆盖的增量面（App 通道本机从未跑过），但痛点未出，先做实验是无的放矢 |
| **③ 候选的重开条件 = ①a 采集真出痛点（痛点触发，非定时）** | 触发条件写死在 ADR 里，避免「为了实验而实验」，也避免无期限遗忘 |
| **④ 本 ADR 走中等版 = 裁定 + 附录清单，不复抄六轴对比表** | 对比表全文唯一真源是调研文档；ADR 复抄一份只会制造第二个漂移点 |
| **⑤ 微信 miniprogram-automator 三能力进附录 B，作「② 门增强候选」** | 它是 ② 门现用 SDK 的官方文档（非新方案），与本 ADR 主裁定正交，登记防丢 |
| **⑥ 与 ADR-0020 双向引用（0044 引 0020；0020 关联节加指针回 0044）** | 0020 管「清退与锁」、0044 管「选型裁定面」，同主题族互指才可追溯 |

## ③ 明确不做的事

- **不引入** `@dcloudio/uni-automator`、DCloud 测试平台，**不补装依赖、不跑其 CLI、不新增 E2E 门**（重开须按 ADR-0043 决策 9 先另立 ADR supersede 0020 并满足其附 C 重启前置）。
- **不动 ②③ 门**的任何脚本、配置与证据口径。
- **不跑任何 prototype**——附录 A 六项全部挂起，痛点触发才开。
- **不把本仓截图阈值移植给官方截图流**（0.5% 同帧标定 / 跨天 0.919% 假红血账，ADR-0043 决策 5 的锁）。
- **不把附录 B 三能力当已验证**：全部标「待实测」，实测前不得据本 ADR 改 ② 门行为或声称 PR #1136 裁决已被推翻。

## ④ 拆分步骤

1. **本 ADR + ADR-0020 指针行 + 调研文档，收进同一 PR**（票 #1925；一步，决策与被决策的记录同批可复核）。
2. （挂起，痛点触发）→ `/prototype` 跑附录 A 中对应实测项 → 结果回写本 ADR，结论若推翻①则按决策 9 走 supersede 程序。
3. （挂起）附录 B 任一能力要落地 → 先实测再立票；改 ② 门口径须同步回写 `0008-移动端验收门与证据.md` 对应节。

## ⑤ 约束（不能动的）

- **ADR-0020 的锁**：E2E 通道裁决维持有效，官方路线重启的唯一合法入口 = 另立 ADR supersede 0020 + 满足其附 C 三条环境前提现测。
- **ADR-0043 决策 5**：跨发版截图阈值不许移植，待第二次发版实测标定。
- **ADR-0041 决策 1**：托管 runner 账号登录态卡点（DCloud `Please Login in!` / 微信 `islogin` ENOENT）未解除前，附录 A 第 6 项按「纸面不可行」处置。
- **本 ADR 纯文档**：改动集不命中运行时面（`*.uvue` / `*.uts` / 三份 json）。

## ⑥ 验收标准

1. 0044 落 `docs/adr/`、编号无冲突，六段体 + 附录 A/B 齐。
2. ADR-0020 正文（关联节）出现指针行引 0044。

## 附录 A：6 项需实测（全部挂起，痛点触发才开 `/prototype`）

纸上判不出的项，不做推断性结论；全文见调研文档 §6。

1. **App 端 Android 真机通道实际可用性**：`program.reLaunch` / `navigateTo` / `Page.waitFor` / `Element` —— ADR-0020 的「恒 `Uncaught [object Object]`」实测对象是**微信通道**（miniprogram-automator + 开发者工具）；官方 uni-automator 的 App 通道在本机从未跑过（`unpackage/**/.automator` 全树 0 命中）。
2. **版本握手能否解开**：HBuilderX「初始化测试环境」能否让 `.automator/*.json` 与 `uni-automator` 版本精确相等（ADR-0020 附 B 的必然失败点）。
3. **截图基准在真机的漂移率**：同 APK 同页跨天/跨电量/跨温度的像素差分布——本仓只有 ①a 侧数据（0.5% 同帧 / 0.919% 跨天），App 自动化截图流未标定。
4. **`page.data` / defineExpose 真实支持度**：api.md 平台矩阵（Android 暂不支持）与 quick-start 更新记录（4.13 起支持）口径打架，须在本机 HBuilderX 5.23/5.24 实测分辨。
5. **整链路耗时账**：`BATCH_SIZE=20` 分批 + testTimeout 30-50s，在本仓 `pages.json` 页面规模下一轮截图回归多久、能否塞进「发版前一次」预算。
6. **云上集成**：受 ADR-0041 决策 1 约束，纸面判不可行；要推翻需在托管 runner 重做探针实验，成本收益待议。

## 附录 B：3 项 ② 门增强候选（待实测）

来源：微信官方 `miniprogram-automator` 文档 https://developers.weixin.qq.com/miniprogram/dev/devtools/auto/quick-start.html —— **正是 ② 门现用 SDK**，以下是「没用上的官方能力」，非新方案；均与本 ADR 主裁定正交。

1. **真机自动化**：`miniProgram.remote()` 打印二维码、手机扫码后同一脚本在**真机**继续跑 —— 可补 ② 门模拟器截图与真机渲染的差；待实测：扫码链路在本机的稳定性、与现有 `mp-weixin-check.ps1` 就绪闸门的兼容性。
2. **登录票据跨机器**：FAQ 的 `miniProgram.getTicket` 可取当前工具登录票据到其它机器登录 —— 是 ADR-0041 微信 `islogin` 卡点的一个**当时未考虑的变量**（票据同步方式需自行维护）；待实测：在托管 runner 重做探针才知能否真解开。
3. **导航 API 与 `mockWxMethod`**：`navigateTo` / `redirectTo` / `navigateBack` / `reLaunch` / `switchTab` 有官方正式文档，`miniProgram.mockWxMethod` 可伪造 `wx.*` 返回绕原生弹窗 —— PR #1136「微信通道只能 page 级断言」可能是**踩坑而非能力缺失**；待实测：0020 附 C 第 5 条的 `Uncaught [object Object]` 是否有解法、流程级断言能否成。

> 附录 B 三项若实测成立并要落地，属 **② 门增强**，不等于重开 0020 的 E2E 官方路线（SDK 不同、对象不同）；落地走「先实测再立票、口径回写 0008」。
