# 0053 - ②门分档裁定：波 3b 暂缓激活，转入验收成本治理（2026-11-02 裁定）

**状态**：已采纳（2026-11-02，来源：维护者对 #2181 波 3a 报告的审阅裁定；3a 报告与复算脚本经 #2191 已合库）。
**承接**：落 `training-app/叉车维修培训学员端跨端应用/docs/adr/0052-验收门②三档分层与Shadow试运行（2026-10-31 裁定）.md` 决策 7 的审阅门——3a 已交、裁定 = **暂缓 3b**。数据文件两开关维持 false/false，门行为零变化。

## ① 目标与范围

只登记裁定结果与下阶段治理次序。前提转变：**能力成立 ≠ 激活值得**——3a 复算读数：反事实收益 0/0、逐文件减配覆盖 1/106、② 真实读数面 19/27、分档声明 27/27 缺席。

## ② 决策

1. **波 3b 暂缓激活**：Shadow 继续运行积累证据，分类结果不得改变验收门行为。同时满足三条件才重评：有持续观测数据面（P0 落库）、有成本账（P1 产出）、有可验证的实际收益。
2. **治理次序（按价值排，非报告原序）**：P0 = 影子数据读数落盘（每次 Shadow 运行产出可追溯、可复算的结果；要素 = 数据来源、采集时间、样本范围、分类结果、异常记录）；P1 = ② 执行成本调研（P0 完成后推进；先测时间消耗，再定优化对象）；P2 = 复算器常备（依 P0 的实现决定；复算器必须独立验证输入完整性，不得只是重复生成相同的错误结果）；P3 = 「暂缓 3b」本身是治理决策、非开发事项，保持现状直到激活条件达成。
3. **总成本尺**（后续一切门禁治理必须回答）：总开发成本 = 开发 + 验收 + 维护 + 返工。两个必答题：验收成本究竟消耗在哪里？新增治理机制究竟减少了多少实际成本？统计口径不限于脚本运行时间，须含人工等待、排查失败、重复执行与维护规则的时间。为省少量验收时间而引入大量规则、Shadow 逻辑与工具维护，即得不偿失。

## ③ 后果

- **正**：决策依据从「分类器能跑」换成「减配值得」；防止验收基础设施自身膨胀为成本中心。
- **负 / 风险**：P0 落库前，波 2 影子读数仍随 CI step 日志蒸发，历史窗口只能靠复算器重放找回；P0/P1/P2 自身也是新增成本，按②-3 记账。
- **可逆性**：P0/P1 为观测与调研，随时可停；期间全部验收门行为与现状一致。
