## ② 选型 + 一句理由

- **登录页不退役，降级为次级落点。** 一句理由：**删页的代价全部落在 ③ 门的冻结锁、两个 ADR 的宿主与 `pages.json` 的人工提交面上，而收益只是"看起来少一张页"。**
- **两端分叉走运行期探测，不走编译期 `#ifdef`。** 一句理由：**运行期探测能达到同等效果（⚠️原写「该端不显示不可用的入口」——已被 2026-10-03 修订作废，现行是「按端别直出入口可见性、并**单独**门禁可达性」两件事），而 `#ifdef` 指令行的增删数可以是 0 ⇒ ② 门免。**

探测件的形状：`composables/useLoginProviders.uts` 返回**可用性判断**（`uni.getProviderSync({ service: 'oauth' })` 里找 `id == 'weixin'` + `UniOAuthWeixinProvider.isWeChatInstalled`），**不是**"要不要渲染"的布尔——后者会被各页各自抄成不一样的前端猜测。跨模块共享：#1484 的 `disabled` 复用同一件。⚠️**2026-10-03 修订**：返回面已由**一个**判断拆成**两个**（展示面 `wechatAvailable` / 接通面 `wechatLoginReady`），且上面那串 provider 探测（`hasWechatOauthProvider()`）**保留但已停用、不参与任何一面**，实测依据与接回条件见文末修订节。「不是要不要渲染的布尔」这条**仍然成立**——它是"判断必须集中在这一个共享件里、不许各页自猜"，与面数无关。

### 3. 用 `#ifdef MP-WEIXIN` 做两端分叉 —— 被否

所以走 `#ifdef` 分叉必然点亮 ② 门（要么新增指令行，要么拆掉 `pages/login/login.uvue:150-152` 那条既有的）；而运行期探测达成同等效果且**指令行增删数 = 0 ⇒ ② 门免**。#1478 两轮都是这么过的：控制器实测「抽取 `.github/workflows/pr-evidence.yml` 内联校验器跑整分支 diff + 同一正则独立扫增删行，双路一致 `needs2=false`」，且没有去拆登录页那条既有 `#ifdef`。
附带收益：探测件可被跨模块复用（#1484），`#ifdef` 分叉不可复用——它只存在于被编译进去的那一个文件里。

## Consequences

- **登录页长期存在但没有主入口地位**：它是 401 顶出、登出、找回密码回跳、注册完成、AI 助手门禁的**落点**，不再是用户主动去的地方。以后看到"这张页在 `pages.json` 里排第二却几乎没人导航到它"，那是本决定的形状，**不是残留**。
- 🔴 **模板 sha 锁的射程盲区（结构性代价，诚实披露）**：协议勾选行从 `pages/login/login.uvue:111-118` 抽成共享件 `components/login-agreement/login-agreement.uvue`（两页同源同文案）之后，`login.uvue` 的**模板整块 sha256 锁对「渲染在登录页上的这一行的文案 / 入口变化」失去感知**——那一行不再是登录页模板的字节。兜底改放在**共享件自己的契约锁**上（`utils/landingLoginContract.test.js` 的 `registerLinkCount = 1` / `registerLinkGated = false` + 两条判别力用例：`gatedByChannel` ⇒ `registerLinkGated == true` 必红、`removed` ⇒ `registerLinkCount == 0` 必红，把"按通道收回入口"和"直接删除入口"两种走偏都钉住）。⇒ 从此**「只改协议行」的 diff 在 `login.uvue` 那把锁上是绿的，这是预期行为，不是漏测**；要审的是共享件那两把。
- 协议行文案与「立即注册」入口从此**一处改两端**：不会再出现"着陆页有注册入口、登录页没有"，代价是登录页的形状审计面变小。
- 微信入口的可见性由**可用性判断**决定，不由"要不要渲染"的布尔决定（口径来自 #1482 第 5 节建议 1/2）。未接入态**不得**在 UI 写「暂不支持微信登录」这类与框架能力相反的静态文案——框架支持（uni-app x 自 HBuilderX 5.08 起 App 端可微信登录），缺的是开放平台凭证。⚠️**2026-10-03 修订**：「可见性由可用性判断决定」被拆成**两个**判断（见文末修订节）；但上面那句**文案禁令原样在案**，且本次 App 端点击后的提示「微信登录暂未开通」是本条的**合规实现**而非违反——理由两条：**(a) 说的是"开通/凭证"缺口，不是"能力"缺口**（"暂未开通"≠"暂不支持"，后者才对框架能力作反事实陈述）；**(b) 它是运行期反馈、不是静态渲染文案**，页面上没有钉着任何一句关于微信通道状态的静态字。
- iOS 侧一条硬约束留在案上：一旦 App 支持微信登录，**必须并列提供 Apple 登录**（#1482 附录一手来源第 1 条），故 Apple 登录的样式槽位应在样式阶段就预留，否则后接时被审核倒逼。
- 本 ADR **不改代码**，且**代码与文档分在两张票**：代码 = PR #1487（#1478），文档 = 本票（#1488）。这本身是一处流程代价——#1478 的票面「文档交付」段在派单时漏抄，导致文档比代码晚一轮。修法已记在 #1488 正文：**文档交付单列一张票，不再搭车。**

## 2026-10-03 修订（①a 真机判红 ⇒ 探测件由一个面拆成两个面）

**性质**：这是本文**首次**由**真机读数**（而不是推理）驱动的改写。上面 ② 的两条选型**一条都没动**；动的是「运行期探测要回答什么问题」和 ① 里那句端别表述。本节**取代**本文中与之冲突的一切措辞。

### 1. 触发：原复合判据在真机上判红，且红法是本文自己点名禁止的形状

设备 Xiaomi `23049RAD8C`（marble，Android），`feat/1478` 树，2026-10-03 23:16–23:42 CST。①a 门（`npm run dev:finish -- -Level standard -Device b32d8398`）步骤全绿，但**逐页 a11y 读数判红**：未登录冷启落在着陆页，页面上渲染出了完整微信入口块（`微信一键登录` 按钮 + 整块微信协议勾选行）。

根因**不是端别判断**（那半是对的），是**能力探测那半**。在 `composables/useLoginProviders.uts` 里临时插桩、经 `npm run hx:run` 部署后读 logcat（tag `console`，形态 `[LOG]---BEGIN:CONSOLE---[{"type":"string","value":"…"}…]---END:CONSOLE---`），实测三个真值：

- `uni.getSystemInfoSync().uniPlatform === "app"`、`onMpWeixin === false` —— **端别半正确**；
- `uni.getProviderSync({ service: 'oauth' }).providerIds === ["weixin"]`（`len === 1`）⇒ 原式里的 `providerFound === true`；
- ⇒ 原复合判据 `onMpWeixin || providerFound` 在**未接入**的 App 端恒真。

**该 API 不反映本工程配置**：`manifest.json` 的 App 侧没有 `oauth` / `sdkConfigs` / `provider` 任何一段（只有 `mp-weixin` 段），`uni_modules/` 下只有 `uni-secure-storage`、**没有任何微信登录模块**——`getProviderSync` 列的是框架内置的 provider 清单。所以「配了 SDK」与「没配」在它眼里**同形**。

后果与**本文 L56 的禁令逐字对上**：入口渲染出来、点击必进 `pages/index/composables/useLandingLogin.uts` 的 catch，`errorHint` 兜出「登录失败，请重试」（该字符串只在 catch 里赋值，页面上出现它就证明链路被真点过并且真失败）。探针日志已 `git checkout --` 完整还原，`[probe]` 残留 = 0。

**已排除的修法**：把原式改成 `onMpWeixin && providerFound` 不行——`getProviderSync` 在小程序端的兼容列表里没有（`useLoginProviders.uts` 文件头自述「未列小程序」），会抛错 ⇒ `providerFound=false` ⇒ AND 之后小程序端也不可用，打死「小程序端可达」那半。

### 2. 维护者口径（本次修订的真源）

移动端**也展示**该入口，**暂不配置**微信登录，「**有个样式即可**」。⇒ App 端**不隐藏**入口；点击改为**友好提示、不发请求**。

### 3. 裁定：探测件返回**两个互不相同**的判断

`composables/useLoginProviders.uts` 的返回面由 1 项判断扩为 2 项（`wechatUnavailableReason` 不动）：

- **展示面 `wechatAvailable` = 端别（`app` **或** `mp-weixin`）** —— 两端**一律**直出该入口。
- **接通面 `wechatLoginReady` = 端别（**仅** `mp-weixin`）** —— 真实微信登录链路当前只有小程序端接通。

两个消费页都拿 `wechatLoginReady` 给点击链上门槛（不发请求、只出单点文案），模板里的 `v-if` 仍绑 `wechatAvailable`。文案**单点**在探测件里导出（`WECHAT_NOT_WIRED_NOTICE = '微信登录暂未开通'`），两页不自带副本。

**注入而非 import**：`pages/index/composables/useLandingLogin.uts` 收「接通面」作**入参**，不 import 探测件——理由是 `useLandingLogin` 自己的源文判据（`utils/landingLoginBehavior.test.js` 的 I5）明令「着陆页 composable 不得自行做端别取数」，它连 `getSystemInfoSync` 的**字面量**都不许出现。`pages/login/composables/useLoginForm.uts` 同理收入参。

**与 L24 那条形状约束的关系**：`hasWechatOauthProvider()`（`getProviderSync` + `isWeChatInstalled`）连同它的 try/catch 塌陷**逐字保留、但已不被任何一面调用**，`TODO(#1482)` 标注接回。所以本件现在的实际形状是"**两个端别判断 + 一个停用的能力判断**"——这是**已知的临时形态，不是终态**：#1482 接通那天，`wechatLoginReady` 应改回「端别 **&&** 能力探测」的复合，`wechatAvailable` 保持端别。

### 4. 与两条选型、与 L57 的关系

- **②（运行期探测 而非 `#ifdef`）不变，且更强**：现在要在**同一份代码**里同时表达"两端都可见"与"只有一端可达"两件独立的事，`#ifdef` 要在同一文件里开第二处分叉；运行期探测下 `#ifdef` 指令行的**增删数仍为 0 ⇒ ② 门仍免**。
- **①（登录页不退役）不受影响**：本次未动 `pages/login/login` 的去留，只改它的微信 mode 点击链。
