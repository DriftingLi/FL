# 0008 - 移动端验收门与证据：把自我声明变成阻塞条件

**状态**：定稿（grilling 收束，2026-09-11）——来源 issue #839；落地实现票 #841
**职责边界**：本 ADR 取代 ADR-0007「每手术 PR 四门验收」章节的口径（0007 保留渐进式重构手册职责，本 ADR 是其执行细则）

## 背景与目标

ADR-0007 规定移动端改动需过四门，其中两道人工门（HBuilderX 全量编译、真机/小程序冒烟）在流水线里**零痕迹**，且不构成合并阻塞——PR 正文里的四门表格只是自我声明。

两次实害：

- **PR #817**（content:// 上传修复，2026-09-11）：首版正文自陈「`getFileSystemManager` 的可用性仍以 HBuilderX 全量编译为准……本地无法验证」→ **同一 PR 内 6 轮修复**（`c942548` → `04cfbd4`，08:44–09:57；含只有云打包 release 才暴露的 Kotlin 错误、只有真机才暴露的上传 602001 与证件 level NPE）→ 10:40 合入。**注意时序**：#839 票面叙述为「合并后连锁返工」，实测相反——返工发生在合入之前、PR 仍打开时；而合入时正文四门表仍写着「⏳ 待人工」，**修复后的状态同样没有任何签收产物**（`reviews` / `comments` 均为 0）
- **PR #837**（论坛采纳按钮）：正文标注「HBuilderX 全量编译 ⏳ 待人工 / 微信开发者工具 ⏳ 待人工」→ **从未执行即合并**，侥幸未出事

两次的共同点：**「如实标注」在现行流程里的作用是免责，而不是阻止合并**。

机制层事实（2026-09-11 审计所得）：

- 移动端唯一的自动门是 `ci.yml` job `mobile-test`（`npm run test:unit`，38 suites / 752 tests 全绿），经 `ci-summary` 汇聚，是 ruleset `20687043` 的**唯一**必检项，`required_approving_review_count: 0`（无人工批准要求）
- 三道人工门（真机、小程序、Kotlin 编译）在 workflows 里**无任何步骤**
- **根仓库没有 PR 模板**：模板错放在 `training-app/叉车维修培训学员端跨端应用/.github/PULL_REQUEST_TEMPLATE.md`（GitHub 只读仓库根的 `.github/`），且其内容要求合到 `main`（默认分支实为 `master`）
- **没有任何 workflow 读取 PR 正文或评论**（全仓 `pull_request.body` / `pull_request.title` / `issue_comment` 命中 0）
- HBuilderX 官方有 CLI（`cli launch app-android --compile true` 仅编译、`cli pack` 云打包、官方「CI 自动化」小节与 Linux CLI），但 CLI 是**驱动主程序**的（连 `cli --help` 都要求主程序可达），且**失败时退出码恒为 0**（实测四处失败全返回 0）；Windows self-hosted runner 的无头可行性未证实

- **发生率（最近 20 个触及 `training-app/**` 且改动 `*.uvue` / `*.uts` 的已合并 PR，全量逐个核对，非抽样）**：14 个在正文声明了 HBuilderX 编译门、5 个声明了真机门，**留下可核验产物（编译日志 / 截图 / 真机结论）的是 0 个**。`docs/` 下无任何验收归档文件；唯一近似记录是 `.gitignore` 掉的 `.scratch/alignment/` 里 4 份勾选式声明——而 ADR-0007 第 186 行自己就写着「口头/勾选式『签收』不构成证据」。
目标：让每道门的执行留下**可核验产物**并使缺产物成为**合并阻塞**；把成本高到无法保持的规定显式降级，而不是留一条注定被跳过的条款。

## 决策清单（六段）

① **目标与范围**：给移动端验收门补上「执行位」——每道门的执行留下可核验产物，缺产物即阻塞；只动验收门与证据机制，不动手术本身、不动源码。
② **选型 + 一句理由**：
- 人工门**按改动面分级**（运行时面触发、文档/测试面免）——一条打在所有 PR 上的门注定被跳过，分级才有执行力。
- 证据落 **PR 正文固定段** + 截图入仓 `docs/verification/`——正文与 commit 同生共死且可被 workflow 读取（仓内文件会被覆盖、评论会被折叠）。
- 阻塞 = **`pr-evidence` 可见检查 + `AGENTS.md` 硬规「agent 不得自合」**——本仓只有 `zhengcookie`（write）与 `DriftingLi`（admin）两个账号，维护者不持有后者，而 `zhengcookie` 改 ruleset 实测返回 404（无 admin），**「必检 + approve=1」在本仓装不上**；阻塞因此落在「人执行合并」这条约束 agent 行为的规则上（见下「单账号约束」）。
- 编译门做成**半自动脚本**（`npm run build:compile` → `.ci-verify/build.log`）——「可复现命令 + 日志」正是 0007 一直要求却从未落地的可核验产物。
- 第④门**拆 dev（每 PR）与 release 云打包（按触发条件）**——release 按次消耗不公开风控额度，做不到每 PR；与其写一条必被跳过的规定，不如写明触发条件。
③ **明确不做**：不把 HBuilderX 搬进 CI；不校验证据真伪；不给小程序端逐页冒烟（测试期）；不追溯已合并 PR；不改 `ci.yml` 触发语义；不动移动端源码。
④ **拆分步骤**（单票 #841，顺序执行）：PR 模板迁移改写 → `pr-evidence.yml` → 半自动编译门脚本 → `AGENTS.md` 落「agent 不得自合」→ 用一张实测 PR 验证门真的会红。**（ruleset 的「必检 + approve」两步已裁定不做，见「单账号约束」）**
⑤ **约束**：`ci.yml` 的分支 push 语义不变，`pr-evidence` 是「PR 事件不触发 CI/CD」的**唯一豁免**且只读正文、不构建不部署；**agent 不得自行合并触及运行时面的 PR**（本仓无 admin 通道，「必检 + approve」装不上，见「单账号约束」）；应急通道（`gh workflow run cd.yml`）不经验收门，但必须在正文声明风险接受。
⑥ **验收标准**：缺证据的运行时面 PR 被 `pr-evidence` 判红、补齐转绿（本仓它是可见检查，不进 ruleset 必检）；`AGENTS.md` 已落「agent 不得自行合并触及运行时面的 PR」；`npm run build:compile` 产出零 ERROR 的 `build.log`。

## 门的定义

| 门 | 类型 | 何时必须过 | 证据（产物） | 阻塞方式 |
| --- | --- | --- | --- | --- |
| ① Android 真机逐页截图对比 | 人工 | 触及运行时面 | before/after 截图成对 + 四字段 | 合并前 · **人执行合并**（`pr-evidence` 判红可见） |
| ② 微信开发者工具无报错 | 人工 | 命中 MP-WEIXIN 面 | 入口页 + 被改页无报错 + 四字段 | 合并前 · 同上 |
| ③ `npm run test:unit` 全绿 | 自动 | 一律 | CI run 链接 | 已阻塞（`ci-summary` 必检） |
| ④a dev 全量编译 0 新增 error | 半自动 | 触及运行时面 | `.ci-verify/build.log` + 日志片段 | 合并前 · 同上 |
| ④b release 云打包编译 | 半自动 | 收口 PR / 新增 async / 新增 composable | `cli pack` 日志 | 高风险改动必跑（非每 PR） |

### 触发判据：「运行时面」

命中任一即需过 ① 与 ④a：`**/*.uvue`、`**/*.uts`、`manifest.json`、`pages.json`、`platformConfig.json`。

- 不触发（一律免人工门）：`*.test.js`、`docs/**`、`AGENTS*.md`、`.opencode/**`、`jest.config*.js`
- 只触发自动门：`package.json` / `package-lock.json`（CI 自己会跑）

判据必须是**可机检的路径匹配**（`git diff --name-only`），不得靠自然语言判断——否则又会退化成「我以为这算运行时改动」。

### 证据形态与判据字段

每门一行四字段：**执行人**（GitHub handle，不得是 agent 账号）/ **日期** / **复测对象**（页或流程清单）/ **结论（含产物）**。无产物、只有勾选 = 缺证据。

产物按门：③ = CI run 链接；④a = 命令 + HBuilderX 版本 + 时间戳 + ERROR 行数 + 日志尾部若干行；①/② = 截图（见下）。

**传输与落点分离**：对话粘贴只是**通道**，不是载体——文本日志由 agent 逐字转写进 PR 正文；截图由 agent 压缩为 JPEG(q80) 提交到 `docs/verification/<模块>/<PR号>/<页>-before.jpg` 与 `<页>-after.jpg`，PR 正文用相对路径引用。（理由：#839 的教训是「摩擦高的门会被跳过」，对话粘贴是最低摩擦入口；但会话记录不进仓库、PR 与校验都读不到，故不能当载体。截图托管方式可切换——若仓库体积优先，改由人工拖入 PR 正文，GitHub 托管。）

### 截图粒度（第①门）

模块页面 ≤10 → **全部页面**前后对比；>10 → **变更页 + 模块入口页 + 一条主流程**，其余页在证据段列「未改动」清单。纯新增页只需 after。

### 小程序门（第②门）：测试期口径

小程序端现状：真实 appid（`wx38c3e31b16a7ced0`）、在 `platformConfig.json` 目标内、源码有 MP-WEIXIN 条件编译分支，但**只发过测试版、无正式用户**。

- **测试期**：命中 MP-WEIXIN 面（条件编译段 / `manifest.json` / 平台 API 包装）才必过，打开入口页 + 被改页无报错；其余 PR 免
- **正式发布前必须补一次全量逐页冒烟**，作为发布前置条款（一次性门，不写进每 PR 流程）

### 第④门：dev 编译门与 release 云打包门

- **④a dev 编译门（每张触及运行时面的 PR 必过）**：`npm run build:compile` → `cli.exe open` → `project open --path <项目>` → `launch app-android --project <项目> --compile true`；**必须解析 stdout 判成败**（CLI 退出码恒为 0，不可用）；日志固定落 `.ci-verify/build.log`（不入库）
- **④b release 云打包门（按触发条件，非每 PR）**：触发 = ① 模块手术系列的**收口 PR**；② diff 出现**新增 `async function` 或新增 composable**（缺口四/五的高发面）；③ 维护者判断触及 Kotlin 类型推断时自行加跑。执行 = `cli pack`（需 DCloud 账号登录，按次消耗不公开风控额度，需排队）
- 依据：ADR-0007 已录「release 云打包比 dev 编译更严」，缺口五（async 缺返回类型）只有云打包才暴露

### 风险接受通道

允许例外，**禁止静默**：PR 正文必须出现固定字样「已接受未验证风险」+ 理由 + 事后验证计划，且事后要有回执（补跑或记 issue）。未声明而缺证据 = 门未过。**走了这条通道的 PR 必须由人执行合并**（agent 不得自合，见下节）。

### 实现层约束与已知缺口（#841 落地时实测，2026-09-11）

- **`pr-evidence` 的行为由 head 分支里的 workflow 文件决定**（GitHub 对 `pull_request` 事件的取值方式）：带该文件的分支即生效，不带的老分支**永不报这项检查**。实测：基于 master 的探针分支确实没跑该检查。因为 ruleset 开了 `strict_required_status_checks_policy`（分支必须与 master 同步），老分支本来就必须 merge master 重推，所以不会永久挂起——但**这条耦合记在这里：日后若有了 admin 通道要把 `pr-evidence` 设为必检，必须先确认目标分支带该文件**。
- **该文件本身可被 PR 修改**（head 提供校验逻辑是 GitHub 的固有模型）。当前防线 = `AGENTS.md` 的「agent 不得自行合并触及运行时面的 PR」+ 评审时看这个不足 200 行的 diff（本仓装不上 approve 门，见下节）。若日后要抗篡改，可改用 `pull_request_target`（校验逻辑取自 master，而本 job 不 checkout、不执行 PR 代码，无「不可信代码 + 写权限」风险）——但**其 check run 能否满足 ruleset 必检尚未实测**，未证实前不采用。
- **「未命中运行时面即放行」的判据取的是文件清单**（`*.uvue` / `*.uts` / `training-app` 下的三份 json）；④b 的触发判据取 diff 的 `patch` 字段，GitHub 对超大 patch 会截断 —— **只会漏判（少要求一门），不会误判（不会凭空拦人）**，方向上安全。
- 校验器**只校结构与产物字段，不校真伪**（重申）：不校验 `build.log` 是否真存在、截图链接是否可达；真伪由维护者读证据判定。
- ④a 的脚本实跑一次约 **4.6 分钟**（`--cleanCache true`，50 页全量，HBuilderX 5.24）；CLI 连不上主程序时会**挂住不返回**，脚本以每步超时兜底并归为「环境不可用」（`exit 2`），不会被误判成编译失败或编译通过。
### 单账号约束：本仓装不上「必检 + approve」（2026-09-11 裁定）

本仓只有两个 GitHub 账号：`zhengcookie`（write，agent 会话所用，也是 PR 作者）与 `DriftingLi`（admin，仓库所有者）。**维护者不持有 `DriftingLi`**，而 `zhengcookie` 对 ruleset 的写操作实测返回 **404**（权限不足：读得到、写不了）。

后果照实记录：

- **`pr-evidence` 只能作为可见检查运行，不进 ruleset 必检**：把 `pr-evidence` 加进必检、或把 `required_approving_review_count` 改成 1，都需要 admin 权限——做不到。
- **`approve=1` 若强行加上就是死锁**：作者不能自批，而唯一可批的账号维护者拿不到 ⇒ 所有 PR 永久合不了，且没有回退手段（改回去也要 admin）。故本 ADR 不采用它。
- 于是「人工门只能人签」在本仓**落到 agent 行为约束上**：`AGENTS.md` 规定 **agent 会话不得自行合并触及运行时面的 PR**（改动集含 `*.uvue` / `*.uts` / training-app 下的 `manifest.json` / `pages.json` / `platformConfig.json`）；这类 PR 必须把证据填齐后停在「待人工签收」，**由人执行合并**。非运行时面（纯文档 / 测试 / CI 配置）不受此限——否则文档改动也要人守，流程会被拖死。
- **残余风险照实说**：单账号下 GitHub 侧无法机械区分「人」与「agent」，这条靠 `AGENTS.md` 约束 agent（agent 的必读面），**不是密码学保证**。要真正的机械隔离只有两条路——增加一个由人控制的签收账号，或用签名（私钥与口令只在人手里）；本 ADR 不采用，但记在这里备选。
### 闭环条款：人工门是规则来源

人工门当场抓到的问题，收口时**必须回写为守护规则或注入自检**（先例：`utsAndroidCompile.test.js` 规则 A–Y 全部来自编译现场），做不到的在 ADR/票面写明理由。人工门因此不是一次性检查，而是规则的来源——这是它值得保留的理由。

### 生效时点与追溯

从**下一张合并到 master 的手术 PR** 起适用，**不追溯已合并 PR**。`refactor/exam`（#645 T07）是第一条适用的票：不要求它补历史证据，只要求它自己的四门证据。

## 明确不做

- **不把 HBuilderX 搬进 CI**：官方 CLI 存在（`cli launch --compile true` / `cli pack`），但 CLI 驱动主程序、`cli --help` 都要求主程序可达，官方无 `--headless` 文档，Windows self-hosted runner 的 session 0 无头可行性未证实——若日后证实可无头，再议
- **不校验证据真伪**：`pr-evidence` 只校结构与字段完整性；真实性由维护者读日志/截图判定，AI 不替代签收
- **不给小程序端逐页冒烟**（测试期，见上）
- **不追溯历史 PR**、不改 `ci.yml` 既有触发语义、不动移动端源码
