## 背景与目标

ADR-0007 规定移动端改动需过四门，其中两道人工门（HBuilderX 全量编译、真机/小程序冒烟）在流水线里**零痕迹**，且不构成合并阻塞——PR 正文里的四门表格只是自我声明。

两次实害：

- **PR #817**（content:// 上传修复，2026-09-11）：首版正文自陈「`getFileSystemManager` 的可用性仍以 HBuilderX 全量编译为准……本地无法验证」→ **同一 PR 内 6 轮修复**（`c942548` → `04cfbd4`，08:44–09:57；含只有云打包 release 才暴露的 Kotlin 错误、只有真机才暴露的上传 602001 与证件 level NPE）→ 10:40 合入。**注意时序**：#839 票面叙述为「合并后连锁返工」，实测相反——返工发生在合入之前、PR 仍打开时；而合入时正文四门表仍写着「⏳ 待人工」，**修复后的状态同样没有任何签收产物**（`reviews` / `comments` 均为 0）
- **PR #837**（论坛采纳按钮）：正文标注「HBuilderX 全量编译 ⏳ 待人工 / 微信开发者工具 ⏳ 待人工」→ **从未执行即合并**，侥幸未出事

两次的共同点：**「如实标注」在现行流程里的作用是免责，而不是阻止合并**。

机制层事实（2026-09-11 审计所得）：

- 移动端唯一的自动门是 `ci.yml` job `mobile-test`（`npm run test:unit`，38 suites / 752 tests 全绿），经 `ci-summary` 汇聚，是 ruleset `20687043` 的**唯一**必检项，`required_approving_review_count: 0`（无人工批准要求）
- 三道人工门（真机、小程序、Kotlin 编译）在 workflows 里**无任何步骤**
- **根仓库没有 PR 模板**：模板错放在 `training-app/叉车维修培训学员端跨端应用/.github/PULL_REQUEST_TEMPLATE.md`（GitHub 只读仓库根的 `.github/`），且其内容要求合到 `main`（默认分支实为 `master`）
- **没有任何 workflow 读取 PR 正文或评论**（全仓 `pull_request.body` / `pull_request.title` / `issue_comment` 命中 0）
- HBuilderX 官方有 CLI（`cli launch app-android --compile true` 仅编译、`cli pack` 云打包、官方「CI 自动化」小节与 Linux CLI），但 CLI 是**驱动主程序**的（连 `cli --help` 都要求主程序可达），且**失败时退出码恒为 0**（实测四处失败全返回 0）；Windows self-hosted runner 的无头可行性未证实

- **发生率（最近 20 个触及 `training-app/**` 且改动 `*.uvue` / `*.uts` 的已合并 PR，全量逐个核对，非抽样）**：14 个在正文声明了 HBuilderX 编译门、5 个声明了真机门，**留下可核验产物（编译日志 / 截图 / 真机结论）的是 0 个**。`docs/` 下无任何验收归档文件；唯一近似记录是 `.gitignore` 掉的 `.scratch/alignment/` 里 4 份勾选式声明——而 ADR-0007 第 186 行自己就写着「口头/勾选式『签收』不构成证据」。
目标：让每道门的执行留下**可核验产物**并使缺产物成为**合并阻塞**；把成本高到无法保持的规定显式降级，而不是留一条注定被跳过的条款。

## 决策清单（六段）

① **目标与范围**：给移动端验收门补上「执行位」——每道门的执行留下可核验产物，缺产物即阻塞；只动验收门与证据机制，不动手术本身、不动源码。
② **选型 + 一句理由**：
- 人工门**按改动面分级**（运行时面触发、文档/测试面免）——一条打在所有 PR 上的门注定被跳过，分级才有执行力。
- 证据落 **PR 正文固定段** + 截图入仓 `docs/verification/`——正文与 commit 同生共死且可被 workflow 读取（仓内文件会被覆盖、评论会被折叠）。
- 阻塞 = **`pr-evidence` 可见检查 + `AGENTS.md` 硬规「agent 不得自合」**——「必检 + approve=1」在权限上**装得上**（维护者持有仓库所有者账号 `DriftingLi`，API 实测 `admin: true`），但**裁定不装**：逐 PR 人工审批会把维护者变成串行瓶颈，成本高于约束收益。阻塞因此落在「人执行合并」这条约束 agent 行为的规则上（见下「为何不装『必检 + approve』」）。
- 编译门做成**半自动脚本**（`npm run build:compile` → `.ci-verify/build.log`）——「可复现命令 + 日志」正是 0007 一直要求却从未落地的可核验产物。
- 第④门**拆 dev（每 PR）与 release 云打包（按触发条件）**——release 按次消耗不公开风控额度，做不到每 PR；与其写一条必被跳过的规定，不如写明触发条件。**（2026-09-11 修订：dev 面 ④a 与整模块 ④c 合并为「④ 本地编译门」，④b 触发改按打包面——见「第④门」与文末「④b 维持云端」节。）**
③ **明确不做**：不把 HBuilderX 搬进 CI；不校验证据真伪；不给小程序端逐页冒烟（测试期）；不追溯已合并 PR；不改 `ci.yml` 触发语义；不动移动端源码。
④ **拆分步骤**（单票 #841，顺序执行）：PR 模板迁移改写 → `pr-evidence.yml` → 半自动编译门脚本 → `AGENTS.md` 落「agent 不得自合」→ 用一张实测 PR 验证门真的会红。**（ruleset 的「必检 + approve」两步已裁定不做，见「为何不装『必检 + approve』」）**
⑤ **约束**：`ci.yml` 的分支 push 语义不变，`pr-evidence` 是「PR 事件不触发 CI/CD」的**唯一豁免**且只读正文、不构建不部署；**agent 不得自行合并触及运行时面的 PR**（本仓可装「必检 + approve」但裁定不装，见「为何不装『必检 + approve』」）；应急通道（`gh workflow run cd.yml`）不经验收门，但必须在正文声明风险接受。
⑥ **验收标准**：缺证据的运行时面 PR 被 `pr-evidence` 判红、补齐转绿（本仓它是可见检查，不进 ruleset 必检）；`AGENTS.md` 已落「agent 不得自行合并触及运行时面的 PR」；`npm run build:compile` 产出零 ERROR 的 `build.log`。

### 风险分层：低风险运行时面免 ①②（2026-09-11 修订）

**判据（可机检、fail-closed，实现见 `pr-evidence.yml`）**：设 `runtime` = 命中运行时面的文件；当 `runtime` 非空**且**改动集里**每个**文件都满足「低风险」时，`lowRiskRuntime = true`：

- `training-app/` 下的 `*.uts`（**仅逻辑层**）✔ 低风险
- `training-app/` 下的 `*.uvue`（模板/样式面）✘ 不算低风险
- `uni_modules/**`（原生插件面）✘ 不算低风险
- `training-app/` 下的三份 json（`manifest.json` / `pages.json` / `platformConfig.json`）✘ 不算低风险
- 测试/文档/配置（`*.test.js` / `*.md` / `jest.config*.js`）与非移动端文件 ✔ 不影响本判据（不因它们把面「抬高」）

**减免什么**：免 ① 真机逐页截图与 ② 微信开发者工具 —— 这两门在正文里**可以整行不写**（缺行不报错）；若写了，写「免（低风险运行时面：仅 .uts 逻辑改动）」也算通过。

**不减免什么**：③ `npm run test:unit` 与 ④ 本地编译门**仍必过**（.uts 逻辑改动正是 Kotlin 编译期错误的来源面）；④b 仍按打包面触发；**合并仍由人执行**（`AGENTS.md` 硬规不变）。

**代价照实说**：低风险面的风险不是消失了，而是**推迟**——真机/渲染类问题（布局、生命周期、原生能力差异）本地编译门抓不到，靠**发版前的 ① 全量逐页冒烟**兜底（发布前置条款）。校验器会在 `notes` 里带出这条提示。


### 触发判据：「运行时面」

命中任一即需过 ① 与 ④ 本地编译门：`**/*.uvue`、`**/*.uts`、`manifest.json`、`pages.json`、`platformConfig.json`（低风险面上 ① 免，见上「风险分层」）。

- 不触发（一律免人工门）：`*.test.js`、`docs/**`、`AGENTS*.md`、`.opencode/**`、`jest.config*.js`
- 只触发自动门：`package.json` / `package-lock.json`（CI 自己会跑）

判据必须是**可机检的路径匹配**（`git diff --name-only`），不得靠自然语言判断——否则又会退化成「我以为这算运行时改动」。

### 证据形态与判据字段

每门一行四字段：**执行人**（GitHub handle，不得是 agent 账号）/ **日期** / **复测对象**（页或流程清单）/ **结论（含产物）**。无产物、只有勾选 = 缺证据。

产物按门：③ = CI run 链接；④ = 命令 + HBuilderX 版本 + 时间戳 + ERROR 行数 + 日志尾部若干行（④c 记 `KOTLIN_ALL_RESULT … log=.ci-verify/kotlin-all.log`，④a 记 `COMPILE_RESULT … log=.ci-verify/build.log`）；①/② = 截图（见下）。

**传输与落点分离**：对话粘贴只是**通道**，不是载体——文本日志由 agent 逐字转写进 PR 正文；截图由 agent 压缩为 JPEG(q80) 提交到 `docs/verification/<模块>/<PR号>/<页>-before.jpg` 与 `<页>-after.jpg`，PR 正文用相对路径引用。（理由：#839 的教训是「摩擦高的门会被跳过」，对话粘贴是最低摩擦入口；但会话记录不进仓库、PR 与校验都读不到，故不能当载体。截图托管方式可切换——若仓库体积优先，改由人工拖入 PR 正文，GitHub 托管。）

**门评论的绑定判据：祖先 + 运行时面未变（2026-09-12 修订）**：绑定 = ① `commit` 等于 head（旧行为保留），**或** ② 它是 head 的**祖先**（compare `status ∈ {ahead, identical}` 且 `merge_base_commit.sha` == 它）**且**二者之间改动集不含运行时面文件（判据同「运行时面」：`*.uvue` / `*.uts` / 三份 json）。**守护边界**：中间只要有**任一**运行时面文件改动，立即退回「必须重跑重贴」——只有「只改了文档/脚本/测试」才免跑；其余情况（不是祖先 / head 上找不到该 sha / 其间运行时面已变）按「缺该行」报红并写明原因；compare 取不到（异常 / 超时 / 超大 diff 被截断）一律 **fail-closed 判不绑**，绝不因 API 异常放行。**放宽的只有绑定口径**：仍**不校真伪**（不验那次编译是否真按该 sha 跑过），「执行人」栏仍由人签收、合并仍由人执行。**摘要措辞纪律（2026-09-13 补正）**：门评论摘要行必须点名**证据实际所在的 commit**，祖先绑定时显式写出「祖先口径，当前 head 为 `<head7>`」—— 不得一律写 head，否则摘要会读成「证据是在当前 head 上跑出来的」，在只校结构的门里属于往「更可信」方向失真。
**已知边界（2026-09-13 补充，刻意不收紧）**：本判据复用的「运行时面」就是门自己的触发判据（同一个 `isRuntimeFile`：`*.uvue` / `*.uts` / 三份 json），因此它**不覆盖打包面**（`uni_modules/**/utssdk/app-android/**`、`*.aar`、`libs/*.jar`）—— 祖先链上若只有打包面改动，④/② 的证据仍算绑上。这是**继承自触发判据**的边界（不是本次放宽引入的），且**刻意不收紧**：改用更宽的打包面会把本修订要消掉的 churn 放回来。打包面自身的收敛另有出口 —— ④b 按打包面触发，其证据走正文而非评论绑定。
**动机**：ruleset 的 `strict_required_status_checks_policy` × master 当日前进 10+ 次 ⇒ 每次 sync 都出新 head ⇒ 旧口径下**已贴证据全部作废、必须重跑重贴**（#624 反复被拖的主因），而其中多数前进无害（只改文档/脚本/测试，运行时面逐字节未变）。**代价照实说**：祖先链上一旦混入运行时面改动，证据同样全量作废——判据不看改动是否属于被证据覆盖的模块。

### 截图证据的结构性判据（2026-09-12 复测修订）

**坑位（假绿来源）**：旧的 `screenshot` 产物判据是一条过宽的**子串**正则
（`/!\[[^\]]*\]\(|https?:\/\/|docs\/verification\/|\.ci-verify\/\S+\.png|mp-weixin\.png/`）：
`https?:\/\/` 与 `.ci-verify/\S+\.png` 意味着**人在「结论」里贴个本地 png 路径、或随手贴一个链接**，这门就**结构上被判满足**——截图从没进过仓库，也无人能核验。

**改为结构性判据**（仍**只校结构、不校真伪**，见下「明确不做」）：截图证据必须来自三者之一 ——

1. **GitHub 托管的图片**：Markdown 图片语法 `![...](…)` 指向**远程图片**（GitHub 附件 / 图床直链 / 带图片扩展名的 `http(s)` URL），或直链 `https://github.com/user-attachments/…`、`https://…user-images.githubusercontent.com/…`；
2. **仓库内路径**：`docs/verification/<模块>/<PR号>/<页名>.<ext>`（`<PR号>` 必须是**数字段**；`ext` ∈ `png|jpg|jpeg|webp|gif|bmp`）——与上面的截图落点约定一致，可点开预览、可核验；
3. **sha 绑定门评论的链接**：`…/pull/<n>#issuecomment-<id>`（评论本身已由校验器按 `gate-evidence:<门号>` + `commit: <sha>` 绑定到 head）。

**明确不接受**：裸的本地产物路径（`.ci-verify/*.png`、`mp-weixin.png` 之类——**连写成 `![](.ci-verify/x.png)` 也不接受**，它不在仓库里、渲染即裂图）与任意 `http(s)` 链接（裸 URL 除非是 GitHub 附件/图床直链，否则一律不认）。判据收紧**只影响结构**，不引入真伪校验。

### 截图粒度（第①门）

模块页面 ≤10 → **全部页面**前后对比；>10 → **变更页 + 模块入口页 + 一条主流程**，其余页在证据段列「未改动」清单。纯新增页只需 after。

**2026-09-12 修订：② 从人工门降为半自动门**（spike #883 实测，口径与 ④a 同款 = #870 裁定 B）：

- **载体**：`scripts/mp-weixin-check.ps1`（`npm run build:mp-weixin-check`），取证核心是同目录的 `scripts/mp-weixin-probe.mjs`。

- **断言**：**可验证子集**（只有这几条判门过/不过）= `connected=true`、`pageStack` 非空（**前置断言**）、入口页在栈内、`errorsTotal == 0 && exceptionsTotal == 0`、**至少 1 张当前页截图**；「逐页导航 + 每页截图」这组在导航 API 不可用时记 **SKIP**（见下面的降级条款），**既不写 true 也不写 false**，且不产生 `failures`。
- **产物**：`MP_WEIXIN_RESULT appid=… pageStack=… entry=… errorsTotal=0 exceptionsTotal=0 shots=… navigation=ok|skip(unsupported) [navigationSkipReason=navigation-api-unsupported] log=.ci-verify/mp-weixin.log` + `.ci-verify/mp-weixin.log` + `.ci-verify/*.png`；`failures=` **只在可验证子集不过时非空**。
- **证据可由 sha 绑定评论承载**：脚本 `-PostToPr <n>` 在门通过时贴 `<!-- gate-evidence:② -->` + `commit: <head sha>` 的评论（与 ④ 同款），`pr-evidence` 认出即跳过 ② 行的字段校验并给 notes。
- **三条必须抄进脚本的实测坑位（#883 + 2026-09-12 复测）**：① `pageStack` 为空会让**所有 page 级 API** 报同一个误导弹错 `Cannot destructure property 'rawPath' of 't.getPageMetaByWebviewId(...)' as it is null` —— 根因是自动化会话里没有页面被打开，处置 = 先 `close` 再 `auto`，并把 `pageStack` 非空作前置断言；② `mp.screenshot()` 挂在 **MiniProgram** 上、不在 Page 上（`page.screenshot` is not a function）且不返回内容，产物只能靠落盘文件取；③ `page.$()` 元素级断言在 `miniprogram-automator@0.12.1` + 开发者工具 Stable v2.01.2510290 组合下**不可用**（实测挂起 15s 超时）⇒ 本门只做 page 级导航 + console/exception + 整页截图。**2026-09-18 复测补全（见顶部同日修订）**：此前只实测过**标签选择器**（`$("view")`）；本次把**类选择器**与不存在的 class 一并测了 —— **都不可用**，`page.data()` 同样超时。
- **两条「时序」坑位（2026-09-12 复测新增，直接决定这门红还是绿）**：④ `cli.bat auto` **必须等它跑完**——它会派生子进程去起自动化服务，**中途 kill 掉 auto 会让自动化端口永远不监听**；且端口是**auto 跑完之后延迟出现**的，故脚本在 auto 之后**轮询**端口（`-PortWaitSeconds`，默认 90 秒）而不是固定等待。⑤ automator 连接与 `pageStack` 就绪是**异步**的，实测**首次常失败**（报 `Failed connecting …, check if target project window is opened with automation enabled`），往往第 2–3 次才成功 ⇒ 探针必须**重试**（`-ProbeAttempts`，默认 6）。这两条不是可选加固：按固定时长探测会得到「端口不监听 / pageStack 超时」的**假失败**。
- **时序坑位 ⑥（2026-09-12 复测钉死，此前让 ② 在本机结构性跑不通）**：`cli.bat close` 会把**项目窗口一起关掉**，而 `cli.bat auto` **不会重开** ⇒ 少了「重开窗口」这一步，`pageStack` **恒空**，所有 page 级 API 报同一个误导弹错（坑位①的表象），整门结构性不成立。处置：顺序写死 **`close → open --project <dist> → auto`**（脚本内为一条显式步骤并写进日志；`-SkipBuild` 下同样定位构建产物目录），守护测试 C12。补证：插入 `open` 后 `pageStack=["pages/index/index"]`、`errorsTotal=0`。
- **导航不可用时诚实降级为 SKIP（2026-09-12 复测；**不许假绿**，也**不得**算成通过）**：本机 `miniprogram-automator@0.12.1`（× 开发者工具 Stable v2.01.2510290）下 `mp.reLaunch` / `mp.navigateTo` **恒报 `Uncaught [object Object]`**，而 `mp.connect` / `mp.pageStack` / `mp.screenshot` 正常 ⇒ 「逐页导航 + 每页截图」这组断言在此环境**不可能成立**。处置：探针捕获到该族异常后把这组断言记 **SKIP（reason=navigation-api-unsupported）**，在 JSON `navigation` 字段、结果行（`navigation=skip(unsupported) navigationSkipReason=navigation-api-unsupported`）与 PR 门评论里**显式写明**；门只对上面的**可验证子集**作结论，`failures=` 只在该子集不过时非空。守护测试 C13（含「SKIP 不得写成 PASS」）。**2026-09-18 更新（见顶部同日修订）**：本条现象**已对着完全就绪的会话复测证实**（`mp.reLaunch` / `mp.navigateTo` 均 `Uncaught [object Object]`），并**排除**了「dist 没跑起来」这一替代解释（`App.callWxMethod('getSystemInfoSync')` 通、能收到小程序自身 console warn）⇒ 结论不变，继续 SKIP。**仍未定位根因**（工具组合 vs 工程/IDE 状态，未分离）——本条不宣称已定位根因，也不据此改门的语义。新增一条阻断：`App.captureScreenshot` 亦超时 ⇒「至少 1 张当前页截图」当前不成立。**首跑校准**：首次在任何机器上跑本门，须人工核对结果行的 `navigation=` 字段与日志里的 `navigation=SKIP reason=…` 行；`navigation=ok` 时逐页组仍按「每步导航后当前页 == 目标页」（`allRoutesVisited`）与「每页都有 PNG」（`screenshotsProduced`）判——判据取**导航本身的结果**，**不拿导航前读到的 `pageStack` 去比所有路由**（那样恒假，会让健康机器上的门永远过不去）。
- **端口监听面（照实记，未做加固）**：`cli.bat auto --auto-port` 实测绑**通配地址**（`Get-NetTCPConnection` 显示 `::`）⇒ 自动化端口在局域网内可访问；`cli auto -h` 无绑定地址参数，CLI 侧无法收窄。共享网络上跑本门前先确认防火墙。
- **截图入库纪律（P2，2026-09-12 维护者追加）**：带 `-PostToPr <n>` 时把截图**压缩后提交到当前 PR 分支**的 `docs/verification/<模块>/<PR号>/<页名>-after.<ext>`，并在评论里用**仓库内相对路径**列出每张图。优先 **WebP q75**（探测 `cwebp` / `ffmpeg` / `magick` 择一），本机三者皆无则退 **JPEG q75**（.NET `System.Drawing`，Windows 自带）；**宽 ≤720px（等比、不放大）**；**每 PR ≤10 张、单张 ≤150KB、合计 ≤1.5MB**；超限先降质 → 再缩尺 → 再减图（减图须在评论里写明省了哪几页）。提交仅在「当前分支 = 该 PR 的 head」且「工作树除本次入库外无其他改动」时进行；**任何失败只打印警告 + 给出待执行的 `git add`/`commit` 命令，不得让门失败**；`-NoArchive` 为逃生开关。**入库提交不带 `[skip ci]`**：CI 会为新 sha 重跑（成本可接受），而带 `[skip ci]` 会让 PR head 缺 `ci-summary` 检查、反而不满足 ruleset 必检。
- **维持不变的**：门的语义（入口页 + 被改页无 console error / exception）、**「执行人」栏由人签收**（agent 不得代填、不得写「已通过」）、**合并仍由人执行**。
- **测试期口径（不变）**：命中 MP-WEIXIN 面（**条件编译指令行的增删 / `manifest.json` / `platformConfig.json`** —— 机检口径见下节「② 触发判据的可机检口径」）才必过；旧表述里的「平台 API 包装」**不是**可机检的触发面（在既有 `#ifdef` 块内新增 `wx.*` 调用不动指令行 ⇒ 不点亮 ②），如实记在此处以免两处口径并存；**正式发布前必须补一次全量逐页冒烟**，作为发布前置条款（一次性门，不写进每 PR 流程）。

#### ② 触发判据的可机检口径（2026-09-15 修订，#1030）

**坑位（实测 #1028）**：`pr-evidence.yml` 里 ② 的第二条判据是 `(f.patch || '').includes('MP-WEIXIN')` —— 判的是**改动文本里出现过这个字符串**，不是本 ADR 定义的「命中 MP-WEIXIN **面**」（交付形态，更严）。实害有二：① **误报** —— 在 ADR/文档里写「② 免（未命中 MP-WEIXIN 面）」这句话**本身**就把门点亮（#1028 因此判红；同一 PR 的**正文**里写同样的话却没事，因为判据只扫 `files[].patch`、不扫正文 ⇒ 「措辞在正文里安全、写进文件就中招」的隐性陷阱，写 ADR 的人几乎必然踩到）；② **反向激励** —— 想不被误报只能**不写**这个术语，而本 ADR 恰恰要求把这类口径写进文档。同族误报：`utils/useBiometric.test.js` 用字符串**断言** `// #ifdef APP || MP-WEIXIN` ⇒ 改那个测试文件也会凭空要求 ②。

**新判据（两条，任一命中即需过 ② —— 低风险运行时面另按「风险分层」减免 ①②，见上；实现见 `pr-evidence.yml` 的 `hitsMpWeixinFace`）**：

1. **文件清单**：`training-app/**` 下的 `manifest.json` / `platformConfig.json` 改动（不读 diff 文本）；
2. **条件编译指令行的增删**：**运行时面文件**（`*.uvue` / `*.uts` / 三份 json —— 与 `isRuntimeFile` 同一判据）的 diff 里，增删了一条**真指令** —— 去掉 `+`/`-` 标记后行首（允许 `//` `/*` `<!--` `"` `'` 包装）为 `#ifdef` / `#ifndef` / `#if`，且**条件表达式**里含 `MP-WEIXIN`（`#ifdef APP || MP-WEIXIN` 同算；**删除**指令行同样算 —— 那也改变了交付形态）。判据只看 `#ifdef` 与平台名之间的**条件表达式**那一段（只允许平台表达式字符）：`// #ifdef APP-PLUS // 与 MP-WEIXIN 分支不同` 这类「真指令行 + 同行散文提及」**不算**命中 —— 那与第 ② 条要修的是同一个病。

**面外不判（写实）**：第 2 条**不含** `training-app/**/*.js` / `*.ts` / `*.vue` / `*.scss` —— 理由不是「它们不会写条件编译」，而是本仓实测这些扩展名下的 `#ifdef` **只出现在测试断言字符串里**（`utils/useBiometric.test.js` 等，正是要排除的误报面），且它们的改动本来也不进「运行时面」触发集。若日后真有 `*.js` 交付面写条件编译，先按「运行时面」口径把它纳入触发集，再谈 ②。

**明确不算命中**：文档/测试/注释里**提到**该术语（`.md` 正文、代码块引例、`*.test.js` 的断言字符串、散文提及）。② 是「交付形态变了」的门，不是「文本里出现了这个词」的门。

**为什么第 2 条要限定在运行时面文件**：改动集不含运行时面时 `pr-evidence` **直接放行、根本走不到门校验**，故把 ② 的 patch 面收窄到运行时面不会少拦任何**可执行**的场景；不收窄则文档/测试会重新点亮它。判据仍**可机检**（路径匹配 + 单行正则），不靠自然语言判断。

**可见性（本修订的另一半诉求）**：门被点亮时 `pr-evidence` 的摘要必须点名是**哪个文件**命中了 MP-WEIXIN 面 —— 旧判据下唯一的「排查手段」是改措辞、重推、看红绿，那不该是排查手段。

**落锁（守护）**：`.github/scripts/pr-evidence-check.test.mjs` 的「2026-09-15 修订（#1030）」段 —— 4 条负例（文档措辞 / `*.test.js` 断言字符串 / 非运行时面文件里引真指令 / 运行时面文件里的散文提及与「指令行 + 同行散文提及」）+ 1 组正例（6 种指令形态：新增、删除、多平台表达式、模板注释、样式块注释、`pages.json` 条件编译键）+ 1 条静态自检（**代码行**里不得再出现 `.includes('MP-WEIXIN')`，只看代码行是为了不误报修订说明里引用的旧判据原文）。**判别力实测**（三条变异各自定向）：把旧判据塞回去 ⇒ 5 条负例/静态自检红、其余 62 条不动；把指令正则置为恒假 ⇒ 正例组与既有的 `diff 出现 MP-WEIXIN 条件编译` 用例一起红；把正则退回宽松的 `[^\n]*` ⇒ **恰 1 条红**（「指令行 + 同行散文提及」那条）。

**已知边界（写实，本次不收紧）**：第 2 条读 `patch`，而 GitHub 对**超大 diff / 二进制**不给 `patch` ⇒ 这类文件判不出指令行，该路径 **fail-open**（不要求 ②）。这与 ④b 当年从「读 patch」改成「文件清单」要躲的漏判同源；但**条件编译面天然只能从文本判**，改不成文件清单。收紧（`patch` 缺失即判 `needs2`）会把改名的 `.uvue` 也拖进 ②，收益不抵成本，故照实记为边界。

#### ② 就绪闸门：`auto` 返回 ≠ 会话可用（2026-09-13 实测定位）

② 此前**时好时坏**的原因已用裸 ws 帧实测钉死，**不是竞态，也不是端口问题**：

| 里程碑（相对 `cli.bat auto` 返回） | 实测 |
| --- | --- |
| 端口开始接受连接 | t ≈ 1s（`auto` 返回后仍有一小段 ECONNREFUSED） |
| `Tool.getInfo` 回包里出现 `SDKVersion` | t ≈ 1–3s（早于此，回包**只有 `version`、没有 `SDKVersion`**） |
| `App.getPageStack` 开始应答 | t ≈ 24–34s（两次实测 24s / 34s） |

两条门红都由此产生，且**都被误报成「自动化端口连不上」**：

1. `miniprogram-automator@0.12.1` 的 `Launcher.connect` 在 ws 打开后**立刻**调 `MiniProgram.checkVersion()`，它读 `(await send('Tool.getInfo')).SDKVersion`；该字段缺失时 `licia/cmpVersion` 对 `undefined` 调 `.split('.')` ⇒ 抛 `Cannot read properties of undefined (reading 'split')`，再被 `connectTool` 的 catch 换成 “Failed connecting to …” 文案。复现栈：`licia/cmpVersion.js:4` ← `MiniProgram.checkVersion`。
2. 探针 `mp.pageStack()` 的超时原本取 30s，**正落在 24–34s 这段就绪窗口中间** ⇒ 同一份代码红绿不定。

**处置（已落地）**：

- **就绪闸门 `scripts/mp-weixin-ready.mjs`**：`close → open → auto` 之后、探针之前，用裸 ws 等齐「`SDKVersion` 存在」与「`App.getPageStack` 开始应答」两个里程碑，再把端点交给 automator；超预算才判 env 不可用，且 `reason` 明确写出缺的是哪个里程碑。它只读、用完即关 —— 实测**不影响**随后的 automator 会话（同一端口先跑闸门再 `connect()`，`pageStack=["pages/index/index"]` 正常）。
- 探针超时抬到 `-ProbeTimeoutMs`（默认 60s ≈ 实测窗口上界 34s 的 1.8 倍）；结果行增记 `ready=<秒>s sdk=<SDKVersion> ide=<IDE 版本>`，让「会话就绪耗时」可机检。
- 探针新增 `connectError.kind`（`not-ready` / `unreachable` / `timeout` / `unknown`），把「会话未就绪」与「端口连不上」**分开报**。
- **删除**「`自动化端口连不上` ⇒ 重试无益」这条裁量：那一类恰恰是**短暂**的，旧裁量让门在第 2 次尝试就放弃 ⇒ 必红。现在只对「缺 `miniprogram-automator` 模块」提前放弃。
- **补正 2026-09-12 的结论**：`close` 与 `auto` 之间缺 `open` 那条**未与就绪窗口隔离**（当时那次的绿也可能是会话恰好就绪），不得再据它宣称「缺 `open` 必然 `pageStack` 恒空」；`open` 步骤保留（`close` 确实会把项目窗口一起关掉）。

**`-Doctor` 体检模式（`npm run build:mp-weixin-doctor`）**：只体检（走 `close → open → auto → 就绪闸门` 同一条路径，但**不接 HBuilderX、不构建、不跑探针、不贴评论、不入库**），逐层给 `OK` / `WARN` / `FAIL`（L1 工具链 / L2 登录态 / L3 进程端口 / L4 构建产物 / L5 项目窗口 / L6 自动化端口 / L7 会话就绪），有 FAIL 则退出码 2。**它绿 ≠ ② 通过**：门结论只能由探针的 `MP_WEIXIN_RESULT` 产出。

**待排查（本轮未定位，如实记）**：`-Doctor` 首跑实测到一次「`cli.bat auto` 回显 `√ auto`，但端口 9420 在 90s 内始终没监听」，紧接同一条命令 **8s 内**就起来了。已排除的两项：`netsh interface ipv4 show excludedportrange protocol=tcp` 显示 9420 **不在** Windows 保留/排除段内（保留段只有 5357 与 50000–50059），且手工 `TcpListener` `bind 9420` 成功 ⇒ **不是端口保留问题**。

第二次（同一天）见到的形态更重：IDE 有 **16** 个 `wechatdevtools.exe`、且 9420 已被**残留自动化会话**占用，此时 `cli.bat auto` **直接挂住 >180s**（不是返回后端口不起）。为验证「残留会话」这一猜测做了一次干净复现：`cli.bat quit` → `wechatdevtools.exe` 归 0、遗留 listener 全清 → 再跑 `-Doctor`，**一次通过**（L1–L7 全 OK，77s）。

据此记下**当前最佳猜测（是猜测，不是结论）**：开发者工具自己的 HTTP 服务端口**跨重启会变**，`cli.bat` 会打印 `IDE may already started at port <旧端口>, trying to connect`，并可能以 `#initialize-error: wait IDE port timeout` 收尾（本次 `-Doctor` 的 L5 原样抓到了这两句，端口从 16342 变成 44037）⇒ 当 `close`/`open`/`auto` 撞上 IDE 尚未稳定的重启窗口时，`auto` 会挂住或起不来；**残留会话与堆叠的 IDE 实例会放大这个窗口**。

处置：① 怀疑这一族时**先 `cli.bat quit` 把 IDE 清干净再跑**（实测有效，但属经验处置、非修复）；② `-PortWaitSeconds` 默认 90 → 180（抬预算）；③ 把状态做成可机检（结果行 `reason=port-not-listening` / `reason=auto-timeout`，`-Doctor` 的 L6 标 `FAIL`）。**不得**据此宣称已定位根因，也**不得**用 `Stop-Process` 之类去 kill IDE（ADR 的 HBuilderX 红线同理）。

**本轮不变、仍然为真**：`mp.reLaunch` / `mp.navigateTo` 在本机恒报 `Uncaught [object Object]` —— 已对着**完全就绪**的会话复测（`connect` 成功、`pageStack=["pages/index/index"]`），确认它与就绪与否**无关**，故「逐页导航 + 每页截图」继续诚实记 `SKIP(reason=navigation-api-unsupported)`，**未证实**是否为版本组合问题。

**appid 口径诊断（2026-09-12，回答 #883 的遗留问题）**：结论是「**`manifest.json` 的 `mp-weixin.appid` 是唯一权威来源；`--appid` 只影响上传**」——

- **权威来源**：HBuilderX 从项目 `manifest.json` 的 `mp-weixin.appid` 读小程序 appid，并写进构建产物的 `project.config.json`；**该字段为 `null` / 缺失时产物落成 `touristappid`（游客 appid）**，`cli.bat auto` 也随之回显 `Using AppID: touristappid`。
- **master 上的现状（已核对全历史）**：`manifest.json` 的 `mp-weixin.appid` 在 master 上**一直是真实 appid `wx38c3e31b16a7ced0`**，**不是 `null`**。该文件最近 5 次触及提交是 `1bf6124`(#435) / `f1ab264`(#361) / `2494eb8`(#275) / `ea2baba`(#141) / `1201836` —— **#882 的改动集里没有它**。（注：`--depth 1` 浅克隆下 `git log -- <path>` 会把这个唯一提交列出来，那是浅克隆的假象，不可作为「谁改了它」的判据。）
- **⚠️ 实测坑位（本次新增，最要紧的一条）**：**HBuilderX 在首次导入 / 编译项目时会回写工作树的 `manifest.json`，把 `mp-weixin.appid` 置为 `null`**（实测 mtime 与 `publish` 启动同秒）。由此有两层结论：
  - **(a)** #883 spike 看到的「manifest 是 null / 产物 appid = `touristappid`」是**该回写行为造成的工作树脏改**，**不是 master 的事实**——spike 当时是在自己的克隆里跑 HBuilderX，manifest 被它改脏后没还原，于是把脏状态当成了仓库现状。
  - **(b) 任何 HBuilderX 门（④a / ④c / ②）在共享工作树里跑都可能静默改脏一个「运行时面」文件**（`manifest.json` 命中运行时面判据），而 `git diff --name-only` 正是 `pr-evidence` 判「运行时面 / 打包面」的依据 ⇒ 脏改会污染判据。故：**脚本对「源 manifest appid」与「产物 appid」都做 fail-closed 前置断言**（不匹配即 `exit 1`，不拿游客 appid 出个绿）；**维护者/agent 跑完任何 HBuilderX 门后必须先 `git status` 看 `manifest.json` 是否被改脏**，脏了就 `git checkout -- manifest.json` 再继续。
- **⚠️ 回写不止 `manifest.json`（2026-09-13 实测追加）**：**HBuilderX 每次「运行到手机」还会往 `pages.json` 追加一段 `condition`**（启动页配置，其注释自述「仅开发期间生效」），把 GUI 里当前选的启动页写进工作树。后果比 `manifest.json` 更严重 —— `pages.json` **同时是「运行时面」与「打包面」判据的来源** ⇒ 这段脏内容一旦被误提交，PR 会**凭空命中 ④b release 云打包的触发条件**。实测：④a 跑完 `git status` 即出现 `M pages.json`。处置：**跑完任何 HBuilderX 步骤后 `git status` 要同时看 `manifest.json` 与 `pages.json`**；`condition` 属本地开发配置、**禁止提交**，脏了直接 `git checkout -- pages.json` 还原。
- **无独立配置面**：HBuilderX 的按项目本地配置（`%APPDATA%\HBuilder X\projects\<hash>\setting.json`）里**只有打包面字段**（`appPack.*`，如 `ANDROID_PACKNAME` / `ANDROID_CERT_TYPR` / `IOS_APPID`），**没有 mp-weixin appid 字段**（只报字段名，未读任何凭证内容）。
- **`--appid` 的作用面**：`cli publish mp-weixin --help` 确有 `--appid 小程序 appid`，但它服务于 `--upload` / `--privatekey` 那条**上传**链路；实测传了 `--appid` 也**不改**产物 appid。脚本仍透传它以保留「`-AppId` 参数化」的入口。
- **真 appid 下 ② 已实测可通（2026-09-12）**：把产物 `project.config.json` 的 appid 设为真值后，`cli.bat auto` 回显 `√ Using AppID: wx38c3e31b16a7ced0`，automator 连上后 `pageStack: ["pages/index/index"]` ⇒ **真 appid 不需要额外扫码/授权**（开发者工具当前登录态即可）。

### HBuilderX 是单实例串行资源：忙检测 + 等待上限 + agent 互斥锁（2026-09-12）

**坑位（实测）**：`cli.exe` 只驱动**同一个主程序**，`publish` / `launch` / `pack` 等重活都要排进主程序的编译队列。**维护者用 GUI 编译/运行时，agent 的门脚本若并发发起**：既会拖慢维护者，也会因为排队而**产生假失败**——实测一个会话的 `cli publish mp-weixin` 被排在另一个会话的 `launch app-android --compile true --cleanCache true` 之后，输出停在「正在编译中...」**不返回**，`auto`/端口/探针一路连锁失败。

**处置**：四个需要 HBuilderX 的门脚本统一 dot-source **`scripts/lib/hx-busy.ps1`**（② `mp-weixin-check.ps1`、④a `compile-check.ps1`、④c `kotlin-all-check.ps1` 的 publish 段；仿真机冒烟不接这条——纯 adb/emulator）：

- `Wait-HxFree -CliExe <cli.exe> -TimeoutSeconds <默认 600> [-NoWait]`：先取 **agent 跨进程互斥锁** `$env:TEMP\hx-agent.lock`（内容 pid + 起始时间；**持有超过 30 分钟视为陈旧、可抢占**），再探测主程序可响应性（一次轻量 `cli.exe project list` 带 **5 秒硬超时**），忙则按 10 秒间隔重试到上限。
- **超时/忙 ⇒ `exit 2`（环境不可用）**，提示语里给出不依赖 HBuilderX 的替代门（仿真机冒烟 / ④c `-SkipPublish` / `npm run test:unit`），并**绝不 kill 主程序、绝不抢占项目**。
- `-NoWait`：不等待，探测到忙立即 `exit 2`。
- 日志与 PR 评论里写一行 `HX_BUSY wait=<实际等了多少秒> result=free|timeout`（便于事后核对是不是被排队拖慢）。
- **锁在调用方脚本的 `finally` 路径里释放**（`Release-HxLock`）；契约测试 `utils/hxBusyGateContract.test.js` 守护 H1–H9（含「不得出现按名字强杀主进程的调用」「忙/超时必须是 `exit 2` 而非 `exit 1`」「finally 里必须释放锁」）。

**限制要写实（不要假装能探测 GUI）**：机械上**无法可靠探测「维护者的 GUI 是否正在编译」**。上述探测实测**能**区分「主程序可达且响应」与「连不上 / 无响应」（可达时 `project list` 约 0.5–2 秒返回），但**不能**区分「主程序空闲」与「主程序正在为别人编译」——实测在主程序正跑另一编译任务时 `project list` **仍毫秒级返回**（它不进编译队列）。所以本机制是**锁 + 探测 + 上限**的 **fail-safe**：宁可 `exit 2` 也不抢，**维护者的 GUI 优先**。

**配套纪律（与「回写 manifest」坑位合并）**：HBuilderX 在首次导入 / 编译项目时还会**回写工作树的 `manifest.json`、把 `mp-weixin.appid` 置为 `null`**（详见上「appid 口径诊断」）。两条合并成一句操作纪律：**跑完任何 HBuilderX 门后，先 `git status` 看 `manifest.json`（及其它运行时面文件）是否被改脏**，脏了就 `git checkout -- manifest.json` 再继续——否则会污染 `pr-evidence` 的「运行时面 / 打包面」判据。

### 门脚本共享载体 `scripts/lib/gate-common.ps1`：准入门槛（2026-09-13）

门脚本家族存在成规模重复（实测：`Test-PeHeader` 4 份、`Write-Log` 4 份，`Get-HeadSha` / `Save-Jpeg` / `Get-WebpEncoder` / `Publish-GateComment` 各 3 份），但**只有 `Get-HeadSha` 上移进了共享库**，因为它（且仅它）满足两条准入门槛，缺一不可：

1. 各副本**逐字节相同**（三份 412 B / 14 行，实测完全一致）；
2. **未被任何 `utils/*Contract.test.js` 作为字面量锚点 pin 住**（`Get-HeadSha` 在守护里 0 命中）。

门槛的由来（**这是本条决策的核心理由**）：本仓守护断言的是门脚本的**源码文本**，不是行为 —— `mpWeixinGateContract` 直接 pin 住 `Invoke-Process -FilePath $devTools -Arguments @('auto'`、`Invoke-Process -FilePath $devTools -Arguments @('open', '--project', $dist)`、`Write-Log "…devtools-open`、`$ProbeTimeoutMs = ` 等**调用点**原文。把被 pin 的代码搬进共享库，守护会立刻失配，而唯一的「修法」是放宽守护 ⇒ 等于把防护拆掉。故：

- `Test-PeHeader`（4 份形态各异：305 / 433 / 438 / 504 B）**刻意保留在原处** —— 它没被 pin，但四份形态不同，得先定出哪一份是权威行为，属设计问题而非搬运问题；
- `Save-Jpeg` / `Get-WebpEncoder` / `Publish-GateComment` **保留在原处**，它们已被守护 pin 住。

该门槛由 `utils/gateCommonLibContract.test.js` 守护（G1 唯一性 / G2 调用方只 dot-source 不再自定义 / G3 门槛文字必须在库头部），防止后续会话顺手把别的函数也搬进去。**真正的收束不在搬运，而在让守护从「断言文本」改成「断言行为」**（例如门脚本支持 `-DryRun` 输出结构化步骤计划，守护断言该输出）—— 那件事**已由 #914 落地**，见下节。

### 决策：门脚本守护从「断言源码文本」改为「断言行为」（2026-09-13，#914 收束落地）

**决定做收束（这条 ADR 就是那个决定的记录）。** 载体：`scripts/mp-weixin-check.ps1` 增加 `-DryRun`，把四类不变量 —— ① 步骤序列（`close → open --project <dist> → auto → port-listening → ready-gate → probe`）、② 每步的**参数值**与判据、③ 超时预算与**谁决定 exit 2**、④ 结果行字段清单 —— 从调用点原文收成**一份数据**（`New-GatePlan`），执行路径按 id 取用（`Get-GateStep`），`-DryRun` 只输出**一行** `GATE_PLAN {json}` 后 `exit 0`（不跑任何外部命令、不写工作树、不接 HBuilderX，因而在没有 HBuilderX / 开发者工具的机器上也能跑，含 Linux CI）。

守护 `utils/mpWeixinGateContract.test.js` 随之改判据面：

- **C2 / C12 / C15 / C13** 改为**跑 `-DryRun` 并断言这份 JSON**（顺序、参数、预算、判据文字、结果行字段逐项对数据断言），不再 pin `Invoke-Process -FilePath $devTools -Arguments @('auto'` 这类调用点原文；
- 新增 **C18**「计划是唯一真源」：六步序列逐字写死、每步都有 `tag`/判据/exit 2 归属、预算与步骤不得分叉、exit 2 汇总视图与各步声明一致、**执行路径必须按 id 取用每一步**、调用点原文在代码里**至多出现一次**（执行路径不得再写死一份）；
- **C14 收窄**为只对**代码行**判（帮助文本 bullet 不再误报，见 ADR-0007 同名节）。

**理由**：文本口径下，任何把被 pin 的调用点原文抽进共享库的重构都会让守护失配，而唯一的「修法」是放宽守护 —— 风险正好落在最脆的一环上（本轮提议者本人差点据此把已被 pin 的 `Save-Jpeg` / `Get-WebpEncoder` / `Publish-GateComment` 一起搬进共享库，那会让 C2/C12/C15 静默失守）。文本守护**确实抓到过真缺陷**（C14：贴评论调用少一个续行反引号 ⇒ 参数变成另一条命令，入库截图清单从未进过评论），但这一类（顺序/参数/预算）用计划数据能抓得更准，且注入用例仍能证明判据不是空跑。

**代价（写实）**：

- 每个门脚本各要加一个开关与一份计划输出 —— 其余门脚本**各自一票跟进，不打包**（本票只做 ②）；
- 守护多了一个运行时依赖：**`pwsh`**。Windows 本机与 CI 的 `ubuntu-latest` runner 都自带 PowerShell 7（runner 镜像的 Software Report 有 PowerShell Tools 段），CI 的 `mobile-test` job 已在跑 `npm run test:unit`；**拿不到 `pwsh` 或计划不可解析时 fail-closed 抛错，不退化成「跳过」**；
- 计划与执行有了「两份」的可能分叉 ⇒ 落 C18 的「按 id 取用 + 原文至多一份」两条来封住。

**不变的部分（勿误读为门槛已撤）**：`scripts/lib/gate-common.ps1` 的两条准入门槛**照旧生效** —— 其余门脚本（④a / ④c / ① 取证等）仍被文本守护 pin 住，`utils/gateCommonLibContract.test.js`（G1–G3）原样保留。收束按门脚本逐个推进，每落地一个，它的调用点原文才可以搬。

**验证口径（本票实际做到的）**：`-DryRun` 行为断言（含「输出恰一行 / 不写工作树 / 不出现 `>>> [` 进程回显」三条现场断言）+ `npm run test:unit` 全绿 + 用「假开发者工具（`node.exe` 冒充 `cli.bat`）」把 `close → open → auto → 端口 → 就绪闸门` 段真跑一遍（参数逐字来自计划）。**② 门本身未在共享工作树里实跑**：本票是非运行时面改动（不触发 ②），且 HBuilderX 是单实例串行资源、GUI 优先 —— 这条如实标注，不宣称「② 已通过」。

### adb 解析的唯一真源：`scripts/lib/env-check.ps1` 的 `Resolve-AdbExeLocal`（2026-09-15，#1027）

**坑位（本机实测，机制级复现）**：同一份 adb 解析在本仓被写了**三遍** —— `scripts/hx-run.ps1` 的 `Resolve-AdbExe`、`scripts/lib/env-check.ps1` 的 `Resolve-AdbExeLocal`（前两份候选集相同：`$env:ANDROID_SDK_ROOT` → `$env:ANDROID_HOME` → `D:\android-sdk\platform-tools\adb.exe` → `PATH`）、以及 `scripts/lib/auto-screenshot.ps1` 里**内联的第三份**。内联那份**漏了 D 盘兜底** ⇒ 本机（两个 env 都没设、`adb` 不在 PATH、adb 只在 D 盘）`dev:finish` **步骤 2/5 能过、步骤 6 恒报「找不到 adb.exe」**；而步骤 4/5 已经真跑完并产生副作用（编译 ~5 分钟 + 推送 162 秒），步骤 7–9（截图对比 / 生成证据 / 还原 `manifest.json`·`pages.json`）永远到不了。这正是本节上文「门脚本共享载体」记的那类分叉：**解析器被复制而不是复用，两份悄悄漂移**。

**裁定（窄修，#1027）**：`auto-screenshot.ps1` 删掉内联副本，改为 dot-source `env-check.ps1` 并调 `Resolve-AdbExeLocal`（懒加载：`Get-Command` 判存在才补加载，与 `level-detect.ps1` 同一套写法）；**候选集不动** —— 不加 `-AdbPath` 形参、不补 Android Studio 默认路径（备选路线本次不采纳）。`hx-run.ps1` 那份**刻意不动**：它自带 D 盘兜底、不在本 bug 路径上，且是被 C7 等文本守护触及的关键脚本；收束它另开一票。**为什么没搬进 `gate-common.ps1`**：三份不满足上文第 1 条准入门槛（函数名/形态不同，非逐字节相同）——本裁定是「**指定唯一真源 + 调用方复用**」，不是搬运；被删的内联副本未被任何守护 pin 成字面量锚点，故无守护失配。

**落锁（守护）**：`utils/autoScreenshotContract.test.js` **S21**（结构性：代码里不得再出现 `ANDROID_SDK_ROOT` / `ANDROID_HOME` / `platform-tools` / `Get-Command adb` 候选集原文；必须懒加载并调 `Resolve-AdbExeLocal`；解析不到仍 fail-closed 返回）+ 新增 `utils/autoScreenshotAdbAgreementBehavior.test.js` **A1–A3**（行为：懒加载形态与 dev:finish 形态下，步骤 6 与步骤 2/5 的解析结论必须一致）。**判别力实测**：把修复前的文件塞回去 ⇒ S21 / A2 / A3 三条**同时红**、其余 21 条不动；修复版 24 条全绿。

**两个实现坑（本次各踩一次，勿重蹈）**：① 该行为守护第一版在 JS 侧匹配中文错误文本 `找不到 adb\.exe` —— pwsh 默认按 **OEM 码页（GBK）** 写 stdout，中文到 Node 侧成乱码 ⇒ 正则恒不匹配 ⇒ 任何错误都被判成「解析到了」⇒ **假绿**（把修复前的文件塞回去它照样全绿，是变异检查才把它照出来）。故**布尔判据一律在 PowerShell 侧算成 ASCII token**（与 S20 的 UTF-8 钉同一坑位）。② 函数体内的 dot-source 落在**函数作用域**：独立调用后顶层 `Get-Command Resolve-AdbExeLocal` 仍为 `False`（实测），故判据不能用「函数在调用方可见」，只能用**解析结论**。

**验证边界（写实）**：本票只做到「解析结论一致」+ 契约/行为守护全绿；**步骤 6 的端到端真机链路（截图落盘 / hash 冲突 / 未唤醒前置）未复跑**（需设备 + HBuilderX，且后者是单实例串行资源）⇒ issue 停在 95% · 待确认，不宣称门已通过。

### 「画面稳定」判据必须宽容比较，不得用全帧 hash（2026-09-15，#1027 收尾真机实测）

**坑位（真机实测，血账）**：`Wait-NavSettled` 的「画面稳定」原先是**全帧 SHA256 相等**。而系统状态栏里有**应用控制不了**的实时读数（MIUI「显示实时网速」的 KB/s，每 1–2 秒就变）⇒ 在本机设备（`b32d8398`，1080×2400）连拍三帧（间隔 5 秒）**两两 sha256 不同**；按 100px 横带逐带比较，差异**只在顶部 0–99px 状态栏**（MaxDiff 188），**其余整幅逐字节相同**。后果：该判据在这类设备上**永远不可能满足** ⇒ 步骤 6 必然等到 420 秒超时、该页记 `Skipped`、`Ok=false` ⇒ **步骤 7–9（对比 / 证据 / 还原）永远跑不到**，而 app 画面其实早就落定了。这是 #1027 的**第二个**阻塞（第一个是 adb 解析分叉），是「先把事做完、验完，再开 PR」那条纪律逼出来的真机复跑照出来的。

**裁定（2026-09-15，维护者，A 案）**：把「一致」从**逐字节相同**改成**采样网格上的差异像素占比 ≤ 阈值**（新函数 `Compare-ScreenFrames`，与 `Test-ScreenBlank` 同一套 24 步网格；阈值是参数 `-StableMaxDiffPercent`，默认 **0.5%**）。**明确不做**「先裁掉状态栏区域再比」那条路：状态栏高度是设备相关量，脚本要为它引入设备查询与猜测，而宽容比较不需要任何设备知识。**也不做**「把阈值调到很大」：那会让真切页/滚动也被判「稳定」，等于把这条判据拆掉。

**阈值是实测标定的（不是拍的）**：只有状态栏在变的真机两帧 ⇒ 24/48/96 网格上差异 **0%**、192 网格 **0.011%**；对照「真切页」（真帧 vs 全黑帧）⇒ **~100%**。⇒ 0.5% 卡在噪声上方 ~45×、真变化下方 ~200×。**写法面的边界（不许假称它更严）**：面积小于阈值的动态元素（例如某个 100×100 的动画角标）会被判成「稳定」——这是有意的取舍（判据的目标是「别把切页过渡帧/白屏当证据」，不是抓微动画）。

**落锁**：`utils/autoScreenshotContract.test.js` **S22**（结构性：必须存在 `Compare-ScreenFrames`、必须带 `-PrevPath $prevFile` 的调用、上一帧必须留盘、阈值必须是可调参数且默认 0.5；**不得回写** `$h = (Get-FileHash … ProbeFile)` / `$h -eq $prev` / `$prev = $h` 这三行旧写法）+ 新增 `utils/autoScreenshotStabilityBehavior.test.js` **B1–B5**（行为：逐字节相同 ⇒ 判一致；命中 1/600 采样点的微变 ⇒ **仍判一致且差异占比 > 0**；半幅变化 ⇒ 判不一致；缺上一帧 ⇒ 判不一致并回带原因）。**判别力实测**：把旧写法塞回去 ⇒ S22 + B1–B5 **六条同时红**、其余 24 条不动。**平台边界写实**：`System.Drawing` 是 Windows-only ⇒ Linux CI（ubuntu）上 B 套件验的是**缺件时的 fail-closed 语义**（判不出 ⇒ 不判稳定，`DiffPercent=-1` 哨兵是「没比较」与「比过了但不同」的区分点），Windows 上才验「微变宽容 + 巨变拦得住」两面；两支都真断言，**没有静默跳过**。

**另一条实测约束（本次撞到，勿再当缺陷追）**：改动的页面若**自跳转**（本机 `pages/index/index` 启动即跳 `/pages/dashboard/dashboard`），`Wait-NavSettled` 的**页身份**判据会如实点名「请求页 X，实际进入 Y」并 fail-closed 超时 —— 这是 S17 的**设计行为**，不是 bug；**要跑通步骤 6，改动页必须选一个不自跳转的页**（本次改用 `pages/dashboard/dashboard` 后通过）。

**同一次复跑照出的第三个阻塞（同属步骤 7–9 的路径）**：`screenshot-diff.ps1` 的 `$currentFiles = Get-ChildItem …` 只命中**一个** png 时会退化成**标量**，而 `dev-finish.ps1` 以 `Set-StrictMode -Version Latest` 跑 ⇒ `$currentFiles.Count` 抛「在此对象上找不到属性 Count」⇒ **步骤 7 直接崩、步骤 8–9 跑不到**；触发面 = 基线目录不存在（首次运行）+ **恰好一页**改动，正是单页改动的常态（本次真机跑就是 1 页）。处置：两处 `Get-ChildItem` 都用 `@(...)` 包住；同处一并订正步骤 7 的文案（原写「首次运行，已建立基线」，但该函数只在 `-UpdateBaseline` 时才把截图拷进基线目录，否则只建了个**空目录** ⇒ 现在据实分流，不再把空基线说成已建立）。落锁：`screenshotDiffContract` **D7**（结构性：不得出现裸 `$x = Get-ChildItem`）+ 新增 `screenshotDiffSingleFileBehavior` **P0 / C1–C4**（行为：在 `Set-StrictMode -Version Latest` 下真跑「单文件 / 双文件 / 零文件 / 同内容基线」四个场景）。**判别力实测**：把旧写法塞回去 ⇒ 探针当场复现「在此对象上找不到属性 Count」，D7 / P0 / C1（连带 C2–C4）全红。

### 第④门：本地编译门（④c 默认 / ④a dev 面）与 release 云打包门

**2026-09-11 修订：④a 与 ④c 合并为「④ 本地编译门」。** 二者都是本地编译证据、都要过，分成两个门号只是历史包袱；合并后正文一门一行，选哪个载体由改动面决定：

- **④c 整模块编译 = 默认载体（每张触及运行时面的 PR 必过）**：`npm run build:kotlin-all`（`scripts/kotlin-all-check.ps1`）—— appResource 产物 + HBuilderX 自带 kotlinc 整模块编译；日志固定落 `.ci-verify/kotlin-all.log`；**必须解析输出判成败**（CLI 退出码恒为 0，不可用）。它复刻的是「整模块」语义，也是 ④ 目前**唯一能每 PR 跑**的形态。
- **④a dev 全量编译 = dev 专属面追加**：`npm run build:compile`（`scripts/compile-check.ps1`）→ `cli.exe open` → `project open --path <项目>` → `launch app-android --project <项目> --compile true`；日志 `.ci-verify/build.log`。**追加条件（命中任一）**：改动 `pages.json` / `manifest.json` / `platformConfig.json`；新增页面（`pages/**` 下新增 `.uvue`）；模块手术系列的**收口 PR**。理由：dev 编译走的是「dev 运行时 + 页面注册 + 条件编译」这条链路，正是这些改动的特有面；④c 只编 Kotlin，看不到页面注册与 dev 端资源处理。
- **④ 的证据载体（P1，2026-09-11）**：编译门结果不再要求手抄进正文——脚本加 `-PostToPr <PR号>` 后，**门通过时自动贴一条 sha 绑定的 PR 评论**（正文见 `.github/PULL_REQUEST_TEMPLATE.md` 注释）；`pr-evidence` 认「同时带 `<!-- gate-evidence:④ -->` 标记与 `commit: <head sha>`（允许短 sha 前缀互含）」的评论，命中即跳过 ④ 门的字段校验、正文该行写「见评论 <链接>」即可。**校验器只校结构与 sha 绑定，不校真伪**（与正文证据同一口径）——真伪仍由维护者读日志判定。
- **④b release 云打包门（按触发条件，非每 PR）**：触发 = **按交付形态**——改动**打包面**（`training-app/**/manifest.json` / `pages.json` / `platformConfig.json`、`uni_modules/**/utssdk/app-android/**`、新增 `*.aar`、`libs/*.jar`）；维护者判断触及证书签名 / R8 / aar 依赖解析时自行加跑。执行 = `cli pack`（需 DCloud 账号登录，按次消耗不公开风控额度，需排队）。**发布前置条款：正式发版前必须跑一次云打包并装机自测**（不写进每 PR 流程）。
- **④b 的测试期裁定（2026-09-13，维护者）**：**项目仍在测试阶段，④b release 云打包暂不执行** —— 部署到真机走的是 HBuilderX **调试基座**（`cli launch app-android`），与云打包无关，测试期不需要它。触及打包面的 PR 在该行写「免（测试期裁定）」并在正文用风险接受通道声明。**发布前置条款不变：正式发版前必须跑一次云打包并装机自测。**
- 依据：ADR-0007 已录「release 云打包比 dev 编译更严」；2026-09-11 修订把 ④b 的触发从「按代码形态（新增 async / 新增 composable）」改为「按交付形态（打包面）」——**打包链路（AAPT2 资源合并、AndroidManifest 合并、R8/aar 依赖解析、证书签名）只有真打包才覆盖，本地编译门不覆盖**；而「新增 async」这类代码形态在 ④a / ④c 的编译期就能暴露（#859 实测），拿它当 ④b 的触发条件既拦不住真风险、又白白消耗云资源。

### 风险接受通道

允许例外，**禁止静默**：PR 正文必须出现固定字样「已接受未验证风险」+ 理由 + 事后验证计划，且事后要有回执（补跑或记 issue）。未声明而缺证据 = 门未过。**走了这条通道的 PR 必须由人执行合并**（agent 不得自合，见下节）。

### 实现层约束与已知缺口（#841 落地时实测，2026-09-11）

- **`pr-evidence` 的行为由 head 分支里的 workflow 文件决定**（GitHub 对 `pull_request` 事件的取值方式）：带该文件的分支即生效，不带的老分支**永不报这项检查**。实测：基于 master 的探针分支确实没跑该检查。因为 ruleset 开了 `strict_required_status_checks_policy`（分支必须与 master 同步），老分支本来就必须 merge master 重推，所以不会永久挂起——但**这条耦合记在这里：日后若要（由维护者）把 `pr-evidence` 设为必检，必须先确认目标分支带该文件**。
- **该文件本身可被 PR 修改**（head 提供校验逻辑是 GitHub 的固有模型）。当前防线 = `AGENTS.md` 的「agent 不得自行合并触及运行时面的 PR」+ 评审时看这个不足 200 行的 diff（本仓可装 approve 门但裁定不装，见下节）。若日后要抗篡改，可改用 `pull_request_target`（校验逻辑取自 master，而本 job 不 checkout、不执行 PR 代码，无「不可信代码 + 写权限」风险）——但**其 check run 能否满足 ruleset 必检尚未实测**，未证实前不采用。
- **「未命中运行时面即放行」的判据取的是文件清单**（`*.uvue` / `*.uts` / `training-app` 下的三份 json）；低风险分层（免 ①②）同样取文件清单，**fail-closed**：只要有一个 `*.uvue` / 三份 json / `uni_modules` 文件在改动集里，就回到常规面（①② 照旧必过）。**④b 的触发判据自 2026-09-11 起改为文件清单（打包面路径匹配），不再读 diff 的 `patch` 字段** —— 因此不再受 GitHub 截断超大 patch 的影响（旧判据的漏判风险随之消失），方向上更安全。
- **门评论绑定判据的 compare 面（2026-09-12 新增，与上面同源的风险）**：新判据要读 `repos.compareCommits` 的 `.files[].filename`，而该接口的 files 列表**上限 300 且不分页**（与可分页的 `pulls.listFiles` 不同）⇒ **实现依赖「files 完整」**。处置 = 调用点按 `files.length >= 300` 判「疑似截断」，给校验器传 `filesTruncated` 并按 **fail-closed 判不绑**（宁可让人重跑，也不拿被截断的列表当「其间没有运行时面改动」）。**未证实**：GitHub 在恰好 300 个文件时究竟是「正好 300」还是「截断到 300」——文档未写明，故这条阈值是**保守近似**（≥300 一律当截断）。（`compareCommits` 另有调用量配额消耗，故同一 base 的 compare 结果在单次运行内缓存、`commit == head` 时根本不调。）
- 校验器**只校结构与产物字段，不校真伪**（重申）：不校验 `build.log` / `kotlin-all.log` 是否真存在、截图链接是否可达、PR 评论里的 sha 是否真对应那次编译；真伪由维护者读证据判定。（2026-09-12 的绑定放宽不改这一条：祖先判定同样**不看那次编译是否真按该 sha 跑过**，只判「该 sha 在 head 的历史里、且其后运行时面没动」。）
- ④a 的脚本实跑一次约 **4.6 分钟**（`--cleanCache true`，50 页全量，HBuilderX 5.24）；CLI 连不上主程序时会**挂住不返回**，脚本以每步超时兜底并归为「环境不可用」（`exit 2`），不会被误判成编译失败或编译通过。**帖评论（`-PostToPr`）只发生在门通过分支**，且 `gh` 不可用 / 取不到 sha 时只打警告、不改门结论。
### 为何不装「必检 + approve」：成本裁定（2026-09-11 裁定；同日修订事实前提）

**事实前提（2026-09-11 修订）**：本仓两个 GitHub 账号——`zhengcookie`（write，移动端开发本人；agent 会话也以该账号提交）与 `DriftingLi`（admin，仓库所有者 = 维护者）。**维护者持有 `DriftingLi`**：API 实测该账号对本仓返回 `admin: true`，ruleset 读得到（`protect master` / `enforcement=active`）。`zhengcookie` 侧 404 只是因为它没有 admin，**不代表无人有** ⇒ 本仓**存在可用的 admin 通道**。

> 本 ADR 初稿曾写「维护者不持有 `DriftingLi`」「装不上」——**该前提有误，已按实测修订**。裁定不变，但理由从「能力受限」改为「成本取舍」——两者对未来读者的含义不同：前者会让人以为本仓物理上无法使用阻塞门，后者才是真实的可重新审视的取舍。

裁定与后果：

- **`pr-evidence` 只作为可见检查运行，不进 ruleset 必检**：加必检、或把 `required_approving_review_count` 改成 1，都是**可执行**的（需 `DriftingLi` 操作），**裁定不做**——逐 PR 人工审批会把维护者变成所有 PR 的串行瓶颈。
- **`approve=1` 不采用**：作者不能自批，于是每个 PR 都要维护者手动批；本仓 PR 多为 agent 产出、量大，审批成本高于它带来的约束收益。
- 这是**可重新审视的取舍，不是物理限制**：若验收门漏网造成实害、且维护者愿意承担审批量，两条路都可走（改前先确认目标分支带 `pr-evidence.yml`，见上节）。
- 于是「人工门只能人签」在本仓**落到 agent 行为约束上**：`AGENTS.md` 规定 **agent 会话不得自行合并触及运行时面的 PR**（改动集含 `*.uvue` / `*.uts` / training-app 下的 `manifest.json` / `pages.json` / `platformConfig.json`）；这类 PR 必须把证据填齐后停在「待人工签收」，**由人执行合并**。非运行时面（纯文档 / 测试 / CI 配置）不受此限——否则文档改动也要人守，流程会被拖死。
- **残余风险照实说**：agent 会话与 PR 作者（`zhengcookie`）**共用同一账号**，GitHub 侧**无法机械区分「人」与「agent」**，这条靠 `AGENTS.md` 约束 agent（agent 的必读面），**不是密码学保证**。要真正的机械隔离只有两条路——agent 会话改用独立账号提 PR，或用签名（私钥与口令只在人手里）；本 ADR 不采用，但记在这里备选。
### 闭环条款：人工门是规则来源

人工门当场抓到的问题，收口时**必须回写为守护规则或注入自检**（先例：`utsAndroidCompile.test.js` 规则 A–Y 全部来自编译现场），做不到的在 ADR/票面写明理由。人工门因此不是一次性检查，而是规则的来源——这是它值得保留的理由。

### 生效时点与追溯

从**下一张合并到 master 的手术 PR** 起适用，**不追溯已合并 PR**。`refactor/exam`（#645 T07）是第一条适用的票：不要求它补历史证据，只要求它自己的四门证据。

### ④a 的运行前提与 ④b 的判定（#859 spike 实测，2026-09-11）

**④a 的运行前提（本仓坑位）**：HBuilderX CLI 只驱动主程序，靠**本地 IPC**（命名管道 / 本地套接字）通信；**受限沙箱下 CLI 报「与主程序的连接已中断，可能已关闭」**，切到全访问权限后 `open` / `project open` / `publish` / `launch` 全部正常（#859 实测）。⇒ agent 会话跑 ④a **必须申请全访问权限**，不得以「sandbox 限制」为由直接走例外通道 —— #840 正是如此（④a / ④b 两行均写「已接受未验证风险：AI agent 无法启动 HBuilderX」），把本可在编译期暴露的 Kotlin 错误放行到了云打包。
**口径已裁定（2026-09-11 维护者裁定 B，#870）**：④a 为**半自动门** ——

- **agent 会话可执行 ④a**：`npm run build:compile`（即上面「第④门」定义的 `cli.exe open` → `project open` → `launch app-android --compile true`，成败一律解析 stdout），产出 `.ci-verify/build.log` + 日志片段，证据形态不变。
- **④a 的「执行人」栏**填执行会话所用的 GitHub 账号（本仓 agent 会话即 `zhengcookie`），并在结论里注明「agent 执行」；**① 真机截图与 ② 微信开发者工具仍只能由人执行**，其「执行人」栏不得由 agent 代填、不得由 agent 写「已通过」。（**2026-09-16 修订**：① 的「执行人」栏在该行**只覆盖 ①a** 时允许写「agent 执行」；含 ①b 时仍由人给出原文、agent 可代录。见 `0016-真机门的人工性收缩与按批取证.md`。）
- **合并仍由人执行**：agent 不得自合触及运行时面的 PR（`AGENTS.md` 硬规不变）。
- **运行前提（硬前提）**：HBuilderX CLI 靠与主程序的本地 IPC，**受限沙箱下会报「与主程序的连接已中断」** ⇒ agent 会话跑 ④a **须以全访问权限执行**。这不是可选项：#840 正是「agent 跑不了 ④a」而走了例外通道，才把编译错误放行到云打包。

**④b 维持云端，本 ADR 不改写**：#859 票面预设的改写条件（「若验证通过」）未成立，三条实测为据 ——（**2026-09-11 修订只改触发口径**：从「新增 async / 新增 composable」改为「触及打包面」，见上「第④门」；下面第二条实测正是这次修订的依据。）

- **成本前提被推翻**：云打包实测 **5 分 40 秒**（#849，18:23:19 → 18:28:59），不是「半小时 + 排队」。
- **「只有 release 才暴露」在本机不可复现**：复刻 error17 形态的合成探针在 **④a 就被抓到**（`error: Assignment type mismatch: actual type is 'UTSPromise<Unit>' …` + `Function invocation … expected.` + `[plugin:uni:app-uts] kotlin编译失败`）⇒ 拿「新增 async function / 新增 composable」当 ④b 触发条件并不指向真风险（本地编译门就覆盖）；而 `publish app-android --type appResource` 反而**报「编译成功」**（该路径 `result.kotlinc = false`，本机不做 Kotlin 编译），本地整模块 kotlinc 同样抓得到。
- **真跑 `compileReleaseKotlin` 的门槛**：Google Android SDK + uni-app x 原生 SDK 工程（19–23 个 aar + `uts-kotlin-compiler-plugin` / `uts-kotlin-gradle-plugin`）+ keystore + 离线 appkey（人工申请），一次性投入远超 5 分钟云打包的收益。

**已知坑位：dev 编译缓存不是自洽的编译单元。** `runUVueKotlinDev()` 只编译本次变更的 .kt，并把上一次的 `class/` 目录放进 classpath 以补齐符号；#859 实测把该缓存 96 个 .kt 一次性整模块编译**必然失败**并产生大量 `unresolved reference`（被引用的类型只存在于陈旧 `class/*.class` 里）。要做本地整模块 Kotlin 编译，输入必须取 **appResource 产物**（`unpackage/resources/app-android/**`，含 `uni_modules/**/utssdk/app-android/src`）。

**④c（已落锁，2026-09-11，#870 T2；2026-09-11 修订为 ④ 的默认载体）**：appResource 产物 + HBuilderX 自带 kotlinc 2.2.0（+ 自带 Corretto 17 + `plugins/uniapp-runextension/lib2` classpath + UTS 编译插件）做**整模块**编译 —— 实现 `scripts/kotlin-all-check.ps1`（`npm run build:kotlin-all`），日志 `.ci-verify/kotlin-all.log`，守护 `utils/kotlinAllGateContract.test.js`（C1–C10）。实测：干净树 `errors=0 classes=1261`（93 个 .kt，214s）；注入 82999f5 的错误形态即报同文本 error。它与 `compileReleaseKotlin` **不等价**（Gradle / AGP / 插件版本不同），只作本地加固，不改 ④b 定义。**边界**：① 输入只能用 appResource 产物（用 dev 缓存必然大量 `unresolved reference`）；② `publish` 一步仍需主程序可达，`-SkipPublish` 可让受限会话只跑 kotlinc 部分。

**CLI 勘误**：`cli publish app-android --type appResource` **必须带 `--project`**；缺参实测 `[uniapp-extension] 参数 project 值不能为空`，**且退出码仍为 0**（再次坐实「退出码不可用、一律解析 stdout」）。

### 非门辅助：仿真机前置冒烟（2026-09-11，#883 / O2）

> **非门（不替代 ① 真机门）——仅前置冒烟：仿真机截图与无异常证据，鉴权/生物识别/厂商 ROM/真机上传路径类问题仿真机抓不到。**

**结论（维护者选 O2）**：①「真机」门的语义**不放宽**——仿真机**不替代**真机；只是把仿真机做成 **agent 跑的前置自动冒烟**，产出截图 + 无异常证据，让① 的人工执行者只需看**已过滤过的候选页**。① **仍是人工门**，仍由人在真机执行（「执行人」栏不得由 agent 代填，不得写「已通过」）。

**为什么不放宽（#883 spike 实测）**：开发者工具 console 实测报 `checkIsSupportSoterAuthentication:fail … 请使用真机进行开发`；且本 ADR 记的两次实害——`content://` 上传 602001、证件 level NPE、生物识别强转崩溃——**都是真机独有失败模式**。

**载体**：`scripts/emulator-smoke.ps1`（`npm run smoke:emulator`）。默认 **headless**（`-no-window -no-audio -no-boot-anim`，不弹窗、不抢焦点），仅 `-ShowWindow` 才开窗；截图走 `adb exec-out screencap -p`（headless 下可用）。收尾 `adb emu kill` **写在 `finally`**，异常/断言失败/超时都不留跑着的模拟器。判成败只看输出与 logcat（FATAL EXCEPTION / ANR 计数 + 前台 Activity + 进程存活），**不看退出码**。守护：`utils/emulatorSmokeContract.test.js`（C1–C7）。

**边界**

- **抓得到**：布局/渲染崩坏、页面加载期 UTS/JS 异常、导航状态、截图看版式。
- **抓不到**：生物识别、运行时权限弹窗行为、厂商 ROM 差异、真机上传路径（`content://`）。
- **不是门**：本项**不进** `.github/workflows/pr-evidence.yml` 的校验器；PR 评论用标记 `<!-- prefilter:emulator-smoke -->`（**刻意不用 `gate-evidence:` 前缀**，避免被误当作门证据）。改验收门逻辑的 PR 与本项无关。

### ①a 真机自动取证（预置，待 #624 实测后落锁；2026-09-12）

**① 真机门拆成两半**：**①a** = agent 用 adb 自动逐页截图 + logcat 断言 + 记录前台 Activity；**①b** = **人**走关键交互（生物识别指纹按压、运行时权限弹窗、真机上传路径）。拆分只把「agent 能机械执行的那一半」自动化，**门的语义不放宽**。

**载体**：`scripts/device-capture.ps1`（`npm run capture:device`），守护 `utils/deviceCaptureContract.test.js`（D1–D10）。

**它只替代什么**：只替人省掉 ① 里「逐页截图 + 抓日志 + 记前台 Activity」这一步的**取证劳动**；**①a 不替代 ①b**——指纹、权限弹窗、真机上传路径这三类仍由人在真机上走，结论仍由人写。**「执行人」栏仍由人签收**，agent 只产出截图与日志。

**机械上无法替代真机生物识别的理由**（引用 #883 的 devtools console 证据）：spike #883 的开发者工具 console 实测报 `checkIsSupportSoterAuthentication:fail … 请使用真机进行开发`；更根本的是指纹要**人把手指按上去**才产生一次成功/失败事件，而 adb 里**没有任何只读命令**能代替这次按压（`adb shell input` 类事件注入既被本脚本禁用，也**不触发指纹传感器**）。故 ①b 不是流程冗余，是这类风险的唯一覆盖点。

**只读禁令（红线）**：本脚本可能正跑在维护者**正在调试的真机上**（先例 #781），故正文中**一律禁止** `kill-server` / `install` / `uninstall` / `force-stop` / `logcat -c` / `push` / `pull` / `input`。理由逐条：`kill-server` 会顶掉维护者与其它工具共享的 adb server；清缓冲会抹掉他正在看的崩溃输出；杀进程或抢前台会让调试会话断开。一句话口径：**取证不该改变被取证的对象**——而维护者的调试会话本身正是要被取证的对象。只用只读命令：`adb devices`、`exec-out screencap -p`、`shell dumpsys …`、`shell logcat -d`（`-d` 取完即退、**不清**缓冲）。**只用 `D:\android-sdk\platform-tools\adb.exe`**（与 HBuilderX 共用同一个 server）；**不要**用 HBuilderX 自带的那份 adb，会起第二个 server 顶掉连接。

**连带结论（照实记）**：不能清缓冲 ⇒ 崩溃计数做不到「清缓冲后再统计」。处置 = 启动时取**设备自己**最新日志行的 epoch 时间戳作窗口起点（`logcat -d -v epoch -t 1`），结束时只统计「大于等于起点」的行；`-LogcatSeconds` 大于 0 时取「最近 N 秒」与「启动以来」的**交集**。起点取自设备本身，故设备时钟与宿主时钟不同步不影响结果；连起点都取不到就写 `logcat=SKIP`，**不拿历史日志冒充本次**。

**切页默认关闭**：`am start` 默认**不发**（会打断维护者的调试会话），只有显式 `-AllowAppStart` 才开；`-NoStartApp` / `-SkipAppStart` 则**无论如何**都不发（即便同时给了 `-AllowAppStart`，**以禁止为准**，fail-safe）。默认只读模式只对**当前前台**采 1 张图，`-Pages` 其余条目记 `SKIP（未切页：切页默认关闭）`——**不假装跑过**。**多设备时必须显式 `-Device`**，否则 `exit 2`（实测同一台真机会同时以 `<ip:port>` 与 `_adb-tls-connect._tcp` 两条 transport 出现，本机就是这个形态 ⇒ 不自动猜）。

**判成败只看输出**（`DEVICE_CAPTURE_RESULT=`，沿用本仓「退出码不可用」口径）：断言 = 前台 Activity 可取得 + 截图落盘且非 0 字节 + 窗口内无 `FATAL EXCEPTION` + 窗口内无 `ANR in <前台包名>`；环境不满足 `exit 2`；**截图压缩与入库失败只警告、不改结论**（`-NoArchive` 为逃生开关）。截图入库沿既有纪律（WebP q75 → 无编码器退 JPEG q75、宽 ≤720、每 PR ≤10 张 / 单张 ≤150 KB / 合计 ≤1.5 MB），落 `docs/verification/device/<PR号>/`。

### ①a 取证手法补遗（2026-09-15 实测，#850 / PR #1004）

第①门实操时用到的四条机械手法；**与上文旧记录不一致的地方已就地标出**，下一会话请按本节现测，别按记忆。

1. **深链到「带参数」的页面 = `--pagePath` + `--pageQuery`**（上文只记了 `--pagePath`）。实测
   `cli.exe launch app-android --project <项目绝对路径> --deviceId <serial> --pagePath pages/forum/forum-detail --pageQuery "id=14"`
   一步进到带参页 ⇒ **不必**为取证临时改 `pages.json` 首页（那条老办法仍是备选）。
   **前置**：项目必须处于「已导入」状态 —— 跑过 `cli project close` 之后同一条命令报
   `项目 … 不存在，请先导入`，先补 `cli project open --path <项目>` 再 launch。
2. **点击坐标必须取 `uiautomator dump` 的 bounds，不能按截图目测**。预览里的截图常被缩放，
   按目测坐标点会**静默点空**（实测按目测连点 3 次：画面逐字不变、命令退出码仍为 0）。
   正确做法：`adb exec-out uiautomator dump --compressed /dev/tty` → 取目标节点 bounds
   （形如 `[323,2162][831,2216]`）→ 点中心。**判「点没点中」看画面 / ui dump 文案是否变化，不看退出码**
   （`input` 类命令失败也常返回 0，沿用本仓「退出码不可用」口径）。
3. **`input` 能不能注入要现测**：2026-09-13 记的是 `INJECT_EVENTS` 系统硬拒（那正是 ① 拆成 ①a/①b 的理由之一）；
   **2026-09-15 同一台设备（2510DRK44C / USB 连接 / 同一份 `D:\android-sdk` adb）`input swipe` 与 `input tap` 均可用**，
   本轮因此自己完成了「滚动到底 → 点加载更多 → 抓追加态与到底态」。**成因未证实**（怀疑与「USB 调试（安全设置）」有关，
   不据此下结论）⇒ **每次现测**：各发一次 `swipe`/`tap`，看有无 `SecurityException`。
   **2026-09-17 补第三个数据点（换到另一台设备）**：`b32d8398`（Xiaomi `23049RAD8C` / Android 15）上
   `input tap` 与 `input swipe` 同样可用（`shell "input tap …; echo TAP_RC=$?"` 返回 `rc=True`，logcat 无 `INJECT_EVENTS`）。
   本轮据此**独立完成了一次完整 ①a 取证**：进课程详情 → 进章节课 → 连续 `swipe` 滚到正文底部（30 次批量 swipe）→
   点新增的「标记本章完成」按钮 → 返回 → 点右上角收藏位；配合 `exec-out screencap -p` 截图，
   证据落在 `docs/verification/device/1115/` 与 `docs/verification/device/1114/`（PR #1114 / #1115）。
   ⇒ 至此**两台设备、两个 Android 版本上注入均可用**，「系统硬拒」更像是 09-13 那次连接的个体现象，而非常态。
   **仍不据此改脚本红线**（下条不变），但**会话式 ①a 取证应把 `input` 视为可用工具、每次现测即可**，
   不要因 09-13 那条旧结论直接放弃真机驱动。
   ⚠️ **与上文只读红线的关系**：`device-capture.ps1` 内**仍然禁 `input`**（那是为了保护维护者正在调试的设备）；
   本节说的是**会话式人工取证**在「设备归本次取证专用」时可以动用 `input`，**不是放宽脚本红线**。
4. **为取证造数据（夹具）**：接口要鉴权而 agent 不碰凭证 ⇒ **由人在浏览器里登录一次**，
   agent 用 CDP 驱动那个会话操作页面；若该站前端 axios 超时过短（本站实测**连发第 2 条即「请求超时」**），
   就在**页面上下文里用页面自身的 `fetch`** 直调同一接口（token 不出浏览器、agent 不读取也不打印）。
   **造出来的数据必须在 PR/issue 里披露**（改了哪条、加了多少条、怎么清理）——#850 先例：
   在 topic 14 上加 20 条「分页验收测试 NN」，把该帖做成 `total=30 / pages=2` 的夹具。
5. **带查询参数的页面（参数化页）只能走会话式取证，自动截图模块覆盖不了**（2026-09-16，#1040 实测）：
   `scripts/device-capture.ps1` 与 `lib/auto-screenshot.ps1` 只拼 `--pagePath`、**不支持 `--pageQuery`**
   （`grep pageQuery scripts/**.ps1` 零命中）⇒ 对 `pages/ai-assistant/ai-feature?featureKey=…` 这类页面，
   自动模块只能裸进页；而该页在无键时**故意 fail-closed 弹回上一页**，于是自动模块会静默截到**别的页**
   （正是它自己的 D10「页身份」判据要防的形态）。正确做法：按本节第 1 条的 `--pagePath` + `--pageQuery`
   会话式跑，并**复用** `auto-screenshot.ps1` 里已被真机验证的落定判据（`Wait-NavSettled`：页身份 + 非全黑 + 画面稳定）。
   **给自动模块加 `--pageQuery` 是一条独立改动**（须带自己的守护），不在取证会话里顺手做。
6. **`uiautomator dump` 取页面文字：uvue 的文字在 a11y 树里是 `content-desc`，不是 `text`**（2026-09-16，#1040 实测）。
   按 `text="…"` 取只会拿到 `android.widget.EditText`（输入框占位符）与原生 tabBar 的 5 项，
   看起来像「页面没渲染」——**实测该页明明渲染正常**（截图非全黑、页身份已落定）。改取 `content-desc`
   即可**逐字核验**页面内容（宫格标签、页面标题、助手回复正文），这是「agent 看不见截图」时唯一可核的文本判据：
   #1040 用它证实了「4 格标签 == 注册表 label」「4 个功能键各自的页面标题」「专项页实发一轮拿到诊断通道回复」。
   ⚠️ 同理，**截图内容 agent 自己核不了**（本会话模型不支持图片输入、视觉工具配额见底）⇒ 不许把「截图已入仓」
   当成「内容已核对」，文本判据与截图必须成对取。
7. **给项目目录改名前后要收口 HBuilderX 会话**（2026-09-16，#1040 实测）：真运行 `launch` 的会话**常驻**并攥着项目目录，
   此时 `Rename-Item <项目目录>` 报 `being used by another process` ⇒ 先 `cli project close --path <项目>`（实测即刻可改），
   再改名。这与上文「删 worktree / 改名之前先 `cli project close`」是同一条坑位，此处补的是**实测命令与症状**。
   ⚠️ 该括号里的「实测即刻可改」**已被下一条第 8 点修正为版本相关**：`project close` 是**必要但不充分**的。
8. **`cli project close` 不足以释放项目目录 ⇒ 改名仍被拒；收口要连「常驻 launch 的那几个 `cli.exe`」一起结束**（2026-09-16，#1042 实测，修正第 7 条的乐观括号）。
   在 HBuilderX `5.24.2026081301` 上实测：`cli project close --path <项目>` 返回 `项目关闭完成`（退出码 0），
   再发一次 close 甚至报「项目已不在列表」，而 `Rename-Item <项目目录>` **依旧** `Access is denied`（连试两次），
   期间**没有别的会话持锁**（`HX_BUSY wait=0 result=free`）。`cli --help` 里**没有**「停止运行」这类命令
   （只有 `cli app quit`，它会连**共享的主程序**一起结束 —— 不可用）。
   **可用的收口顺序**：`cli project close` → 改名仍被拒时，**只结束命令行里引用「本项目路径」的那些 `cli.exe`**
   （逐个核对进程的 `CommandLine`，**绝不按名字批量杀**）→ 再改名（实测第 1 次即成功）。
   **红线不变**：**绝不**结束 `HBuilderX.exe` 主程序，**绝不**碰别的会话的 `cli`。
   **与既有反模式的张力（如实记）**：「绝不 kill `cli`」是上文《反模式》的一条；本次是在「目录被箝住 ⇒ 不结束它就把整棵工作树留成 ` D` 状态
   （每个受控文件都读成删除，比一次改名失败严重得多）」之间的两害相权，按上述最小面执行（仅 2 个进程、仅本项目、无锁在持），
   并在 PR 正文里披露。**若日后 HBuilderX 提供「停止运行」的 CLI，本条应改走那条路，不再 kill。**
   守护：`utils/deviceCaptureContract.test.js` **未**覆盖本条（它是会话式取证的坑位，不在 `device-capture.ps1` 内）—— 故以本文字为准。
9. **`pwsh -File` 传数组实参会被压成一个字符串**（2026-09-18，#1113 实测）。会话式取证脚本若用数组参数接页表
   （`pwsh -NoProfile -File .ci-verify/x-capture.ps1 -Pages 'a','b','c'`），`-Pages` 收到的是**一个**带引号的字符串
   （页名全线走错，实测还让最后一项带上尾引号 `mock-exam'`）——`-File` 不走 PowerShell 的参数解析，逗号列表不会被拆成数组。
   ⇒ 两个可用形态：**把页表写死在脚本里**（命令行只传 `-All` 这类开关；#1113 采用）、或改走 `pwsh -Command "& script.ps1 -Pages 'a','b'"`（`-Command` 按 PowerShell 语法解析）。
   同族坑位：**空字符串实参会被吞掉并挤位**，故「本页无 query」用 `-` 占位、脚本里再把 `-` 当空串。
10. **①a 的「改前对照」必须先验产物、再截图**（2026-09-18，#1113 实测，一次约 20 分钟的死路）。
   为做红控制把源码还原成改前态后跑 `hx:run`，**编译产物并没有跟着变**：`unpackage/dist/build/.uvue/**` 的副本与
   `unpackage/cache/.app-android/src/**/*.kt` 里那处改动的计数恒为 0（与源文件不符），同批 launch 日志里能读到 HBuilderX 自己的原话
   `检测到编译缓存有效，跳过编译`；删掉这两处 per-page 产物后重跑、以及 `hx:run -Full`（干净缓存重建）之后，
   **设备侧 `www/pages/**/classes.dex` 里仍为 0** ⇒ 那一轮「改前截图」整批作废。
   **判据（三处命中同一处改动才算产物真的换了）**：源文件 → 本地 `unpackage/dist/build/.uvue/**` 或 `unpackage/cache/.app-android/src/**/*.kt`
   → 设备 `www/**/classes.dex`。**核不到就不要出对照结论**，按「未验证到的面」写进证据目录（#1113 就是这么收口的：①a 只主张改后 0 错行，
   改前状态的存在性引用 #1081 的同源实测）。

## 明确不做

- **不把 HBuilderX 搬进 CI**：官方 CLI 存在（`cli launch --compile true` / `cli pack`），但 CLI 驱动主程序、`cli --help` 都要求主程序可达，官方无 `--headless` 文档，Windows self-hosted runner 的 session 0 无头可行性未证实——若日后证实可无头，再议
- **不校验证据真伪**：`pr-evidence` 只校结构与字段完整性；真实性由维护者读日志/截图判定，AI 不替代签收
- **不给小程序端逐页冒烟**（测试期，见上）
- **不追溯历史 PR**、不改 `ci.yml` 既有触发语义、不动移动端源码
