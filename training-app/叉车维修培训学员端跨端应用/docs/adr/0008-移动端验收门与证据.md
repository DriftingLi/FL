# 0008 - 移动端验收门与证据：把自我声明变成阻塞条件

**状态**：定稿（grilling 收束，2026-09-11）——来源 issue #839；落地实现票 #841
**2026-09-11 修订（#859 / #870 收口）**：① ④a 与 ④c 合并为「**④ 本地编译门**」（④c 整模块为默认载体，dev 专属面追加 ④a）；② ④b 触发从「按代码形态（新增 async / 新增 composable）」改为「**按交付形态（触及打包面）**」，并新增「正式发版前必跑一次云打包装机自测」的发布前置条款；③ ④ 门的证据可由脚本 `-PostToPr` 贴的 **sha 绑定 PR 评论**承载（免手抄）；④ 新增**风险分层**：低风险运行时面（仅 `.uts` 逻辑改动）免 ①②。四条修订都不改结论（该拦的仍拦），只改触发与证据口径。
**2026-09-12 修订（#883 收口）**：② 从**人工门**降为**半自动门** —— spike #883 实测全链路**完全无人值守**（≈4.5 分钟/次），载体 = `scripts/mp-weixin-check.ps1`（`npm run build:mp-weixin-check`）；② 的证据同样可由 `-PostToPr` 贴的 **sha 绑定评论**（`<!-- gate-evidence:② -->`）承载。**门的语义不变**（入口页 + 被改页无 console error / exception），**「执行人」栏仍由人签收、合并仍由人执行**。同次修订记下 appid 口径的诊断结论（见「第②门」）。
**职责边界**：本 ADR 取代 ADR-0007「每手术 PR 四门验收」章节的口径（0007 保留渐进式重构手册职责，本 ADR 是其执行细则）

## 背景与目标

ADR-0007 规定移动端改动需过四门，其中两道人工门（HBuilderX 全量编译、真机/小程序冒烟）在流水线里**零痕迹**，且不构成合并阻塞——PR 正文里的四门表格只是自我声明。

两次实害：

- **PR #817**（content:// 上传修复，2026-09-11）：首版正文自陈「`getFileSystemManager` 的可用性仍以 HBuilderX 全量编译为准……本地无法验证」→ **同一 PR 内 6 轮修复**（`c942548` → `04cfbd4`，08:44–09:57；含只有云打包 release 才暴露的 Kotlin 错误、只有真机才暴露的上传 602001 与证件 level NPE）→ 10:40 合入。**注意时序**：#839 票面叙述为「合并后连锁返工」，实测相反——返工发生在合入之前、PR 仍打开时；而合入时正文四门表仍写着「⏳ 待人工」，**修复后的状态同样没有任何签收产物**（`reviews` / `comments` 均为 0）
- **PR #837**（论坛采纳按钮）：正文标注「HBuilderX 全量编译 ⏳ 待人工 / 微信开发者工具 ⏳ 待人工」→ **从未执行即合并**，侥幸未出事

两次的共同点：**「如实标注」在现行流程里的作用是免责，而不是阻止合并**。

机制层事实（2026-09-11 审计所得）：

- 移动端唯一的自动门是 `ci.yml` job `mobile-test`（`npm run test:unit`，38 suites / 752 tests 全绿），经 `ci-summary` 汇聚，是 ruleset `20687043` 的**唯一**必检项，`required_approving_review_count: 0`（无人工批准要求）
- 三道人工门（真机、小程序、Kotlin 编译）在 workflows 里**无任何步骤**
- **根仓库没有 PR 模板**：模板错放在 `training-app/叉车维修培训学员端跨端应用/.github/PULL_REQUEST_TEMPLATE.md`（GitHub 只读仓库根的 `.github/`），且其内容要求合到 `main`（默认分支实为 `master`）
- **没有任何 workflow 读取 PR 正文或评论**（全仓 `pull_request.body` / `pull_request.title` / `issue_comment` 命中 0）
- HBuilderX 官方有 CLI（`cli launch app-android --compile true` 仅编译、`cli pack` 云打包、官方「CI 自动化」小节与 Linux CLI），但 CLI 是**驱动主程序**的（连 `cli --help` 都要求主程序可达），且**失败时退出码恒为 0**（实测四处失败全返回 0）；Windows self-hosted runner 的无头可行性未证实

- **发生率（最近 20 个触及 `training-app/**` 且改动 `*.uvue` / `*.uts` 的已合并 PR，全量逐个核对，非抽样）**：14 个在正文声明了 HBuilderX 编译门、5 个声明了真机门，**留下可核验产物（编译日志 / 截图 / 真机结论）的是 0 个**。`docs/` 下无任何验收归档文件；唯一近似记录是 `.gitignore` 掉的 `.scratch/alignment/` 里 4 份勾选式声明——而 ADR-0007 第 186 行自己就写着「口头/勾选式『签收』不构成证据」。
目标：让每道门的执行留下**可核验产物**并使缺产物成为**合并阻塞**；把成本高到无法保持的规定显式降级，而不是留一条注定被跳过的条款。

## 决策清单（六段）

① **目标与范围**：给移动端验收门补上「执行位」——每道门的执行留下可核验产物，缺产物即阻塞；只动验收门与证据机制，不动手术本身、不动源码。
② **选型 + 一句理由**：
- 人工门**按改动面分级**（运行时面触发、文档/测试面免）——一条打在所有 PR 上的门注定被跳过，分级才有执行力。
- 证据落 **PR 正文固定段** + 截图入仓 `docs/verification/`——正文与 commit 同生共死且可被 workflow 读取（仓内文件会被覆盖、评论会被折叠）。
- 阻塞 = **`pr-evidence` 可见检查 + `AGENTS.md` 硬规「agent 不得自合」**——「必检 + approve=1」在权限上**装得上**（维护者持有仓库所有者账号 `DriftingLi`，API 实测 `admin: true`），但**裁定不装**：逐 PR 人工审批会把维护者变成串行瓶颈，成本高于约束收益。阻塞因此落在「人执行合并」这条约束 agent 行为的规则上（见下「为何不装『必检 + approve』」）。
- 编译门做成**半自动脚本**（`npm run build:compile` → `.ci-verify/build.log`）——「可复现命令 + 日志」正是 0007 一直要求却从未落地的可核验产物。
- 第④门**拆 dev（每 PR）与 release 云打包（按触发条件）**——release 按次消耗不公开风控额度，做不到每 PR；与其写一条必被跳过的规定，不如写明触发条件。**（2026-09-11 修订：dev 面 ④a 与整模块 ④c 合并为「④ 本地编译门」，④b 触发改按打包面——见「第④门」与文末「④b 维持云端」节。）**
③ **明确不做**：不把 HBuilderX 搬进 CI；不校验证据真伪；不给小程序端逐页冒烟（测试期）；不追溯已合并 PR；不改 `ci.yml` 触发语义；不动移动端源码。
④ **拆分步骤**（单票 #841，顺序执行）：PR 模板迁移改写 → `pr-evidence.yml` → 半自动编译门脚本 → `AGENTS.md` 落「agent 不得自合」→ 用一张实测 PR 验证门真的会红。**（ruleset 的「必检 + approve」两步已裁定不做，见「为何不装『必检 + approve』」）**
⑤ **约束**：`ci.yml` 的分支 push 语义不变，`pr-evidence` 是「PR 事件不触发 CI/CD」的**唯一豁免**且只读正文、不构建不部署；**agent 不得自行合并触及运行时面的 PR**（本仓可装「必检 + approve」但裁定不装，见「为何不装『必检 + approve』」）；应急通道（`gh workflow run cd.yml`）不经验收门，但必须在正文声明风险接受。
⑥ **验收标准**：缺证据的运行时面 PR 被 `pr-evidence` 判红、补齐转绿（本仓它是可见检查，不进 ruleset 必检）；`AGENTS.md` 已落「agent 不得自行合并触及运行时面的 PR」；`npm run build:compile` 产出零 ERROR 的 `build.log`。

## 门的定义

| 门 | 类型 | 何时必须过 | 证据（产物） | 阻塞方式 |
| --- | --- | --- | --- | --- |
| ① Android 真机逐页截图对比 | 人工 | 触及运行时面（低风险面免，见下） | before/after 截图成对 + 四字段 | 合并前 · **人执行合并**（`pr-evidence` 判红可见） |
| ② 微信开发者工具无报错 | **半自动**（2026-09-12 起：agent 可执行 `scripts/mp-weixin-check.ps1` 并附证据；**合并仍由人**） | 命中 MP-WEIXIN 面（低风险面免，见下） | 入口页 + 被改页无报错（`MP_WEIXIN_RESULT`）+ 截图 + 四字段；可由 sha 绑定评论承载 | 合并前 · 同上 |

| ④ 本地编译门（默认 ④c 整模块；dev 专属面追加 ④a） | 半自动 | 触及运行时面 | `.ci-verify/kotlin-all.log` 或 `.ci-verify/build.log` + 日志片段（可由脚本贴的 sha 绑定 PR 评论承载） | 合并前 · 同上 |
| ④b release 云打包编译 | 半自动 | 触及打包面（`manifest.json` / `platformConfig.json` / `pages.json`、`uni_modules/**/utssdk/app-android/**`、新增 `*.aar` / `libs/*.jar`） | `cli pack` 日志 | 高风险改动必跑（非每 PR）；**发布前置条款：正式发版前必须跑一次云打包并装机自测** |

### 风险分层：低风险运行时面免 ①②（2026-09-11 修订）

**判据（可机检、fail-closed，实现见 `pr-evidence.yml`）**：设 `runtime` = 命中运行时面的文件；当 `runtime` 非空**且**改动集里**每个**文件都满足「低风险」时，`lowRiskRuntime = true`：

- `training-app/` 下的 `*.uts`（**仅逻辑层**）✔ 低风险
- `training-app/` 下的 `*.uvue`（模板/样式面）✘ 不算低风险
- `uni_modules/**`（原生插件面）✘ 不算低风险
- `training-app/` 下的三份 json（`manifest.json` / `pages.json` / `platformConfig.json`）✘ 不算低风险
- 测试/文档/配置（`*.test.js` / `*.md` / `jest.config*.js`）与非移动端文件 ✔ 不影响本判据（不因它们把面「抬高」）

**减免什么**：免 ① 真机逐页截图与 ② 微信开发者工具 —— 这两门在正文里**可以整行不写**（缺行不报错）；若写了，写「免（低风险运行时面：仅 .uts 逻辑改动）」也算通过。

**不减免什么**：③ `npm run test:unit` 与 ④ 本地编译门**仍必过**（.uts 逻辑改动正是 Kotlin 编译期错误的来源面）；④b 仍按打包面触发；**合并仍由人执行**（`AGENTS.md` 硬规不变）。

**代价照实说**：低风险面的风险不是消失了，而是**推迟**——真机/渲染类问题（布局、生命周期、原生能力差异）本地编译门抓不到，靠**发版前的 ① 全量逐页冒烟**兜底（发布前置条款）。校验器会在 `notes` 里带出这条提示。


### 触发判据：「运行时面」

命中任一即需过 ① 与 ④ 本地编译门：`**/*.uvue`、`**/*.uts`、`manifest.json`、`pages.json`、`platformConfig.json`（低风险面上 ① 免，见上「风险分层」）。

- 不触发（一律免人工门）：`*.test.js`、`docs/**`、`AGENTS*.md`、`.opencode/**`、`jest.config*.js`
- 只触发自动门：`package.json` / `package-lock.json`（CI 自己会跑）

判据必须是**可机检的路径匹配**（`git diff --name-only`），不得靠自然语言判断——否则又会退化成「我以为这算运行时改动」。

### 证据形态与判据字段

每门一行四字段：**执行人**（GitHub handle，不得是 agent 账号）/ **日期** / **复测对象**（页或流程清单）/ **结论（含产物）**。无产物、只有勾选 = 缺证据。

产物按门：③ = CI run 链接；④ = 命令 + HBuilderX 版本 + 时间戳 + ERROR 行数 + 日志尾部若干行（④c 记 `KOTLIN_ALL_RESULT … log=.ci-verify/kotlin-all.log`，④a 记 `COMPILE_RESULT … log=.ci-verify/build.log`）；①/② = 截图（见下）。

**传输与落点分离**：对话粘贴只是**通道**，不是载体——文本日志由 agent 逐字转写进 PR 正文；截图由 agent 压缩为 JPEG(q80) 提交到 `docs/verification/<模块>/<PR号>/<页>-before.jpg` 与 `<页>-after.jpg`，PR 正文用相对路径引用。（理由：#839 的教训是「摩擦高的门会被跳过」，对话粘贴是最低摩擦入口；但会话记录不进仓库、PR 与校验都读不到，故不能当载体。截图托管方式可切换——若仓库体积优先，改由人工拖入 PR 正文，GitHub 托管。）

### 截图粒度（第①门）

模块页面 ≤10 → **全部页面**前后对比；>10 → **变更页 + 模块入口页 + 一条主流程**，其余页在证据段列「未改动」清单。纯新增页只需 after。

### 小程序门（第②门）：半自动门（2026-09-12 修订，#883）与 appid 口径

小程序端现状：真实 appid（`wx38c3e31b16a7ced0`）、在 `platformConfig.json` 目标内、源码有 MP-WEIXIN 条件编译分支，但**只发过测试版、无正式用户**。

**2026-09-12 修订：② 从人工门降为半自动门**（spike #883 实测，口径与 ④a 同款 = #870 裁定 B）：

- **载体**：`scripts/mp-weixin-check.ps1`（`npm run build:mp-weixin-check`），取证核心是同目录的 `scripts/mp-weixin-probe.mjs`。
- **全链路无人值守（≈4.5 分钟/次，#883 实测）**：`cli.exe open` → `cli.exe project open --path <项目>`（HBuilderX 只认「已导入项目」；这一步就是无人值守的导入入口）→ `cli.exe publish mp-weixin --project <项目> --appid <真实 appid>`（**构建成功后会自己拉起开发者工具并打开项目**）→ `cli.bat close --project <dist>`（清残留自动化会话）→ `cli.bat auto --project <dist> --auto-port 9420 --trust-project`（开自动化端口，**不需要人在 GUI 里点任何开关**）→ 探针经 `miniprogram-automator` 连通后读 `pageStack` / console / exceptions 并逐页 `mp.screenshot()`。
- **断言**：`pageStack` 非空（**前置断言**）、入口页与被改页都在栈内、`errorsTotal == 0 && exceptionsTotal == 0`、每页截图落盘且是真 PNG。
- **产物**：`MP_WEIXIN_RESULT appid=… pageStack=… entry=… errorsTotal=0 exceptionsTotal=0 shots=… log=.ci-verify/mp-weixin.log` + `.ci-verify/mp-weixin.log` + `.ci-verify/*.png`。
- **证据可由 sha 绑定评论承载**：脚本 `-PostToPr <n>` 在门通过时贴 `<!-- gate-evidence:② -->` + `commit: <head sha>` 的评论（与 ④ 同款），`pr-evidence` 认出即跳过 ② 行的字段校验并给 notes。
- **三条必须抄进脚本的实测坑位（#883 + 2026-09-12 复测）**：① `pageStack` 为空会让**所有 page 级 API** 报同一个误导弹错 `Cannot destructure property 'rawPath' of 't.getPageMetaByWebviewId(...)' as it is null` —— 根因是自动化会话里没有页面被打开，处置 = 先 `close` 再 `auto`，并把 `pageStack` 非空作前置断言；② `mp.screenshot()` 挂在 **MiniProgram** 上、不在 Page 上（`page.screenshot` is not a function）且不返回内容，产物只能靠落盘文件取；③ `page.$()` 元素级断言在 `miniprogram-automator@0.12.1` + 开发者工具 Stable v2.01.2510290 组合下**不可用**（实测挂起 15s 超时）⇒ 本门只做 page 级导航 + console/exception + 整页截图。
- **两条「时序」坑位（2026-09-12 复测新增，直接决定这门红还是绿）**：④ `cli.bat auto` **必须等它跑完**——它会派生子进程去起自动化服务，**中途 kill 掉 auto 会让自动化端口永远不监听**；且端口是**auto 跑完之后延迟出现**的，故脚本在 auto 之后**轮询**端口（`-PortWaitSeconds`，默认 90 秒）而不是固定等待。⑤ automator 连接与 `pageStack` 就绪是**异步**的，实测**首次常失败**（报 `Failed connecting …, check if target project window is opened with automation enabled`），往往第 2–3 次才成功 ⇒ 探针必须**重试**（`-ProbeAttempts`，默认 6）。这两条不是可选加固：按固定时长探测会得到「端口不监听 / pageStack 超时」的**假失败**。
- **端口监听面（照实记，未做加固）**：`cli.bat auto --auto-port` 实测绑**通配地址**（`Get-NetTCPConnection` 显示 `::`）⇒ 自动化端口在局域网内可访问；`cli auto -h` 无绑定地址参数，CLI 侧无法收窄。共享网络上跑本门前先确认防火墙。
- **截图入库纪律（P2，2026-09-12 维护者追加）**：带 `-PostToPr <n>` 时把截图**压缩后提交到当前 PR 分支**的 `docs/verification/<模块>/<PR号>/<页名>-after.<ext>`，并在评论里用**仓库内相对路径**列出每张图。优先 **WebP q75**（探测 `cwebp` / `ffmpeg` / `magick` 择一），本机三者皆无则退 **JPEG q75**（.NET `System.Drawing`，Windows 自带）；**宽 ≤720px（等比、不放大）**；**每 PR ≤10 张、单张 ≤150KB、合计 ≤1.5MB**；超限先降质 → 再缩尺 → 再减图（减图须在评论里写明省了哪几页）。提交仅在「当前分支 = 该 PR 的 head」且「工作树除本次入库外无其他改动」时进行；**任何失败只打印警告 + 给出待执行的 `git add`/`commit` 命令，不得让门失败**；`-NoArchive` 为逃生开关。**入库提交不带 `[skip ci]`**：CI 会为新 sha 重跑（成本可接受），而带 `[skip ci]` 会让 PR head 缺 `ci-summary` 检查、反而不满足 ruleset 必检。
- **维持不变的**：门的语义（入口页 + 被改页无 console error / exception）、**「执行人」栏由人签收**（agent 不得代填、不得写「已通过」）、**合并仍由人执行**。
- **测试期口径（不变）**：命中 MP-WEIXIN 面（条件编译段 / `manifest.json` / 平台 API 包装）才必过；**正式发布前必须补一次全量逐页冒烟**，作为发布前置条款（一次性门，不写进每 PR 流程）。

**appid 口径诊断（2026-09-12，回答 #883 的遗留问题）**：结论是「**`manifest.json` 的 `mp-weixin.appid` 是唯一权威来源；`--appid` 只影响上传**」——

- **权威来源**：HBuilderX 从项目 `manifest.json` 的 `mp-weixin.appid` 读小程序 appid，并写进构建产物的 `project.config.json`；**该字段为 `null` / 缺失时产物落成 `touristappid`（游客 appid）**，`cli.bat auto` 也随之回显 `Using AppID: touristappid`。
- **master 上的现状（已核对全历史）**：`manifest.json` 的 `mp-weixin.appid` 在 master 上**一直是真实 appid `wx38c3e31b16a7ced0`**，**不是 `null`**。该文件最近 5 次触及提交是 `1bf6124`(#435) / `f1ab264`(#361) / `2494eb8`(#275) / `ea2baba`(#141) / `1201836` —— **#882 的改动集里没有它**。（注：`--depth 1` 浅克隆下 `git log -- <path>` 会把这个唯一提交列出来，那是浅克隆的假象，不可作为「谁改了它」的判据。）
- **⚠️ 实测坑位（本次新增，最要紧的一条）**：**HBuilderX 在首次导入 / 编译项目时会回写工作树的 `manifest.json`，把 `mp-weixin.appid` 置为 `null`**（实测 mtime 与 `publish` 启动同秒）。由此有两层结论：
  - **(a)** #883 spike 看到的「manifest 是 null / 产物 appid = `touristappid`」是**该回写行为造成的工作树脏改**，**不是 master 的事实**——spike 当时是在自己的克隆里跑 HBuilderX，manifest 被它改脏后没还原，于是把脏状态当成了仓库现状。
  - **(b) 任何 HBuilderX 门（④a / ④c / ②）在共享工作树里跑都可能静默改脏一个「运行时面」文件**（`manifest.json` 命中运行时面判据），而 `git diff --name-only` 正是 `pr-evidence` 判「运行时面 / 打包面」的依据 ⇒ 脏改会污染判据。故：**脚本对「源 manifest appid」与「产物 appid」都做 fail-closed 前置断言**（不匹配即 `exit 1`，不拿游客 appid 出个绿）；**维护者/agent 跑完任何 HBuilderX 门后必须先 `git status` 看 `manifest.json` 是否被改脏**，脏了就 `git checkout -- manifest.json` 再继续。
- **无独立配置面**：HBuilderX 的按项目本地配置（`%APPDATA%\HBuilder X\projects\<hash>\setting.json`）里**只有打包面字段**（`appPack.*`，如 `ANDROID_PACKNAME` / `ANDROID_CERT_TYPR` / `IOS_APPID`），**没有 mp-weixin appid 字段**（只报字段名，未读任何凭证内容）。
- **`--appid` 的作用面**：`cli publish mp-weixin --help` 确有 `--appid 小程序 appid`，但它服务于 `--upload` / `--privatekey` 那条**上传**链路；实测传了 `--appid` 也**不改**产物 appid。脚本仍透传它以保留「`-AppId` 参数化」的入口。
- **真 appid 下 ② 已实测可通（2026-09-12）**：把产物 `project.config.json` 的 appid 设为真值后，`cli.bat auto` 回显 `√ Using AppID: wx38c3e31b16a7ced0`，automator 连上后 `pageStack: ["pages/index/index"]` ⇒ **真 appid 不需要额外扫码/授权**（开发者工具当前登录态即可）。

### HBuilderX 是单实例串行资源：忙检测 + 等待上限 + agent 互斥锁（2026-09-12）

**坑位（实测）**：`cli.exe` 只驱动**同一个主程序**，`publish` / `launch` / `pack` 等重活都要排进主程序的编译队列。**维护者用 GUI 编译/运行时，agent 的门脚本若并发发起**：既会拖慢维护者，也会因为排队而**产生假失败**——实测一个会话的 `cli publish mp-weixin` 被排在另一个会话的 `launch app-android --compile true --cleanCache true` 之后，输出停在「正在编译中...」**不返回**，`auto`/端口/探针一路连锁失败。

**处置**：四个需要 HBuilderX 的门脚本统一 dot-source **`scripts/lib/hx-busy.ps1`**（② `mp-weixin-check.ps1`、④a `compile-check.ps1`、④c `kotlin-all-check.ps1` 的 publish 段；仿真机冒烟不接这条——纯 adb/emulator）：

- `Wait-HxFree -CliExe <cli.exe> -TimeoutSeconds <默认 600> [-NoWait]`：先取 **agent 跨进程互斥锁** `$env:TEMP\hx-agent.lock`（内容 pid + 起始时间；**持有超过 30 分钟视为陈旧、可抢占**），再探测主程序可响应性（一次轻量 `cli.exe project list` 带 **5 秒硬超时**），忙则按 10 秒间隔重试到上限。
- **超时/忙 ⇒ `exit 2`（环境不可用）**，提示语里给出不依赖 HBuilderX 的替代门（仿真机冒烟 / ④c `-SkipPublish` / `npm run test:unit`），并**绝不 kill 主程序、绝不抢占项目**。
- `-NoWait`：不等待，探测到忙立即 `exit 2`。
- 日志与 PR 评论里写一行 `HX_BUSY wait=<实际等了多少秒> result=free|timeout`（便于事后核对是不是被排队拖慢）。
- **锁在调用方脚本的 `finally` 路径里释放**（`Release-HxLock`）；契约测试 `utils/hxBusyGateContract.test.js` 守护 H1–H9（含「不得出现按名字强杀主进程的调用」「忙/超时必须是 `exit 2` 而非 `exit 1`」「finally 里必须释放锁」）。

**限制要写实（不要假装能探测 GUI）**：机械上**无法可靠探测「维护者的 GUI 是否正在编译」**。上述探测实测**能**区分「主程序可达且响应」与「连不上 / 无响应」（可达时 `project list` 约 0.5–2 秒返回），但**不能**区分「主程序空闲」与「主程序正在为别人编译」——实测在主程序正跑另一编译任务时 `project list` **仍毫秒级返回**（它不进编译队列）。所以本机制是**锁 + 探测 + 上限**的 **fail-safe**：宁可 `exit 2` 也不抢，**维护者的 GUI 优先**。

**配套纪律（与「回写 manifest」坑位合并）**：HBuilderX 在首次导入 / 编译项目时还会**回写工作树的 `manifest.json`、把 `mp-weixin.appid` 置为 `null`**（详见上「appid 口径诊断」）。两条合并成一句操作纪律：**跑完任何 HBuilderX 门后，先 `git status` 看 `manifest.json`（及其它运行时面文件）是否被改脏**，脏了就 `git checkout -- manifest.json` 再继续——否则会污染 `pr-evidence` 的「运行时面 / 打包面」判据。

### 第④门：本地编译门（④c 默认 / ④a dev 面）与 release 云打包门

**2026-09-11 修订：④a 与 ④c 合并为「④ 本地编译门」。** 二者都是本地编译证据、都要过，分成两个门号只是历史包袱；合并后正文一门一行，选哪个载体由改动面决定：

- **④c 整模块编译 = 默认载体（每张触及运行时面的 PR 必过）**：`npm run build:kotlin-all`（`scripts/kotlin-all-check.ps1`）—— appResource 产物 + HBuilderX 自带 kotlinc 整模块编译；日志固定落 `.ci-verify/kotlin-all.log`；**必须解析输出判成败**（CLI 退出码恒为 0，不可用）。它复刻的是「整模块」语义，也是 ④ 目前**唯一能每 PR 跑**的形态。
- **④a dev 全量编译 = dev 专属面追加**：`npm run build:compile`（`scripts/compile-check.ps1`）→ `cli.exe open` → `project open --path <项目>` → `launch app-android --project <项目> --compile true`；日志 `.ci-verify/build.log`。**追加条件（命中任一）**：改动 `pages.json` / `manifest.json` / `platformConfig.json`；新增页面（`pages/**` 下新增 `.uvue`）；模块手术系列的**收口 PR**。理由：dev 编译走的是「dev 运行时 + 页面注册 + 条件编译」这条链路，正是这些改动的特有面；④c 只编 Kotlin，看不到页面注册与 dev 端资源处理。
- **④ 的证据载体（P1，2026-09-11）**：编译门结果不再要求手抄进正文——脚本加 `-PostToPr <PR号>` 后，**门通过时自动贴一条 sha 绑定的 PR 评论**（正文见 `.github/PULL_REQUEST_TEMPLATE.md` 注释）；`pr-evidence` 认「同时带 `<!-- gate-evidence:④ -->` 标记与 `commit: <head sha>`（允许短 sha 前缀互含）」的评论，命中即跳过 ④ 门的字段校验、正文该行写「见评论 <链接>」即可。**校验器只校结构与 sha 绑定，不校真伪**（与正文证据同一口径）——真伪仍由维护者读日志判定。
- **④b release 云打包门（按触发条件，非每 PR）**：触发 = **按交付形态**——改动**打包面**（`training-app/**/manifest.json` / `pages.json` / `platformConfig.json`、`uni_modules/**/utssdk/app-android/**`、新增 `*.aar`、`libs/*.jar`）；维护者判断触及证书签名 / R8 / aar 依赖解析时自行加跑。执行 = `cli pack`（需 DCloud 账号登录，按次消耗不公开风控额度，需排队）。**发布前置条款：正式发版前必须跑一次云打包并装机自测**（不写进每 PR 流程）。
- 依据：ADR-0007 已录「release 云打包比 dev 编译更严」；2026-09-11 修订把 ④b 的触发从「按代码形态（新增 async / 新增 composable）」改为「按交付形态（打包面）」——**打包链路（AAPT2 资源合并、AndroidManifest 合并、R8/aar 依赖解析、证书签名）只有真打包才覆盖，本地编译门不覆盖**；而「新增 async」这类代码形态在 ④a / ④c 的编译期就能暴露（#859 实测），拿它当 ④b 的触发条件既拦不住真风险、又白白消耗云资源。

### 风险接受通道

允许例外，**禁止静默**：PR 正文必须出现固定字样「已接受未验证风险」+ 理由 + 事后验证计划，且事后要有回执（补跑或记 issue）。未声明而缺证据 = 门未过。**走了这条通道的 PR 必须由人执行合并**（agent 不得自合，见下节）。

### 实现层约束与已知缺口（#841 落地时实测，2026-09-11）

- **`pr-evidence` 的行为由 head 分支里的 workflow 文件决定**（GitHub 对 `pull_request` 事件的取值方式）：带该文件的分支即生效，不带的老分支**永不报这项检查**。实测：基于 master 的探针分支确实没跑该检查。因为 ruleset 开了 `strict_required_status_checks_policy`（分支必须与 master 同步），老分支本来就必须 merge master 重推，所以不会永久挂起——但**这条耦合记在这里：日后若要（由维护者）把 `pr-evidence` 设为必检，必须先确认目标分支带该文件**。
- **该文件本身可被 PR 修改**（head 提供校验逻辑是 GitHub 的固有模型）。当前防线 = `AGENTS.md` 的「agent 不得自行合并触及运行时面的 PR」+ 评审时看这个不足 200 行的 diff（本仓可装 approve 门但裁定不装，见下节）。若日后要抗篡改，可改用 `pull_request_target`（校验逻辑取自 master，而本 job 不 checkout、不执行 PR 代码，无「不可信代码 + 写权限」风险）——但**其 check run 能否满足 ruleset 必检尚未实测**，未证实前不采用。
- **「未命中运行时面即放行」的判据取的是文件清单**（`*.uvue` / `*.uts` / `training-app` 下的三份 json）；低风险分层（免 ①②）同样取文件清单，**fail-closed**：只要有一个 `*.uvue` / 三份 json / `uni_modules` 文件在改动集里，就回到常规面（①② 照旧必过）。**④b 的触发判据自 2026-09-11 起改为文件清单（打包面路径匹配），不再读 diff 的 `patch` 字段** —— 因此不再受 GitHub 截断超大 patch 的影响（旧判据的漏判风险随之消失），方向上更安全。
- 校验器**只校结构与产物字段，不校真伪**（重申）：不校验 `build.log` / `kotlin-all.log` 是否真存在、截图链接是否可达、PR 评论里的 sha 是否真对应那次编译；真伪由维护者读证据判定。
- ④a 的脚本实跑一次约 **4.6 分钟**（`--cleanCache true`，50 页全量，HBuilderX 5.24）；CLI 连不上主程序时会**挂住不返回**，脚本以每步超时兜底并归为「环境不可用」（`exit 2`），不会被误判成编译失败或编译通过。**帖评论（`-PostToPr`）只发生在门通过分支**，且 `gh` 不可用 / 取不到 sha 时只打警告、不改门结论。
### 为何不装「必检 + approve」：成本裁定（2026-09-11 裁定；同日修订事实前提）

**事实前提（2026-09-11 修订）**：本仓两个 GitHub 账号——`zhengcookie`（write，移动端开发本人；agent 会话也以该账号提交）与 `DriftingLi`（admin，仓库所有者 = 维护者）。**维护者持有 `DriftingLi`**：API 实测该账号对本仓返回 `admin: true`，ruleset 读得到（`protect master` / `enforcement=active`）。`zhengcookie` 侧 404 只是因为它没有 admin，**不代表无人有** ⇒ 本仓**存在可用的 admin 通道**。

> 本 ADR 初稿曾写「维护者不持有 `DriftingLi`」「装不上」——**该前提有误，已按实测修订**。裁定不变，但理由从「能力受限」改为「成本取舍」——两者对未来读者的含义不同：前者会让人以为本仓物理上无法使用阻塞门，后者才是真实的可重新审视的取舍。

裁定与后果：

- **`pr-evidence` 只作为可见检查运行，不进 ruleset 必检**：加必检、或把 `required_approving_review_count` 改成 1，都是**可执行**的（需 `DriftingLi` 操作），**裁定不做**——逐 PR 人工审批会把维护者变成所有 PR 的串行瓶颈。
- **`approve=1` 不采用**：作者不能自批，于是每个 PR 都要维护者手动批；本仓 PR 多为 agent 产出、量大，审批成本高于它带来的约束收益。
- 这是**可重新审视的取舍，不是物理限制**：若验收门漏网造成实害、且维护者愿意承担审批量，两条路都可走（改前先确认目标分支带 `pr-evidence.yml`，见上节）。
- 于是「人工门只能人签」在本仓**落到 agent 行为约束上**：`AGENTS.md` 规定 **agent 会话不得自行合并触及运行时面的 PR**（改动集含 `*.uvue` / `*.uts` / training-app 下的 `manifest.json` / `pages.json` / `platformConfig.json`）；这类 PR 必须把证据填齐后停在「待人工签收」，**由人执行合并**。非运行时面（纯文档 / 测试 / CI 配置）不受此限——否则文档改动也要人守，流程会被拖死。
- **残余风险照实说**：agent 会话与 PR 作者（`zhengcookie`）**共用同一账号**，GitHub 侧**无法机械区分「人」与「agent」**，这条靠 `AGENTS.md` 约束 agent（agent 的必读面），**不是密码学保证**。要真正的机械隔离只有两条路——agent 会话改用独立账号提 PR，或用签名（私钥与口令只在人手里）；本 ADR 不采用，但记在这里备选。
### 闭环条款：人工门是规则来源

人工门当场抓到的问题，收口时**必须回写为守护规则或注入自检**（先例：`utsAndroidCompile.test.js` 规则 A–Y 全部来自编译现场），做不到的在 ADR/票面写明理由。人工门因此不是一次性检查，而是规则的来源——这是它值得保留的理由。

### 生效时点与追溯

从**下一张合并到 master 的手术 PR** 起适用，**不追溯已合并 PR**。`refactor/exam`（#645 T07）是第一条适用的票：不要求它补历史证据，只要求它自己的四门证据。

### ④a 的运行前提与 ④b 的判定（#859 spike 实测，2026-09-11）

**④a 的运行前提（本仓坑位）**：HBuilderX CLI 只驱动主程序，靠**本地 IPC**（命名管道 / 本地套接字）通信；**受限沙箱下 CLI 报「与主程序的连接已中断，可能已关闭」**，切到全访问权限后 `open` / `project open` / `publish` / `launch` 全部正常（#859 实测）。⇒ agent 会话跑 ④a **必须申请全访问权限**，不得以「sandbox 限制」为由直接走例外通道 —— #840 正是如此（④a / ④b 两行均写「已接受未验证风险：AI agent 无法启动 HBuilderX」），把本可在编译期暴露的 Kotlin 错误放行到了云打包。
**口径已裁定（2026-09-11 维护者裁定 B，#870）**：④a 为**半自动门** ——

- **agent 会话可执行 ④a**：`npm run build:compile`（即上面「第④门」定义的 `cli.exe open` → `project open` → `launch app-android --compile true`，成败一律解析 stdout），产出 `.ci-verify/build.log` + 日志片段，证据形态不变。
- **④a 的「执行人」栏**填执行会话所用的 GitHub 账号（本仓 agent 会话即 `zhengcookie`），并在结论里注明「agent 执行」；**① 真机截图与 ② 微信开发者工具仍只能由人执行**，其「执行人」栏不得由 agent 代填、不得由 agent 写「已通过」。
- **合并仍由人执行**：agent 不得自合触及运行时面的 PR（`AGENTS.md` 硬规不变）。
- **运行前提（硬前提）**：HBuilderX CLI 靠与主程序的本地 IPC，**受限沙箱下会报「与主程序的连接已中断」** ⇒ agent 会话跑 ④a **须以全访问权限执行**。这不是可选项：#840 正是「agent 跑不了 ④a」而走了例外通道，才把编译错误放行到云打包。

**④b 维持云端，本 ADR 不改写**：#859 票面预设的改写条件（「若验证通过」）未成立，三条实测为据 ——（**2026-09-11 修订只改触发口径**：从「新增 async / 新增 composable」改为「触及打包面」，见上「第④门」；下面第二条实测正是这次修订的依据。）

- **成本前提被推翻**：云打包实测 **5 分 40 秒**（#849，18:23:19 → 18:28:59），不是「半小时 + 排队」。
- **「只有 release 才暴露」在本机不可复现**：复刻 error17 形态的合成探针在 **④a 就被抓到**（`error: Assignment type mismatch: actual type is 'UTSPromise<Unit>' …` + `Function invocation … expected.` + `[plugin:uni:app-uts] kotlin编译失败`）⇒ 拿「新增 async function / 新增 composable」当 ④b 触发条件并不指向真风险（本地编译门就覆盖）；而 `publish app-android --type appResource` 反而**报「编译成功」**（该路径 `result.kotlinc = false`，本机不做 Kotlin 编译），本地整模块 kotlinc 同样抓得到。
- **真跑 `compileReleaseKotlin` 的门槛**：Google Android SDK + uni-app x 原生 SDK 工程（19–23 个 aar + `uts-kotlin-compiler-plugin` / `uts-kotlin-gradle-plugin`）+ keystore + 离线 appkey（人工申请），一次性投入远超 5 分钟云打包的收益。

**已知坑位：dev 编译缓存不是自洽的编译单元。** `runUVueKotlinDev()` 只编译本次变更的 .kt，并把上一次的 `class/` 目录放进 classpath 以补齐符号；#859 实测把该缓存 96 个 .kt 一次性整模块编译**必然失败**并产生大量 `unresolved reference`（被引用的类型只存在于陈旧 `class/*.class` 里）。要做本地整模块 Kotlin 编译，输入必须取 **appResource 产物**（`unpackage/resources/app-android/**`，含 `uni_modules/**/utssdk/app-android/src`）。

**④c（已落锁，2026-09-11，#870 T2；2026-09-11 修订为 ④ 的默认载体）**：appResource 产物 + HBuilderX 自带 kotlinc 2.2.0（+ 自带 Corretto 17 + `plugins/uniapp-runextension/lib2` classpath + UTS 编译插件）做**整模块**编译 —— 实现 `scripts/kotlin-all-check.ps1`（`npm run build:kotlin-all`），日志 `.ci-verify/kotlin-all.log`，守护 `utils/kotlinAllGateContract.test.js`（C1–C10）。实测：干净树 `errors=0 classes=1261`（93 个 .kt，214s）；注入 82999f5 的错误形态即报同文本 error。它与 `compileReleaseKotlin` **不等价**（Gradle / AGP / 插件版本不同），只作本地加固，不改 ④b 定义。**边界**：① 输入只能用 appResource 产物（用 dev 缓存必然大量 `unresolved reference`）；② `publish` 一步仍需主程序可达，`-SkipPublish` 可让受限会话只跑 kotlinc 部分。

**CLI 勘误**：`cli publish app-android --type appResource` **必须带 `--project`**；缺参实测 `[uniapp-extension] 参数 project 值不能为空`，**且退出码仍为 0**（再次坐实「退出码不可用、一律解析 stdout」）。

### 非门辅助：仿真机前置冒烟（2026-09-11，#883 / O2）

> **非门（不替代 ① 真机门）——仅前置冒烟：仿真机截图与无异常证据，鉴权/生物识别/厂商 ROM/真机上传路径类问题仿真机抓不到。**

**结论（维护者选 O2）**：①「真机」门的语义**不放宽**——仿真机**不替代**真机；只是把仿真机做成 **agent 跑的前置自动冒烟**，产出截图 + 无异常证据，让① 的人工执行者只需看**已过滤过的候选页**。① **仍是人工门**，仍由人在真机执行（「执行人」栏不得由 agent 代填，不得写「已通过」）。

**为什么不放宽（#883 spike 实测）**：开发者工具 console 实测报 `checkIsSupportSoterAuthentication:fail … 请使用真机进行开发`；且本 ADR 记的两次实害——`content://` 上传 602001、证件 level NPE、生物识别强转崩溃——**都是真机独有失败模式**。

**载体**：`scripts/emulator-smoke.ps1`（`npm run smoke:emulator`）。默认 **headless**（`-no-window -no-audio -no-boot-anim`，不弹窗、不抢焦点），仅 `-ShowWindow` 才开窗；截图走 `adb exec-out screencap -p`（headless 下可用）。收尾 `adb emu kill` **写在 `finally`**，异常/断言失败/超时都不留跑着的模拟器。判成败只看输出与 logcat（FATAL EXCEPTION / ANR 计数 + 前台 Activity + 进程存活），**不看退出码**。守护：`utils/emulatorSmokeContract.test.js`（C1–C7）。

**边界**

- **抓得到**：布局/渲染崩坏、页面加载期 UTS/JS 异常、导航状态、截图看版式。
- **抓不到**：生物识别、运行时权限弹窗行为、厂商 ROM 差异、真机上传路径（`content://`）。
- **不是门**：本项**不进** `.github/workflows/pr-evidence.yml` 的校验器；PR 评论用标记 `<!-- prefilter:emulator-smoke -->`（**刻意不用 `gate-evidence:` 前缀**，避免被误当作门证据）。改验收门逻辑的 PR 与本项无关。

### ①a 真机自动取证（预置，待 #624 实测后落锁；2026-09-12）

**① 真机门拆成两半**：**①a** = agent 用 adb 自动逐页截图 + logcat 断言 + 记录前台 Activity；**①b** = **人**走关键交互（生物识别指纹按压、运行时权限弹窗、真机上传路径）。拆分只把「agent 能机械执行的那一半」自动化，**门的语义不放宽**。

**载体**：`scripts/device-capture.ps1`（`npm run capture:device`），守护 `utils/deviceCaptureContract.test.js`（D1–D9）。

**它只替代什么**：只替人省掉 ① 里「逐页截图 + 抓日志 + 记前台 Activity」这一步的**取证劳动**；**①a 不替代 ①b**——指纹、权限弹窗、真机上传路径这三类仍由人在真机上走，结论仍由人写。**「执行人」栏仍由人签收**，agent 只产出截图与日志。

**机械上无法替代真机生物识别的理由**（引用 #883 的 devtools console 证据）：spike #883 的开发者工具 console 实测报 `checkIsSupportSoterAuthentication:fail … 请使用真机进行开发`；更根本的是指纹要**人把手指按上去**才产生一次成功/失败事件，而 adb 里**没有任何只读命令**能代替这次按压（`adb shell input` 类事件注入既被本脚本禁用，也**不触发指纹传感器**）。故 ①b 不是流程冗余，是这类风险的唯一覆盖点。

**只读禁令（红线）**：本脚本可能正跑在维护者**正在调试的真机上**（先例 #781），故正文中**一律禁止** `kill-server` / `install` / `uninstall` / `force-stop` / `logcat -c` / `push` / `pull` / `input`。理由逐条：`kill-server` 会顶掉维护者与其它工具共享的 adb server；清缓冲会抹掉他正在看的崩溃输出；杀进程或抢前台会让调试会话断开。一句话口径：**取证不该改变被取证的对象**——而维护者的调试会话本身正是要被取证的对象。只用只读命令：`adb devices`、`exec-out screencap -p`、`shell dumpsys …`、`shell logcat -d`（`-d` 取完即退、**不清**缓冲）。**只用 `D:\android-sdk\platform-tools\adb.exe`**（与 HBuilderX 共用同一个 server）；**不要**用 HBuilderX 自带的那份 adb，会起第二个 server 顶掉连接。

**连带结论（照实记）**：不能清缓冲 ⇒ 崩溃计数做不到「清缓冲后再统计」。处置 = 启动时取**设备自己**最新日志行的 epoch 时间戳作窗口起点（`logcat -d -v epoch -t 1`），结束时只统计「大于等于起点」的行；`-LogcatSeconds` 大于 0 时取「最近 N 秒」与「启动以来」的**交集**。起点取自设备本身，故设备时钟与宿主时钟不同步不影响结果；连起点都取不到就写 `logcat=SKIP`，**不拿历史日志冒充本次**。

**切页默认关闭**：`am start` 默认**不发**（会打断维护者的调试会话），只有显式 `-AllowAppStart` 才开；`-NoStartApp` / `-SkipAppStart` 则**无论如何**都不发（即便同时给了 `-AllowAppStart`，**以禁止为准**，fail-safe）。默认只读模式只对**当前前台**采 1 张图，`-Pages` 其余条目记 `SKIP（未切页：切页默认关闭）`——**不假装跑过**。**多设备时必须显式 `-Device`**，否则 `exit 2`（实测同一台真机会同时以 `<ip:port>` 与 `_adb-tls-connect._tcp` 两条 transport 出现，本机就是这个形态 ⇒ 不自动猜）。

**判成败只看输出**（`DEVICE_CAPTURE_RESULT=`，沿用本仓「退出码不可用」口径）：断言 = 前台 Activity 可取得 + 截图落盘且非 0 字节 + 窗口内无 `FATAL EXCEPTION` + 窗口内无 `ANR in <前台包名>`；环境不满足 `exit 2`；**截图压缩与入库失败只警告、不改结论**（`-NoArchive` 为逃生开关）。截图入库沿既有纪律（WebP q75 → 无编码器退 JPEG q75、宽 ≤720、每 PR ≤10 张 / 单张 ≤150 KB / 合计 ≤1.5 MB），落 `docs/verification/device/<PR号>/`。

**不是门 + 本次不改验收门校验器**：本项**不进** `.github/workflows/pr-evidence.yml` 的校验器；PR 评论用标记 `<!-- prefilter:device-capture -->`（**刻意不用验收门证据那套前缀**，避免被误当作门证据）。本次**不改验收门校验器**——① 行仍按人工门口径填，只是「截图与日志」这半由 agent 产出，**①b 仍由人签字**。

**实测状态（照实记，不夸大）**：只读路径（`devices` / `screencap` / `dumpsys` / `logcat -d`）**已在本机真机实测跑通**（`DEVICE_CAPTURE_RESULT=PASS`）；`-AllowAppStart` 切页分支与截图归档入库**尚未在真机跑过**（维护者当时正用该真机调试 #781，不得打断）⇒ 本节标注为**预置，待 #624 实测后落锁**。
