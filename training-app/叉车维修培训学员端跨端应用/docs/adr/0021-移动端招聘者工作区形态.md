# 0021 - 移动端招聘者工作区形态

> 状态：已裁定（grilling 收敛，2026-09-20）｜来源：本会话对企业招聘者（第四角色）移动端形态的十项裁定
> **职责边界**：只定移动端（`training-app/叉车维修培训学员端跨端应用/`）的招聘者面形态、身份模型与切票方式；
> **不动后端**（零新增端点、零契约变更）、**不动 web 的 `recruit.` 子域工作区**、**不动 `pr-evidence.yml`**。
> **落地状态：文档口径已落；④ 的四条线均未开工。**

**① 目标与范围**

在学员端 App 内新增企业招聘者（第四角色，`recruiter_users` 独立表）的移动端形态。范围止于**响应侧**：投递处置（按职位查看 / 详情 / 标记不合适）、联系方式交换（发起与状态）、简历库检索。

**为什么是「响应侧」**：招聘域的价值闭环在**响应**——被标记不合适后有 30 天冷却、交换申请 `pending` 14 天过期，晚回一天就是损失；而职位发布是低频重表单，桌面（web 的 `recruit.` 子域）本来就是它的家。本决定让移动端页面族从 web 的 6 页缩到 4 页（砍掉 `JobManage`）。

现状锚点（现测）：学员端 App 已有 `pages/jobs/{job-list,job-detail}.uvue` 与 `pages/resume/{resume,resume-edit,resume-attach}.uvue`；招聘者侧**一行都没有**——唯一存在物是 `pages/login/login.uvue:114-122` 一个「招聘者」角色选择器，其 `roleType`（`:194`、`:321-323`）**只被选择器自己读写**，`onSubmit`（`:538`）从不读它，且**无测试锁住**。

**② 选型 + 一句理由（十项裁定）**

- **形态 = 并入学员端 App**（同基座、角色切换）—— 邀约制的小众角色（企业维度 1:1，`credit_code` 唯一索引保证）值不得第二套基座、上架与验收门；代价是隔离要在原生端重建。
- **身份关系 = 互斥**（同一时刻只有一个身份）—— 以「登录任一方即清空另一方」换取与 web host-only cookie 同等的隔离强度，且复用现有单槽存储。
- **登录入口 = 独立招聘者登录页 + 学员登录页底部低调入口** —— 招聘者只有密码一种登录方式（`/auth/recruiter-login`），塞进学员的四方式认证页会制造一条长期回归分支；`login.uvue` 的死桩**摘掉**（无测试锁住，零阻力）。
- **导航骨架 = 独立页面栈、无 tabBar** —— tabBar 已满 5/5（微信小程序上限），而响应侧只有 4 页、招聘者不是每日逗留角色，常驻入口的价值不成立。
- **工作台无未读信号、零后端改动** —— 客户端逐职位拉 `unread_count` 最多 50 次请求，与 `fillApplyStates` 已落锁的「单次批量 join、**禁 N+1**」相悖；宁可不做。
- **凭据 = 招聘者不提供记住密码 / 生物识别** —— 单槽 `STORAGE_KEY_CREDENTIALS` 不动，`0004`/`0005` 的「学员个人凭据 + 生物门控」语义保持纯净；企业账号可能多人共用，凭据不留个人设备。
- **打码简历 = 原生渲染脱敏字段为主 + 带鉴权 PDF 下载作次要出口** —— 原生端无内嵌 PDF 能力（web 的 `OnlineResumePdf.vue` 是 blob 内嵌，不可移植），而打码字段与 PDF 是**同一投影**（spec #1051 已把打码规则与三处字段清单收进同一文件）。
- **平台面 = 仅 Android/iOS** —— 培训类小程序里嵌企业招聘与个人信息处理有类目/审核风险；且小程序端排除后，主包 2 MB 约束随之消失（现测产物 1.22 MB / 48 页，主包无分包配置）。
- **鉴权通道 = 只用 Bearer** —— cookie 通道在原生端不存在，「依次尝试 `hrwai_token` 与 `recruiter_token`」那套（`middleware/middleware.go:128`）无从复用。
- **切票 = 四条独立线各自 PR** —— 其中两条是**现网缺陷**、两条是新功能，混在一个 PR 里会让缺陷的修复被新功能的验证拖着（违背「一个 PR = 一件做完且已在目标环境验证过的事」）。

**③ 明确不做的事**

- **不做职位发布 / 编辑 / 上下架** —— 移动端看到的职位全部来自 web 的 `recruit.` 子域；工作台第一屏是**只读**职位列表（`GET /api/recruit/jobs`）。不渲染任何「功能开发中」式占位。
- **不动后端**：不做工作台未读聚合（不给 `JobPostingDTO` 加 `unread_count`、不新增 `/recruit/summary`）、不改邮件正文。
- **不做邮件深链**：不给邮件补跳转链接，不引入 App scheme / AppLink —— 那会动 `manifest.json`（命中 ④b 云打包门）。
- **不做小程序端 / 支付宝小程序端**。
- **不做并存身份**：不做工作区切换指针、不做双槽凭据、不做按请求打角色戳的 401 消歧。
- **不做自定义 tabBar**（不开 `tabBar.custom`）。
- **不改 web 的招聘者工作区**，不改 `pr-evidence.yml` 的任何判据。
- **不做分包**（可选优化；平台面排除小程序后 2 MB 约束不再适用）。

**④ 拆分步骤（四条独立线，可并行，无先后依赖）**

1. **缺陷 · 简历附件删除打的是不存在的端点** —— `api/resume.uts:286` 发 `DELETE /resume/attachment`（调用点 `pages/resume/resume-attach.uvue:159`），而后端 `resume` 组只有 `GET ""` / `PUT ""` / `PUT /visibility` / `POST /pdf` / `DELETE /pdf` / `POST /image`，**全仓无任何 `/attachment` 路由** ⇒ 真机删附件必 404。改调 `DELETE /resume/pdf`。
2. **缺陷 · 投递态不回流** —— `api/job.uts` 的 `JobPosting` 类型补 `apply_state` / `cooldown_days`（后端 `job_posting_service.go:83-84` 已定义、`:261`/`:344` 按学员视角批量回填），`job-list` / `job-detail` 按 `none / applied / not_hired(+冷却天数)` 三态渲染。现状：`job-detail.uvue:129` 只有一个本地 `hasApplied` ref，页面重进即丢，投过的职位按钮复活、点了吃 400（`ErrApplyCooldown`「该职位 30 天内暂不能再次投递」）。
3. **学员侧招聘面新建** —— 我的投递（`GET /api/resume/applications` + 撤回）、收到的交换申请（`GET /api/resume/contact-requests` + 同意/拒绝/撤回）、打码在线简历（原生渲染 + 带鉴权下载）。入口复用现有「就业在线」链路（`pages/profile/profile.uvue:162` → `job-list` → 头像 → `resume`）。
4. **招聘者工作区（本 ADR 主体）** —— 独立登录页 → 工作台（只读职位列表）→ 投递列表（`GET /api/recruit/jobs/{id}/applications`，响应自带 `unread_count`）→ 投递详情（`GET /api/recruit/applications/{id}`，打开即记已读）+ 标记不合适 → 简历库（`GET /api/recruit/resumes`）→ 简历详情（`GET /api/recruit/resumes/{id}`）+ 发起交换（`POST /api/recruit/contact-requests`）→ 我的交换申请（`GET /api/recruit/contact-requests`）；含身份互斥接线、401 按当前角色定向、小程序端条件编译隔离。

**⑤ 约束**

- **与 web 的语义分叉只许停在移动端**：web 上 `hrwai_token`（父域）与 `recruiter_token`（host-only）**并存**、由子域决定用哪个（#370 招牌隔离）；移动端改**互斥**，此分叉不得反向影响 web 的 cookie / 子域隔离。
- `recruiter_users` 与 `hrwai_users` **无共享 ID 空间** —— `middleware/credential_scope.go:39` 已记照 `sub` 直查会命中**同号陌生学员行**；招聘者身份不得参与学员的证件作用域与预筛选拦截（`current_credential_id IS NULL` 对 recruiter 不适用）。
- 401 定向改造须避开 `0017-冷启动并发401误判登出缺口` 的同类雷区：`request.uts:119-127` 现在是**不区分角色**的全局单点登出，且硬编码 `'auth_user'` 而非常量。
- 招聘者面只走 Bearer，cookie 通道不复用。
- 移动端 ADR 独立编号（本仓 `0001` 起），本文不引用、不修改根仓库 ADR 编号体系。
- 术语「招聘模块」在本仓历史上指**学员侧**招聘面，与本 ADR 的「招聘者工作区」是两面，不得混用（`CONTEXT.md` 已登记）。
- 分包不做；若日后要做，须先现测 uni-app-x 在 App 端的分包支持度。

**⑥ 验收标准**

- 四条线各自 PR，线 1、2（缺陷）可独立合并、不等待其余线。
- 线 4 命中运行时面：**④a** 本地编译门（新增页面亦触发）+ **①a** 逐页截图；**能力面**是否命中按 `scripts/lib/capability-surface.ps1` 白名单与 PR 模板自报**现测**（若命中真机上传或运行时权限弹窗，**①b** 的「执行人」栏须由**人**给出原文）。
- 行为判据（**断言行为、不断言源码文本**）：招聘者身份登入后，学员的 `auth_token` / `auth_refresh_token` / `auth_user` 三键被清空；学员身份登入后招聘者态不可恢复；401 按**当前角色**定向到对应登录页。
- 移动端不存在职位发布入口，也不存在任何「功能开发中」式占位（沿用 #705 摘掉 mock 招聘 tab 的判据：**看起来能用、用了必失败**的入口比没有入口更贵）。
- `pr-evidence.yml` 的改动量 = 0。
