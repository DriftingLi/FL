# 逐字输出②：分块通道接线、整包降级、status 与 401 重发纪律

- 状态：已采纳（2026-11-10，#2389 实施同批写入；通道选型与末帧口径见 #2363 调研笔记）

## 背景

#2363 已拍通道：`uni.request({enableChunked:true,responseType:'arraybuffer'})` + `RequestTask.onChunkReceived`，三端统一；#2388 已交付字节级解析器 `utils/sseIncrementalParser.uts`（feed/finish、末帧无空行不派发、401 必须新实例）。但 `api/aiAssistant.uts#sendStream` 仍只走 `success` 整包 + `parseStreamSSE`，`status` 帧被静默丢弃，401 重发会把已消费的增量留在气泡里。本票只做接线，不重做解析。

## 决定

1. `sendStream` 开 `enableChunked: true, responseType: 'arraybuffer'`，`task.onChunkReceived` 里 `parser.feed(res.data)` 逐帧派发；**API 层不切帧**，半包/粘包/跨块 UTF-8 全归 #2388 解析器。
2. 能力探测 fail-open 到整包：task 为 null、无 `onChunkReceived`、或注册抛错 ⇒ 不启用分块，`success` 里走 `bodyToText` + `parseStreamSSE`。`parseStreamSSE` 保留，**只服务这条降级路**。
3. 收口唯一：`settled` 闸 + `received` 标记。收到过分块则 `success` 只做 `parser.finish()` 收尾，`!terminated` 判 `STREAM_MSG_INCOMPLETE`；未收到分块才整包解析。done 已由分块收口后 success 再来，直接早退（不重放正文）。
4. `status` 帧进 `StreamChatCallbacks.onStatus`：`handleStreamSSEEvent` 增 `status` 分支，`data.text` 非空才派发；`useAiChat` 以 `statusText` 驱动等待态文案，空则退回「思考中... / 已等 N 秒」。
5. 401 重发纪律：先 `settled = true` 作废旧尝试 → `renewOrExpire` → 成功则 `onRestart` 清占位气泡与 `statusText` → **新建解析器**重发；旧尝试的迟到 chunk 因 `settled` 被丢弃。
6. `done.content` 仍无条件整体替换（#2310 口径不变），`thinking=false` 时机不变。

## 后果

- 后端零改动、计费与会话接口零改动；回退矩阵 6 行全落既有路径，不新增后端/计费分支。
- 五个 `loadUts` 装载 `api/aiAssistant.uts` 的套件必须补 `createSseParser` 绑定（fail-closed）；新增 `utils/aiStreamChunkedBehavior.test.js` 真跑 10 例覆盖竞争、断流、降级、401。
- 真机逐字与「拿不到 chunk 时降级生效」只能真机实测，归发版冒烟（ADR-0043）。

## 不采用的备选

- 自建 XHR / WebSocket 通道：三端不统一，且 #2363 已裁定。
- 在 API 层按 `\n\n` 切帧：与 #2388 重复且必然漂移。
- 401 重发复用旧解析器：残留半帧会把重发后的首帧拼坏。
