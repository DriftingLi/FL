# 0017 - 冷启动并发 401 被误判为登录过期（假登出）

**状态**：已修复（#1124，2026-09-17）；原为「已确认、暂不处理」

## 现象

安卓端（HBuilderX 自定义基座）**冷启动瞬间**弹出「登录已过期，请重新登录」，**随后首页照常可用**。Web 端不复现。

## 缺口描述

「登录已过期，请重新登录」是**移动端硬编码文案**（`api/request.uts` 的 `logoutAndReject`），对任意端点的任意 401 都会照发，**不携带真因**——服务端对 access 过期说的是另一句「Token无效或已过期，请重新登录」（`backend/internal/middleware/middleware.go:93`）。故这句文案本身不能用于定位。

冷启动时 `App.uvue` 的 `validateToken()` 自述「不阻塞渲染」（fire-and-forget），而 `pages/dashboard/dashboard.uvue` 的 `onShow` 立刻并发发出多个过 `JWTAuth` 的请求。access 已过期（固定 2h，根仓库 `ADR-0016`）时它们全部 401：

1. 第 1 个 401 抢到 `isRefreshing = true`，真去 `POST /auth/refresh`（一次网络往返）。
2. 其余 401 落在这个窗口内：首行 `if (isRefreshing) return false` ⇒ 调用方走 else 分支 `logoutAndReject()`。
3. `logoutAndReject` ⇒ `handleUnauthorized()`：清 storage 的 `auth_token`/`auth_user` + `reLaunch('/pages/login/login')`，随后 toast。`isRefreshing` 还要等刷新 settle 后**再 100ms** 才复位，窗口被进一步拉宽。
4. 但第 1 个的刷新**成功了**并写回新 token；登录页 `onLoad` 随即 `restoreFromStorage()` 后判 `auth.isLoggedIn.value`——而它在 storage 为空时**提前 `return false`、不重置内存 ref**，内存 `isLoggedIn` 仍是 `true` ⇒ **又 `reLaunch` 回首页**；此时新 token 已在 storage 里，首页请求全部 200。

净效果：**一次持续几百毫秒、能自我修复的假登出**——用户只看到一个 toast，故长期被当作「莫名其妙」。触发条件是「access 已过期」×「≥2 个 401 落进同一次刷新窗口」，因此与**多久没打开 App** 强相关，而非随机。

## 为什么只有移动端（与 Web 的三条结构性差异）

| # | 差异 | Web | 移动端 |
| --- | --- | --- | --- |
| 1 | 启动是否阻塞渲染 | 路由守卫 `await authStore.initialize()`，`/auth/me` 未 settle 前不挂载页面 | `onLaunch` 明确「不阻塞渲染」，dashboard `onShow` 立即并发发请求 |
| 2 | 并发 401 的刷新语义 | 模块级共享 `refreshPromise`，并发 401 等**同一个**刷新再各自重试 | `isRefreshing` 布尔量，第二路直接 `return false` ⇒ 登出 |
| 3 | 启动探针是否静默 | `/auth/me` 带 `X-Silent: 1`，失败只静默跳转，不弹提示 | `getUserInfoApi()` 未传 `silent`（默认 `false`）⇒ 这条路必弹 toast |

## 复现配方（可控，不必等 2 小时）

等价构造：正常登录一次后，把 `auth_token` 改成**签名无效**的串、**保留 `auth_refresh_token` 不动**，再冷启动。这与真实的「access 过期」走**同一条 401 路径**（`middleware.go:93`），区别只是不必等 2 小时。

预期（修复前）：冷启动瞬间 ≥1 次「登录已过期，请重新登录」toast，`logcat` 同一秒内 ≥2 条该错误，随后首页可正常使用。

对照组：Web 端同样污染 `localStorage.token` 后刷新 —— 无任何提示。

## 影响

- **二阶循环**：第 3–4 步在「刷新失败」时会退化成**登录页 ⇄ 首页来回跳**（`isHandlingUnauthorized` 只有 2s 去重窗口）。
- **同源旁路（同一句文案、不同成因）**：① 上传接口 401 **直接登出、永不尝试刷新**；② 「清除缓存」只恢复 `auth_token`/`auth_user`，**静默丢掉 `auth_refresh_token`**，此后自动续期失效；③ SSE 401 **只提示、不登出**。
- **反证：多设备 / 跨端互踢不是成因（勿再排查）**。后端**零**单会话/设备数策略（根仓库 `ADR-0016`），登录路径不吊销任何 token，唯一跨会话吊销是改密（`backend/internal/service/auth_service.go:299`）；且「弹完页面仍可用」这一事实**独立地**排除了吊销类成因。

## 修复（#1124 已实施，2026-09-17）

新增 `api/refreshGate.uts`（单飞闸门），`api/request.uts` 的 `tryAutoRefresh()` 改为走它：

1. **并发 401 共享同一次在飞刷新**（验收 1/5）。不变量：**「另一次刷新正在进行」绝不等于「刷新失败」**。`gateRefresh()` 在已有在飞 Promise 时**返回那个 Promise**（对齐 Web 的模块级 `refreshPromise`），`false` 只代表刷新**真的**失败（无回调 / 被拒 / 抛错）。服务端轮换语义不变——一次风暴只发**一次** `POST /auth/refresh`。
   **去重认「触发这次 401 的那个 access token」，不认时间盒**（`gateRefresh(runner, forToken)`）：风暴成员的 401 会在不同时刻到达（本票真机日志里相隔可近 1 秒），但它们带的都是**同一个已被替换掉的**旧 token ⇒ 刷新 settle 之后再到达的迟到成员，仍并入那一次的结果，不会再发第二次。时间盒被显式否掉：窗口多长都是拍脑袋，短了漏、长了会把「重新登录后的新 401」误并进旧失败。请求侧因此要记录「本次实际发出的 token」（`sentTokenOf(reqHeader)`；不能读 storage —— 那时它已被刷新换掉）。
2. **空 storage ⇒ 内存登录态同步归零**（验收 3）。`stores/auth.uts` 抽出单一重置点 `resetAuthState()`，`clearAuthData()` 与 `restoreFromStorage()` 共用；后者在「无 token」与「有 token 但 user 读不出」两个分支都先归零再 `return false`，登录页不再拿陈旧 `isLoggedIn` 弹回首页。**只重置内存、不动 storage**——refresh_token 按 `0004-生物识别门控.md` 留给快捷登录。
3. **清理缓存不丢续期**（验收 4）。`pages/profile/settings.uvue` 的恢复清单补上 `auth_refresh_token` 与 `auth_login_provider`。

跳转职责仍留在 `handleUnauthorized()`（只由真实失败触发）。

**明确不做（另立票）**：启动期阻塞挂载（对齐 Web 的守卫语义，与现有启动体验取舍冲突）；上传 401 的刷新语义；SSE 401 的登出语义；把跳转整体迁出请求层；`auth_refresh_token` 保留而 `auth_secure_credentials`（生物识别包络）仍被「清理缓存」清掉这一处不一致。

## 本票新增的测试缝（守护落锁）

`.uts` 无法在 jest 里 `import`，此前只能用**源码文本契约**（`requestOutletContract` / `quickLoginContract`）——它证明不了「刷新被调用了几次」「并发请求最终 resolve 还是 reject」，而本票的验收恰恰要求这一点。故新增 `utils/utsHarness.js`：把 `.uts` 去类型后用 `new Function` 真正执行（依赖由测试注入；import / export 形态不支持即 fail-closed），于是**行为**可机检。边界写实：它证明的是 JS 行为，**不证明 Kotlin 可编译性**（那是 ④ 的活）。

| 文件 | 钉住什么 |
| --- | --- |
| `utils/concurrent401RefreshBehavior.test.js` | 跑真的 `refreshGate.uts`/`request.uts`/`auth.uts`：4 个并发 401 ⇒ 刷新计数 **1**、各自带新 token 重试并 resolve；**刷新 settle 后**才到的迟到 401 仍不产生第二次刷新（G4/G5/I1b）；真失败 ⇒ 4 个 reject、跳转**恰好 1 次**、access 侧凭据清空而 refresh_token 保留、`restoreFromStorage()` 后 `isLoggedIn=false`（不弹回） |
| `utils/concurrent401RefreshContract.test.js` | 接线与 key 清单：`isRefreshing` 读法已删除、闸门收 `forToken` 且不得回退成时间盒/代际号、`tryAutoRefresh(sentTokenOf(reqHeader))` 的接线、登出只由真实失败触发、`resetAuthState` 是单一重置点、settings 恢复清单完整 |

**Q-A 落锁**：两个套件的 token `concurrent401Refresh` 已加进 `scripts/lib/contract-tests.ps1` 的 `Get-ContractTestPattern`（唯一真源）+ `utils/contractTestPatternBehavior.test.js` 的逐字钉住（P1/P2/P3）——否则 `dev:finish` 的 Q-A 路径**永不执行**它们（本仓反复踩过的假绿形态）。

**可证伪性已验证**：把闸门的 token 去重与 `restoreFromStorage` 的归零分别退回修复前形态，`G4`/`G5`/`I1b`/`I2` 立刻变红（不是恒绿）。
