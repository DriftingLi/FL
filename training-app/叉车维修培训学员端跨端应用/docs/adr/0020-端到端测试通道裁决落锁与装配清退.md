# 0020 - 端到端测试通道裁决落锁与装配清退

**状态**：已接受（2026-09-19，来源：`docs/spec-永绿整改.md` §② 的 E2E 通道裁决（PR #1136）在**配置与文档面从未落锁**；本 ADR 把那条裁决落到仓库面）

> **一句话**：`spec-永绿整改.md` 已裁定「微信小程序通道只能做 page 级断言、不能做流程验证」并写明「别再重开这个问题」，但仓里仍躺着一整套**未激活却看起来可用**的 uni-automator 装配（配置 + 依赖 + 示例用例 + 两份教程 + `AGENTS.md` 的承诺）—— 本 ADR 把它整体清退，并把「为什么不做」与「将来要重启怎么做」写成可复核的记录。

## ① 目标与范围

**要解决的是「文档与配置承诺了一个不存在的能力」**，不是重新评估 E2E 通道（那条已在 PR #1136 裁决，本 ADR 不重开）。

三处可复核的误导面（实测，出处见「附」）：

1. `AGENTS.md` 的「## 测试约定」整段仍写着「使用 uni-app 官方测试框架 `@dcloudio/uni-automator`」「`npm run test`（默认 H5）」「`npm run test:mp-weixin`」—— 而其中 **H5 通道已被 spec §③ 否决**（`Cannot find module '@dcloudio/uni-h5/...'`），mp-weixin 通道**只能做 page 级断言**。
2. `TESTING_GUIDE.md`（144 行）与 `AGENTS.test.md`（91 行）是整套模板教程：教人点 HBuilderX「工具 → 自动化测试」、跑 `npm run test:web` / `test:app-android` / `test:app-harmony` —— **这些脚本在 `package.json` 里一个都不存在**。`spec-永绿整改.md` §③ 已把它当成「只写文档靠自律」的**活体反例**在引用。
3. 项目根仍有 `jest.config.js`（`testEnvironment` 指向 `@dcloudio/uni-automator`）、`env.js`（H5/Android/iOS/微信小程序四平台设备配置）、`pages/index/index.test.js`（唯一的 E2E 用例，断言首页三条文案），以及 `package.json` 里 4 个 `test:*` 脚本与 4 个对应 devDeps。

**范围**：`training-app/叉车维修培训学员端跨端应用/` 的**测试装配面与承诺该装配的文档**（`jest.config.js` / `env.js` / `pages/index/index.test.js` / `AGENTS.test.md` / `TESTING_GUIDE.md` / `package.json` / `package-lock.json` / `AGENTS.md` / `.github/workflows/ci.yml`）以及本 ADR。

**不含**：不动 `spec-永绿整改.md` 的裁决与 S1–S8 票（那是「验证层整改」的 spec，本 ADR 只清退它的**遗留装配**，唯 §③ 反例行加一句注记以免悬空）；不动 ①②③④ 门的触发面与证据口径；不动 `utils/**` 的任何测试；不动业务代码。

## ② 选型 + 一句理由

| 决策 | 一句话理由 |
| --- | --- |
| **① 清退整套装配，不做「只删平台段」的最小清理** | 删 `h5` 段而留 `app-plus` / `mp-weixin` 段，等于留下一个**必然失败**的配置（机制见附·B）—— 半死状态正是本 ADR 要消灭的东西 |
| **② 删除两份教程文件，不改成「已废弃」注记** | 它们的**全部内容**都在教一个不存在的通道；spec §③ 已判「写进文档靠自律」无效 ⇒ 保留即制造第二次误导 |
| **③ 一并移除 4 个 devDeps 并重生成 `package-lock.json`** | `@dcloudio/uni-automator@2.0.0` 在 npm 上已带 `deprecated: error version`（ADR-0008 §6 记录）；`cross-env` / `puppeteer` 只被那 4 个脚本引用 ⇒ 留着就是「审计面上声称有这个能力」 |
| **④ `test` 脚本保留，改为等价 `test:unit`** | 全仓口径与 `AGENTS.md` 的历史习惯都是敲 `npm test`；直接删会得到一个「missing script」的**新**坑，而这一行不带任何死依赖 |
| **⑤ 保留 `jest` 与 `jest-environment-node`** | `jest.config.unit.js` 的 `testEnvironment: 'node'` 需要后者；③ 门（`npm run test:unit`）是全仓必检，不能碰 |
| **⑥ 同步改 `ci.yml` 的 puppeteer 跳过段** | 依赖移出后那段 env 与注释成了死代码，且它解释的是一个**已不存在**的下载行为 |
| **⑦ 把「将来要重启」写成配方（本 ADR 附 C）而不是留配置** | 重启需要的信息（插件名与版本、CLI 命令、**精确版本握手**、adb 不在 PATH、uni-app x 该用哪个基座）记在 ADR 里比留在配置里更安全 —— 配置会腐烂，ADR 带日期与判据 |

## ③ 明确不做的事

- **不重开 E2E 通道裁决**（spec §② 已裁决：微信小程序只能 page 级断言、不能做流程验证；PR #1136）。
- **不激活 uni-automator**：不补装依赖、不跑 `cli.exe uniapp.test`、不跑真机/模拟器、不跑 ④ 编译门。
- **不把「单元测试补强」改名叫 E2E**（spec §③ 的命名纪律），**也不新增任何 E2E 门**。
- **不删 `docs/verification/**` 里的历史日志**（含 `1027` 那四份出现 `puppeteer-download-host` warn 的 run 记录）：那是**记录**，从改动集里删它等于篡改证据（`docs/agents/multi-agent-git.md` 开头对同类「历史/现测事实」有明文）。
- **不手改 `package-lock.json`**（由 npm 重生成）。
- **不动 `pages.json` / `manifest.json` / `platformConfig.json`**（运行时面 / 打包面判据来源）。
- **不动 spec 的 ①–⑥ 与票表**；只在其 §③ 的反例行加一句「该文件已由 ADR-0020 删除」。

## ④ 拆分步骤

**一步**（本 ADR 与清退同 PR —— 决策与被决策的动作应当同批可复核）：

1. 新增本 ADR；`AGENTS.md` 的「## 测试约定」整段改成**指向本 ADR 的指针 + 现行真实入口**（`npm run test:unit`）。
2. 删 `jest.config.js`、`env.js`、`pages/index/index.test.js`、`AGENTS.test.md`、`TESTING_GUIDE.md`。
3. `package.json`：删 `test:h5` / `test:android` / `test:ios` / `test:mp-weixin`；`test` 改为等价 `test:unit`；删 `@dcloudio/uni-automator` / `@dcloudio/uni-cli-shared` / `cross-env` / `puppeteer`。
4. `npm install --package-lock-only` 重生成 lock → `npm ci` 证明可装 → `npm run test:unit` 全绿。
5. `ci.yml` 的 `mobile-test`：删 puppeteer 两行 env 与那句注释，步骤名更正。
6. 校正 `AGENTS.md` 的其余同源模板残留：`npm run type-check`（**本项目没有这个脚本**）、「发布流程」第 2 条（「单元测试 + E2E 测试全绿」）、「## 相关文档」里停在 `0001`-`0006` 的 ADR 清单。

**无票号**：本改动无对应 issue（会话内裁定）；**但它是 spec §② 裁决的落锁**，故在 ⑥ 里挂上该 spec 以便追溯。

## ⑤ 约束（不能动的）

- ③ 门的**语义与载体不动**：`npm run test:unit`（`jest.config.unit.js`，node 环境，扫 `utils/**`）仍是唯一入口，CI 的 `mobile-test` 仍跑它、仍被 `ci-summary` 断言。
- 清退后**不得留下任何指向已删文件的引用**（例外只有两处：`docs/verification/**` 的历史产物、`spec-永绿整改.md` §③ 那处**已加注记**的反例行）。
- 改动集**不得命中运行时面**（`*.uvue` / `*.uts` / 三份 json）—— 命中即须按 ADR-0008 走四门，本 ADR 的验收口径随之作废。
- 未来若重启该通道，**必须先把附 C 里那三条环境前提现测一遍**，不得按记忆照做。

## ⑥ 验收标准

1. **可装**：`npm ci` 在清退后的 `package.json` + 新 lock 上成功（证明 ②③ 自洽）。
2. **不红**：`npm run test:unit` 全绿；`mobile-test` 仍是 `ci-summary` 的 `needs` 之一。
3. **零悬空引用**：`git grep -e uni-automator -e UNI_PLATFORM -e cross-env -e puppeteer` 在已跟踪文件里的命中只剩**本 ADR**、`docs/adr/0008` 的实测记录、`spec-永绿整改.md` 的历史反例行、以及 `docs/verification/**` 的历史 run 日志。
4. **级别判定不退化**：`npm run dev:finish:dry` 对本次改动集判 🟢 `quick`（工具链/测试改动，未命中运行时面）。
5. **CI 真跑一次**：分支 push 后 `ci-summary` 绿（`mobile-test` 不得因缺 puppeteer 而红）。
6. **可追溯**：PR 正文的 `## 验收证据` 段写 `免（未命中运行时面）`（先例 #908），并注明本 ADR 承接 `spec-永绿整改.md` §②。

### B. 版本握手这个坑（为什么「把路径填对」也不够）

`@dcloudio/uni-automator` 启动时读产物侧的 `.automator/<platform>.json`，并**要求其 `version` 与自身 `package.json` 的 `version` 精确相等**（不相等的分支直接判不可用）。产物由 **HBuilderX 树内**的编译器版本写入，而项目 `jest.config.js` 的 `testEnvironment` 会**优先解析项目本地**的那份（2.0.0）⇒ 即使路径与设备都填对，这一步**仍然对不上**。**这是「配置齐全」表象下的必然失败点**，也是本 ADR 不采用「只填占位」方案的根本原因。

### C. 重启配方（若将来真要重启，按此现测一遍）

1. 前提三条**逐条现测**：插件在位（`plugins\hbuilderx-for-uniapp-test`）→ 项目本地 `@dcloudio/*` 与 HBuilderX 树内版本**对齐、或让解析走到树内** → adb 挂进 PATH 或显式 `--device_id`。
2. 用 HBuilderX 侧入口创建测试环境（「初始化测试环境」），让插件补齐**配对版本**的运行时与 `env.js` / `jest.config.js`；**不要**照抄本 ADR 清退掉的旧配置。
3. CLI 跑测：`cli.exe uniapp.test app-android --project <项目> [--device_id <id>] [--testcaseFile pages/index/index.test.js]`（平台名另有 `mp-weixin` / `web-chrome`）。
4. **判成败必须解析 stdout**：HBuilderX CLI 失败时**退出码恒为 0**（仓内 `hx-run.ps1` 已实测钉死）。
5. **预期回报很低**（这是本 ADR 不做的直接依据）：`docs/adr/0008` 的 2026-09-18 修订已用专用探针实测 —— `mp.reLaunch` / `mp.navigateTo` **恒 `Uncaught [object Object]`**，`page.$('view')` 与**不存在的 class 同样超时**（类选择器与标签选择器**都**不可用）⇒ **元素级与导航级断言在本机组合下都不可用**，而这恰恰是 E2E 唯一能提供的东西。
