# 0027 - 分页列表模块：页面列表装载协议的单点实现

**状态**：已接受（2026-09-27；来源：architecture review 的 K1 候选 → grilling 逐项定案 → PR1 落地。
落锁见 ⑥，实施记录见文末）

> **一句话**：本仓有 **20 个页面 + 2 个 composable** 各写一遍同一段分页装载协议，且已经分叉出
> 三种终止算法、四种失败标记、且只有两页手写过「丢弃过期响应」。本 ADR 把它收成一个模块
> （`composables/usePagedList.uts`），并记下四条边界：**生命周期留壳层**、**模块不吃后端信封**、
> **`hasMore` 由调用方给 + 空批次兜底**、**代际守卫内置**。

## ① 目标与范围

协议本体（现状逐页手写）：

```
if (loading) return → 归 1 → noMore 短路 → loading=true → try
  → 替换或 concat → 重算终止（len>=total | items<pageSize | page<pages）→ catch（toast / 标志）
```

分叉面（实测）：终止算法 3 种（`pages/courses/courses.uvue:183`、`pages/jobs/job-list.uvue:165`、
`pages/search/search.uvue:200-202`）；失败标记 4 个名字 2 种类型（`loadError` boolean / `loadError` string /
`failed` / `loadFailed`）；只有 `pages/search/search.uvue:211` 与 `pages/points/points-detail.uvue:200-229`
手写了丢弃过期响应。

范围：模块本体、两个样板页迁移（`courses` / `job-list`）、行为守护与棘轮、声明表与词条。
**范围外**：列表空态/失败态的样式与组件（review K6）、多分区页（`search` / `personal-activity`）、
`api` 层的信封归一（review K3）。

## ② 选型 + 一句理由

| 决策点 | 取值 | 理由 |
| --- | --- | --- |
| 模块边界 | **只出状态与动作**：无模板、不注册 uni 生命周期、不碰 `uni.*` | 「composable 不注册 uni 生命周期」是既有约定（`pages/register/composables/useRegisterForm.uts:8-10`、`ADR-0007:153`），且 19 个分页页的触发面是**模板绑定** `@scrolltolower`（`pages/forum/forum.uvue:38`），本来就不该由模块持有 |
| 取数形状 | `fetchPage(page) => Promise<{ items, hasMore }>`，**模块不吃信封** | 数组键名（`items`/`records`/`materials`/`courses`）与分页字段各域不统一，`types/job.uts:42-45` 连 `page_size` 都没有 ⇒ 认信封是 api 层的账 |
| `pageSize` | **不进接口**，调用方在自己闭包里带着 | 它只影响「取哪一页」，不影响协议状态机；现状命名还分 `pageSize` / `PAGE_SIZE` 两种 |
| `hasMore` | **调用方给**；兜底：批次 `items` 为空 ⇒ 强制假 | 终止条件现有三种算法，模块不猜；兜底防「调用方漏判 ⇒ 死循环」 |
| 失败 | `failed = true`，**保留 `items`、不动 `hasMore`** | 兑现 `ADR-0007:217`「失败必须在页面可见」+ #816 的「失败态与空态分开」；重试即 `loadFirst()` |
| 代际守卫 | **内置**（`loadFirst` 换代；过期响应不写任何状态） | 此前面只有两页手写过它；切筛选后旧响应覆盖新数据是散在各页的隐患 |
| 泛型 | `usePagedList<T>` 返回 `UsePagedListResult<T>` | 页面拿到强类型数组（`Ref<T[]>`），不必退化成 `any`（规则 Q 禁 `ref<any>`）；仓内无泛型 composable 先例 ⇒ 以 ④ 编译门验证 |
| 本地增删 | **不归模块**：只有新批次到达才更新 `hasMore` | 旧写法 `len >= total` 正是被本地删除打歪的那一种（`pages/profile/favorites.uvue:182-189`） |

## ③ 明确不做的事

- 不引 Pinia、不做全局 store（ADR-0002）。
- 不做通用列表组件 / 空态组件 / 失败态组件（K6 的范围，且「重构与 UI 分时」）。
- 不迁 `useTopicFeed.uts` 与 `useTopicDetail.uts`：前者留着当**第三个**样板（内部改委托，forum 的 tab→query 映射留它自己），后者是页数制 + id 去重的另一形态，另票再看。
- 不给模块加 `remove` / `adjustTotal` 之类动作（见 ②「本地增删」）。
- **不设豁免 allowlist**：ADR-0023 决策⑧ / #654 已把守护豁免机制整体退役。
- 不改变任何页面的视觉（PR2 只在 `job-list` 补一个此前缺失的可见失败态）。

## ⑤ 约束

- 形态：结果类型显式声明 + 每个函数成员**箭头包裹**（ADR-0007:240-256，`utils/utsAndroidCompile.test.js`
  规则 U/T 在守）；模块内状态用扁平 `ref`（模块 composable 家族 12/12）；只用花括号 `import`/`export`
  （`utils/utsHarness.js:63-89` 对不支持形态 fail-closed）。
- 滚动容器与 `@scrolltolower` 绑在页面，不得搬进模块（`utils/uvuePageScrollContract.test.js`，#1134 血账）。
- 文件归属：`composables/usePagedList.uts` 登记进 `utils/modules.js` 的 `INFRA.files`（跨切面基础设施，
  与 `api/request.uts` 同类；双向对账在 `utils/modulesDeclarationContract.test.js`）。

## ⑥ 验收标准

- **③（本 ADR 的承重证据）**：`utils/pagedListBehavior.test.js` 用 `utsHarness.loadUts` **真执行**模块，
  并含**成对取证**（必不红对照组 + 三条必红变异：拆代际守卫 / 拆空批次兜底 / 拆重入守卫的 `loading` 半）。
- **棘轮**：`utils/pagedListAdoptionContract.test.js` 两向对账 —— 手写载体（页码游标 + 取数函数）
  计数必须**恰好等于**常量；判据的定义处（模块本体）显式排除，先例 `internal/credentialscope` 的
  `DefinitionFile`。它是**接线守护**，不构成 ③ 证据。
- **分类器下界**：`utils/guardClassification.test.js` 的 `BEHAVIOR_MIN` / `TOTAL_MIN` 上调到本次实测
  （13/99 → **35/138**）。
- **④**：本地编译门证 Kotlin 可编译性（泛型形态的唯一判据；`utsHarness` 只证 JS 行为，ADR-0017:59）。
- **①②**：PR2 起随页面改动照四门。

## 实施记录（PR1，2026-09-27）

- **已落地**：模块本体（泛型形态）、行为守护（19 用例，含 4 组成对取证）、棘轮（基线 22 现测）、
  `utils/modules.js` 的 `INFRA.files` 登记、`utils/guardClassification.test.js` 下界上调、`CONTEXT.md` 词条。
- **③ 实测**：`npx jest --config jest.config.unit.js -i utils/pagedListBehavior.test.js utils/pagedListAdoptionContract.test.js`
  → 2 suites / 19 passed；全量 ③ 门 `npm run test:unit` → **138 suites / 2677 tests 全绿**；
  分类器现测 `total=138 behavior=35 wiring=103`（新行为守护被正确归类，棘轮带载体引用 ⇒ H3/H4 不受影响）。
- **④ 实测（泛型形态已证）**：`npm run build:kotlin-all` → `KOTLIN_ALL_RESULT errors=0 classes=1505 files=120 freshness=fresh`。
  泛型形态的判据是**导出面里真的出现了它**（`open class PagedBatch<T>` / `fun <T> usePagedList(...): UsePagedListResult<T>`），
  不是只看 ✅。
- **一次「绿了但没覆盖」的教训（必记）**：第一次 ④c 判 ✅（`errors=0 classes=1502`）时**没有任何页面 import 本模块**，
  而导出面是 Kotlin **全程序**包（composable 被内联进消费页）⇒ 那次的读数**根本没编译到 usePagedList**。
  之后用一次性 spike（临时把 `pages/jobs/job-list.uvue` 接上 `usePagedList<JobPosting>`）才拿到覆盖当次改动的读数，
  spike 已回退（`git checkout --`，不进 PR）。这与 #1272 记的「旧导出被当成本次读数」是同一族：
  **绿必须问一句「这个读数覆盖了当次改动吗」**。
  同轮另有一次 `publish-no-success-marker` 判红而 `freshness=fresh`（脚本自陈属 #1285 的采集层/文案方向），
  按脚本给的第一条处置（HBuilderX 忙/未就绪，重试）重跑即绿。
- **残留（如实登记）**：PR1 合并后模块仍**无消费方**（首次 import 在 PR2）⇒ 它在合并态下的 ④ 覆盖从 PR2 起生效；
  PR1 交付的是「形态已被真编译证过 + 行为与棘轮已落锁」。
- **④-1 的门口径实测（新发现，下次开工先看这条）**：本 ADR 原按「改动只有 `.uts` / 测试 / 文档 ⇒ 低风险运行时面，免 ①②」
  预估，**实测被 `utils/modules.js` 一行击穿** —— 低风险判定是**逐文件**的（`pr-evidence.yml:119-130`
  的 `LOW_RISK_NON_RUNTIME`），而新增源文件**必须**登记进 `utils/modules.js`（普通 `.js`，不在白名单）
  ⇒ **任何「新增源文件」的 PR 都自动失去免 ①② 的资格**，低风险豁免实际只覆盖「改动既有 `.uts` 逻辑」。
  本次因此改走常规运行时面：①a（`device-capture.ps1` 只读取证，`DEVICE_CAPTURE_RESULT=PASS`）+
  ②（`mp-weixin-check.ps1` 半自动门，`errorsTotal=0 exceptionsTotal=0`）。**两次自动入库都因主树存在
  别的会话的未跟踪目录（`.qoder/` / `wt-*`）而被跳过**（脚本的脏树判据是 `git status --porcelain`），
  截图按脚本自己的预算（宽 ≤720、JPEG q75、≤150KB）手动压缩入库到 `docs/verification/device/1338/`。
