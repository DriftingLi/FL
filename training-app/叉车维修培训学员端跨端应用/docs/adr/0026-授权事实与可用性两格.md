# 0026 - 授权事实与可用性两格：缺席式可选键的落点、不进词表、不互顶

**状态**：已接受（前半 2026-09-23 / 后半 2026-09-24；来源：#1267 前后两半的实现期裁决 —— 根 `ADR-0062`
第十四波把 `company_disabled` 放上交换申请 DTO，第十五波第④批 `ADR-0064` 决策 5 回填到简历卡（后端 PR #1298）；
落地：**#1267 一个 PR 收完两半**）

> **一句话**：「授权**在不在**」与「明文**能不能用**」是两格事实，移动端此前只有第一格有落点。
> 本 ADR 记下第二格的落点选择（读取层归一 + 行级附加说明 + 三个消费面），以及四条**否决**：
> 不新增状态词、不在客户端重推服务端事实、不降级徽章、不把「停用」与「注销」拆成两层。

## ① 目标与范围

后端在**两个位置**发同一个缺席式可选键（`json:"company_disabled,omitempty"`，出现即恒 `true`）：

- 交换申请 DTO：`contact_service.go:80`，唯一赋值点 `:212-219` 是 `approved && !contactPairUsable`
- 简历卡 DTO：`recruit_service.go:75`（#1298 补发），填在 `fillContactStates` 里

它表达的是：**该企业账号已被禁用（处置动作）或已注销 ⇒ 授权记录还在，但联系方式明文已收回**。

两处赋值点形状相同（`companyUnavailable && state == approved`，卡面在 `recruit_service.go:101-108`；
**列表与详情卡走同一个装配点** —— 详情侧是 `GetForRecruiter:243-255`，故详情页那一支的判据是真键不是推断）
⇒ **「已授权 + 已停用」是合法组合，不是矛盾**；反过来，卡面这一格**只在已有授权记录的卡片上**才可能为真，
「从没授权」的那张卡两个键都不发。后端刻意把「查不动」折成 `false`（`:112-118`）——把 DB 故障报成
一条处置事实，比少说一格更坏；移动端照此把「键缺席」读成**无此态**（不说这一格），
而不是读成「企业已被核查过且可用」那种更强的结论。

票面的两处判据，一处随 #1298 成立、一处至今仍成立（写进 `api/recruit.uts` 的注释，不在代码里留假前提）：

- ✅ 简历卡带它 —— 列表角标旁边那一格从此有**自己的**判据，**不**再拿「我发起的 pending 列表」做旁路
- ❌ 明文端点不带它 —— `GET /recruit/resumes/:id/contact` 的 200 体是 `ContactPlainDTO`
  （`contact_service.go:101-107`，无此字段），失败时是三态 403（`backend/internal/api/contact.go:98-140`），
  其「企业自身被停用」那一支的文本就是 `ErrCompanyUnavailable`（`contact_service.go:31`）

范围：读取层（`api/recruit.uts`）、展示判定单点（`utils/recruitDisplay.uts`）、**三个消费面**
（交换段列表行 `contacts.uvue` / 简历卡面 `resumes.uvue` / 详情明文区 `resume-detail.uvue`）。不动后端、不动 Web。

## ② 选型 + 一句理由

| 决策点 | 取值 | 理由 |
| --- | --- | --- |
| 归一层 | **读取层**在**两处边界**逐字同一个形状 `(obj['company_disabled'] as boolean) ?? false`，消费面只判真值 | 缺席是**常态**不是「未知」；归一一次胜过每个消费面各写一遍。先例形状 = `forced_offline`（同文件）。同一个键在两处折成两种形状，就是在暗示它们可能不等价 |
| 呈现形态 | **行级附加说明**（三个面各多一行文本），不是徽章、不是第六种状态 | 徽章那一格挂的是 `ContactGrantState` 五态之一；把「可用性」塞进状态轴 = 让「已同意」与「企业已停用」抢同一个槽 |
| 判定条件 | **只认 `company_disabled` 的真值**，不叠 `status` / `contact_state` | 后端赋值点已是 `approved && !usable`；客户端重推一遍就是把服务端事实换成客户端推断（两个事实来源），且后端哪天放宽赋值点，这层推断会**静默吃掉**新事实 |
| 明文区两种成因 | 停用那一支**优先**说「已收回」，未授权那一支才说「需授权」 | 两者都为真时说「需学员授权」是错的：授权明明在。分开说才不留「拿一种成因盖另一种」的缝 |
| 与有效期的关系 | **两格不互顶**：`剩 N 天` 说时间，收回说明说可用性，同时成立时两行都在 | 用「已过期」盖「已收回」或反之，都是把一格的事实挪去填另一格 |

## ③ 明确不做的事

- **不给状态词表加第 6 行**，也不改任何 `label`。三把「两端同源」锁（取值集合 == 后端 Go 常量表、
  label 逐字 == Web `contactRequestStatus.ts`、消费面 `.tag-<status>` 齐全）只覆盖**状态轴**；
  加行会同时踩破前两把，而那两把是 ADR-0018 的承重件。`company_disabled` 不是 `ContactGrantState` 的取值。
- **不给收回态任何操作入口**（#705：看起来能用、用了必失败的入口比没有入口更贵）——后半把这条从
  「列表不给按钮」扩展到**详情页连「发起交换」入口也不给**：企业已停用时发起必失败。
- **不降级徽章**：角标仍只按 `contact_state` 投影。把 `company_disabled` 喂进徽章会把「被禁用」与
  「从没授权」压回同一个值 —— 那正是根 `ADR-0064` 决策 5 要避免的「两格塌成一格」。
- **不区分「注销」与「禁用」两种成因**：后端一句 `ErrCompanyUnavailable` 覆盖两者，客户端不反推、不分层。
  移动端不为此另开契约（同一句话在两端就是同一个事实，分层需要后端先给具名区分）。
- **不改徽章配色**：配色仍由各消费面的静态 class 承担，说明行走自己的 class（`.row-notice` /
  `.company-notice` / `.contact-notice`，三处同色 `#E5484D`）。

## ⑤ 约束与代价

- **措辞债已还**：前半记的「靠票面记账兜」已换成一把真锁 ——`recruitWorkspaceContract.test.js` 的
  「对照③」**现读** Web 的 `companyAvailability()` label 与后端 `ErrCompanyUnavailable` 首句逐字对账。
  代价是**三端锁步**：任何一方改词，移动端这侧就红，必须三端一起改（这正是「同键同措辞」要的）。
- **一处事实三处渲染** ⇒ 页面只做投影：全仓单点扫描（任何 `.uvue` / `.uts` 内联那句裸串即红）
  与「模板不直调 import 函数」两条共同承担。多出来的成本是给每个面写一个薄包装。
- **今天是潜伏态**：后端在 #1265 给的现测是「生产 3 条 approved 全指存活企业」⇒ 这三行真机上
  暂时不会出现。因此 ①a 取证**必然**要用夹具（本地临时强制该键为 `true` 后编译，产物不入仓、
  代码不提交），并按 ADR-0008 的手法补遗第 4 条**披露夹具**；三个消费面各出一张图。
- **窗口语义**：该键只在吊销生效窗口内（根 `ADR-0060`）与「禁用后仍存活的授权」这一交叉里有意义，
  别把它当审计面或历史面来读。
- 缺席式键的代价：契约测试里 `company_disabled: false` 那条断言守的是「后端**从不**发 false，
  但万一发了也不得折成 true」—— 它不是对现状的描述，是对映射层方向的约束。

## ⑥ 验收标准

- [x] 键缺席 / 为 `false` ⇒ 三个面零附加说明（不给装饰性提示）
- [x] 键为 `true` ⇒ 交换段行、列表卡、详情明文区各出该行，且 `status` / `contact_state` 取任何值都不改变它
- [x] 详情明文区「已收回」优先于「未授权」，且该支**无**「发起交换」入口
- [x] 徽章仍只按 `contact_state` 投影（那条链不认识 `company_disabled`）
- [x] 三把状态词同源锁保持绿（词表 5 行未变、label 未变）+ 对照③ 与 Web / 后端首句逐字相等
- [ ] 真机 ①a：正常态无回归；夹具态三行均可见，文本可被 `uiautomator` 的 `content-desc` 逐字核到
