# 0011 - 一键完成（dev:finish）的并发与失败语义

> 状态：已生效 ｜ 2026-09-14 ｜ 来源：PR #978/#989 暴露的假绿 + 用户裁定的 Q-2/A-3/Q3
> **职责边界**：裁定 `dev:finish` 工具链在**并发会话**下的锁纪律与**失败语义**；不动验收门本身（见 `0008-移动端验收门与证据.md`），不动 UI。

**① 目标与范围**：把「编译 → 部署 → 截图 → 证据」的判定做成**不可能假绿**；并让多会话并发只**排队**、不互相破坏。

**② 选型 + 一句理由**

- **quick 拆成 Q-A / Q-B 两档（2026-09-14 修正，原「quick = 编译诊断」的前提被实测推翻）**：**默认 Q-A 静态守护**（契约测试；**秒级、不取锁、不占设备**），要编译诊断须**显式 `-Compile`** ⇒ Q-B（`hx-run -CompileOnly`）—— 实测 Q-B 在冷/失效缓存下 **>901 秒**，**比真运行（4–5 分钟）还慢**，把编译塞进默认 quick 等于谎称「快速」；Q-A 必须**明说「未做编译诊断」**（不是静默跳过，这正是旧口径被废止的原因）。
- **部署判定复用 `hx-run.ps1`**（解析其 `HX_RUN` / `HX_RUN_DEPLOY` 机检行）—— 真运行路径已实测，**重复实现正是第一版假绿的来源**。
- **A-3 一个临界区覆盖步骤 4–6** —— 部署与截图共享设备状态，分次持锁会被别的会话插进来换页（截到别人的页面）。
- **锁交接**（`$env:HX_LOCK_OWNER` + PID 比对）—— 锁按 PID 判定且**不可重入**，父持锁再调子脚本会**自死锁**；交接是唯一不必改写共享库语义就能连跑的办法。
- **截图只截改动页**（git diff 推导 + `-Pages`，`-MaxPages` 兜底）—— 每页一次 launch 都要过一遍 HBuilderX，50 页全量不可接受。

**③ 明确不做的事**：不改 `hx-busy` 锁的**时间线**（仍 30 分钟陈旧可抢占；#974 只在它**之前**追加「持有者已死即陈旧」，见 ④）；不动 `0008` 的四门与证据格式；不做 GUI 热刷新的自动化（秒级那条路仍在人手）；不做多设备并行（真机自动化本质受 HBuilderX 单实例约束）。

**④ 拆分步骤**（可并行项已标）：`hx-busy` 加交接（H10/H11）→ 之后的五项**互不依赖彼此产出**、仅共享 `hx-busy`：`build-deploy` 改调 hx-run（B4–B14）｜ `test-compile` 的 Q-A/Q-B 分档（T3/T8/T10-T12）｜ `auto-screenshot` 限范围（S8–S12）｜ `dev-finish` 包临界区（F6–F11）｜ `env-check` 加 Q-A 轻量检查（E9）｜ `level-detect` 空 diff 崩溃修复 + **行为级守护 G1–G3**（2026-09-14 补）｜ `hx-busy` 陈旧判据加「持有者已死」+ `hx-deploy` 最短部署观察窗（#974，H12 / C14 / 运行期 B1–B4）。

**⑤ 约束**：HBuilderX **单实例串行，绝不 kill/绝不抢占**；锁超时一律 `exit 2`；**只有真需要 HBuilderX 的路径才取锁**（Q-A 取了锁就白等，秒级定位即失效）；结论字段（`$deployed` 等）**默认 false**，只有拿到证据才置真；契约测试断言的是**源码文本**，故被守护的字面量**不得出现在注释里**（本仓已多次踩中「注释命中断言」）；`hx-run` 自身默认 `-TimeoutSeconds 900` 对冷态偏短 ⇒ 调用方**必须显式透传**（本工具链默认 1800）。

**compile-only 成本实测（2026-09-14 两次取数，48 页工程）**：**热缓存 257 秒**（紧接上一次成功编译、无源码改动，落在旧口径 205–261 秒内 ✅ 复现）；**冷 / 上次被打断后 826 秒**（另有更早一次跑到 901 秒被超时切断、仍在编译）。两者差 **3.2 倍** —— 这组数字是 Q-A/Q-B 分档的依据。

**⑥ 验收标准**：12 套件 **106** 用例全绿（#974 起把 `hxRun` 与 `hxTimingBehavior` 纳入 Q-A，守护 T13 —— 守护若 `dev:finish` 永不执行就等于空跑）；锁交接有**行为验证**（带 env ⇒ `result=inherited`；无 env ⇒ `result=timeout` + `exit 2`）；**Q-A 路径不取锁、不要求设备与主程序**（守护 E9 / F10）；无改动页时 `TargetPages=0` 且**不回退全量**；真实并发表现为**排队**（`HX_BUSY wait=…`）而非假失败；`dev:finish` 任一失败路径都经 `finally` 释放锁并清 env。

**关键分支必须有运行期守护（2026-09-14 补，G1–G3）**：`level-detect` 的**空 diff**（干净工作树）分支曾在 `Set-StrictMode -Latest` 下崩溃 —— `$allFiles = @(...) | Select-Object -Unique` 的 `@()` 只包住了前面的相加、**没包住管道**，空 diff 时管道零输出 ⇒ 变量为 `$null` ⇒ `$allFiles.Count` 抛「The property 'Count' cannot be found on this object」，`dev:finish` 在步骤 1 即 `exit 1`。**8 条源码文本断言（L1–L8）全部无法发现它**：L8「空 diff → quick」只断言文件里出现过 `无改动文件（空 diff）` 这一**字符串字面量**，分支从未被执行。⇒ 纪律：**「出现某字面量」≠「该分支可执行」**；`dev:finish` 自身路径上的关键分支（尤其 catch / 空集 / 默认值分支）除文本断言外**必须补运行期断言**（先例 `utils/levelDetectBehavior.test.js` G1–G3：实际调 pwsh 执行 `Get-DetectLevel`，**pwsh 不可用时 fail-closed 抛错、不 skip**）。同类先例：`hx-run.ps1` 注释「调用点必须包 `@(...)`」。**#974 的两个缺陷同理**：`Test-HxLockStale` 只看 mtime（持有会话已被强杀仍要白等到 30 分钟）、部署判定在首个采样就下结论（资源落盘比推送晚 7–21 秒 ⇒ 误判未部署，白重跑一轮编译）—— 两处文本断言都是「绿」的，因为**判据本身判错**。故补 `utils/hxTimingBehavior.test.js`（B1–B4：死/活 pid 各判一次；fake 采样「第 N 次才前进」仍必须 PASS），并把 `hxRun` 与 `hxTimingBehavior` 纳入 Q-A。
