## 3. 字节抽样：损坏类别定性

判据本体 `lib/evidence-encoding.mjs:47-67`：先测「字节是否合法 UTF-8」→ 不合法=B1；合法则数 U+FFFD（>0=B2）、再数乱码码位（≥3=A）。ffd/moji 是**字节层判定**，不猜来源，来源靠下面的上下文与 git 交叉。

### 3.1 test-behavior-changed.log = B2，且 FFFD 是「子进程 cp936 被误读」的产物，不是块边界切断

`node -e` 只读抽样：629,319 字节里 107 个 `EF BF BD`，**成簇**（相邻 hit 间隔 ≤6 的聚成 ~17 簇，首簇 @298810 起连续）。取 `Stop-GateStage ` 之后到行尾的原始字节做 GBK 回环：

```
raw hex:  ef bf bd ef bf bd ce b4 ef bf bd d5 b6 ce a3 ef bf bd ... cb bd ... ca be ...
as-GBK:   "锟斤拷未锟秸段（锟斤拷退锟斤拷示锟斤拷锟斤拷锟斤拷 Start 未 Stop 锟斤拷"
gate-stages.ps1:51 真串:  "无未闭段（早退揭示：断在已 Start 未 Stop 的段，或从未 Start）"
```

`EF BF BD EF BF BD` 连排再按 GBK 解出「**锟斤拷**」= 教科书级「UTF-8 的替换字符序列又被当 GBK 读了一次」的双解码签名；`ce b4→未`、`53 74 61 72 74→Start` 等半 ASCII 半乱。同一段紧邻的 `D:\FL\training-app\叉车维修…` 路径里，`e6 b3 b5→泵`、`ce ac→¬`、`d1 b5→ѵ`（西里尔）= 「**GBK 字节恰好也凑成合法 UTF-8**」的错字（不计 moji 码位表），只有非凑对的部分落成 U+FFFD ⇒ 净结果 ffd=107 / moji=0 ⇒ 判 B2。

结论：坏字节**在进 `Read-Utf8Chunk` 之前就已烤入**——是「UTF-8 内容里混了 cp936 误读的产物」，与 #2139 修的「同一 buffer 块边界把多字节序列切断」**不是同型**（块边界 FFFD 会散落在临时文件读取边界、且源若是纯 UTF-8 不会出「锟斤拷」双解码签名）。

### 3.2 t2164-gate.log = B1，原始 GBK 字节直落盘

`node -e` 只读抽样：46,113 字节，`TextDecoder('utf-8',{fatal:true})` **抛**（validUtf8=false），检出 5614 组 GBK 双字节序列。首个 GBK 对起点的上下文按 **GBK 解码完全可读**：

## 7. 与「存量不救、判据只打新产出」口径的关系

- **哪些是 #2139 没覆盖的漏网路径**：`test-behavior-changed.log`（③ 门测试**内部子进程** cp936 误读，B2）与 `t2164-gate*`（**bash 控制台重定向**，B1）。两者都不在 #2139 射程 —— 前者在「dev-finish 自身增量 reader 之下、再往上一层的 jest 探针」，后者**根本不经 PowerShell 采集层**。#2139 的题眼是「把无状态 `UTF8.GetString` 换成按块留前缀的 `Read-Utf8Chunk`」，只治**块边界切断**这一种 FFFD；它治不了「字节在上游就已 cp936 误读」和「重定向抄控制台原始字节」。
- **哪些疑似修复后新引入**：**编码损坏没有一例是 #2139 引入的回归** —— §3.1 的 FFFD 是双解码签名（锟斤拷），与 #2139 修的块边界切断不同型；§3.2 的 B1 绕开了改过的采集层。唯一「修复引入」的是 `373e5f90`（#2175）修的 `$PSScriptRoot` 加载回归，属加载/执行问题、与编码正交、且已在 11-01 修掉。故本文对「修复后仍损坏」的定性是：**旧漏网面在修复后继续产出**，不是新 bug 被修出来。
- **与口径的关系**：`preflight-pr` 的判据 `check-evidence-encoding.mjs --since-branch-point`（`:26/80-92`）只对本次新产出（`mtime ≥ merge-base(HEAD, master)`）判红、存量按 `skippedStale` 豁免。这套口径**能**兜住 §4 里 11-01/11-02 的新产出（只要有人在自己分支上跑预检，`test-behavior-changed.log`/`t2164-*` 会被点名判红），**但它只判「可解码性」、不改采集** ⇒ 上游两条漏网路径（测试子进程、手工 bash 重定向）会**持续**产出坏文件，每次都得靠各分支跑判据时当场发现。换句话说：判据是「发现网」不是「止血钳」——#2139 止的是**块边界**这一种血，本文坐实的**子进程码页**与**控制台重定向**这两处口子仍需各自的采集修复（见 §6 最小修复点）才谈得上止血；在此之前，口径的正确反应是「让预检红，逼产出方换 UTF-8 采集」，而非指望判据替生产者修好。
