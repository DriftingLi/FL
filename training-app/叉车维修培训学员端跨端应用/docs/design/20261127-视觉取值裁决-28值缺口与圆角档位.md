## 2. 裁决判据（第一性）

1. **token 承载的是语义角色，不是色板来源。** 一个值来自 Element / Ant / Material 只说明它从哪个组件抄来，不说明它该有一席之地。反例是 `#409EFF`——它是 Element 主色，但在这套界面里扮演的就是「主色文字」，所以它该映射 `$primary-color`，不该立 `$element-primary`。
2. **同角色已有 token ⇒ 映射，不立新 token。** 28 值的角色全部落在既有 token 的射程内（主/成功/警示/危险/文字三级/边框三档/页面底/浅主底/浅灰底），所以**新增色 token = 0**。这与 #2352 立 `$text-strong` 是两种情形：那次是「角色存在、token 缺位」，这次是「token 都在、只是没被接上」。
3. **立新 token 等于给色板背书。** 给 4 个 Element 值、4 个 Ant 值、3 个 Material 值各立 token，之后每次换色都要同时维护 4 套色板；而映射只改 21 处声明位，收口后色板只剩一套。**收敛的收益正好在「不立」这一侧。**
4. **纯装饰（渐变 / 徽章 / 图标底 / 浅蓝钮）不进 token。** 这类色不承载状态语义，进 token 会让「改一个 token 影响一个内容色」成为假契约；按其固有做法进白名单，逐值写承载与「为什么不立」。
5. **圆角一档 = 一种承载语义，值只在一张表里。** 原有 38 种写法里一大半是「半高写成字面量」（胶囊按钮写 `44rpx`、方形头像写 `48rpx`），它们与 `999rpx` / `50%` 几何等价——定档后归并是零视觉的，不需要重设计。

## 4. 圆角定档（8 档）

档位表与归并规则的真源是 `docs/ui-spec.md` §3，这里只记裁决理由与增量：

- **新增 2 个 token**（值全部取自存量字面量，属 #2863 的「值面有真实消费 ⇒ 接上」形态，不是空档）：`$radius-xs 4rpx`（2/3/5/6rpx 的非半高承载，档内合计 39 处）、`$radius-base 12rpx`（10/11/12rpx 的归处，12rpx 单项 66 处主承载）。两个 token 本轮引用数为 0，属 §1.8 记过的「先立档、后归并」过渡态，P3 归并时自然接上——**这是有意的，不是空 token**。
- **不立「整圆」档**：`50%`（8 处）与 `999rpx` 对宽高相等的容器几何等价，`$uni-border-radius-circle` 已是框架内建值（px、不参加业务 token 对账）——再立 `$radius-circle` 就是第三个整圆写法，故方形头像 / 图标容器统一按规则 1 归 `$radius-pill`。
- **不新增大档**：26/28/33/36/40/44/48/50/53/54/58rpx 实测 12 种值 103 处，承载多为按钮 / 头像 / 胶囊标签，即「半高或方形」；是否真是半高由 P3 按承载件高度现场判，本票不逐处断言。
- **不反转既有裁定**：`$radius-lg` 24rpx（#1597 C2）、`$radius-xl` 32rpx、`$radius-pill` 999rpx、`$radius-card` 20rpx（#2509 R2）全部保持；`$radius-card` 与 `$radius-md` 的边界按「整卡 vs 卡内件」写进 §3。
- **归并是判断类**：同一字面量在不同承载件上可落不同档（规则 1 优先于规则 2），属真机观测项；本票只给规则，不建断言、不改页面。
