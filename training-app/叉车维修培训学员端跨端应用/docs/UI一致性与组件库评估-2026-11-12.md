# 移动端 UI 一致性与组件库兼容性评估

> 对应 issue：#2436
> 调研日期：2026-11-12
> 取证基线：**origin/master = 30a38a4c**（#2431 招聘端 9 页切出主包后）。本地 master 落后 9 个提交，主树另有他人未提交改动，本报告全部结论以 `git show origin/master:<path>` / `git grep origin/master` 为准。
> 性质：只读调研，未改任何已跟踪文件、未构建、未启动 HBuilderX / 微信开发者工具。

---

## 一、结论速览

1. **8 个 `app-*` 组件里只有 1 个真正活着。** `app-nav-bar` 被 52 处引用（页头事实标准）；`app-empty-state` 4 处（2 个文件）；其余 6 件（`app-badge` / `app-button` / `app-card` / `app-chip` / `app-list-item` / `app-tabs`）**全仓 0 引用**。其中 5 件自身 `<style>` 缺 `lang="scss"`、4 件引用了 `uni.scss` 里不存在的变量名 —— 即使现在去引用，样式也会**静默失效**（uvue 不报错、整段声明被丢弃）。
2. **零引用的机制性原因是 `pages.json` 没有 easycom 配置**（全文无 `easycom` 键），所有组件必须逐页手写 import。组件「存在但没人用」不是审美问题，是接入成本问题。
3. **一致性最大的缺口不是「缺组件」，是「token 真空区」。** 41 / 112 份 `pages/**/*.uvue` 用裸 `<style>`（无 `lang="scss"`），全部落在 `pages/*/components/` 子组件目录；这 41 份 token 引用数为 **0**、裸 hex 合计约 **490 处**。全仓裸 hex：pages 1793 处 + components 244 处，token 引用仅 644 处。
4. **主色迁移在页面上没生效。** `uni.scss` 已把主色定为 `#239EDD`（#1603），但页面与组件里旧主色 `#2979ff` 仍残留 **218 处**，新主色仅 **11 处**。改 token 定义 ≠ 改页面。
5. **组件库选型：只有 1 个候选真正兼容 uni-app x。** `uni-ui x`（DCloud 官方，为 uni-app x 全新设计）**兼容**；`uView Pro X`（第三方 UTS+UCSS）**兼容但付费 + 1.1MB**；`uview-plus` **未验证**（无官方 uni-app x 落地文档）；`wot-design-uni` **不兼容**（官方 2024-08 明确回复「还不支持」，此后无支持性讨论）；经典 `uni-ui` **不兼容蒸汽模式**（选项式 API）。
6. **裁定建议：复用现有组件 + 补 easycom，不引入第三方库。** 理由：唯一兼容的官方库 `uni-ui x` 恰好**没有**本项目最缺的 card / button / empty-state / list-item / tag（官方升级映射表对这些逐项标注「无」，并原文建议「让 AI 直接写相关 UI 比下载学习一个组件更合适」）；而唯一功能对得上的 `uView Pro X` 要付费、1.1MB、且默认主色 `#2979ff` 与本仓旧主色同值，接入即引入一次全量换肤。真正卡住一致性的 218 处旧主色 + 41 份裸 style + 无 easycom，**换库一样要还**。

## 四、屏幕适配风险

### 4.1 好的部分（无需动）

- **写死 px 尺寸 = 0**。`(width|height|min-width|max-width|min-height): <n>px` 在 pages + components 命中 **0 处**。pages 内 `rpx` 出现 3667 次、`px` 仅 34 次，且 34 次全是 `border: 1px solid #xxx` 发丝线或注释里的换算说明（如 `pages/ai-assistant/ai-assistant.uvue:726-727,754` 注释「4 列格宽 19% ≈ 71px」）。
- **安全区覆盖无缺口**。`utils/system.uts` 里 `DEFAULT_STATUS_BAR_HEIGHT = 44`（全站唯一回退值，#1602 消除 44/20 两派）、`useSafeArea(): Ref<SafeAreaInfo>`（`statusBarHeight` / `capsuleLeft` / `rightSlotWidth`）。MP-WEIXIN 走 `uni.getMenuButtonBoundingClientRect()`，`pxToRpx = v * 750 / win.windowWidth`，`rightSlotWidth = Math.max(0, 750 - capsuleLeft)`；H5 `sbh = 0`；`#ifndef APP-ANDROID` 才挂 `uni.onWindowResize`（App 端无该 API，Kotlin unresolved）。
  - 直接调用面仅 4 页，全是 N06 无页头白名单页：`pages/index/index.uvue:56,60`、`pages/login/login.uvue:166,171`、`pages/profile-setup/profile-setup.uvue:45,50`、`pages/search/search.uvue:121,129`；另有 `components/app-nav-bar/app-nav-bar.uvue`、`components/ai-chat/ai-chat-nav.uvue` 内部调用。**有页头的页面靠页头件吃安全区，无页头页自己吃**，逻辑闭合。
- **布局骨架统一**：`getSystemInfoSync().windowHeight` 51 处 / 53 文件；`width: 100%` 32 处；`flex: 1` 236 处。

### 4.2 风险点

| 风险 | 证据 | 小屏（SE 375pt）/ 大屏（Pro Max 430pt）表现 |
| --- | --- | --- |
| **长文本无截断** | 全 pages 仅 2 处 `numberOfLines`、28 处 `text-overflow` | 岗位名 / 课程名 / 用户名超长时撑破卡片或换行挤压布局；rpx 等比缩放不解决「字数」问题，两种屏都会溢出 |
| **固定宽度弹层** | `pages/forum/components/forum-report-dialog.uvue:61` `width:600rpx`、`pages/jobs/job-detail.uvue:485` `width:600rpx`、`pages/profile/components/info-dialog.uvue:64` `width:600rpx`、`pages/recruiter/components/recruiter-filter-drawer.uvue:258` `width:620rpx` | 600rpx = 屏宽 80%，两档屏都安全（SE 300pt / Pro Max 344pt）。**不构成风险**，但 620rpx 抽屉已到 82.7%，再加宽会顶到边 |
| **固定高度区块** | `pages/featured/featured-list.uvue:200,208` `height:300rpx`、`pages/courses/components/course-cover-section.uvue:51` `height:280rpx`、`pages/forum/components/forum-markdown-input.uvue:327` `height:400rpx` | 高度固定 + 内部文字不截断 ⇒ 小屏上文字被裁、大屏上留白过多 |
| **触摸目标偏小** | 见 P2 #8 | 28px 高的发帖按钮在两种屏上都不达 44pt 建议值 |

> 结论：**屏幕适配本身不是主要矛盾**（px 零写死、安全区闭合、rpx 全覆盖）。真正的适配风险来自「长文本不截断 + 固定高度容器」这一组合，而它恰好是「手搓 UI 各写一遍」的副产品 —— 收编组件时顺手解决，比单独做适配专项划算。

### 为什么「基于 web CSS 的库」在 uvue 上基本不可用

官方 <https://doc.dcloud.net.cn/uni-app-x/css/> 原文：「uni-app x 在 app平台实现了 web css 的子集」「仅支持 flex 布局和绝对定位」「选择器只能用 class 选择器，不能用 tag、#id、[attr] 等选择器」「样式不继承」；CSS 属性白名单里**没有 gap / grid / float**。

本仓 `docs/agents/uvue-css.md` 的红线进一步收窄（引用时引小节名）：

- 选择器：class ✅、group ✅；descendant ⚠️（有性能损耗，Vapor 不支持）、child `>` ⚠️、adjacent `+` ⚠️；**tag ❌、ID ❌、伪类/伪元素 ❌、属性选择器 ❌**
- 不支持属性：`gap`/`row-gap`/`column-gap`、`text-decoration`、`calc()` + `env()`、`vh`/`vw`、`align-items: baseline`、`max-height: 百分比`、**`var(--xxx)`（原生端不支持 CSS 变量）**、`currentColor`、`display: grid`、**`transition` / `animation`（原生端不支持 CSS 动画）**
- 文字类样式（font-size / color / text-align / font-weight）只能落 `<text>`/`<button>`/`<input>`/`<textarea>`（font-weight 另多 `<loading>`），否则渲染层判错并忽略，真机日志原文 ``style property `font-size|color` is only supported on `<text>|<button>|<input>|<textarea>`. there is an error on `<view class="mode-tab">` ``；机检 `utils/uvueFontCarrierContract.test.js`
- `<view>` 默认 `display:flex; flex-direction:column`，横排必须显式 `flex-direction: row`（反例：`app-nav-bar` 的 `.nav-bar-right` 在 #2410 前没 row，2 个以上图标竖排）

> 这解释了为什么「换库」在本项目不是「装个包」：任何依赖 CSS 变量、伪类、tag 选择器、gap、transition 的库，在 App 端要么编译报错、要么**静默不生效**（WARNING 不阻断）。

## 八、对「复用现有组件 vs 引入库」的裁定建议

**建议：复用现有组件，补齐接入机制，不引入第三方库。**

支撑理由（按权重）：

1. **唯一兼容的官方库补不上缺口。** `uni-ui x` 的 21 个组件里没有 card / button / empty-state / list-item / tag —— 而这 5 类正是本仓手搓最严重的（`.empty-tip` 组在 18 页各写一遍、`.job-card`/`.course-card`/`.product-item` 各写一遍）。官方升级映射表对这些逐项标注「无」，并原文写「标记为 无 的，大多比较简单，让AI直接写相关UI比下载学习一个组件更合适」。
2. **唯一功能对得上的库代价高。** `uView Pro X` 要付费（9.90 / 99.00 元）、插件包 1.1MB、加密版不能直接 `@import` 主题、默认主色 `#2979ff` 与本仓旧主色同值 —— 接入即触发一次全量换肤，等于把 P1 #4 的 218 处旧主色问题换个地方重做。
3. **换库不解决真正的病根。** 218 处旧主色、41 份裸 `<style>`、无 easycom、850 处裸字号 —— 这四项与「用谁的组件」正交。换库后这些页面照样是裸 hex、照样没有 easycom。
4. **现有 `app-nav-bar` 已经证明「自建 + 收编」这条路走得通。** 52 处引用、289 行、内部吃安全区、胶囊让位、标题脱流居中（#2402）、右槽让位（#1592）、88rpx 触摸目标 —— 这是全仓最成熟的 UI 件，且是自建的。

**建议的推进顺序**（供后续拆票参考，不在本报告执行）：

1. **批 0（机制层，收益最高）**：`pages.json` 加 easycom 规则（`^app-(.*)` → `@/components/app-$1/app-$1.uvue`）；给 5 件缺 `lang="scss"` 的组件补上；修 4 处变量名。
2. **批 1（token 真空区）**：41 份 `pages/*/components/*.uvue` 的裸 `<style>` 补 `lang="scss"`，裸 hex 换 token。这是 490 处裸 hex 的集中地。
3. **批 2（主色迁移）**：218 处 `#2979ff` → `$primary-color`。
4. **批 3（收编手搓件）**：按 ui-spec §11 的批次走，优先 `.empty-tip` 组（18 页）→ 卡片（25 文件）→ chips → tabs → 按钮。
5. **批 4（长文本）**：给卡片标题类补 `numberOfLines` / `text-overflow`，与批 3 同批做。

> 若后续仍要评估引入库，唯一值得再看的候选是 `uni-ui x`（2.1KB、官方、兼容），但应定位为「补 `uni-icons` / `uni-forms` / `uni-data-checkbox` 这类本仓确实没有的件」，而不是替换现有 `app-*` 体系。
