# ADR-0025：招聘链路——职位发布与投递即授权

> 编号说明：`docs/adr/` 下存在**两个 ADR-0022**（「问答积分直记与招聘角色隔离」与「真题套卷模型与全池隔离」），本 ADR 因此从 **0025** 起编号，避免后人继续误引。

## 背景

企业招聘者此前**只能读**：在简历库里翻脱敏简历卡、发起联系方式交换。平台没有企业「我要招什么人」的表达面，导致：学员没有主动通道（只能被动等企业来翻）、企业的招聘意图无处落地（`contact_requests` 语义是「让我看到你的电话」，不含岗位诉求）、简历库与真实岗位错配（两侧共用培训域字典却没有任何「岗位」实体把它们对上）。

同时暴露一个既有粒度矛盾：词汇表说「同一企业对同一学员 pending 唯一、单企业日限 20」，代码却全按招聘者账号粒度实现——同一家企业两个 HR 各发一个重复职位、投了 HR1 之后 HR2 联系又得重新授权。

## 决策

1. **投递即授权，且授权仍只有联系方式交换这一个载体**。投递在学员点下那一刻，在同一事务内写入/复活一条 `approved` 的联系方式交换记录，用 `source` 区分「企业发起」（`recruiter`）与「投递产生」（`application`）。明文判定的既有实现（GetContact 查 `approved` 状态）一行不改。
2. **`visibility` 口径收窄**为「仅管控 L2 被动浏览面」。`hidden` 简历同样可投递——同一个学员可能简历库里搜不到、却出现在某企业自己职位的投递列表中。两条读路径的门禁条件不同。
3. **实时读 + 版本指针，不存简历快照**。投递记录只存「投递那一刻的简历更新时间」，内容永远读最新；企业端据此提示「收到投递后简历已更新」。与「简历卡改一次即最新、无快照」的既有决策一致。
4. **`recruiter` 账号与企业 1:1**。统一社会信用代码加唯一（`idx_recruiter_users_credit_code`），使「按招聘者账号」与「按企业」两种表述等价。本期不引入 `companies` 表——真到需要多个 HR 那天再拆，迁移路径清晰（账号拆分 + 职位/投递/授权按企业重挂）。
5. **职位必挂专业方向**（复用培训域 `specialty` 字典，业务层必填、库层可空——字典项删除置空不级联），另带自由文本职位名承担细化。职位名**不叫「岗位」**：本系统「岗位」已是专业方向的历史别名（术语登记见 CONTEXT.md，前端文案本期不改）。
6. **职位生命周期二态 `open`/`closed`**，另记首次发布时间用于新鲜度排序。不加草稿态、不加有效期自动过期、**不加招聘人数（headcount）**——砍掉录用就抽掉了「招满」的事实来源，headcount 会成为一个永远对不上的字段。
7. **投递三态 `applied`/`rejected`/`withdrawn`**，不发明「意向」这类无条款的中间态。学员侧的正反馈改用机器记录的 `employer_viewed_at`（已读是事实，不需要企业额外做动作，也不会被误读成承诺）。
8. **约束集**（与既有联系方式交换同一哲学）：同一学员对同一职位 `applied` 期间唯一（部分唯一索引，与 `pending` 唯一同构）；学员自行撤回可立即重投（他自己的犹豫不该罚）；被企业标记不合适后 30 天内不能再投（拒绝是有记忆的）；学员每日投递上限 10、单企业活跃职位上限 50（宽松值只防误操作）；投递不带自由附言（授权记录 message 用系统固定句式含职位名，保证审计可读）；投递产生的授权**不计入企业日限、不受冷却限制**（那是防企业骚扰的，学员主动投递不该消耗它）。
9. **撤回不连带**。撤回投递默认不动联系方式授权，授权的生命周期出口只有两个：学员显式撤回、学员注销。连带与否交给撤回弹窗里一个**默认不勾选**的选项——避免把「授权是否有效」变成需要 join 投递状态现算的推导。
10. **内容治理走先发后审**：学员可举报职位，管理员可带原因强制下架，被强制下架的职位企业**不能自行重新上架**。理由：邀约制的可信度本质是「可追责」（信用代码、经营范围、联系人都在册），而不是「内容必合规」；先审后发会把供给端活跃度掐死。举报用招聘域自己的存储（`job_reports`），不挂到论坛举报表上（那是论坛域的两列形状）。
11. **招聘者收不到站内信**（站内信收件人外键锁在学员表）。企业侧通知走邮件 + 列表内「新投递」计数徽标；同时把邮件发送器从「注入 nil、只写日志」修成真实通道，并把「生产 SMTP／开发降级日志／测试替身」的选择逻辑收成一个单点（`NewMailSender`），供验证码通道与招聘域共用——兑现「学员同意交换后邮件通知招聘方」这一从上线起就写在文档里的承诺。

## 备选与拒绝理由

- **投递自带明文权限（第二授权路径）**：会在 L3 上开出第二条授权路径，学员「撤回授权」的语义随之被击穿——撤回后通过投递路径仍能看见明文。选定方案让明文判定实现一行都不用改。
- **先审后发**：把供给端活跃度掐死；邀约制可信度本质是可追责而非内容必合规。
- **`companies` 表与多 HR 账号**：本期只有单一联系人需求，1:1 已够；拆表是等真出现多联系人需求后的清晰迁移。
- **简历快照**：与「简历卡改一次即最新、无快照」的既有决策冲突；需要锁时点的是承诺类事实（本期没有），不是简历实体。
- **headcount 与职位有效期**：砍掉录用后「招满」无事实来源，headcount 永远对不上；有效期自动过期是草稿态的另一面，都会制造与真实供给不一致的状态。
- **招聘者站内信**：收件人外键锁在学员表，改外键会让消息中心模型变脏；邮件 + 徽标已覆盖企业侧通知需求。
- **「意向」等中间态**：在没有承诺条款的前提下，「意向」几乎一定被读成「内定」；已读（`employer_viewed_at`）是事实，不会被误读。

## 后果

- 明文授权判定保持单路径（联系方式交换 `approved`），撤回/注销语义与既有实现一致。
- 三条新表（`job_postings`/`job_applications`/`job_reports`）+ `contact_requests.source` + 信用代码唯一索引，全部随迁移落地。
- 职位对未登录者整体不公开（L1 从简历延伸到职位），无 SEO 面。
- `job_applications` 冗余 `recruiter_id`（授权落地与企业维度查询都需要它，避免每次 join 职位）。
- 契约测试跑在 sqlite 上、不执行 SQL 迁移，部分唯一索引在生产由迁移保证、在测试由业务层判定保证（沿用既有 `pending` 唯一索引的同款双轨做法，测试注释已写明）。
