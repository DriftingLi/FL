# ADR-0095：站内信收件人身份空间——双可空外键 + 章节归属

- 状态：Accepted（2026-11-14）
- 日期：2026-11-14
- 领域：通知与审计 / 培训领域（章节归属）
- 票：#2537（实施）· 缺口来源 #2499（C10 投递面摘除）

## 背景

`notifications.user_id` 的外键是 `REFERENCES hrwai_users(id) ON DELETE CASCADE`（`backend/migrations/000001_baseline.up.sql:3313`），即这张表从建表起就把「收件人」钉死成**学员**一种身份。全仓 11 种既有通知（论坛互动、投稿全生命周期、资料审核、联系方式交换、积分扣罚等）确实都只发学员，这个假设一直没被挑战。

#2499 实现章节审核站内信（spec C10）时撞上了它：章节提交人是**讲师**，而讲师在 `tutor` 表（独立 identity），`hrwai_users` 里没有行。照现状写库的两种后果都是事故——`tutor_id` 与某个学员 id 撞号（两边都是自增小整数，几乎必然）则**通知投给无关学员**，章节名与课程名外泄；无该 id 则外键违约，**整笔审核事务回滚 500**。当时处置是摘除投递调用、只保留 typed event 构造器契约，把投递面转出到 #2537。

同时暴露出第二个、更根本的缺口：**本仓没有「章节属于哪个讲师」这个概念**。`chapter` 表与 `course` 表都没有 `tutor_id` 列（`000001_baseline.up.sql:203-254`），讲师 `GetCourses` 是 `OnlyMounted: true`（`backend/internal/tutor/service.go:42-47`）——任何讲师都能看到所有已挂载课程、编辑任何章节。唯一带讲师 id 的事实是 `chapter_content_slot.submitted_by`（`000054:14`），而它**只存在于 pending 槽**：管理员直接生效（C7）走 `publishWorkingCopy` 会把槽全删重建，`submitted_by` 落 0。

## 决策

**一、收件人身份空间用双可空外键，不用角色列、不拆表。**

```sql
ALTER TABLE notifications ALTER COLUMN user_id DROP NOT NULL;
ALTER TABLE notifications ADD COLUMN tutor_id INT REFERENCES tutor(tutor_id) ON DELETE CASCADE;
ALTER TABLE notifications ADD CONSTRAINT chk_notifications_recipient
    CHECK (num_nonnulls(user_id, tutor_id) = 1);
```

**二、章节获得稳定归属：`chapter.tutor_id INT NULL REFERENCES tutor(tutor_id) ON DELETE SET NULL`**，只在讲师侧写、**首次落定后不改**（讲师提交审核或编辑章节时若为 NULL 则落当前讲师 id，非 NULL 则不动；管理员写面不动归属）。

**三、`/api/notifications` 保持单端点，按 JWT role 分派查哪一列**；role 不在 `{hrwai_user, tutor}` 白名单时显式 403，不返回空列表。

**四、`ChapterReviewEvent` 的收件人字段改名 `TutorID`，写入走 `CreateForTutorWithTx`**；`CreateWithTx` 保留给学员面（11 处调用零改动）。

**五、审核结果通知走强一致族**（与状态流转同事务，失败回滚），沿积分扣罚先例。

## 被否备选

- **加 `recipient_role` 列 + 外键整个删掉**（#2537 票面原提议）：单列语义直白、未来角色扩展不用加列，但**学员侧 11 种通知会失去 DB 级外键与级联**。「通知投错人」从此只能靠代码纪律——而本票的存在恰恰证明代码纪律不足。用一列换掉两个外键的机器保证，是把 P0 的根因（单外键无法覆盖多身份）从「修好」退化成「绕开」。
- **拆独立 `tutor_notifications` 表**：每张表外键都干净，但读面/已读/未读/前端面板要两套实现，「站内信」这个领域概念被劈成两个；未来 admin 通知再加一张表。三张表会漂移成三个事实源。
- **`Recipient{Kind, ID}` 结构**：最显式，但 11 处既有事件全要改签名，收益与「字段改名 + 双外键」相同而成本大一个量级。等真出现第三种身份（admin 通知）时再升级。
- **C7 管理员直接生效不发通知**：严格贴合 spec C10 字面（「过审/驳回发站内信」），但 C7 是同一审核机制的第三条出口——漏掉它，讲师永远不知道自己章节被谁改过、working 草稿被覆盖，与「讲师通知中心」的目的相悖。
- **C7 通知收件人用 pending 槽的 `submitted_by`**：不改 schema 的捷径，但 C7 的典型场景恰恰是**没有 pending 槽**（管理员改的是已发布或草稿章节），这条路径基本永远不发。
- **迁移加 `recipient_role` 列并回填**：存量通知全是学员的，「`user_id` 非空、`tutor_id` 为空」这个既有形状**恰好就是新约束的合法形态**——迁移可以纯 DDL 零回填。加角色列等于多一个与「哪列非空」漂移的事实源。

## 后果

**收益**：①「通知不会投给学员」从测试纪律升级为 **DB 约束**（CHECK 在迁移完成瞬间生效，不需要回填、没有窗口期；判据 `backend/internal/api/notification_recipient_postgres_contract_test.go` 在真 PG 上验两面都拦）；②「章节属于谁」第一次有稳定事实源，C10 通知、未来的内容归属与「讲师只看自己课程」都靠它；③11 处既有学员写入路径零改动。

**代价**：①`user_id` 失去 `NOT NULL`，完整性由 `num_nonnulls` CHECK 承接（语义等价且更强，但读 DDL 的人要先理解这个函数）；②`chapter.tutor_id` 是**超出 #2537 票面**的 schema 变更，#2537 从「通知域改造」扩成「章节归属建模 + 通知域改造」；③存量章节 `tutor_id` 为 NULL，C7 通知对老内容仍发不出——但这是**如实**的「不知道作者是谁」，不是静默丢失；④`admin` / `recruiter` 角色调 `/api/notifications` 得 403（此前是查 `user_id` 返回空）——把「没有信箱」与「信箱是空的」区分开，是刻意的行为变更。

**读面单一事实源**：role→列的映射必须收敛在一个地方，不能散在 `List` / `UnreadCount` / `MarkRead` / `MarkAllRead` 四处各写一遍，否则就是第二事实源。实现落在 `RecipientForRole`（`backend/internal/notification/service.go`），四个读面统一收 `Recipient` 值类型。

**角色字面量与 core 常量的漂移防线**：`RecipientForRole` 内用字面量 `"hrwai_user"` / `"tutor"` 而非 `core.HrwaiRole` / `core.TutorRole`——`core → aiassistant → points → notification` 已间接依赖 notification 包，反向 import 会成环。一致性由**外部测试包** `backend/internal/notification/recipient_vocab_test.go`（`package notification_test`）钉住：它同时 import core 与 notification，断言两个 core 常量确实被接受。包内测试做不到这件事（会成环），写成包内就是同义反复的假绿。

**不跨列兜底**：`MarkRead` 只按当前角色对应的列收口。`user_id=5` 与 `tutor_id=5` 是两个不同的人（四张身份表各自自增，撞号几乎必然），任何「先查 user_id 再查 tutor_id」的兜底都会造成跨身份读写。`Recipient.column()` 对未知角色返回空串并报 `errInvalidRecipient`（fail-closed），不兜底到 `user_id`。

**C7 通知与发布同事务**：`publishWorkingCopyInTx` 是事务原语，`AdminService.UpdateChapter` 把它与 `notifyChapterAdminEdit` 包进同一个事务——通知写失败则发布回滚。这是决策五在 C7 这条路径上的落实（#2537 评审发现初版是两次独立提交，已修）。

**payload 携带来源标记**：C7 通知与普通过审共用 `chapter_review` 类型，payload 为 `{"review_status": "...", "source": "review"|"admin_edit"}`——决策七要求「payload 区分来源」，实现若只靠 title 文案区分，消费方就得读文案判事实，本仓一贯禁止。
