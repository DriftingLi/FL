# API 时间契约：业务时区墙钟 + 显式偏移

`formatISO`（全仓唯一的时间出参格式化函数，16+ 处调用）此前输出的是**裸 UTC**：`2026-09-11T12:16:52.203824`——转成了 UTC，却**不带任何时区标记**。而 `API.md` 一直写着「北京时区」。实现与文档不符，且没有任何客户端能正确解读这个字符串：

- **Web**（`new Date(iso)`）：ECMAScript 规定不带时区标记的日期时间按**本地时区**解析，于是东八区读到的是「UTC 墙钟当作北京墙钟」，恒早 8 小时。
- **移动端论坛**（`formatDateStr` / `formatDateTimeStr` 纯 `substring` 截取）：直接展示 UTC 墙钟，同样早 8 小时。移动端练习页 / 职位页另有 `new Date()` 解析，与 Web 同病。

两处表现一致地偏 8 小时，所以长期没被发现：列表里的**绝对日期**看起来完全合理（差 8 小时的两个日期只在跨日边界露馅），直到某处把它渲染成**相对时间**——新发的回复立刻显示「8 小时前」。

本次把契约明确为 **RFC 3339 + 业务时区（Asia/Shanghai）墙钟 + 显式 `+08:00` 偏移 + 微秒定长**，与 `API.md` 的既有表述对齐。

## Consequences

- **选业务时区而非 UTC**：移动端论坛按 `substring` 展示、不做任何时区换算，只有发出北京墙钟它才正确（这也正是 `API.md` 原本的措辞）。若改为 `UTC + Z`，Web 与移动端 `new Date()` 路径同样正确，但移动端论坛会继续差 8 小时——同一个产品里两种正确性，不如统一。
- **偏移恒定为 +08:00**（中国无夏令时，`clock.Location()` 单点定义于 `internal/clock`）。`student_service` 等多处按字符串**字典序**当时间序排序（如「最后学习时间倒序」）；偏移一旦逐值浮动，字典序即失效。固定偏移保持该性质，这也是本次能安全改动的关键。
- **跨日边界一并修正**：北京 07:00（= UTC 前一日 23:00）此前会显示成前一天的日期，现在落在当日。
- **对既有客户端的兼容性**：修复向后兼容——携带偏移是 RFC 3339 的合法形态，旧版本前端 bundle（只做 `new Date()`）与移动端（`substring`）都自动变正确，无需同步发版。这也意味着**不需要兼容窗口**。
- **移动端的残留口径**：移动端 `formatDateTimeStr` 展示的是北京墙钟而非设备本地时区；用户身在国外时会看到北京时间。这是既有行为，本次未改（要改需移动端自行做时区换算）。
- **时间字段一律经 `formatISO`**：不要在 DTO 里直接序列化 `time.Time`（会得到 Go 默认的 RFC3339Nano，与全仓格式不一致）。本次未新增约束，只是把已有惯例写明。

## Considered Options

- **UTC + `Z`**（`t.UTC().Format(... Z07:00)`）：API 语义最标准。拒绝——不修移动端论坛的 `substring` 路径，且与 `API.md` 既有表述相反，会让同一产品里出现两套时间语义。
- **仅仅在前端补偿**（`utils/format.ts` 检测无偏移则补 `Z`）：零后端改动、影响面最小。拒绝有两条：一是**已缓存的旧 bundle 仍会继续错**（补 `Z` 反而能让旧 bundle 自愈）；二是八个客户端的解析点各补一次，属于在消费侧反复兜生产的底。
- **移动端后续自行做时区换算、API 保持 UTC**：把正确性押在一个尚未上线的客户端上，且 Web 侧仍要依赖偏移。拒绝。
