# ADR-0023: 积分簿记收敛与幂等占坑

- 状态：已接受（2026-08-30）
- 领域：培训域 / 积分簿记（「流水直记」家族的写路径收敛；承接 ADR-0022-问答积分直记的家族语义）

## 背景

「流水直记」家族经积分基座（#354/#355）、课程直兑、真题兑换（ADR-0022）与问答采纳奖励（ADR-0022）四波落地后，同一套簿记配方（幂等键 → Redis SetNX → 先查后写 → 事务{流水 + 余额 + 封底 0} → 事务外重读余额）在 6 个公开入口被手写 10 遍：`Claim` / `RedeemCourse` / `RedeemRealPaper` / `RedeemShop` / `DeductAI` / `AdminPenalty`，加 `forum_service` 侧 `AcceptReply`×2 与 `rollbackAcceptedBonusTx`。无共享簿记核心；余额扣减 SQL 有 7 个变体、封底 0 有 4 种写法；forum 侧绕过 PointsService 裸操作 `PointsLedger` / `points_balance` 10+ 处。

复制漂移已产生两个实锤缺陷：

1. **RedeemShop 缺并发守卫**：`points_service.go:529` 缺少 `AND points_balance >= ?` 条件（`RedeemCourse:398` 与 `RedeemRealPaper:477` 均有），先查余额与扣减之间存在并发双花窗口，仅靠事务后 GREATEST 兜底。
2. **`Delta: 0` 违反 CHECK**：`forum_service.go:775` 在答主余额为 0 时写 `Delta: 0` 的 rollback 流水以充当「已处理」标记，而 `000002` 迁移定义 `delta INT NOT NULL CHECK (delta <> 0)`——该路径一旦走到，整笔删帖事务因约束违反而失败。

另：`points_ledger` 无幂等唯一约束，rollback 路径无 Redis 锁（两次并发删同一帖可双扣）；DeductAI / AdminPenalty 的 requestID 现场生成（`{uid}-{UnixNano}`），先查与 `isDuplicateError` 永不命中，幂等形同虚设。

## 决策

1. **缺陷随深化一次落地**：不单独开热修 PR，两个缺陷的修复并入簿记收敛同一 PR——改动同源，避免缺陷修复另等一个深化周期分叉（接受上线前的暴露窗口）。
2. **事务内簿记核心 `applyTx`**：PointsService 内单一实现，参数面 `{UserID, Delta, Reason, RefType, RefID, IdemKey, FloorZero}`；封底 0 单一写法；余额扣减一律带守卫；Redeem 三胞胎（Course / RealPaper / Shop）收敛为一个参数化实现，仅 sku / 价格来源 / reason / refType 不同。
3. **通用幂等占坑表 `points_entry_idem`**（`idem_key VARCHAR PRIMARY KEY, created_at`）：把 `points_task_claim` 的占坑先例推广到全部直记路径。「一事件一分」与回收 settle 传确定性键：`accepted_bonus:{topicID}`、`rollback:{topicID}`、`redeem:{ref}`；占坑冲突 = 已处理，整笔事务回滚。**`Delta: 0` 标记行消失——占坑行即标记**；`points_ledger` 表结构与 `CHECK (delta <> 0)` 一字不动。
4. **forum 收编**：ForumService 构造注入 PointsService，采纳奖励与违规回收经其事务内导出方法落账；依赖方向 forum→points 单向无环。`rollbackAcceptedBonusTx` 的幂等/封底逻辑上收为 `applyTx` 语义。
5. **键不可得的路径如实降级**：AI 扣费由调用方传稳定键（请求标识）；管理员罚分不传键（有意重复罚分合法，双击防抖留在 UI 层）。占坑键可选是 `applyTx` interface 的一部分，不强行全覆盖。
6. **读取路径不动**：`GetBalance` / `GetLedger` / `HasEntitlement` 已是深接口，无重复问题。

## 备选

- **ledger 部分唯一索引（reason 白名单）**：拒绝——只对「一事件恰好一行流水」的 reason 成立；余额为 0 的 settle 场景无行可写，幂等语义被劈成「流水行」与「settle 标记」两处。
- **抽中立 pointsbook package**：拒绝——当前消费者只有一族，deletion test 结论是平移而非深化；forum→points 单向依赖已足够。
- **不收编 forum、只深化 PointsService 六入口**：拒绝——10 处直写中 7 处在 forum 侧（含 rollback 双扣与 `Delta: 0` 缺陷本体），不收编则深化不完整。
- **独立热修 PR 先行**：拒绝——缺陷修复与簿记深化同源，用户决策接受窗口期、一次落地。

## 后果

- 一篇 migration（占坑表建表；`points_ledger` 与 `hrwai_users` 零结构变更）。
- PointsService 公开面：六入口签名不变；新增事务内导出方法族供 forum 调用；`forum_service` 中 ledger 直写与裸余额 SQL 全部删除。
- 回归断言三件：RedeemShop 并发双花、删帖时答主余额为 0 的回收路径（修复前整笔事务失败）、占坑幂等（同键二次提交整事务回滚）。
- 前端与 uni-app 契约无感（接口签名与响应形状不变）。
- 「流水直记」语义（ADR-0022）不变：深化的是写路径归属，不是记账模型——积分仍逐笔流水、reason/ref 自由文本、每帖只发一次采纳分的不变式原样保留。
