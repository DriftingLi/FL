# 打卡积分直记化与每日登录事实源迁移

打卡收益原走任务中心 `daily_checkin` 领取制（打卡只记录、5 分要点一下才到账），且路由寄生在论坛域（`/api/forum/check-in/*`）。本次把打卡剥离为独立激励模块：**打卡即直记入账**（每日基础 5 分 + 连击满 3/7/30 天当日额外 5/10/50，每连续段重新发，断签清零，跨档合并单笔，幂等键 `checkin:{uid}:{date}`），路由迁 `/api/check-in/*` 并**删除旧路径**，Web 端落地独立页面 `/training/check-in`（日历三态色块 + 逐日分数角标）。同时任务中心的每日打卡任务替换为**每日登录（daily_login）**，事实源为新增的每日登录日表（`(user_id, date)` 主键幂等），由**登录成功与 refresh 续期双入口**写入。

取舍与理由：双令牌体系（access 2h + refresh 7d，ADR-0016）下，「登录动作」不再是每日事件——常驻用户可能数周不重新登录，仅靠密码/验证码登录写表会让 daily_login 对真实活跃用户长期不可达；而 refresh 轮换是每天首次使用必然发生的、防伪的会话级事件，语义上等价「今日到访」，故一并落表。打卡放弃领取制是因为它本质是「行为→即时奖励」的连续激励，领取制把收益割到另一个页面、且任务中心每日限领一次无法表达连击阶梯。旧路由不做双挂过渡是有意选择：本仓库 Web 端是唯一在维护的前端消费方，uni-app-x 移动端尚未上线对齐，保留死路由只会让「打卡离开论坛域」在 URL 上说谎——移动端适配以 GitHub Issue 单独追踪。领取接口（Claim）本次补上与 GetTasks 同源的行为达成校验（ErrTaskNotDone 哨兵），堵住「未达成直接 POST 领取」的空领面——这同时是「完善资料/每日任务」进度口径可信的前提。

被否选项：首次登录才算 daily_login（活跃用户领不到，任务形同虚设）；任意认证请求算登录（每请求多一次 Redis，「登录」名不副实）；旧路由双挂过渡（拖延域解耦，移动端反正要按新契约改日历逐日分值）；阶梯奖终身只发一次（对老用户失去连续激励）。
