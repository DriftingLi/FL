# ADR-0093：诊断切流的不可逆点与「没有回滚开关」的取舍

- 状态：Accepted（2026-11-05）
- 日期：2026-11-05
- 领域：AI 域 / 外部服务接入 / 部署面（承接 ADR-0029 单 port、ADR-0032 传输通道、ADR-0048 SSE 不走信封、ADR-0091 图片白名单代理、ADR-0088 部署面）
- 票：地图 #2236 · 执行票 #2240（`wayfinder:task`）、前置 #2237 / #2242 / #2243 / #2244 / #2245
- 判据物：`deploy/docker-compose.prod.yml:203-209`（三行配置）、`.github/workflows/cd.yml`（secret 注入）、`backend/internal/config/config.go:664`（`validateDiagnosisV2`）、`backend/internal/aiassistant/diagnosis_proxy.go:79`（白名单）、`docs/design/2240-诊断切流-runbook.md`（执行口径）

## 背景

智能维修诊断（`fault_diagnosis`）在 2026-11-03 之前走的是**内部虚拟机上跑的外部服务**：pve-01 的 lxc101（内网 `:8000`）上跑 v1 交付包，通道是阻塞 JSON 伪流式，工程上包在 `/assistant/api/*` 后面。

#2237 把这条链路整个换掉：改成对方在阿里云 ECS 上部署的 v2（FastAPI + bge-m3 本地向量检索 + LLM），单轨 SSE（`POST /api/v2/chat`），v1 的代码路径、四个周边只读端点、`foldHistoryIntoQuery` 之外的兼容层**全部物理删除**（该函数为何保留见 ADR-0094）。

于是切流这件事有个与常规部署不同的形状：**没有 `legacy` 可回退**。这里需要先排除三个看起来像答案、实际都不是的东西：

1. **没有「上游开关」**。`grep -r "upstream\|legacy" backend/internal/aiassistant/` 的 11 处命中全是 HTTP 语义（解 `health` JSON、解子路径、测试里的 `"upstream boom"`），唯一像开关的 `config.go:433-444` 是 AI 模型配置回退，与本功能无关。票面 #2240 初稿写的「把上游开关设为 ecs / 改回 legacy」是它写于 2026-11-03、当时 #2237 还没落地造成的。
2. **配置本身**就是开关。`DIAGNOSIS_ASSISTANT_URL` 为空 ⇒ `NewDiagnosisAssistantModel` 返回的 adapter 在 `Stream` 第一行就回「智能维修诊断服务未配置，请联系管理员」（502）；非空且 `DIAGNOSIS_V2_API_KEY` 有效 ⇒ 走 v2。
3. **lxc101 不构成回滚通道**。它在 2026-11-04 停机、`onboot` 置 0；更重要的是 #2237 之后**没有任何代码路径指向它**（`grep -r '/assistant/api/' backend/` 零命中——代码里连地址都没有了，把机器拉起来也不会有流量过来）。停机前 7 天实测业务请求只有 13 条（11 条 chat + 2 条 fault-codes），都在 `2026-11-03T13:54:43Z` 之前。

## 决策

1. **不设回滚开关，回滚动作就是「清空两个 secret + 重新部署」**。理由：开关只有在「回退目标还活着」时才有意义，而这里回退目标已被物理删除。留一个指向死服务的开关比没有开关更危险——它让人以为按一下就安全了。回滚的真实代价必须被看见：一次 CD 部署的时间（实测 3~5 分钟），期间诊断功能 502，其他功能不受影响（`/diagnosis/health` 返 `{"ok":false,"app_configured":false}` 而不是 503，前端据此隐藏引导面而不是报错）。
2. **v1 物理删除而非开关化**，且这个选择在 #2237 就定了（PR #2265）。理由：两套通道并存意味着两套图片归一、两套错误语义、两套历史形状要长期维护；而 v1 的实际使用量（7 天 13 条）不足以支撑这份成本。删除的代价是切流不可逆——这正是本条 ADR 要记的事。
3. **不可逆点具体在「`gh secret set` 成功且 CD 部署完成」这一步**，不在写代码、不在合并 PR。在此之前随便回退（代码可 revert、分支可弃），在此之后唯一的回头路是重新实现 v1 或让对方重开旧实例。
4. **切流不是一次性动作，是七条前置 + 七节走查**。`docs/design/2240-诊断切流-runbook.md` 是执行口径：§0 前置（其中「传输加密」至今是 ⚠️ 明文 http）、§2 逐条实测（不接受「部署成功」当证据）、§3 历史兼容判据、§4 观察窗口至少一个工作日、§6 回滚演练必须真做一次。
5. **长答案的写超时必须单独拉长**（#2301）。`http.Server` 的 60 秒 `WriteTimeout` 是绝对截止时间，不是空闲超时；诊断链路的 `aiStreamTimeout` 是 300 秒。两者差 5 倍，表现是「上游成功、浏览器 network error、access 日志仍记 200」。`writeSSEHeaders` 里用 `http.NewResponseController` 把该连接拉到 300 秒，全局保护对其它端点不变。这条不是切流的附带修补，而是**切流后才可能暴露的既有缺陷**——v1 的阻塞通道从没跑过 60 秒以上。

## 后果

- **正面**：切流后诊断能力从「内部虚拟机上的一台机器」变成「对方托管的服务」，我方不再承担机器可用性；单轨 SSE 让首字延迟从整段等待变成逐段可见；配图经白名单代理收口（ADR-0091），第三方主机不再收到学员浏览器的请求。
- **负面 / 已接受的代价**：
  - 不可逆。出事后止损 = 一次 CD 部署（3~5 分钟），且回来的是「功能不可用」而不是「旧版本可用」。
  - 传输仍是**明文 http**（`http://<v2 主机>:8080`）。对方上 TLS 后只需把 `DIAGNOSIS_ASSISTANT_URL` 换成 `https://…` 再部署一次，代码侧零改动——但这个「只需」要等到对方真的上 TLS。
  - 单点依赖对方服务。对方限流（实测 300 次/分钟）我方如实转 429 并给中文文案，但不透传 `Retry-After`。
- **不做的事**：不写「自动切回」逻辑（没有可信的回退目标）；不在代码里保留 `if env == "legacy"` 分支（死代码比没有代码更贵）；不为切流单独做灰度（使用量基数太小，灰度只会拉长不可逆窗口）。

## 与票面 #2240 的差异

票面写于 2026-11-03，当时 #2237 未落地。三处措辞与代码事实不符，已在 2026-11-04 按实测改写（票面评论留痕）：第 1 步「上游开关设为 ecs」（无此开关，见决策 1）、第 3 步「旧会话来源折叠仍显示 manual 形状且能下载」（`DiagnosisSources.vue` 只回放文字、不产出 URL）、第 4 步「legacy 服务保留 30 天作回滚通道」（无代码路径，见决策 3）。
