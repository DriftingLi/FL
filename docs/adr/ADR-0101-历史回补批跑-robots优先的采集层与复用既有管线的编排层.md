# ADR-0101：历史回补批跑——robots 优先的采集层与复用既有管线的编排层

- **状态**：已接受
- **日期**：2026-11-20
- **领域**：拍卖数据管线 / 采集层
- **票**：#2677（父 spec #2671）

## 背景

spec #2671 把 rmfysszc 定为「零反爬、最佳发现入口」，一期要「一条命令完成 2015–2026 历史回补」。但执行时实测到两件与票面前提相冲突的事实：

1. **`www.rmfysszc.com` 已被劫持**——现在返回的是赌博站内容，不是拍卖网站。真实站点是 `www.rmfysszc.gov.cn`（最高法主管的公告聚合门户）。
2. **真实站点的 `robots.txt` 对 `User-agent: *` 是 `Disallow: /`（全站禁采）**，并且逐条列出了 Bytespider / Googlebot / 百度 / 搜狗等爬虫各自的 `Disallow: /`。仓库 #2664「挂牌采集合规边界」建立的判据框架里，「robots 明示禁止」= 不可采。

也就是说：**判据「诚实 UA」与「robots 禁止」不能同时满足**。诚实 UA 的代价正是「你被认出来时，对方已经明确说过不行」——伪装成浏览器去绕过，既违反 #2664 的判据，也让「诚实 UA」这条判据本身失去意义。

## 决策

**一、robots 优先，默认遵从；不遵从只能人工显式放行，且必须留审计。** 采集层启动时先读站点 `robots.txt` 并解析成对本 UA 生效的策略（具体 UA 段优先于 `*` 段、最长前缀胜、同长度 Allow 胜）。被禁则**拒绝抓取并抛错**，不是静默跳过、也不是静默放行。人工确需采集时显式传 `--allow-robots-override`，此时仍抓，但 `RobotsDecision.overridden=true` 并写进请求日志的 `robots_override` 状态——「绕过」是个可审计事实，不是被藏起来的分支。

**二、读不到 robots 时 fail-closed。** 网络错误 / 404 一律按「全站禁止」处理。空 robots 文本会被解析成「允许全部」，所以这条必须显式构造 `Disallow: /` 规则，不能靠 `parse_robots("")` 的默认值——「没读到」不等于「没有限制」。

**三、限速下限写死 2 秒，不可配置变小。** 判据是 ≤1 req/2s 的合规窗口，`RateLimiter(min_interval=...)` 传小于 2.0 直接 `ValueError`。时间来源可注入（假时钟），所以测试不真的等 2 秒——「测试可验证」与「不拖慢测试」不冲突。

**四、回补不另写一份管线。** 回补 = 「发现 URL 集合」×「对每个 URL 跑既有 batch 管线」。为此把 `run_batch` 的抽取→清洗→匹配→落库抽成 `_process_html(conn, html, ...)`，batch 与 backfill 共用同一段；回补只新增「发现层」（列表页 HTML → 公告条目）与「编排层」（年份过滤、幂等判重、逐个抓取、得率报告）。若回补另写一份，清洗/匹配逻辑必然漂移——这正是 spec #2671 反复强调的硬约束。

**五、幂等靠 `source_url` 判重，且已入库的详情页根本不再抓。** 判重集合来自 `SELECT DISTINCT source_url FROM market_transactions`；命中则跳过。这不只是「不重复落行」，也是「不重复请求」——幂等同时省流量，减少对站点的压力。

**六、得率报告记录为事实，不设门槛。** 报告输出各清洗状态计数、各剔除原因计数与占比、清洗得率（`cleaned / total`）；无样本时得率为 `None` 而不是 `0`（避免误读成「全废」）。#2662 已裁定清洗得率不设硬门槛，本票不新增任何 CI 判据或阈值检查。

**七、回补窗口 2015–2026，无日期公告丢弃。** 窗口来自 spec；无发布日期的公告无法归年，不进回补（宁可漏，不可把年份不明的样本混进时间序列）。

**八、robots 策略绑定 host，跨 host fail-closed。** robots.txt 按 host 生效（RFC 9309）——读自 `www` 的策略不能拿去放行 `www1` 的列表页。`RobotsPolicy` 记录来源 host，`decide()` 遇其它 host 一律按禁止处理；`load_robots` 从 `base_url` 的 netloc 绑定 host、读不到则 fail-closed。显式 override 仍可跨 host，但记 `robots_override` 审计。统一错误文案只留 `robots_denied_message()` 一处，client 复用 `ensure_allowed()`，不再两处手抄。

**九、每条 URL 一个独立事务，抓取在事务外。** 千条回补按 ≤1 req/2s 要跑约 1 小时——不能全程开着一个事务（idle-in-transaction / 锁），单条失败也不该回滚整轮已落的行。所以网络抓取在事务外，每条 URL 单独 `conn.transaction()`。关键细节：循环前的只读查询（配置/幂等 SELECT）在 psycopg 默认 autocommit=False 下已隐式开了一个事务，必须先 `commit()` 结束它，否则循环内的 `transaction()` 只是 savepoint，外层 rollback 仍会吞掉全部——这条有专门的回归测试钉住。

**十、跨 URL 去重信号逐条累积。** 清洗规则⑥（车商批量帖去重：图哈希/描述相似度/同公司跨城）需要看见同轮其它 URL 的样本。`_process_html` 返回本轮新增样本列表，回补逐条累积进 `stored_samples` 并作为下一条的 `existing_samples`——否则「同一车多城重发」因 URL 不同、精确判重抓不到，会被重复入库。

## 被否备选

- **按票面前提直接抓列表页，不读 robots**：与站点明示的 robots 冲突，且与 #2664 建立的判据框架矛盾。票面的「零反爬」是基于 `.com` 站点（已劫持）的旧事实，不能当作绕过 robots 的授权。
- **读不到 robots 就当没限制（fail-open）**：最省事的写法，但把「网络抖动」变成了「永久放开」。合规系统里 fail-open 是最不该有的默认。
- **限速间隔做成可配置且允许调小**：看起来更灵活，但等于把合规窗口变成运行参数；某次为了赶进度调成 0.1s 就再也不会调回来。
- **回补另写一条管线（复制抽取/清洗/匹配）**：能快速出活，但两份实现必然漂移，而漂移的后果是「同一批公告在 batch 和 backfill 下得出不同的标签」——下游校准无从判断该信哪份。
- **按发布年份在 SQL 里过滤，而非发现层过滤**：会让窗口外的公告也走完抓取 + 抽取 + 清洗 + 匹配才被丢弃，白花钱且白打扰站点。
- **得率报告设通过率门槛**：违反 #2662 的裁定（记录为事实、不设硬门槛）。一期语料规模小，任何门槛都只是噪声。

## 后果

**收益**：①采集行为落在可解释的合规窗口内——robots 遵从 + 诚实 UA + ≤1 req/2s + 指数退避，四条都可单测、可日志核验；②回补与 batch 共用同一段管线，标签口径只有一份；③幂等同时省请求，重跑安全；④得率报告让「这批数据值不值得用」可被事实性回答，而不是靠感觉；⑤抓取层可注入（`fetcher` seam），回补编排的全部测试都不碰网络。

**代价**：①在 robots 禁止的站点上，默认路径**抓不到任何东西**——这是设计意图，但意味着「一条命令完成历史回补」在合规默认下只对允许采集的站点成立；真实回补需要人工显式放行（或走商务渠道取得授权）。②`_process_html` 的抽取让 batch 从「一次解析一批」变成「逐样本追加去重信号」，语义上更严格（后续样本能去重到本批前面的样本），与原先「整批样本作为 existing」略有差异——batch 场景下两者等价（解析器一条公告只返回一条样本），回补场景下新语义更正确。③回补是串行的（受 ≤1 req/2s 约束，并发没有意义），千条量级预计耗时约 1 小时，属可接受的一次性成本。④幂等是应用层的（`source_url` 判重），原价表无 UNIQUE 约束——并发跑两个回补进程理论上可交错读-插导致重复落行；回补是一次性批跑、约定串行执行，故接受此边界。

**实施边界（本票不做）**：增量 daemon 与周更（#2678）、多平台采集面（京东/gpai/产权交易所）、LLM 抽取与清洗规则的任何改动、评估路径改动、管理端 UI。
