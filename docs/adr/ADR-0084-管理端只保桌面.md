# ADR-0084: 管理端只保桌面（最小 1280×720）

- 状态：Proposed（草案，待维护者签字）
- 日期：2026-10-26
- 关联：#1937（响应式盘点）；`docs/design/1937-响应式现状盘点.md`；ADR-0080（字号阶梯）；ADR-0086（宽表策略）

## 背景

管理端 23 个路由、197 处 `el-table`。2026-10-26 两轮实测（9 条路由 × 5 个宽度，Edge headless + CDP）的结论是**"不崩，但干不了活"**：

- **页面级横向溢出 0 例** —— 375px 下页面不崩；
- 表格页在 `≤1024` 就出现**表体内部横滚**：`/admin/hrwai-users` 375 下表体 **1230 / 319（3.9×）**、`/admin/profile-review` 810 / 301、`/admin/statistics` 660 / 271；
- 右侧固定「操作」列在 375 下压住内容，可见列只剩 ID / UID / 操作（`docs/verification/web/1937/admin-hrwai-users-375.png`）；
- 外壳在 `≤768` 折叠为图标条（`SidebarLayout` 的 `@media`）——**唯一成体系**的窄屏退化。

管理端的动作是"审 / 改 / 批量"，都依赖表格的横向上下文；3.9 倍横滚下完成这些动作不现实。

## 决策

**管理端只保桌面：最小支持宽度 1280×720。**

1. 管理端页面**不承诺** 1024 以下的可用性；375 / 768 只保证「不崩、可滚动」，不保证能完成业务动作；
2. **不为管理端新增任何 ≤768 的布局分支**；现有零散 `@media` 逐条复核——属于外壳折叠的保留，属于单页补丁的清理（另开票）；
3. 设计契约写明：管理端新页面的验收宽度是 **1280 / 1024** 两档；
4. 将来若确有手机端管理诉求，**另立 ADR**，不在本条内渐进放开。

## 理由

- **动作决定下限**：审核与批量操作要横向上下文，降到 375 后即使降列也不足以完成动作，等于"能看不能干"。
- **成本对比**：23 页逐一适配 375、平均每页 3–5 个断点分支，且表格降列还要另设卡片形态（见 ADR-0086）；收益只是"手机上能看"。
- **本条只是把既成事实写成契约**：现状已经是事实上的桌面优先，写明之后每个新页面不必重新纠结一次。

## 备选

- **全量适配 375**：成本高、业务动作仍不可完成，且与 197 处表格的降列改造叠加。
- **只保平板 768**：实测 `≤1024` 表格就已横滚，为这 128px 维护一整套断点不划算。
- **按页面分级**（列表页只保桌面、配置页适配手机）：分级标准会漂移，且当前没有任何手机端管理诉求。
- **加"请在桌面端打开"的强制提示**：提示不替代可用性，反而增加噪声；等真出现手机端误入再议。

## 后果

- 管理端新页面验收宽度 = 1280 / 1024；375 只作"不崩"冒烟。
- 现有 15 条零散 `@media` 要清理：外壳折叠相关保留，单页补丁逐条判定（另开票）。
- 与 ADR-0086 联动：既然管理端不承诺窄屏，"宽表降列"就不必为管理端做。

## 证据边界

量测只覆盖浅色主题、列表仅 1 行数据（饱满态未测）。若饱满态改变列宽与横滚倍率，本条的结论方向不变（只会更差，不会更好）。
