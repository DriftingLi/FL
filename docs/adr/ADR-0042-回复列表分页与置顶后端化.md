# 论坛回复列表改分页读取，置顶改由后端承载

`GET /api/forum/topics/:id` 一直把**全部回复一次性**查出返回（回复查询无 LIMIT），前端也全量渲染——热门帖会把整棵回复集塞进单次响应。本次改为**分页读取**：`page`/`page_size`（默认 20），响应补 `page`/`pages`/`total`，与列表接口同构。

连带必须一起改的是**置顶的承载方**：「被采纳回复恒置顶」（`CONTEXT.md` 论坛词条）此前的实现是 Web 前端派生——`ForumDetail.vue` 的 `sortedReplies` 把 `is_accepted` 的那条 splice 到首位。分页后前端只拿得到一页，这个派生**必然失效**：被采纳回复若排在第二页，置顶就没了。故置顶上升为**后端事实**：被采纳回复固定占**首页第一条**，并从排序结果中剔除（避免重复），首页容量相应变为 `page_size − 1`（无采纳回复时首页仍为 `page_size`）。这不是新增字段——`is_accepted` 已存在，语义即「首页第一条 + 该标记」。

置顶放首页还顺带关掉了一个深链缺口：采纳通知的 link 是 `/training/forum/:id#reply-{replyID}`（`notification_service.go`，`forum_accept_event_constructor_test.go` 断言），指向的正是被采纳回复。置顶占首页第一条后，该深链**恒命中首页**，Web 侧无需「循环加载直到命中」的兜底逻辑。

## Consequences

- **首页条数不再恒定**：有采纳回复时首页 = 1（置顶）+ 19（排序），其余页固定 20。任何「第 N 页 = offset N×page_size」的朴素实现都是错的。
- **置顶与排序是两条正交轴**：置顶**优先于** `sort`/`order`，其余回复照常按 `latest`/`hot` 排序分页。切排序维度重置到第 1 页（沿用列表页既有惯例）。
- **`reply_count` 口径不变**：仍是含楼中楼子树的回复总数，置顶那条计入其中；因此 `total` 与 `reply_count` 一致，列表页展示不受影响。
- **楼中楼维持扁平一层**：`parent_id` 只表达「回复了谁」，不构成折叠子树；详情接口在 `parent_name` 之外再 join 回填 `parent_avatar_url`，供「昵称 › 被回复人」带小头像的行内形态使用。**不引入两级折叠**（若要做得单独立项）。
- **移动端需同步适配**：uni-app x 的 `getForumTopicDetail` 直接消费顶层 `replies` 全量数组（`api/forum.uts`），改分页后只看得到首页。因移动端尚未上线，本项目**不留兼容窗口**、一次到位，移动端适配另立 Issue 交给该侧负责人（#850）。
- **旧的「详情返回全量」路径彻底退役**，不存在「不传参数 = 全量」的双语义参数。

## Considered Options

- **新增独立端点 `/api/forum/topics/:id/replies`，主接口保持全量**：零破坏、seam 干净，移动端与既有契约测试完全不受影响。拒绝原因有二：一是会留下**两条读路径**，而 `topic` 响应里的 `replies` 退化成「只有移动端在用」的冗余字段；二是「不传参数即全量」仍保留着把内存打爆的路径。移动端尚未上线，没有需要保护的线上调用方，兼容包袱不成立。
- **给主接口加双语义参数（不传 = 全量，传了 = 分页）**：改动最小，但同一参数两种语义，后续调用方极易误用，且全量路径仍在。拒绝。
- **放弃恒置顶，采纳回复只留「✓ 已采纳」标记、排其自然位置**：分页即纯排序，语义最简单。拒绝——「被采纳回复恒置顶」是已写入 `CONTEXT.md` 的领域约定，且采纳通知深链会因此要求用户点多次「加载更多」才能看到自己的答案。
- **置顶项独立成字段/接口（响应里单独回传 `accepted_reply`，与分页列表完全分离）**：语义最干净。拒绝——响应结构与两端消费形态都要改，改动面明显大于收益，而「首页第一条」已足以承载同一语义。
- **前端循环加载直到命中 hash 目标**：只在深链场景下补丁式解决置顶缺失。被后端置顶取代，不需要了。
