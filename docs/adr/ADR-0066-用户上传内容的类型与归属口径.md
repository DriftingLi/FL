# ADR-0066: 用户上传内容的类型与归属口径（一份类型表 / 静态投递分档 / 投稿附件按用户分区）

- 状态：已接受（2026-09-28，真实缺陷评审 grilling 定案）
- 领域：文件上传与静态投递 —— 上传白名单 / 静态资源响应头 / 投稿附件归属
- 来源：真实缺陷 #1（匿名 SVG ⇒ 存储型 XSS）与 #13（投稿附件归属），决策过程见同轮评审报告

## 背景

匿名上传端点（`POST /api/ai-assistant/upload-image`，`OptionalAuth`）接受 `svg`，而 `shouldCompressImage` 对 svg 返回 false ⇒ 原样入库；`/static/*` 由 `c.File` 按扩展名回 `image/svg+xml` 且无 `Content-Disposition`；前端 access/refresh 双令牌都在 `localStorage`。四段各自「按设计工作」，串起来是一条存储型 XSS 链：任何人上传一个带 script 的 SVG 拿到同源链接，受害者（含管理员）点开后脚本读走 `refresh_token`，再调 `/api/auth/refresh` 轮换出新令牌对（7 天窗口）。

同族的第二处：`POST /api/contributions` 完全信任客户端提交的 `file_url/file_name/file_size/content_type`，服务层只校验 size；且所有用户的暂存文件都落在同一个扁平前缀 `contributions/`——「归属」这件事在数据里根本不存在，上传端点的扩展名白名单与大小上限因此可被整个绕过。

## 决策

1. **可执行类型不入上传白名单**：`image` 白名单移除 `svg`（全仓无消费者、无文档依赖）；白名单与静态投递判据**读同一张类型表**，表内每项标 `safe` / `unsafe` / `unknown` 三档之一。
2. **静态投递分档**：`safe`（pdf / 图片 / 视频 / office）保持 inline（现状 + `X-Content-Type-Options: nosniff`）；`unsafe` 与 `unknown` 一律 `Content-Disposition: attachment` + `application/octet-stream`。判据落在后端 staticHandler 单点；nginx 的 `/static/` 只反代、不复制规则（避免两份名单漂移）。
3. **不做一刀切 attachment**：PDF 的内联预览是一等需求（`DocumentViewer.vue` 的 iframe 与新窗打开、投稿附件预览都依赖它），按类型分档而不是按前缀一刀切。
4. **存量已上传的 svg 不清理**：分档后它们落到 `unknown` ⇒ attachment + octet-stream，已不可执行；清理是数据操作且有误删风险，若要做另开数据票。
5. **投稿附件归属由路径承载**：暂存前缀按用户分区 `contributions/<uid>/`；创建投稿时校验四件事——前缀属于本人、扩展名在投稿白名单内、同一 URL 未被任何投稿登记过、文件真实存在。不引入暂存表。
6. **两条机器锁**：① 类型表不得出现可执行类型（svg / html / xml / xhtml / js…）；② 未识别扩展名必须回 attachment + octet-stream。新类型进表时被这两条锁逼着表态。

## 被否备选

- **一刀切 `/static/uploads` 全前缀 attachment**：实现最简，但 PDF 内联预览与新窗预览会退化成下载（功能降级）。
- **一刀切 + PDF 预览改 blob 取回**：语义干净，但改动从前端一个组件扩散到取回链，且大文件内存翻倍。
- **只改上传白名单、不做静态面**：掐掉已知注入源，但存量 svg 仍可执行，且下一个新扩展名即复发。
- **投稿附件改走「暂存行表 + 只认 id」或「上传票据」**：语义更正，但要新建表 / 票据基础设施与生命周期，与本轮「小改动收口」的规模不匹配。
- **只查前缀 `contributions/` 不判归属**：同前缀内他人的暂存文件仍可被冒名登记。
