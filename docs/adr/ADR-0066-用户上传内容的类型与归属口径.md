# ADR-0066: 用户上传内容的类型与归属口径（一份类型表 / 静态投递分档 / 投稿附件按用户分区）

- 状态：已接受（2026-09-28，真实缺陷评审 grilling 定案）
- 领域：文件上传与静态投递 —— 上传白名单 / 静态资源响应头 / 投稿附件归属
- 来源：真实缺陷 #1（匿名 SVG ⇒ 存储型 XSS）与 #13（投稿附件归属），决策过程见同轮评审报告

## 背景

匿名上传端点（`POST /api/ai-assistant/upload-image`，`OptionalAuth`）接受 `svg`，而 `shouldCompressImage` 对 svg 返回 false ⇒ 原样入库；`/static/*` 由 `c.File` 按扩展名回 `image/svg+xml` 且无 `Content-Disposition`；前端 access/refresh 双令牌都在 `localStorage`。四段各自「按设计工作」，串起来是一条存储型 XSS 链：任何人上传一个带 script 的 SVG 拿到同源链接，受害者（含管理员）点开后脚本读走 `refresh_token`，再调 `/api/auth/refresh` 轮换出新令牌对（7 天窗口）。

同族的第二处：`POST /api/contributions` 完全信任客户端提交的 `file_url/file_name/file_size/content_type`，服务层只校验 size；且所有用户的暂存文件都落在同一个扁平前缀 `contributions/`——「归属」这件事在数据里根本不存在，上传端点的扩展名白名单与大小上限因此可被整个绕过。

## 决策

1. **可执行类型不入上传白名单**：`image` 白名单移除 `svg`（全仓无消费者、无文档依赖）；白名单与静态投递判据**读同一张类型表**，表内每项标 `safe` / `unsafe` / `unknown` 三档之一。
2. **静态投递分档**：`safe`（pdf / 图片 / 视频 / office）保持 inline（现状 + `X-Content-Type-Options: nosniff`）；`unsafe` 与 `unknown` 一律 `Content-Disposition: attachment` + `application/octet-stream`。判据落在后端 staticHandler 单点；nginx 的 `/static/` 只反代、不复制规则（避免两份名单漂移）。
3. **不做一刀切 attachment**：PDF 的内联预览是一等需求（`DocumentViewer.vue` 的 iframe 与新窗打开、投稿附件预览都依赖它），按类型分档而不是按前缀一刀切。
4. **存量已上传的 svg 不清理**：分档后它们落到 `unknown` ⇒ attachment + octet-stream，已不可执行；清理是数据操作且有误删风险，若要做另开数据票。
5. **投稿附件归属由路径承载**：暂存前缀按用户分区 `contributions/<uid>/`；创建投稿时校验四件事——前缀属于本人、扩展名在投稿白名单内、同一 URL 未被任何投稿登记过、文件真实存在。不引入暂存表。
6. **两条机器锁**：① 类型表不得出现可执行类型（svg / html / xml / xhtml / js…）；② 未识别扩展名必须回 attachment + octet-stream。新类型进表时被这两条锁逼着表态。

## 被否备选

- **一刀切 `/static/uploads` 全前缀 attachment**：实现最简，但 PDF 内联预览与新窗预览会退化成下载（功能降级）。
- **一刀切 + PDF 预览改 blob 取回**：语义干净，但改动从前端一个组件扩散到取回链，且大文件内存翻倍。
- **只改上传白名单、不做静态面**：掐掉已知注入源，但存量 svg 仍可执行，且下一个新扩展名即复发。
- **投稿附件改走「暂存行表 + 只认 id」或「上传票据」**：语义更正，但要新建表 / 票据基础设施与生命周期，与本轮「小改动收口」的规模不匹配。
- **只查前缀 `contributions/` 不判归属**：同前缀内他人的暂存文件仍可被冒名登记。

## 实施回写（2026-09-28，随 P0 修复批）

- **决策 6 锁①的落地形态**：实现为「可执行类型必须**显式登记**为 unsafe 且不可上传」（表内 svg / svgz / html / htm / xhtml / xml / js / mjs / cjs）。比「不得出现」的字面更严：未登记走 unknown（同样强制下载），显式登记让「考虑过它」留在表里；决策 4 的存量 svg 因此落在 unsafe 档（对外行为与 unknown 相同）。
- **一份类型表已扩到第三处**：MIME 推断（原 `mimeTypeFromExt` 的 switch）并入同一张表，不再有第二份扩展名清单。
- **决策 2 的单点范围（原记载有误，2026-09-28 更正并定档）**：判据落在后端 staticHandler，只覆盖 `STORAGE_DRIVER=local`。本段原写「生产当前默认 local」——**事实是生产跑 r2**（`deploy/env.defaults` 的 `local` 只是默认值，生产 `.env` 覆盖为 `STORAGE_DRIVER=r2` + 自建 RGW `R2_ENDPOINT=http://172.17.1.42:8088`、`R2_PUBLIC_DOMAIN=https://www.gccsmile.com`）。故分档在生产不是「潜在缺口」而是**现状不生效**：nginx 的 RGW location（`frontend/nginx-host.conf`）直出，实测 `curl -sI https://www.gccsmile.com/avatars/….webp` 无 `content-disposition`、无 `x-content-type-options`。
  收敛风险的两条事实（同日实测）：新文件已进不来（上传白名单在各路径统一走 `ValidateImage` → unsafe 档显式不可上传）；库里所有文件引用列 0 条危险扩展名（`question.image_url` / `course.cover_image` / `featured_content.cover_image` / `chapter_file.file_url` / `user_contribution_file.file_url` / `hrwai_users.avatar_url`）。**残余暴露面 = 桶内 DB 已不再引用的存量对象**（ListBucket 未公开，只读无法证否），而分档正是为这一格准备的输出侧判据——r2 模式下输出侧是 nginx。
  **决策（票 #1364）**：在 nginx 层补齐分档，但**不在 nginx 手抄第二份**——由 `cmd/gen-deploy` 从 `fileTypeTable` 生成 nginx map 片段（safe → `inline`；unsafe 与 unknown → `attachment`）并在 CI 比对生成物；被否备选是「读路径收回后端」（判据单一，但为一个响应头付掉直出的缓存与吞吐）。
- **决策（票 #1364）的落地形态（2026-09-28 实施回记）**：
  - **产物落点不是「另一个片段文件」而是就地生成区**：`frontend/nginx-host.conf` 开头（所有 `server` 块之前——nginx 的 `map` 只能在 http 上下文声明）有一段两行标记夹住的**生成区**，由 `go run ./cmd/gen-deploy -only nginx` 覆写，`map $uri $delivery_disposition` 给出每个登记扩展名的 `inline` / `attachment`，`default attachment` 承载 unknown。之所以不另出片段文件：compose 只把 `nginx-host.conf` 挂成 `default.conf.template`（`docker-compose.prod.yml` 的 frontend 卷），多一个文件就多一条「打包清单漏了它 ⇒ 容器里 include 不到、`nginx -t` 起不来」的部署面风险（2026-09-13 的 PG_VOLUME 事故同族：链路中段静默失配）。
  - **两个 RGW location 各自加两行**：`add_header Content-Disposition $delivery_disposition always;` 与 `add_header X-Content-Type-Options "nosniff" always;`（与后端 `applyUploadDeliveryHeaders` 同口径——nosniff 两档都设）。**Content-Type 刻意不覆写**（票 #1364 决策 3）：`attachment` 已决定浏览器不渲染，覆写要 `proxy_hide_header` + 每扩展名 MIME map，收益零、风险是把 RGW 回的正确 MIME 弄丢；后端 local 面覆写是因为它自己就是 MIME 的出处（`MimeTypeOf`），nginx 不是。**两面因此存在一处有意的口径差**：local 面 unsafe/unknown = attachment + octet-stream，nginx 面 = attachment + RGW 原 MIME；两面的**下载判据**（Content-Disposition）逐字同源。
  - **扩展名全集取自表，不取自导出面**：`fileTypeTable` 是包内私有，导出面里没有任何「列出全部扩展名」的函数（`AllowedExtensionsFor` 按上传类别取，unsafe 与投稿专用行的 upload 都是空串，拼不出全集；漏一行 = 静默落到 default）。故生成器用 AST 读表拿键、用 `service.FileTypeClassOf` 拿值，并逐行**双向对账**（源码声明的 class ≠ 运行期返回值即拒绝生成）——同形态先例见 `internal/deploy/topology_test.go` 用 AST 读 `internal/config/config.go`。表是**只读**的，本票没动它一行。
  - **锁落了几条**：① 生成链全等锁 `TestNginxDeliveryMapInSync`（`codegen.AssertInSync`，改表不重生成 / 手改生成区即红）；② 逐档一致锁 `TestNginxDeliveryMapCoversFileTypeTable`（独立再取一次表，与生成区**双向**比：不少行、不多行、不改档，`default` 必须是 attachment）——①只比「现算 vs 磁盘」，若现算本身漏了某一档，①会跟着绿，故必须有一条独立取表的②；③ 接线锁 `TestNginxDeliveryWiring`（生成区在第一个 server 之前、两个 RGW 出口都真的用上分档头、分档值不许在别处手写、不许出现 `proxy_hide_header Content-Type`）；④ 传播锁 `TestNginxDeliveryMapPropagation`（喂合成行证明「表里多一行 ⇒ 产物必须多一行」，不必去动只读的表）；⑤ 结构锁 `TestNginxHostConfStructure`（括号配平 + map 条目语法 + 键唯一，是 `nginx -t` 的静态替身、**不等于跑过** `nginx -t`）。CI 侧新鲜度锁挂在 `frontend-check`（判据同「Swagger 产物新鲜度」：现算 → `git diff` 必须为空）——生成物住在 `frontend/`，而 backend-lint / backend-test 都由 `changes.backend` 门控，只改 `nginx-host.conf` 时那两个 job 根本不跑。同一步骤在比对之后再用 `-count=1` 把六条 nginx 锁在这一面重跑一遍：接线锁判的两行 `add_header` 在生成区**之外**，`git diff` 看不见它，而「摘掉分档头 / 把值写死」的 PR 只命中 `frontend/**` ⇒ backend job 整个被跳过，全 CI 只有这一步会真跑到它。
  - **同 bucket 的第三个出口已点名而非忽略**：`location /kbimg/`（dify 子域反代知识库图片，落同一个 `forklift-files`）不在票 #1364 的口径内，登记在 `nginx_delivery_gen_test.go` 的 `rgwKnownUncovered` 里并写明理由；新增直出 RGW 的 location 若既不纳入分档又不登记，该锁判红。
  - **一条实测到的锁失效面（记下来，别踩）**：生成物在 Go 模块外（`frontend/`），`go test` 的**结果缓存不把它算作输入**——本机实测：删掉生成区里一行后，`go test ./internal/deploy/ -run TestNginx` 仍报 `ok (cached)`，加 `-count=1` 才判红。所以 ① 在 CI 里的承重形态是 `go run` + `git diff`（现算不受缓存影响），而 `make test` / `go test ./...` 那条全等锁只在**包内有任何改动**时才真跑。本批同日复测再次命中同一形态：删掉生成区里 `~*\.xml$` 那一行后，`go test ./internal/deploy/ -run TestNginx` 仍回 `ok (cached)`，加 `-count=1` 才判红 ⇒ `frontend-check` 里那一条 `go test` 的 `-count=1` 不是装饰，去掉它这条锁在 CI 上会静默失效。这不削弱判据：表变 ⇒ 依赖图变 ⇒ 缓存失效 ⇒ 全等锁真跑；只改产物 ⇒ backend job 整个被 `changes.backend` 跳过，由 frontend-check 的现算比对兜住。
  - **判据 ②④ 的本机验证与仍未闭合的部分（2026-09-28 实测）**：本机 Windows 侧无 docker daemon、无 nginx，但 WSL Ubuntu 里有 nginx 1.28.3 与 envsubst，于是把**真实渲染链**跑了一遍：`frontend/nginx-host.conf` → 与 `frontend/docker-entrypoint.sh` 逐字同一句 `envsubst '${DOMAIN} ${BACKEND_HOST_PORT} ${PORTAL_HOST_PORT}'` → `nginx -t` **test is successful**（整份文件，含新 map 与两个 location；唯一改写是证书目录与 `listen` 端口——非 root 绑不了 80/443、`/etc/nginx/ssl` 不存在，分档 map 与两行 `add_header` 逐字未动）。再在同一份 conf 上真起 nginx、把 RGW 上游换成回 Content-Type 的本地 stub，`curl -sI` 逐档实测：`/avatars/*.pdf|png|webp` → `content-disposition: inline` + `x-content-type-options: nosniff`（内联预览未破，判据 ③）；`/reports/r.pdf` → `inline` + `max-age=3600`（与改前「无 Content-Disposition」同解）；`/avatars/t.svg|html` → `attachment` + nosniff **且 `content-type` 仍是上游的 `image/svg+xml` / `text/html`**（决策 3 的「不覆写」被正面观察到）；未登记扩展名与无扩展名 → 走 `default` = `attachment`。负向对照：同一 stub 直连（不经被测 location）两个头都不出现，证明头确实由这两个 location 发出。**仍未闭合**：真 RGW（Ceph）在中间的那一次——本机的 stub 不证明 Ceph 不会自带同名头、也不证明真桶里的对象逐条如此；且生产镜像是 `nginx:1.27-alpine`，本机是 1.28.3。判据 ② 的「生产或 staging 实测一次」与容器内那次 `nginx -t`（真实挂载 + 真证书）由部署面补验，写在票 #1364 的验收证据段。
