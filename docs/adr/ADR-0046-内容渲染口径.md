# 内容渲染口径：内容面 × 端 × 能力矩阵 + 子集与降级规则

同一份 Markdown 内容在本平台有 **6 个渲染点、4 条渲染路径**：章节正文（讲师 Vditor 写 → Web 用 marked + highlight.js 渲染 → 移动端用手写解析器渲染）、内容精选（管理端 Vditor 写 → 门户 Nuxt 与移动端各自渲染）、论坛正文与 AI 助手回答（markstream + `html-policy="escape"`）、管理端 AI 生成预览（裸 `marked.parse`，连代码高亮都没有）。

没有矩阵时，这些差异靠「谁也没注意」维持：表格在移动端是破的（生产 28 篇章节里 24 篇含表格，而移动端解析器没有表格实现），公式与图表在 Web 只有一半的面有，编辑端的所见不等于发布端的所得。本 ADR 把「哪个内容面在哪一端有什么能力」显式化，给每项能力定降级规则，并记下据此补齐的口径（spec #899，实现 #900–#904）。

## 内容面 × 端 × 能力矩阵

「内容面」= 一份内容被撰写与呈现的位置，「端」= Web / 移动 / 门户（词汇见 `CONTEXT.md`）。

| 能力 | Web 论坛 / AI 助手 | Web 章节 | Web 内容精选 | 移动端 | 门户 |
| --- | --- | --- | --- | --- | --- |
| 标题 / 列表 / 引用 / 代码块 | 有 | 有 | 有 | 有 | 未知 |
| 图片 / 链接 | 有（图片走图集，正文内嵌图展开为 alt） | 有 | 有 | 有 | 未知 |
| 表格 | **刻意禁用**（子集不含） | 有 | **降级为原始文本** | **无（线上破口）** | 未知 |
| 代码高亮 | **本批开启** | 有 | 有 | 无 | 未知 |
| 公式 | **本批开启（仅块级）** | **本批开启** | 降级为源码 | 无 | 无 |
| mermaid 图 | **本批开启** | 不做 | 不做 | 无 | 无 |

矩阵里只有「无（线上破口）」那一格是**必须马上补**的：它会让内容读不出来。移动端不在本仓库工作范围，已立票交付（表格与公式渲染 + 子集口径，见 issue tracker 的移动端票 #905）。

## 降级规则只有两类

跨端一致性**不追求能力齐平**，只在一件事上强制：

- **破坏可读性的降级**——读者看到的不再是「同一份内容」，而是坏掉的结构（表格丢结构、代码块丢缩进到不可读）。这类降级必须在每一端补齐，否则它本质上是**不同的内容**。
- **仍可读的降级**——能力缺失时退回源码或纯文本（公式显示为 `$...$`、mermaid 显示为代码块、代码块无高亮）。这类允许单端先开，因为它没有改变读者能读到的信息。

判据是「读者能不能读出原意」，不是「两端是否一模一样」：按「一模一样」定标准会得到一个互相等待、谁也不敢先开的矩阵；按「能不能读」定标准，才能让章节先有公式、移动端随后跟上。

## 决定

### 1. 不统一渲染器，只统一口径

可信面（章节 / 内容精选）继续走 marked + `v-html` 栈，不可信面（论坛 / AI 助手）继续走 markstream + escape 单点，两条路都不改道。理由见「Considered Options」——把可信面并进 markstream 会为一处安全收益付出「重写章节渲染、丢掉既有排版与移动端对称性」的代价；反过来把 UGC 并到 marked + `v-html` 则是把已经收敛掉的一条 XSS 面重新打开。

### 2. 能力开在 Web 的三个内容面，启用收敛成启动单点

`katex` / `mermaid` / `stream-diffs` 三个 markstream 可选 peer 本批装上并开启（论坛 / AI 助手面）；章节面另接 marked 的 KaTeX 扩展（**渲染栈不变**，只是多一个扩展）。

- **一律动态 import**：三个 peer 各自独立 chunk，只有页面上真的出现公式 / 图表 / 增强代码块时才下载。这条不是「优化建议」而是硬约束——见「Consequences」的体积实测。
- **启用是一个单点**（`frontend/src/utils/markstreamRuntime.ts`，在 `main.ts` 调用）：这些开关写的是库的进程级全局状态，散在各渲染组件里会变成「谁后挂载谁说了算」。连**开启动作本身**也走动态 import——markstream 本体是 900KB+ 的 chunk，静态挂在 `main.ts` 上会让**每一个**路由 chunk 通过入口的静态依赖继承它。
- **组件文案中文化**用 `setDefaultI18nMap`，不引入 `vue-i18n`（只需要把十几个写死的英文按钮换成中文，不值得一个 i18n 框架）。

### 3. 内容精选正文取三端交集

内容精选正文的子集 = **门户 / Web / 移动端三端的交集**：标题 / 列表 / 引用 / 代码块 / 图片 / 链接，**不含表格与公式**。

它由管理员撰写、面向门户访客与 SEO，**表达力让位于三端一致**——与章节正文（读者是已报名学员、只需要 Web 正确）的取舍不同，不是同一套标准的两次应用。

契约落在 `API.md` 与管理端编辑器提示上，**不做后端强校验**：误伤存量与未来合法内容的成本高于收益，判据留在作者看得见的地方（编辑器提示 + 发布端预览里的越界说明）。

### 4. 编辑端加「发布端预览」

讲师与管理员在编辑页能看到的，必须是**读者真正看到的那份渲染结果**，而不是 Vditor 内部 lute 引擎的解释。实现上抽一个共享单点（`renderPublishMarkdown` + `PublishMarkdown.vue`），学员阅读页与编辑页预览**调同一份**；管理端 AI 生成预览也改用同一渲染器（顺带修掉它连代码高亮都没有的问题）。

这条同时是 ADR-0044 里那句拒绝理由的反向应用：当初拒绝「复用 Vditor 当学员端编辑器」，理由正是「它的预览走自有引擎，会与发布后的渲染结果不一致」。

### 5. 安全口径（三个闸门都不动）

- **UGC 与 AI 输出继续走 markstream + `html-policy="escape"`**：raw HTML 一律渲染为文本（不是丢弃），新开的能力不许绕过它；
- **mermaid 固定 `securityLevel: "strict"`**（库的 `MermaidBlockNode` 默认如此，本仓不覆盖）：禁脚本、禁事件属性、不开 `htmlLabels`；
- **KaTeX 保持 `trust: false`**（markstream 面用库默认、章节面显式传）：`\href` / `\htmlClass` 这类命令不生效——渲染输出会进 DOM，公式不能变成第二条注入路径。

## Consequences

- **首屏体积**：三个 peer 的 chunk 体积实测（2026-09-12，`npm run build`）：katex 545KB / gzip 159KB、mermaid 3017KB / gzip 816KB、stream-diffs 10745KB / gzip 1838KB。**三者都不在入口静态图里**（入口只剩 index / vue-vendor / element-plus / vendor / dayjs，与改造前一致）。差异在路由层：mermaid 与 stream-diffs 由 markstream 面**动态**拉取；katex 会随**章节路由 chunk 静态**加载（matched 的公式扩展在解析期就要 katex，而 marked 是同步渲染）——即打开任一章节页会多下载 164KB(gzip)，即使该章节没有公式。这个取舍记在这里：要消掉它只能把渲染改成异步两段式（先出文本、再回填公式），代价是首屏内容闪一次。
- **按需下载不等于免费**：论坛里出现第一个代码块时，那个 1.8MB(gzip) 的 stream-diffs chunk 就会被拉下来。这是 #900「代码块出现高亮 span」的直接代价，记在这里供后续判断（若实际体验不可接受，退路是给 UGC 面设 `render-code-blocks-as-pre`，即回到纯 `<pre>`，属性上属「降级仍可读」）。
- **构建期依赖闭包**：`vite.config.ts` 里按 `node_modules` 现算 peer 的**独占**依赖闭包（mermaid 的闭包有 100 个包）。必须减去「应用其余依赖的闭包」——否则公共库（如 `lodash-es`，element-plus 也在用）会被划进 mermaid chunk，让 element-plus 的 chunk 静态 import 整个 mermaid，首屏 +3MB。这类错误的症状是「首屏莫名多出重型 chunk」，排查时先看 chunk 之间的静态依赖边。
- **`marked-katex-extension` 的类型入口是它自己的 TS 源码**，在 `noUnusedParameters` 下报 TS6133；本仓用 `tsconfig.json` 的 `paths` 把该模块的类型面显式接管（运行时仍解析真包），没有为此关掉全仓的检查项。
- **编辑端的所见即所得仍是近似**：预览用的是发布端渲染器，但编辑器本身（Vditor）在编辑态显示的仍是 lute 的解释。作者要看「读者看到什么」，得点开预览。

## 已知限制

- **markstream 当前只认块级公式**：实测 `$$...$$` 渲染成公式，而行内 `$...$`、`\(...\)` 在 `docs` / `chat` × `final` true/false 下都不产生数学节点（上游解析器的行内规则未生效）。因此论坛 / AI 助手面**只有块级公式**；章节面两者都有（marked 扩展）。按上面两类降级规则，行内公式在 UGC 面属「仍可读」。已用一条 characterization 用例钉住这个事实（上游支持后会变红，提示同步本 ADR）。
- **行内公式的边界**：章节面的行内公式用 KaTeX 生态的标准规则——右侧须为空白、标点或行尾。`$T$与文字` 这种紧贴汉字的写法不会被识别（要识别得开 `nonStandard`，代价是 `价格 $5 到 $10` 这类货币写法会被误判成公式）。因此在中文正文里写行内公式，`$` 后面留一个空格或标点。
- **移动端**：表格与公式都不渲染（表格是破口，见矩阵），移动端子集口径另立票交付。
- **门户**：渲染实现不在本仓库，本批只把子集写成契约，不要求门户改代码。

## 明确不做

- **渲染器统一**（把可信面并入 markstream，或把 UGC 并入 marked + `v-html`）：见「决定 1」与「Considered Options」。
- **`@antv/infographic` / `@terrastruct/d2`**：无需求（前者默认就是关的），且都是重型可选 peer。
- **内容精选的后端强校验**：见「决定 3」。
- **UGC 子集扩张**（例如允许论坛正文内嵌图片）：不在本批。

## Considered Options

- **把三个内容面统一到 markstream**（含章节面）：一套渲染器、一处能力开关，长期维护成本最低。拒绝——章节正文目前是 marked + `v-html` + 完整 `markdown.css` 排版，换引擎等于把学员端最重的阅读面重做一遍（表格、图片、代码块样式全部要重新对齐），而它并不在安全收益上得分（章节是可信面）。收益是「一致性」，但一致性已经由矩阵与降级规则显式承担了。
- **把 UGC 并入 marked + DOMPurify + `v-html`**：ADR-0044 已拒绝过一次（新增净化依赖与长期白名单、与「不再有裸 v-html」的收敛方向相反、移动端语义分叉），本批不翻案。
- **内容精选允许表格与公式，门户 / 移动端各自尽力**：表达力更强。拒绝——一盘「门户能看到、移动端看到竖线」的内容，读者会认为内容坏了；而内容精选是**获客面**，三端一致比表达力值钱。
- **给内容精选做后端强校验**（拒绝含表格 / 公式的正文）：契约更硬。拒绝——存量与未来合法内容都可能被判死，而作者已经能在编辑器与预览里看到提示；判据放在看得见的地方，比放在会 400 的地方更合适。
- **不装 `stream-diffs`，只保留纯 `<pre>` 代码块**：省下 1.9MB(gzip) 的按需下载。拒绝——#900 明确要求论坛 / AI 面「代码块出现高亮 span」，且高亮对「一眼分辨故障码与参数」是真实需求（user story 4）。
