# 内容渲染口径：内容面 × 端 × 能力矩阵 + 子集与降级规则

同一份 Markdown 内容在本平台有 **6 个渲染点、4 条渲染路径**：章节正文（讲师 Vditor 写 → Web 用 marked + highlight.js 渲染 → 移动端用手写解析器渲染）、内容精选（管理端 Vditor 写 → 门户 Nuxt 与移动端各自渲染）、论坛正文与 AI 助手回答（markstream + `html-policy="escape"`）、管理端 AI 生成预览（裸 `marked.parse`，连代码高亮都没有）。

没有矩阵时，这些差异靠「谁也没注意」维持：表格在移动端是破的（生产 28 篇章节里 24 篇含表格，而移动端解析器没有表格实现），公式与图表在 Web 只有一半的面有，编辑端的所见不等于发布端的所得。本 ADR 把「哪个内容面在哪一端有什么能力」显式化，给每项能力定降级规则，并记下据此补齐的口径（spec #899，实现 #900–#904）。

## 内容面 × 端 × 能力矩阵

「内容面」= 一份内容被撰写与呈现的位置，「端」= Web / 移动 / 门户（词汇见 `CONTEXT.md`）。

| 能力 | Web 论坛 / AI 助手 | Web 章节 | Web 内容精选 | 移动端 | 门户 |
| --- | --- | --- | --- | --- | --- |
| 标题 / 列表 / 引用 / 代码块 | 有 | 有 | 有 | 有 | 未知 |
| 行内格式（粗体 / 斜体 / 删除线 / 行内代码） | 有 | 有 | 有 | **本票补齐（#1472）**：行内分词器 + 嵌套 `<text>` 逐 run 出样式；个别修饰线在 App 嵌套子 text 上的实际出图属真机待验 | 未知 |
| 图片 / 链接 | 有（图片走图集，正文内嵌图展开为 alt） | 有 | 有 | 图片：图文分离（正文内嵌图展开为 alt、图集另呈）；链接经 #1472 行内可点，**移动端任何链接点开都弹确认**（⑩-9 与 Web 站内直连不打断不同） | 未知 |
| 表格 | **刻意禁用**（子集不含） | 有 | **有**（2026-11 放开，见「修订记录」） | **本批补齐**（章节面渲染成表格；内容精选面按降级规则退回逐行原始文本） | 有 |
| 代码高亮 | **本批开启** | 有 | 有 | 无 | 未知 |
| 公式 | **本批开启（块级 + 行内）** | **本批开启（块级 + 行内）** | 降级为源码 | 降级为源码（`$...$` / `$$...$$` 原样可见，仍可读） | 无 |
| mermaid 图 | **本批开启** | 不做 | 不做 | 无 | 无 |

矩阵里唯一那格「线上破口」（移动端表格）已由移动端票 #905 补齐：**章节面**渲染成原生表格，**内容精选面**与公式按降级呈现（细则见「决定 6」）。**行内格式**那格（粗体 / 斜体 / 删除线 / 行内代码 / 链接）此前在移动端长期「只剥不渲染」（`[文字](url)` 被剥成「文字」、链接不可点，登记时误写作「有」），已由 #1472 补齐（行内分词器 + 嵌套 `<text>` 逐 run 出样式；链接协议闸与点开确认见移动端 ADR-0025 ⑩-8/⑩-9）。其余空格（代码高亮 / mermaid）都是「降级仍可读」，允许继续缺。

## 降级规则只有两类

跨端一致性**不追求能力齐平**，只在一件事上强制：

- **破坏可读性的降级**——读者看到的不再是「同一份内容」，而是坏掉的结构（表格丢结构、代码块丢缩进到不可读）。这类降级必须在每一端补齐，否则它本质上是**不同的内容**。
- **仍可读的降级**——能力缺失时退回源码或纯文本（公式显示为 `$...$`、mermaid 显示为代码块、代码块无高亮）。这类允许单端先开，因为它没有改变读者能读到的信息。

判据是「读者能不能读出原意」，不是「两端是否一模一样」：按「一模一样」定标准会得到一个互相等待、谁也不敢先开的矩阵；按「能不能读」定标准，才能让章节先有公式、移动端随后跟上。

## 决定

### 1. 不统一渲染器，只统一口径

可信面（章节 / 内容精选）继续走 marked + `v-html` 栈，不可信面（论坛 / AI 助手）继续走 markstream + escape 单点，两条路都不改道。理由见「Considered Options」——把可信面并进 markstream 会为一处安全收益付出「重写章节渲染、丢掉既有排版与移动端对称性」的代价；反过来把 UGC 并到 marked + `v-html` 则是把已经收敛掉的一条 XSS 面重新打开。

### 2. 能力开在 Web 的三个内容面，启用收敛成启动单点

`katex` / `mermaid` / `stream-diffs` 三个 markstream 可选 peer 本批装上并开启（论坛 / AI 助手面）；章节面另接 marked 的 KaTeX 扩展（**渲染栈不变**，只是多一个扩展）。

- **一律动态 import**：三个 peer 各自独立 chunk，只有页面上真的出现公式 / 图表 / 增强代码块时才下载。这条不是「优化建议」而是硬约束——见「Consequences」的体积实测。
- **启用是一个单点**（`frontend/src/utils/markstreamRuntime.ts`，在 `main.ts` 调用）：这些开关写的是库的进程级全局状态，散在各渲染组件里会变成「谁后挂载谁说了算」。连**开启动作本身**也走动态 import——markstream 本体是 900KB+ 的 chunk，静态挂在 `main.ts` 上会让**每一个**路由 chunk 通过入口的静态依赖继承它。
- **组件文案中文化**用 `setDefaultI18nMap`，不引入 `vue-i18n`（只需要把十几个写死的英文按钮换成中文，不值得一个 i18n 框架）。

### 3. 内容精选正文的子集：门户与 Web 齐平，移动端降级

内容精选正文的子集 = 标题 / 列表 / 引用 / 代码块 / 图片 / 链接 / **表格**；**不含公式**。

原文（2026-09）取的是**三端交集**、连表格一起排除。**2026-11 修订**：表格从交集里拿出来，理由是本条自己的原则被违反了 ——

- 门户侧一直是 marked 默认 gfm，表格**本来就渲染**（`D:\portal\utils\markdown.ts`，无 table renderer 覆盖）。把 Web 精选档降级成原始文本，产生的是「管理端预览说读者看不到表格、门户读者却看得见」：预览在骗作者，正是决定 4 要防的那件事。
- 表格丢失是「破坏可读性」的降级（ADR-0046 的降级规则第一类），按既定判据本就该补齐而不是容忍。

口径改成：**门户与 Web 渲染表格、移动端仍按决定 6 退回逐行原始文本**，越界提示的文案主语随之从「门户与移动端」收窄为「移动端」（`outsideSubsetNotice`）。公式不动 —— 移动端确实不认，且它属「降级仍可读」（源码可见）。

它由管理员撰写、面向门户访客与 SEO，**表达力让位于「预览不骗人」**——与章节正文（读者是已报名学员、只需要 Web 正确）的取舍不同，不是同一套标准的两次应用。

契约落在 `API.md` 与管理端编辑器提示上，**不做后端强校验**：误伤存量与未来合法内容的成本高于收益，判据留在作者看得见的地方（编辑器提示 + 发布端预览里的越界说明）。

### 4. 编辑端加「发布端预览」

讲师与管理员在编辑页能看到的，必须是**读者真正看到的那份渲染结果**，而不是 Vditor 内部 lute 引擎的解释。实现上抽一个共享单点（`renderPublishMarkdown` + `PublishMarkdown.vue`），学员阅读页与编辑页预览**调同一份**；管理端 AI 生成预览也改用同一渲染器（顺带修掉它连代码高亮都没有的问题）。

这条同时是 ADR-0044 里那句拒绝理由的反向应用：当初拒绝「复用 Vditor 当学员端编辑器」，理由正是「它的预览走自有引擎，会与发布后的渲染结果不一致」。

### 5. 安全口径（三个闸门都不动）

- **UGC 与 AI 输出继续走 markstream + `html-policy="escape"`**：raw HTML 一律渲染为文本（不是丢弃），新开的能力不许绕过它；
- **mermaid 固定 `securityLevel: "strict"`**（库的 `MermaidBlockNode` 默认如此，本仓不覆盖）：禁脚本、禁事件属性、不开 `htmlLabels`；
- **KaTeX 保持 `trust: false`**（markstream 面用库默认、章节面显式传）：`\href` / `\htmlClass` 这类命令不生效——渲染输出会进 DOM，公式不能变成第二条注入路径。

### 6. 移动端的渲染子集（#905 落地，口径与上面的矩阵同一份）
移动端是**手写解析器**（`training-app/…/utils/markdown.uts`，不依赖 DOM），能力按**子集档位**分档，与内容面一一对应：

| 档位 | 内容面 | 表格 | 公式 | 其余 |
| --- | --- | --- | --- | --- |
| `chapter`（缺省） | 章节正文 | **按行解析成 table 块并渲染成原生表格** | 降级为源码 | 标题 / 列表 / 引用 / 代码块 / 图片 / 分隔线 |
| `featured` | 内容精选 | **不解析**，退回逐行原始文本 | 降级为源码 | 同上（不含公式） |

- **表格的移动端形态**：uvue 没有 `grid`，原生表格用「逐行 flex + 等宽单元格」复刻（表头行加底色、加粗，并补表格外框）。**列宽不按内容自适应**、不做横向滚动——长单元格换行显示，这是与 Web `<table>` 的已知观感差异（结构可读性不受影响）。
- **表格在解析器里按行出块**：每行一个 `table` 块，`items` = 该行单元格、`level` = 1（表头，恒为第一行）/ 0（正文）。这不是造型偏好，是 UTS 的硬约束——给 `MarkdownBlock` 加「**自定义类型的数组字段**」（`rows : MarkdownTableRow[]`）会触发编译期改名：产出 `class MarkdownTableRow__1` 而引用处仍是 `MarkdownTableRow`，④c 整模块 kotlinc 报 60 条 unresolved reference 直接判红（#905 实测）。既有扁平字段（`items` / `level`）是唯一零类型风险的形状，别「顺手」改回更漂亮的嵌套类型。
- **公式的降级表现写死为「源码原样可见」**：两档都不做数学排版，`$...$` / `$$...$$` 连定界符一起呈现。**行内标记剥离必须跳过公式跨度**——否则 `$a_1 + b_2$` 的下划线会被斜体规则 `_..._` 吃掉，降级产物就不再是源码（这是本票修掉的一个真实缺陷）。
- **内容精选面与 Web 同口径（2026-11 修订）**：Web 的 `featuredMarked` 与门户的 marked 都**渲染表格**，移动端是唯一降级的一方（退回逐行原始文本）——降级由移动端单侧承担，不再是「两端都说看不到」。越界提示文案的主语因此收窄为「移动端」（`frontend/src/utils/publishMarkdown.ts` 的 `outsideSubsetNotice`），门户与 Web 不再被写进「不渲染」名单。
- **覆盖面登记（#1443 回填本条）**：本票（#905）落地时只接**章节正文 / 内容精选**两个面，当时把论坛与 AI 两面登记为「纯文本、不接解析器」防误读——该登记已随后续两票过时：**论坛正文**由移动端 ADR-0025（#1240）接入（第三档 `SUBSET_FORUM`），**AI 助手回答**由 #1443 接入（同档）。现状口径改为一条**接线纪律**：走解析器的面一律经 `utils/` 壳层解析（论坛 `utils/forumBody.uts`、AI `utils/aiAnswerBody.uts`，内部 `from './markdown'`），**渲染 `.uvue` 不直接 import `utils/markdown`**——解析决策住壳层才可被 utsHarness 真执行（接线守护不构成 ③ 门证据，`docs/agents/guards.md`），该纪律由 `utils/markdownContract.test.js` 的登记用例守着。表格/公式在两面都按上表降级形状呈现，「有了表格」仍不等于「四个面同一套子集」。
- **明确不做**：数学排版（原生端无 DOM/KaTeX）、列宽自适应与横向滚动、mermaid、代码高亮——后两项属「降级仍可读」，留在矩阵的空格里。

### 7. 内容精选支持直接渲染原始 .docx（2026-11）

内容精选新增 `content_type` 两档：`markdown`（默认，正文走上面全部的 Markdown 口径）与 `docx`（正文是一份**原始 Word 文件**，读者端用 `docx-preview` 在浏览器里按 OOXML 还原排版）。

**为什么不是「导入时转成 Markdown」**：转换是有损且不可逆的——页眉页脚、多级列表缩进、合并单元格、图文混排这些正是作者在 Word 里排版的部分，转换后全丢；且转换器本身要维护一套与 Word 渲染对齐的口径，等于又开一个会漂移的渲染面。用户要的是「直接渲染 .docx」，就按字面实现。

**这是第一条不走 Markdown 渲染栈的正文形态**，因此它对上面矩阵的处置是：

- **不进矩阵**：docx 正文没有「标题/表格/公式」这些 Markdown 能力格可填，它的渲染保真度由 docx-preview 决定，不由本 ADR 的子集口径决定。
- **渲染位置**：Web 学员端 `frontend/src/components/render/DocxDocument.vue` 与门户 `D:\portal\components\DocxDocument.vue` 各一份实现（两仓不共享代码，与 `PublishMarkdown` 同理），判据都是 `content_type === 'docx' && docx_url 非空`；两处都**必须在挂载后渲染**（`docx-preview` 只认 DOM，SSR 期没有 `document`），门户因此套 `ClientOnly`。
- **移动端降级**：uni-app x 无 DOM，App 显示摘要 + 「请在网页端查看完整排版」。这属「破坏可读性」的降级，但**没有补齐路径**——原生端跑不了 OOXML 渲染器。故口径定为：**要求移动端读者读全的内容必须用 Markdown 正文**，这一条写进了管理端编辑器的提示文案与使用说明，让作者在选择形态时就知道代价。
- **安全面**：docx 文件由管理员上传（`CapabilityRequired(CapFeaturedManage)`），下载地址必须是本站 `featured/docx/` 前缀的附件（`featuredDocxGate`），与图片同一套闸门；文件按 `.docx` 白名单 + 50MB 上限校验，不做任何服务端解析（不引无头浏览器，不给 OOXML 反序列化开口子）。

## Consequences

- **首屏体积**：三个 peer 的 chunk 体积实测（2026-09-12，`npm run build`）：katex 545KB / gzip 159KB、mermaid 3017KB / gzip 816KB、stream-diffs 10745KB / gzip 1838KB。**三者都不在入口静态图里**（入口只剩 index / vue-vendor / element-plus / vendor / dayjs，与改造前一致）。差异在路由层：mermaid 与 stream-diffs 由 markstream 面**动态**拉取；katex 会随**章节路由 chunk 静态**加载（matched 的公式扩展在解析期就要 katex，而 marked 是同步渲染）——即打开任一章节页会多下载 164KB(gzip)，即使该章节没有公式。这个取舍记在这里：要消掉它只能把渲染改成异步两段式（先出文本、再回填公式），代价是首屏内容闪一次。
- **按需下载不等于免费**：论坛里出现第一个代码块时，那个 1.8MB(gzip) 的 stream-diffs chunk 就会被拉下来。这是 #900「代码块出现高亮 span」的直接代价，记在这里供后续判断（若实际体验不可接受，退路是给 UGC 面设 `render-code-blocks-as-pre`，即回到纯 `<pre>`，属性上属「降级仍可读」）。
- **构建期依赖闭包**：`vite.config.ts` 里按 `node_modules` 现算 peer 的**独占**依赖闭包（mermaid 的闭包有 100 个包）。必须减去「应用其余依赖的闭包」——否则公共库（如 `lodash-es`，element-plus 也在用）会被划进 mermaid chunk，让 element-plus 的 chunk 静态 import 整个 mermaid，首屏 +3MB。这类错误的症状是「首屏莫名多出重型 chunk」，排查时先看 chunk 之间的静态依赖边。
- **`marked-katex-extension` 的类型入口是它自己的 TS 源码**，在 `noUnusedParameters` 下报 TS6133；本仓用 `tsconfig.json` 的 `paths` 把该模块的类型面显式接管（运行时仍解析真包），没有为此关掉全仓的检查项。
- **编辑端的所见即所得仍是近似**：预览用的是发布端渲染器，但编辑器本身（Vditor）在编辑态显示的仍是 lute 的解释。作者要看「读者看到什么」，得点开预览。

## 已知限制

- **行内公式的边界规则，两个面不一样**（写内容时按目标面写）：
  - **论坛 / AI 助手面**（markstream）用自家**宽容**启发式：不要求 `$` 两侧是空白，`$T$与文字` 也认；会挡「区间写法」（`$5~$10` 这类带 `~` / `～` / `-` 的数字区间）与占位符。代价是**成对的美元号会被当成公式**——实测 `价格 $5 到 $10 元` → `text | math_inline(5 到 ) | text`、`编号 $1 与 $2` 同理。
  - **章节面**（marked + KaTeX 扩展）用 KaTeX 生态的**标准**规则：收尾 `$` 右侧须为空白、标点或行尾，`$T$与文字` 不识别。可以开 `nonStandard` 放宽，但会把上面那类货币误判一起引进来。
- **行内公式在单测环境里测不到（覆盖缺口，不是「没有」）**：线上实测正常渲染——论坛回复里 `行内公式 $f(x) = ax + b$` 出公式（2026-09-12，PR #906 的验收）。但本仓单测环境（happy-dom）里 markstream 的**组件**会把 `math_inline` 降级成纯文本节点，只有直接调解析器 `parseMarkdownToStructure()` 才拿得到 `math_inline`。因此本仓**不写行内公式的正/负向单测**（写了就是在断言环境差异），这一格靠线上与人工验证。记在这里，免得下一个人把「单测没覆盖」误读成「不支持」。
- **移动端**：章节面的表格已渲染成原生表格（逐行 flex + 等宽单元格，**列宽不按内容自适应**）；公式与**内容精选面**的表格按降级呈现——公式为源码、表格为逐行原始文本，细则见「决定 6」。
- **门户**：渲染实现在独立仓（`DriftingLi/hrwai-portal`，本机检出 `D:\portal`），本 ADR 只写契约。2026-11 实测门户 `utils/markdown.ts` 用 marked 默认 gfm —— 表格一直渲染、公式不渲染，与本 ADR 修订后的口径一致；门户**不需要为表格改代码**。同一批已在门户补了 docx 正文渲染（`components/DocxDocument.vue` + `pages/content/[id].vue` 按 `content_type` 分叉，套 `ClientOnly` 因为 docx-preview 只认 DOM）与表格对齐/图片居中的两条 CSS 修正。

## 修订记录

- **2026-11（表格放开）**：决定 3 与矩阵的「Web 内容精选 / 门户」两格由「降级为原始文本 / 未知」改为「有」。触发原因是内容精选编辑器加了排版工具栏并做 docx 支持时，回头核对门户实现发现表格**本来就在渲染**，于是原口径下的降级是纯损失（预览骗作者 + 表格本身属「破坏可读性」降级）。移动端口径不变。同一批还补了**内嵌 HTML 排版**（居中 / 左对齐 / 颜色 / 字号 / 图片居中，写法为 `<span style="display:block;text-align:…">`）：门户与 Web 渲染、移动端退回纯文本，属「降级仍可读」，编辑器侧由 `contentStyles` 开关控制只在能渲染的两面开放。
- **2026-11（docx 正文形态）**：新增「决定 7」——内容精选支持 `content_type = docx`，读者端用 docx-preview 直接渲染原始 Word、不经 Markdown。同时修正了两处会压掉作者排版的既有 CSS：`frontend/src/assets/styles/markdown.css` 与 `D:\portal\assets\css\markdown.css` 里 `thead th` 的裸写 `text-align:left` 改为 `:not([align])`，让 GFM 对齐说明符（`:--` / `:-:` / `--:`）渲染出的 `align` 属性不再被盖掉；两处各补一条 `img[style*='margin…auto']` 规则让「图片居中」在 `display:block` 下真正居中。

## 明确不做

- **渲染器统一**（把可信面并入 markstream，或把 UGC 并入 marked + `v-html`）：见「决定 1」与「Considered Options」。
- **`@antv/infographic` / `@terrastruct/d2`**：无需求（前者默认就是关的），且都是重型可选 peer。
- **内容精选的后端强校验**：见「决定 3」。
- **UGC 子集扩张**（例如允许论坛正文内嵌图片）：不在本批。

## Considered Options

- **把三个内容面统一到 markstream**（含章节面）：一套渲染器、一处能力开关，长期维护成本最低。拒绝——章节正文目前是 marked + `v-html` + 完整 `markdown.css` 排版，换引擎等于把学员端最重的阅读面重做一遍（表格、图片、代码块样式全部要重新对齐），而它并不在安全收益上得分（章节是可信面）。收益是「一致性」，但一致性已经由矩阵与降级规则显式承担了。
- **把 UGC 并入 marked + DOMPurify + `v-html`**：ADR-0044 已拒绝过一次（新增净化依赖与长期白名单、与「不再有裸 v-html」的收敛方向相反、移动端语义分叉），本批不翻案。
- **内容精选允许表格与公式，移动端各自尽力**：表达力更强。**部分采纳（2026-11 修订）**——表格已放开（门户与 Web 都渲染，移动端单侧降级）；公式仍排除，因为移动端确实不认公式、且它属「降级仍可读」，把它放进精选面只会让作者白写。
- **给内容精选做后端强校验**（拒绝含表格 / 公式的正文）：契约更硬。拒绝——存量与未来合法内容都可能被判死，而作者已经能在编辑器与预览里看到提示；判据放在看得见的地方，比放在会 400 的地方更合适。
- **不装 `stream-diffs`，只保留纯 `<pre>` 代码块**：省下 1.9MB(gzip) 的按需下载。拒绝——#900 明确要求论坛 / AI 面「代码块出现高亮 span」，且高亮对「一眼分辨故障码与参数」是真实需求（user story 4）。
