# ADR-0080：字号只走 token 阶梯

- 状态：已采纳（2026-10-26；同日第二次扩面，见文末「修订记录」）
- 相关：[#1894](https://github.com/DriftingLi/FL/issues/1894)（原票：字号阶梯收口）、[ADR-0079](ADR-0079-图标体系数据化与状态形变.md)（图标尺寸跟随字号）、[ADR-0078](ADR-0078-可交互图标的尺寸分档.md)（另一条尺寸口径）、[ui-conventions](../../docs/agents/ui-conventions.md)、[checks](../../docs/agents/checks.md)

## 背景

`design-tokens.css` 定义 `--text-xs` … `--text-3xl`（12/14/16/18/20/24/30）七档，但前端长期在用的是另一套，而且是**两套直写**：

- **工具类**：116 处 `text-[<n>px]`，11 种取值（13px 64、15px 19、11px 17、10px 5、22px 5，其余各 1）；
- **scoped 样式**：152 处 `font-size: <n>px`，16 种取值（12px 38、13px 33、14px 24、16px 13、22px 11、18px 10、20px 4、28px 3、10/11/15px 各 3、17px 1、40/44/64px 各 1）。

后果有两条，第二条才是真问题：

1. **token 失效**：直写值不参与变量链，改 `--text-sm` 不会带着它们变 ——「一处改动全站生效」对字号不成立，阶梯退化成文档里的一段文字。
2. **下限失守**：两套合计 34 处落在 9 / 10 / 11px。9px 的中文在任何 DPI 下都读不清；这和 #1892 刚收口的对比度是同一条链上的问题 —— 颜色够黑了，字还是太小。

#1894 的首版结论是「churn 大于收益，留 backlog」。2026-10-26 复评改判：**1px 级位移的机械映射**不需要设计判断（每个直写值只有一个最近的阶梯档），不该按「改版」计价。当天先收工具类（#1929），再按维护者裁定把 scoped 样式一并收（本轮）。

## 决策

### 1. 只有七档

| 工具类 | px | token |
| --- | --- | --- |
| `text-xs` | 12 | `--text-xs` |
| `text-sm` | 14 | `--text-sm` |
| `text-base` | 16 | `--text-base` |
| `text-lg` | 18 | `--text-lg` |
| `text-xl` | 20 | `--text-xl` |
| `text-2xl` | 24 | `--text-2xl` |
| `text-3xl` | 30 | `--text-3xl` |

scoped 样式里写 `font-size: var(--text-*)`；残值域有自己的一套 `--fs-*`（12…48，定义在 `.valuation-root` 内），那三个文件沿用自家习惯并可带 px 兜底：`font-size: var(--fs-sm, 14px)`。

### 2. 直写值按最近档映射，**等距向上取**

| 直写区间 | 归到 | 工具类收口 | scoped 收口 |
| --- | --- | --- | --- |
| 9–12px | 12（`xs`） | 24 | 45 |
| 13–14px | 14（`sm`） | 65 | 57 |
| 15–16px | 16（`base`） | 20 | 16 |
| 17–18px | 18（`lg`） | 2 | 11 |
| 19–20px | 20（`xl`） | 0 | 4 |
| 21–24px | 24（`2xl`） | 5 | 13 |

等距向上取的口径与实际映射一致（13→14、15→16、17→18、22→24）：**宁可大 1px，也不把正文压小**。22px 的标题归到 `text-2xl` 而不是 `text-xl`，是因为它们本来就是手写的页标题（我的收藏 / 学习资料 / 全局搜索 / 精选详情 / 章节标题），与 `UiPageHeader` 同档。

### 3. 射程：工具类与 scoped 样式都收（推翻初版决策 3）

初版把 scoped `font-size` 留在射程外，理由是「R2 冻结区页面的既有样式随改版顺手收」。这条已被推翻 —— 理由：

- **R2 保护的是布局与外观，不是取值来源**。把 `font-size: 13px` 换成 `font-size: var(--text-sm)` 以及 1px 的阶梯归位，属于等价/唯一解的机械替换，不是改版；不换，token 链就是断的。
- 「随改版顺手收」在实践中等于**永不收**：这批页面没有排期，152 处直写会一直存在。

所以本期把 143 处换成 token（另 5 处展示级、3 处 rem 基准按下节放行，并删掉 1 条已死的 `.el-icon` 规则），收口后前端**没有任何一处**「界面文字用裸 px 定字号」。

### 4. 两类必须放行的字面量（不是漏网，是规则的一部分）

| 类别 | 现状 | 判据 |
| --- | --- | --- |
| **展示级** 28 / 40 / 44 / 64px | 5 处（头像字、统计值、封面占位字、残值 `.num-hero` 44 / 64） | 大号数字与占位字形，不进七档；值登记在守卫的 `DISPLAY_TIER`，新增取值要改守卫并在本 ADR 登记 |
| **rem 基准** `html { font-size: 16/14/13px }` | 3 处（≤768 / ≤480 各一档） | 它派生整个 rem 尺度（Tailwind 的 `text-*`、间距都吃它）。改成 `var(--text-*)` 会让「改 token」变成「整体缩放页面」，所以保持字面量，声明上一行打 `font-scale-root` 标记，守卫按标记放行 |

**已知接缝（本票不统一）**：scoped 的 token 是 **px**，工具类 `text-*` 是 **rem**。`html` 在 ≤768 / ≤480 把基准降到 14 / 13px，于是同一档字号在窄屏上会差 81–93%：工具类跟着缩，scoped token 不缩。这在本票之前就存在（scoped 也一直是裸 px），统一要么删掉根字号三档、要么把 token 改 rem，两者都会动全站节奏，另开票。

### 5. 守卫

```
node scripts/check-font-scale.mjs --all                 # 全量（CI 用这个）
node scripts/check-font-scale.mjs --diff origin/master  # 只看新增行
```

两条规则，扫描面 `frontend/src/**/*.{vue,ts,css}`：

- `arbitrary-font-size`：禁 `text-[<数字>px|rem]`（`text-[var(…)]` 是颜色、`text-[1em]` 是相对单位，放行）；
- `literal-font-size`：`font-size` 必须是 `var(--text-*)` / `var(--fs-*, px)` / 关键字值；裸 px 只放行 `DISPLAY_TIER` 与带 `font-scale-root` 标记的 rem 基准。

防空转下界 `minChecked: 400`（当前 486 个文件）；自检 23 例（`scripts/check-font-scale.test.mjs`）。CI 三面接线：frontend-check 的 `--all`、增量门的 `--diff`、`el-controls-selftest` 的自检。

## 后果

- 工具类 116 → 0；scoped 152 → 8（5 展示级 + 3 rem 基准，全部由规则放行）。整体密度 +1px 左右。
- **行高随工具类归一**：`text-sm` 带 Tailwind 默认行高 1.43、`text-base` 带 1.5，此前继承父级行高的元素会取到这两个值。要阅读行高（1.6 / 1.8）仍显式写 `leading-[…]`，本期不动。
- **没有逐页视觉回归证据**：本仓无 Playwright，判据是「机械映射唯一解 + 单测 + 守卫」。实跑 `npm run type-check`、`npm test`、生产构建与守卫自身；深色主题与窄屏观感未逐页截图。风险最高的是 11 处从 9–11px 抬到 12px 的微型元素（幻灯片页码、键盘提示、角标）与 3 处 22→24px 的标题。

## 修订记录

- **2026-10-26（第二次，本轮）**：初版决策 3「射程只到工具类」被推翻 —— scoped `font-size` 一并收口，同时引入「展示级 / rem 基准」两类放行与守卫的第二条规则。判据不变（唯一解映射、等距向上取）；变的只是射程，理由是 R2 保护外观而非取值来源，且「随改版顺手收」在实践中等于不收。

## 被否备选

- **把 13px 加进 token 阶梯**（`--text-13`）：等于给每种直写值都开一档，阶梯失去约束力；13 与 14 并存正是今天的局面。
- **只清 <12px 的部分**：留下的 13 / 15 / 22 三套主流直写，改 token 仍然不生效，问题只是推迟。
- **展示级也塞进七档**（28→30、40→30、44→48、64→48）：大号数字会明显缩小，且七档变成九档就失去了「一屏内可数」的意义。
- **把 `html` 的 rem 基准也 token 化**：见决策 4 —— 那会让「改一个 token」变成「整体缩放页面」，且守卫会把布局基准当成字号误判。
- **流式字号（`clamp()`）**：与「固定密度后台表格 + 密集列表」冲突，行高与列宽会跟着抖。
