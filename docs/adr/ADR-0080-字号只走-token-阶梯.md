# ADR-0080：字号只走 token 阶梯

- 状态：已采纳（2026-10-26）
- 相关：[#1894](https://github.com/DriftingLi/FL/issues/1894)（原票：字号阶梯收口）、[ADR-0079](ADR-0079-图标体系数据化与状态形变.md)（图标尺寸跟随字号）、[ADR-0078](ADR-0078-可交互图标的尺寸分档.md)（另一条尺寸口径）、[ui-conventions](../../docs/agents/ui-conventions.md)、[checks](../../docs/agents/checks.md)

## 背景

`design-tokens.css` 定义 `--text-xs` … `--text-3xl`（12/14/16/18/20/24/30）七档，但模板里真正在用的是另一套：2026-10-26 实测 **116 处** `text-[<n>px]` 直写，**11 种取值** —— 13px 64 处、15px 19 处、11px 17 处、10px 5 处、22px 5 处，12 / 14 / 16 / 17 / 18 / 9px 各 1 处。`--text-sm` 几乎无人使用。

后果有两条，第二条才是真问题：

1. **token 失效**：直写值不参与变量链，改 `--text-sm` 不会带着它们变 ——「一处改动全站生效」对字号不成立，阶梯退化成文档里的一段文字。
2. **下限失守**：23 处落在 9 / 10 / 11px。9px 的中文在任何 DPI 下都读不清；这和 #1892 刚收口的对比度是同一条链上的问题 —— 颜色够黑了，字还是太小。

#1894 的首版结论是「churn 大于收益，留 backlog」。2026-10-26 复评改判：**13→14 与 15→16 的视觉位移 ≤1px**，而收口是**唯一解的机械映射**（每个直写值只有一个最近的阶梯档），不需要设计判断，也就不该按「改版」计价。

## 决策

### 1. 只有七档

| 工具类 | px | token |
| --- | --- | --- |
| `text-xs` | 12 | `--text-xs` |
| `text-sm` | 14 | `--text-sm` |
| `text-base` | 16 | `--text-base` |
| `text-lg` | 18 | `--text-lg` |
| `text-xl` | 20 | `--text-xl` |
| `text-2xl` | 24 | `--text-2xl` |
| `text-3xl` | 30 | `--text-3xl` |

### 2. 直写值按最近档映射，**等距向上取**

| 直写区间 | 归到 | 本次计 |
| --- | --- | --- |
| 9–12px | `text-xs`（12） | 24 |
| 13–14px | `text-sm`（14） | 65 |
| 15–16px | `text-base`（16） | 20 |
| 17–18px | `text-lg`（18） | 2 |
| 19–20px | `text-xl`（20） | 0 |
| 21–24px | `text-2xl`（24） | 5 |
| 25–30px | `text-3xl`（30） | 0 |

等距向上取的口径与本次实际映射一致（13→14、15→16、17→18、22→24）：**宁可大 1px，也不把正文压小**。22px 的标题归到 `text-2xl` 而不是 `text-xl`，是为了与 `UiPageHeader` 的页标题同档 —— 那 5 处本来就是手写的页标题（我的收藏 / 学习资料 / 全局搜索 / 精选详情 / 章节标题）。

### 3. 射程只到工具类

scoped `<style>` 里的 `font-size: <n>px` **本期不动**：那是 R2 冻结区页面的既有样式，按 `ui-conventions` 的约定随该页改版时顺手换成 token / 原子类。

现状 152 处（2026-10-26 实测），其中 **61 处不在阶梯上**：13px 33、22px 11、10px 3、11px 3、15px 3、28px 3、9px 1、17px 1、40 / 44 / 64px 各 1（后三个是展示级大字号，本来就不该进七档）。这条余量**不假装已收口**：守卫只认工具类，`font-size` 直写不会报红。

### 4. 守卫

```
node scripts/check-font-scale.mjs --all                 # 全量（CI 用这个）
node scripts/check-font-scale.mjs --diff origin/master  # 只看新增行
```

- 判定面：`frontend/src/**/*.{vue,ts}` 里的 `text-[<数字>px]` 与 `text-[<数字>rem]`；
- `em` **放行**：`text-[1em]` 是本仓「图标跟随父字号」的写法（`UiActionChip` 的 `UiIcon`），不是一档字号；
- `text-[var(…)]` 是颜色不是字号（正则要求数字 + 单位）；
- `leading-[1.8]` 不判：本仓行高**没有**阶梯，别为了整齐去收行高；
- 防空转下界 `minChecked: 400`（当前 479 个 `.vue` + `.ts`），自检 15 例（`scripts/check-font-scale.test.mjs`）。

CI 三面接线，与其余前端守卫同口径：frontend-check 的 `--all`、增量门的 `--diff`、`el-controls-selftest` 的自检。

## 后果

- 116 处 → 0 处；整体密度 +1px 左右（13→14 的 64 处是主要来源）。
- **行高随工具类归一**：`text-sm` 带 Tailwind 默认行高 1.43、`text-base` 带 1.5，此前继承父级行高的元素会取到这两个值。要阅读行高（1.6 / 1.8）仍显式写 `leading-[…]`，本期不动。
- **没有逐页视觉回归证据**：本仓无 Playwright，判据是「机械映射唯一解 + 单测 + 守卫」。实跑的是 `npm run type-check`、`npm test`（1434 例）、生产构建与守卫自身；深色主题与窄屏观感未逐页截图。风险最高的三处已登记：打卡日历里的 9px 角标（现 12px）、缩略图 16px 方框里的 10px ×（现 12px）、Markdown 工具栏的 11px「H3」（现 12px）。

## 被否备选

- **把 13px 加进 token 阶梯**（`--text-13`）：等于给每种直写值都开一档，阶梯失去约束力；13 与 14 并存正是今天的局面。
- **只清 <12px 的 23 处**：留下的 13 / 15 两套主流直写，改 token 仍然不生效，问题只是推迟。
- **流式字号（`clamp()`）**：与「固定密度后台表格 + 密集列表」冲突，行高与列宽会跟着抖。
- **用 `!important` 或全局 `*` 选择器兜底字号**：绕过 token 链，且与 Tailwind 的 utilities 层顺序打架（见 `tailwind.css` 顶部三条刻意的选择）。
