# ADR-0076: 内容精选的自定义发布时间与定时发布

- 状态：Accepted
- 日期：2026-10-21
- 关联：#1748（功能）；ADR-0043（时间格式单点）；ADR-0061（进程内守护与登记表）；ADR-0064（输入不合法具名事实）；ADR-0039（管理端列表三态状态机）；#1743（门户迁 EdgeOne，内容缓存口径）

## 背景

内容精选的编辑者此前只能在「点发布」的那一刻拿到发布时间：`Publish` 写 `published_at = now`，创建/更新也只在草稿→已发布的瞬间补当前时间。于是两件事做不了：

1. **补录**：今天补一篇昨天的行业动态，文章排到「今天」，读者看到的时间与事实不符，列表顺序与上/下一篇也跟着错；
2. **排期**：想在清晨或周末发，只能人肉守时点「发布」；忘了就迟发，人在休假就发不了。

门户（Nuxt，EdgeOne）与移动端都只消费公开接口，**它们不该为这件事改动**：公开读路径「只发已发布」这条口径本身已经足够表达不可见性，缺的只是「怎么把一篇内容停在草稿但记着什么时候上线」。

## 决策

### 1. 状态模型：三态是「`status` + `scheduled_at` 有无」的组合，不是第三个 `status` 值

| 状态 | `status` | `published_at` | `scheduled_at` | 对外可见 |
| --- | --- | --- | --- | --- |
| 草稿 | 0 | 保留原值（可为空） | 空 | 否 |
| 定时中 | 0 | 空 | 未来时间 | 否 |
| 已发布 | 1 | 发布时间（可过去） | 空 | 是 |

三条不变量：

1. `status = 1` ⇒ `published_at` 非空且 `scheduled_at` 为空；
2. `scheduled_at` 非空 ⇒ `status = 0`（库层 CHECK 兜住：`NOT (status = 1 AND scheduled_at IS NOT NULL)`）；
3. **公开接口继续只认 `status = 1`** —— 定时内容靠「保持草稿态」实现不可见，公开读路径一行不改。

不变量 1 的 `published_at` 半边**不**加 CHECK：存量库里若有「已发布却没有时间」的历史行，加约束会让整个 `up` 失败；那半边由写入侧的**调用处**兜底（`internal/featured/service.go` 的 `Update` 在落点 `status = 1` 且 `published_at` 为空时补当前时间；`Create` / `Publish` 在缺省那一格本来就写 `now`）。

### 2. 写入语义矩阵（创建 / 更新 / 发布共用同一实现）

| 入参 `published_at` | 目标状态 | 结果 |
| --- | --- | --- |
| 缺省 | 1 | 立即发布：`published_at = now` |
| 缺省 | 0 | 草稿：清空 `scheduled_at`（= 取消定时），`published_at` 保留 |
| `≤ now` | 1 | 补录：`published_at = t`、`scheduled_at` 空 |
| `> now` | 1 | 定时：`status = 0`、`scheduled_at = t`、`published_at` 空 |
| 非空时间 | 0 | 400（草稿不排期） |
| 缺省 | 未传（更新，只改标题/正文） | 维持现状：排期**原样保留**（临上线前的小修不必重排） |
| 缺省 | 点名了状态（更新） | 这次是状态落定：草稿→已发布仍补当前时间，排期一律清空（草稿 = 取消定时） |

时间契约：严格 RFC3339；范围 `2000-01-01`（业务时区）～ `now + 10 年`；**空串 = 「用现在」**（编辑器「留空」的显式写法，不是清空）。越界与格式错误同属「输入不合法」→ 具名事实 → 400（`ErrFeaturedPublishTimeInvalid` / `ErrFeaturedDraftWithPublishTime`），不落端点默认面 500。

**关键的一格是「缺省」与「空串」分开**：`nil` 表示「不指定」（维持既有语义），`""` 表示「现在」。若把两者合成一格，编辑器「留空 = 立即发布」这个最常用的路径就会与「只改标题、别动时间」撞成同一个请求，后者的语义（不改时间）无处表达。

### 3. 到点发布：进程内守护 + 一条幂等 UPDATE

- 登记为一条周期守护 `featured-scheduled-publish`，节奏 **1 分钟**（ADR-0061 的登记表，名单锁同批更新）；
- 动作是一条语句：`UPDATE featured_content SET status = 1, published_at = scheduled_at, scheduled_at = NULL, updated_at = now() WHERE status = 0 AND scheduled_at IS NOT NULL AND scheduled_at <= now()`；
- Postgres / SQLite 的 `SET` 右侧都取**旧行值**，故「`published_at := scheduled_at`」与「`scheduled_at := NULL`」在同一句里互不干扰；`status = 0` 的条件保证多实例 / 重跑不会重复发布；
- 条件里的两半 `status = 0 AND scheduled_at IS NOT NULL` 与部分索引 `idx_featured_content_scheduled_at`（`WHERE scheduled_at IS NOT NULL`）同形，守护每分钟只扫这一小块；
- 每轮把补发条数写日志（0 条不写，避免每分钟一条噪音）。
- **写入与比较都折成 UTC**：`scheduled_at` 存的是**时刻**而非墙钟。Postgres 的 timestamptz 本就与偏移无关，折 UTC 是为了 SQLite（测试库）——它把时间存成带偏移的文本、按字符串比较，同一列里混着 `+08:00` 与 `+00:00` 会让 `scheduled_at <= ?` 在某些时区下静默漏行（实测：本机东八区绿、CI 的 UTC runner 红）。显示仍由 `timefmt` 按业务时区输出。

### 4. 接口面：管理端多一列，公开面零变更

- 创建 / 更新：请求体新增**可选** `published_at`；不传 = 与改动前逐字一致（用户故事 22）；
- 发布：由「无入参」改为**可选** body `{ published_at }`，无 body = 立即发布（旧客户端一字不改）；
- 管理端列表：过滤参数由 `status`（0/1）改为 `state`（`draft` / `scheduled` / `published`，空 = 全部）。该接口唯一消费者是管理端，故不保留旧参数 —— 旧参数表达不了「定时中」，留着只会让调用方以为它能筛三态；
- **管理端另起一份列表行类型** `FeaturedContentAdminListDTO`（= 公开列表项 + `scheduled_at`），公开的 `FeaturedContentDTO` 一行未动。这是「公开接口零变更」这条承诺的直接形状：公开列表里 `scheduled_at` 恒为 `null`，多一个恒空键就是一次无谓的契约变更；
- 契约生成物按既有生成链再生成（注解 → swagger → `gen-apitypes`），不手改生成物。

## 理由

- **为什么不用「懒可见」**（保持 `status = 1`，公开查询加 `published_at <= now()`）：零守护，但要改公开列表、详情、上/下一篇、阅读量、收藏门禁等多处读路径；更麻烦的是现有大量测试种子与历史数据只设 `status = 1` 不设时间，语义一旦依赖时间，那些行会突然「已发布却看不见」—— 在管理端最难排查的一类故障。
- **为什么不用 `status = 2` 表示定时**：会把持久化枚举从 0/1 扩成 0/1/2，所有「非 1 即草稿」的隐含假设（公开读、收藏、导出、管理端开关）都要逐个知道 2；而 2 与 0 在「对外不可见」上完全同义，新增取值没有换来任何新信息。`scheduled_at` 非空本身就是「定时中」，它是**数据**而不是**状态枚举**。
- **为什么守护而不是「请求时顺手检查」**：到点发布必须发生在**没有人访问**的时刻（这正是定时发布的意义）；依赖读请求触发意味着没人看就不发，列表里的顺序也会随访问者而变。
- **为什么 1 分钟**：与产品确认的口径是「分钟级」；门户侧还有约 60 秒缓存，秒级承诺本来就不可兑现。粗一档（5 分钟）会让「排 9:00 发」变成 9:04，编辑一眼能看出来。
- **为什么写库侧只实现一次矩阵**：创建 / 更新 / 发布三条路径的差异只有「目标状态怎么来」，落定三字段的规则完全一致。三处各写一遍就是三份会漂的规则，而这里漂一次的症状是「时间与可见性不一致」—— 最难通过肉眼发现的那种。

## 后果

- 编辑者获得三种填法（留空 / 过去 / 未来），列表能按三态筛，定时行可「立即发布」或「转为草稿（取消定时）」；
- **到点延迟 ≤ 1 分钟**，且门户侧另有约 60 秒缓存 ⇒ 观感是「分钟级」而不是「准点秒级」；
- **守护停摆不丢排期**：重启后按 `scheduled_at <= now` 全量补发，补发条数进日志（用户故事 18/19/20）；
- 已发布内容把时间改到未来会**重新进入定时中**（时间与可见性始终一致，用户故事 11）；
- 回滚：迁移 `000043` 的 down 删除该列（新列、无历史数据），「已定时但未到点」的内容退回普通草稿，不会误发布任何内容；
- 全站时区口径不变（Asia/Shanghai），不做用户级时区；编辑器提示只说「将」，生效以服务端为准。

## 明确不做（本票范围外）

- 到点通知 / 推送 / 邮件（到点只是上线）；
- 门户与移动端的任何改动（公开接口不变）；
- 定时内容的对外预览链接；
- 排期日历、批量排期、周期 / 重复发布、草稿协作与审批流；
- 权限模型调整（沿用「内容精选管理」能力点）。
