# ADR-0036: 冻结区「窄口径一次性解冻」机制

- 状态：已接受（2026-09-08）
- 领域：工程治理 / 变更边界（承接 AGENTS.md「不得触碰的边界」）

## 背景

`AGENTS.md` 设了冻结区 —— `pages/admin/**`（管理端页面）、`valuation-tokens.css`、`design-tokens.css` 的 token 值。初衷是保护这批高频业务页面与全局 token 不被样式重构带崩。

但完全冻结会与全站治理冲突。至今已出现两次真实需求：

1. **#554（2026-09-04）**：为清深色模式下不跟随主题的裸 hex，需要动 `components/catalog/**` 与残值域。当时的处理是解冻，但**约束不变** —— catalog 师生管三端共用，只换色值、不新增 prop；`--color-brand-*` 仍禁提升为全局。
2. **#716（2026-09-08）**：弹窗收敛需动 admin 域 18 处 `el-dialog`，占全量 46 处的 39%。

两次都是「需要进冻结区，但只需要做一种很窄的动作」。如果每次都临时讨论口径，或者干脆永久解冻，前者重复决策、后者拆掉防线。需要一个可复用的机制。

## 决策

1. **解冻是例外而非常态**：冻结区默认保持冻结；每次进入必须**由 spec 显式声明**，不写进 AGENTS.md 作为永久变更 —— 避免 AGENTS.md 积累一堆「某次解冻」的历史垃圾。

2. **窄口径三要素，缺一不可**。spec 中必须写清：
   - **范围**：具体到文件集或数量（如「admin 域 18 处弹窗」）；
   - **允许的动作**：具体到可机械核验的程度（如「只允许把 `el-dialog` 替换为 `UiDialog`，含把自定义页脚迁到 `#footer` 或降级为默认页脚」）；
   - **禁止的动作**（如「管理端页面的其它样式、结构、文案一行不动」）。

3. **解冻后原约束不变**：沿用 #554 先例 —— 解冻只放开本次声明的那一个动作，该区域的其它既有约定（如 catalog 三端共用不新增 prop、`--color-brand-*` 不提升为全局）继续生效。

4. **评审口径收窄为一句**：只需核「有没有顺手改别的」。这让大批量机械替换（34 个文件级别）的评审变得可行 —— 评审者不必逐行理解业务，只需识别超出声明范围的改动。

5. **ADR 记录机制、spec 记录口径**：本 ADR 只沉淀机制本身；每次具体解冻的范围与动作写在对应 spec 的 Implementation Decisions 里，作为该次评审的依据。

## 备选

- **永久解冻**：拒绝 —— 冻结区的价值正是防止高频业务页面被样式重构带崩，永久解冻等于拆掉这道防线，且不可逆（很难再冻结回去）。
- **一律不解冻、绕开冻结区**：拒绝 —— #716 若绕开 admin 的 18 处，管理端与学员端弹窗将长期两套观感，且下次还要再开一轮 spec 收尾。
- **每次解冻都修改 AGENTS.md**：拒绝 —— 会在治理文档里堆积一次性条款，读的人分不清哪些是长期约定、哪些是某次的历史许可。
- **用 CODEOWNERS / lint 强制拦截**：暂缓 —— 当前规模（单人 + AI 会话）下，spec 声明 + 评审口径已足够；若后续出现并发会话误改冻结区，再考虑加自动化拦截。

## 后果

- 冻结区仍是默认状态；进入冻结区需要先有 spec，无形中给这类改动增加了一道「先把边界想清楚」的前置。
- 评审负担从「逐行理解改动」转移到「spec 的边界是否写得足够可核验」—— 边界写得含糊，评审就失效。
- 若某个 spec 的解冻范围写得过宽（如「允许调整管理端弹窗相关样式」），本机制等价于失效；写 spec 时必须用机械可核验的措辞。
