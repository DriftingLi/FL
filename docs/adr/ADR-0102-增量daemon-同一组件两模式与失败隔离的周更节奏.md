# ADR-0102：增量 daemon——同一组件两模式，daemon 只加节奏不加管线

- **状态**：已接受
- **日期**：2026-11-20
- **领域**：拍卖数据管线 / 采集层
- **票**：#2678（父 spec #2671）

## 背景

spec #2671 user story 20 明确要求「历史回补与增量采集是同一组件的两种模式，so that 清洗与匹配逻辑共用一份、不漂移」；运行架构票 #2670 进一步裁定「历史回补一次性批跑；增量周更；每平台 ≤1 req/2s + 诚实 UA + 指数退避」。到 #2678 时，回补（#2677）已经建成：发现层 → 年份过滤 → 幂等判重 → 逐条抓取 → 全管线 → 得率报告，采集层（robots/限速/UA/退避）也已就位。

所以本票要回答的问题只有一个：**「周更」到底是加一条新管线，还是给既有那条加个循环？**

## 决策

**一、daemon 是节奏包装，不是第二条管线。** `collector/daemon.py` 只做两件事：定周期、隔离失败。每一轮的实际工作**直接调用 `run_backfill`**（经 `cli.run_daemon_command` 转接），因此发现/年份过滤/幂等/抽取/清洗/匹配/得率报告全部与回补共用同一份代码。`daemon.py` 里没有一行采集、抽取或清洗逻辑——这是判据 2「增量与回补共用清洗/匹配模块（无平行逻辑）」的结构性保证，而不是靠自律。

**二、周期从「本轮开始」算，不从「本轮结束」算。** 下一轮开始时间 = 本轮开始 + interval。千条量级一轮要跑约 1 小时，若从结束算起，周节奏会逐轮累积推后（`interval + 耗时`），一年下来漂移出好几天。本轮耗时超过周期时不再等待（`sleep(0)`），立即开始下一轮。

**三、失败隔离分两层，且**必须**分层。** 第一层是**轮级**：任何单轮异常被捕获并记进 `CycleResult.error`，照常按周期等下一轮；`on_result` 可观测性回调也在隔离范围内（日志管道断了不该杀掉常驻服务）。第二层是**条级（毒丸隔离）**：`run_backfill` 里单条 URL 抓取/落库失败只记进 `failed_urls` 并继续下一条，不再让整轮抛错。

第二层是**常驻模式逼出来的**，不是锦上添花：实测过这个故障——一条永久 404 卡在队头，8 周后库里只落 1 行，排在它后面的公告**从未被抓过**。一次性回补时运维可以重跑/手工跳过；常驻 daemon 没有「看着它失败」的人，一条坏 URL 就等于永久堵死整条管线。条级隔离同时改变了 backfill 的语义（原来整轮抛错），这是本票顺带修掉的既有缺陷。

**四、失败隔离不做熔断。** 采集层已有指数退避处理「站点暂时不健康」，再叠一层「连续失败 N 次就退出」只会把「站点挂了 3 周」变成「服务悄悄消失」。周更任务的正确行为是继续按周期尝试并留下可审计的失败记录。

**五、无 `max_cycles` 即常驻；`--max-cycles 1` 是运维的「手动跑一轮」。** 同一个命令既能常驻周更，也能被人当一次性作业跑，不必维护两个入口。

**六、年份窗口上界跟随当前年，不写死。** 回补是一次性作业，窗口固定 2015–2026 合理；daemon 是常驻服务，若上界写死 2026，**2027-01-01 起每一轮都会「成功但发现 0 条」**——日志全绿、库不再增长、没有任何报错（实测过）。所以 `daemon_end_year()` = `max(BACKFILL_END_YEAR, 当前年)`，daemon 的 `--end-year` 缺省走它。

**七、compose 里 collector 服务改 `restart: unless-stopped` + 常驻 `daemon` command。** 从 #2672 的 `restart: "no"`（一次性 batch 容器）改成常驻周更服务。`COLLECTOR_LIST_URL` 用 bare 替换（无默认值 ⇒ 空默认，漂移锁跳过）；不设就起不来。

**八、启动前校验，而不是「跑到第一轮才炸」。** 常驻服务 + `restart: unless-stopped` 的组合下，「每轮都失败但进程活着」是最难发现的故障形态：容器 healthy、日志有输出、一周只写一条失败。所以 `validate_startup()` 在开始第一轮之前一次性查掉 `--list-url`（空/非 http）、`DATABASE_URL`（缺失）、以及经 `probe` 注入的 PG 连接与 AI 配置解析（`market_sample_extract` 未绑定 / `SECRET_KEY` 解不开 api_key）。任一不满足即 exit 1。

> **注意归因**：守住空 `COLLECTOR_LIST_URL` 的是这个启动前校验，**不是 argparse**——空串是合法的参数值，argparse 拦不住。后续若有人删掉 `validate_startup`，空 URL 会退回「每周期静默空转」。

**九、robots 遵从在 daemon 模式下不变。** daemon 复用的 `CrawlClient` 与回补完全同一个（含 host 绑定、限速写死 2s、诚实 UA、退避）。要抓 robots 禁止的站点仍需人工在 command 里显式加 `--allow-robots-override`（ADR-0101 决策一），周更不会因为「反正常驻跑」就自动放宽。

## 被否备选

- **另写一条 daemon 管线（复制发现/抽取/清洗/匹配）**：最直接的写法，但正是 spec user story 20 要禁止的事——两份实现必然漂移，同一公告在回补和增量下会得出不同标签，下游校准无从判断信哪份。
- **周期从「本轮结束」算**：写起来更自然（`while True: run(); sleep(week)`），但会把每轮耗时累加进周期，产生系统性漂移。
- **失败即退出（让 systemd/compose 重启）**：看似「让编排层管重启」更干净，但会把一次抓取抖动升级成容器重启循环，日志被重启噪声淹没；而重启也解决不了「同一公告连续多周抓不到」这类逻辑失败。
- **连续失败 N 次后熔断退出**：把「站点挂了 3 周」变成「服务悄悄消失了」。周更任务的正确行为是继续按周期尝试并留下可审计的失败记录。
- **常驻服务用 `--max-cycles` 定死轮数后退出**：那样就得靠外部 cron 拉起，等于把节奏搬到 compose 之外，与「独立服务常驻周更」的裁定相反。
- **`COLLECTOR_LIST_URL` 给一个默认的 rmfysszc 列表页 URL**：会让服务在无人配置的情况下自动对准一个 robots 明确禁止的站点——默认值不该替人做合规决定。

## 后果

**收益**：①判据 2 由结构保证——`daemon.py` 不含任何管线逻辑，想漂移都没有第二份可改；②周节奏不漂移；③单轮失败可审计且不终止服务；④同一镜像承载全部模式（batch/backfill/daemon/reclean/rematch/unmatched），部署面只多一个 command 参数；⑤`--max-cycles 1` 让「手动跑一轮」与「常驻周更」共用一条命令。

**代价**：①daemon 无内置的「上次成功时间」持久化——进程重启后周期从重启时刻重新算，不追补遗漏周次；这对周更（窗口足够宽）可接受，但意味着**重启会推迟下一次采集**。②失败只记进程日志，没有外部告警通道（一期无管理端 UI，admin 界面在 spec 的 Out of Scope 里）；发现「周更一直失败」需要人看容器日志。③常驻进程占 256M 内存/0.5 CPU 的常驻配额（compose 既有 limits），即使一周只干活一小时——这是简单性的代价，可接受。④**解析不出样本的公告不会被记住**——它们没有 `source_url` 落库行，因此不在幂等判据里，每周都会重新抓取、重新抽取一遍（判据字面只要求「已入库公告幂等」，故未修；常驻模式下这是每周固定浪费，留作后续票）。⑤**`run_daemon` 会一直累积 `results` 与 `crawler.log`**，`max_cycles=None` 下内存单调增长；周更节奏下年量级可忽略（几百条），但如果有人把它当高频任务用就会出问题。⑥**fail-loud + `restart: unless-stopped` = 配错时docker 重启循环**：`docker compose config -q` 拦不住空 URL，容器会反复起停。这比旧的静默空转更吵、更容易被发现，是刻意选的方向，但确实会在配错时刷屏。⑦**collector 镜像不在任何 CI/CD 构建面**：`deploy.py` 的 APP_SERVICES 不含它，`cd.yml` 也不 build 它——生产周更依赖手工 build 的 `forklift-collector:latest`。这是 ADR 决策五「与后端发布解耦」的直接后果，运维需自行保证镜像更新（留作后续票）。

**实施边界（本票不做）**：多平台采集面（#2679 京东/gpai、#2680 产权交易所）、告警通道、失败次数持久化与追补调度、管理端 UI、评估路径改动。
