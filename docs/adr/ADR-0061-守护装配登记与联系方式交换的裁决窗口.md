# ADR-0061: 守护一律在装配根登记；裁决窗口是 pending 的属性

- 状态：已接受（2026-09-20，#1197 定案）
- 领域：装配根 / 进程内定时任务 / 联系方式交换（L3）/ 跨端契约
- 前置登记：ADR-0022 §三层漏斗（14 天过期的原始口径）、ADR-0025（投递即授权）、ADR-0053 §3（授权读面单点）、移动端 ADR-0022 §⑤/§⑥（缺口与验收条）
- 词汇表：`CONTEXT.md` 的「联系方式交换」条目已登记 **裁决窗口（decision window）** 并列出 `_Avoid_`

## 背景

`contact_requests` 的 14 天过期机制从来没有运行过。决定时点（`842209bf`）的事实：

- `ContactService.StartExpireRunner`（`service/contact_service.go:413-428`）自 `598add7c`（2026-08-30）起就是全仓唯一的生产者，**零调用者**；`cmd/server/main.go:167-168` 只装配了 `forum-image-cleanup` 与 `contribution-file-cleanup` 两个守护。
- 迁移 `000010_contact_requests.up.sql:15` 早就建了 `idx_contact_requests_status (status, expires_at)`——正是 `ExpirePending`（`:372-378`）的谓词形状。**索引是为这个守护建的，守护却没接上**，故属漏装配而非「设计成不跑」。
- 全仓无可外部触发过期的端点，部署侧无业务 cron（`scripts/setup-server.sh:329` 那份 `/etc/cron.d/forklift-maintenance` 只有 docker 缓存清理与日志截断）。⇒ 超期 `pending` 永久停在 `pending`。
- 「同一企业对同一学员 `pending` 唯一」有**两个源**：应用层计数（`:155`）与库层偏索引（`000010:16` `WHERE status = 'pending'`）。守护不跑 ⇒ 两个源一起把该组合长期堵死（唯一的惰性出口是学员点同意/拒绝）。
- 现有的过期测试是**自我实现**的：`contact_contract_test.go:329-340` 在断言失败时现场 `NewContactService` 调一次 `ExpirePending` 再断言，注释还留着「我们无法直接拿到 service」（`:318`）⇒ 漏装可以静默存活三周，正因为这条测试恒绿。
- `expires_at` 在**全部存量行**上严格等于 `created_at + 14d`（生产代码只有两处写入：`:193` 与 `:236`，且无任何更新路径碰它）。⇒ 它要么是冗余列，要么是别的东西——见 §2。

## 决策

### §1 进程内守护在装配根登记，不在 `main.go` 手写调用

`NewDeps` 除了构造服务，还产出 `deps.Daemons`：一张「守护名 + 启动闭包」的登记表，由 `cmd/server` 遍历启动并交给 `daemonCtx`。测试锁 `cmd/server` 侧的名字集合。

- 三个既有守护全部入表：`forum-image-cleanup`、`contribution-file-cleanup`、`contact-request-expire`。
- `middleware/ratelimit.go:44` 的 `rate-limit-cleanup` **不入表**：它由中间件构造时自我装配，结构上不可能被漏装，登记反而会把它的生命周期从所属组件摘出去。

### §2 裁决窗口只约束 pending；`expires_at` 是签发时的承诺

- 领域上：`expires_at` = **裁决窗口**关闭的时刻，**只对 `pending` 有意义**。`approved` 是永久授权（出口只有学员撤回与学员注销），门禁继续不看时间。
- 迁移 `000039`：`expires_at` `DROP NOT NULL` + `CHECK (status <> 'pending' OR expires_at IS NOT NULL)`；`EnsureApproved` 不再给 `approved` 行写该列。
- 14 天收成单点常量，`Create` 与 `EnsureApproved` 共用。**改窗口长度只影响新签发行**，存量行保持签发时的期限。
- 落态有两条互补路径：周期守护收敛无人触碰的行；`Create` 在判唯一前对这一对 (企业, 学员) 做**定向过期**，让正在重试的企业当场拿到真结论。`Approve` 既有的惰性落态保留，三处共用同一个 `expirePending` 单点。
- 撞库层偏索引（23505）映射成与计数分支**同一句**「已存在待处理的申请」。
- 超期落 `expired` 后，同一企业**可立即重发，不设节流**。

## 理由

- **§1 的理由是「漏装必须不可能，而不是必须被记得」**。旧形状下「加一个守护」= 在 `main.go` 里再手写一个 `start*`，与它的服务构造隔了两个文件；新形状下服务与它的守护在同一处登记，测试回答的是「登记表里有没有它」这个行为问题，而不是「源码里有没有那行调用」。仓内标准（移动端 ADR-0022 §⑥ 标题）**断言行为，不断言源码文本**——静态守卫脚本扫 `main.go` 文本能拦住这次的漏装，但改名即可绕过，且与该标准相冲，故否。
- **`expires_at` 不是冗余列，是签发时的快照**。判据是「常量变了该怎样」：若改用 `created_at + 常量` 派生，把 14 天调成 7 天会**追溯改写历史上每一行对学员做过的期限承诺**。物化列正是「承诺 vs 计算」的经典分野，所以列保留、常量收成单点、并由 CHECK 把「pending 必须有窗口」钉在库层——本案的教训恰好是应用层约定会漏。
- **重发不设节流：不响应的代价不该由企业承担**。学员只要点一次「拒绝」就把企业送进 30 天冷却——节流的开关本来就在学员手里，沉默 ≠ 拒绝。反过来若把 `expired` 也塞进冷却，学员的不响应会变成企业被长期遮住，且「冷却中」与「未回应」在 UI 上无法区分。**这是修好之后才会出现的新行为**（今天因为永久堵死而不存在）：节奏 = 窗口长度，每企业每学员 14 天最多一次。
- **冲突文案为真，不是掩盖竞态**：插入撞索引，说明对手已经写入了一条 `pending`，那么「已存在待处理的申请」就是事实。计数分支与索引分支因此收成同一句，三层出口（计数 / 索引 / 文案）不再各说各话。
- **`Start` 首轮等满 interval**（`daemon/runner.go:64` 注释明写）⇒ 存量超期行最迟一小时收敛，加上 §2 的定向过期，企业主动重试时当场收敛，故**不需要**启动即跑一次。

## 被否备选

- **守护挂服务器 cron + 新增触发端点**：必须新造一个外部可写的触发面并保护它（今天全仓没有），而 `internal/daemon` 这个深模块就是为此而生；为假设的运维收益引入第二套适配器 = 假 seam。
- **静态守卫脚本对账 `main.go`**：断言源码文本，与本仓标准相冲，改名即绕过。
- **分布式调度**：本仓无任何调度设施，等于先造一层调度器再装一个过期任务。
- **把「过期」塞进唯一谓词（「过期即释放」）**：Postgres 偏索引谓词必须 IMMUTABLE，`now()` 是 STABLE ⇒ `WHERE status='pending' AND expires_at > now()` 建不出来；只放宽应用层则库层照样 23505。守护 + 定向过期让两个源在同一口径上会合，不需要动索引形状。
- **`expires_at` 改派生表达式 / 远期哨兵值**：前者销毁签发时快照并需要 DROP COLUMN（不可逆）+ 重建索引 + 改对外字段；后者把刚在词汇表里钉开的「裁决窗口」与「授权寿命」重新糊回一个概念。
- **`approved` 也受 `expires_at` 掐断（授权寿命）**：与 `CONTEXT.md` 的「永久授权、撤回实时生效」正面冲突，属面向用户的行为变更，且没有续期/提醒机制时会造出「授权悄悄失效」的信任问题。
- **只装守护、不加定向过期**：最省事，但两次 tick 之间企业看到「已存在待处理的申请」、学员同期点同意得到「申请已过期」，同一对关系两个视图。
- **expired 进 30 天冷却 / 阶梯节流**：见上文理由；阶梯需要新的计数事实源，且当前没有任何被骚扰的反馈证据。

## 锁

- `cmd/server` 测试：`deps.Daemons` 名字集合含三条（漏登记当场红）。
