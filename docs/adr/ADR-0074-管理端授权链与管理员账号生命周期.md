# ADR-0074: 管理端授权链与管理员账号生命周期

- 状态：Accepted
- 日期：2026-10-10
- 关联：#1618（段1 角色权限链）、#1621（段4 授权两页）、#1630（能力中文名）、#1632（新建/删除管理员）、#1639（能力粒度按侧栏叶子）；ADR-0047 §1（能力表是唯一事实源）、ADR-0064 决策 4（口令族与注销族两族终止语义）、ADR-0069（列表装载的写回形状）

## 背景

改造前管理端只有「管理员」一个角色：谁能进后台是**代码里写死的**（`authz.RoleAdmin` 对管理端能力一律 true），超管与普通管理员在权限上无法区分，更谈不上「超管控制其它管理员的权限」。管理员账号本身当时也只有列表可读（#1621 段4 补了角色 CRUD 与改挂角色），**新建与删除没有端点**（#1632）——界面上那两个动作无处可去。

## 决策

**一、授权载体是角色表，不是逐人授权**：`admin_role` + `admin_role_capability` + `admin.role_id`（迁移 000041 一次建齐，同一迁移内 seed 受保护角色并把存量管理员全部挂上——不留「迁移完成但没人有权限」的中间态）。

**二、能力判据走数据层**：`authz` 的静态表对 `admin` **一律 fail closed**（能力行留空集，键保留），有效能力集由 `internal/admincap.Resolver` 按管理员查库（进程内 40s 缓存）。守卫读到的「无能力」渲染 403，**查询故障渲染 500**——故障不得伪装成权限问题。

**三、三层防自锁**（本 ADR 的核心不变式）：

1. **受保护角色不可改能力、不可删**（`protected` 行 + `ErrProtectedRole` → 409）；
2. **最后一个超管不可降级、也不可删除**（`ErrLastSuperAdmin` → 409）——判据在「降级」与「删除」两个动作上同形；
3. 授权界面本身只挂在受保护角色持有的两个能力键上（`admin_role.manage` / `admin_account.manage`）⇒ 界面可达性由能力表自动成立，代码里没有任何特判。

**四、管理员账号的新建与删除**（#1632）：

- **新建**：账号 + 姓名 + 口令 +（可选）角色。口令走 `core.ValidatePasswordLength`（6-20 位，与学员/讲师/招聘者同一处声明）后 bcrypt 落库；账号名唯一（重复 → 409）；**角色可缺省**（`role_id = 0` = 未授权：登得进、什么都看不到，直到超管给它挂角色——与「新建角色默认无能力」同一姿势）。
- **删除**：先写全会话吊销标记、**再**落库删除（注销族语义，ADR-0064 决策 4）：删除不可回退，而令牌在过期前仍然有效——标记写失败即整体不生效（账号还在、人还能重新登录），不留下「人已删、凭证还活着」的中间态。拒绝三种：删自己（409）、删最后一个超管（409）、账号不存在（404）。

**五、防自锁判据的实际可达性**：任何能调删除的操作者本身也持有 `admin_account.manage`（受保护角色持有它），所以「删最后一个超管」通常被「删自己」先挡住；但该能力**可以**被授给普通角色（授权页把它列在可勾选集合里），此时那条判据就是唯一拦住「删掉最后一个超管」的东西——它因此不是死代码，契约测试按这条路径覆盖。

**六、账号停用不在本批**：`admin` 表没有 `status` 列，「停用」要让登录与能力解析**都**尊重它，是独立一小片（与口令代重置一起另开票）。在没有它之前，删除是唯一的下线手段。

## 理由

- **为何用角色表而不是逐人能力**：管理端是「同一批职责的多人共用一套权限」的形态，逐人授权会让「给新来的运营配一遍权限」变成每次都要重做的手工活，且没有可审计的角色名。
- **为何每请求查库而不是把能力集写进令牌**：令牌是 1 小时级的快照，写进去就意味着「收回权限要等令牌过期」。40s 缓存把开销压在每管理员 40s 一次，而撤销的生效延迟与「刷新页面」同量级。
- **为何口令写面复用 core 的动作**：新建账号是口令写面的一种；自建一套哈希/长度校验就会出现「某条入口漏了长度规则」这类不对称（#1355 起仓里的既有教训）。
- **为何删除走注销族而不是口令族**：口令族是「已生效动作之后的补救」（改密不可回退，吊销失败只能记日志）；删除没有这个问题——它完全可以「先吊销、失败就不删」。

## 后果

- 超管给某角色勾了哪些能力，只持有该角色的管理员**下一次能力集刷新**（≤40s 或刷新页面）后看到变化；侧栏按运行时能力集过滤，够不到的菜单不会出现在侧栏里。
- 新增管理端能力时：加进 `authz.go`（键 + 受保护清单）→ `gen-authz` → 前端 `AuthzCapability` 联合类型；授权页的可勾选集合取自**接口返回的并集**，不需要在前端另抄一份清单。展示名走 `utils/capabilityWords.ts`（`Record<AuthzCapability, string>` 穷尽，漏一个即 type-check 红；#1630）。
- 新建的管理员默认未授权：建号与授权是两步，**建号不会顺手扩权**。
- 删除管理员后其 refresh 链当场失效；即便手上还留着 access token，能力解析也会因账号不存在而 fail closed。
- 「删成功」这条契约用例打在服务面（`internal/admin/admin_account_test.go`）而不是 HTTP 面：契约装配里服务持有的会话是 Redis 版，而删除要真写吊销标记。
## 修订（#1639）：能力粒度按侧栏叶子

管理端的能力键此前按**资源域**切：`admin.access` 一个键盖住仪表盘/统计分析/用户管理/讲师管理/AI 配置五页，`catalog.manage` 盖住课程/岗位/证件三页，`content.manage` 盖住内容生成/内容精选两页。后果是授权界面上的一个勾选框对应侧栏的好几页——「只给用户管理、不给讲师管理」表达不出来。

**一、一页一键**（清单即侧栏叶子）：

| 侧栏叶子 | 能力键 | 含义 |
| --- | --- | --- |
| 仪表盘 | `admin.access` | 管理端入口与仪表盘（保留） |
| 统计分析 | `statistics.read` | 统计看板 |
| 用户管理 | `hrwai_user.manage` | HRWAI 用户管理 |
| 讲师管理 | `tutor.manage` | 讲师账号管理 |
| AI 配置 | `ai_config.manage` | AI 配置与功能绑定 |
| 课程管理 | `course.manage` | 课程与章节管理（含方向/等级/证书模板字典） |
| 岗位管理 | `position.manage` | 岗位字典管理 |
| 证件管理 | `credential.manage` | 目标证件管理 |
| 内容生成 | `content.generate` | 课程内容 AI 生成 |
| 内容精选 | `featured.manage` | 内容精选管理（列表与编辑共用一键） |

`catalog.manage` 与 `content.manage` 随之删除：它们的可达面被上表五个细键瓜分完。前端 `config/pages.ts` 里每个管理页描述符的 `capability` 就是上表的一格，`config/__tests__/manageCapabilityPerPage.spec.ts` 锁住「自成标签的管理页两两不同键」。

**二、共享只读面走「任一命中」**：一片只读面被两个叶子共用时，端点无法只声明其中一个——声明成一个就等于给另一个叶子的持有者关上门。守卫因此改为可变参、**任一命中即放行**（单参调用的语义不变）：

| 端点 | 候选能力 | 为什么共享 |
| --- | --- | --- |
| `GET /admin/courses`、`GET /admin/course/:course_id` | `course.manage` / `content.generate` | 生成页要先选课程与章节 |
| `GET /admin/credentials` | `credential.manage` / `course.manage` | 课程按目标证件挂载，课程管理要读这份字典 |
| `GET /admin/catalog/tree` | `course.manage` / `position.manage` / `credential.manage` | 三片叶子都要在树上选挂载点 |
| `GET /admin/statistics` | `statistics.read` / `admin.access` | 仪表盘与统计页读同一份概览 |
| `GET /admin/points/ledger` | `inspection.read` / `points.admin` | 巡检视图读它，积分管理也读它 |
| `GET /admin/job-reports` | `job_report.handle` / `inspection.read` | 举报队列是巡检视图的一格 |

写面一律不给候选：POST/PUT/DELETE 只认自己那一片的键——**读得到不等于改得动**（课程管理员读得到证件列表，建不了证件）。

**三、动作能力不占侧栏页面**：`export.run`（数据导出）、`points.admin`（积分扣罚）、`job_report.handle`（职位举报处置）、`catalog.author`（题库标签）没有对应的管理页，授权界面把它们收在最后一组「动作能力（不占侧栏页面）」。分组标题与顺序（总览/用户与内容/教学管理/系统）都从 `config/pages.ts` 的 `navGroups.manage` 派生，界面不再按资源域分组——按域分组正是「课程管理」「岗位管理」挤在同一个标题下的原因。

**四、旧粗键由迁移展开（不缩权）**：迁移 000042 按「持有者拿到的是同一片可达面」把粗键展开成细键：`admin.access` 的行**保留**并追加 `hrwai_user.manage`/`tutor.manage`/`statistics.read`/`ai_config.manage`；`catalog.manage` 展开出 `course.manage`/`position.manage`/`credential.manage` 后**删除该行**；`content.manage` 展开出 `content.generate`/`featured.manage` 后**删除该行**。旧键必须删干净：留着它既会让可达面比授予时更宽（新代码里它已不在能力表内，界面看不到也管不着，守卫却仍会放行），也会让保存角色直接 400——后端按能力表收口，表里持有表外键会让整次保存失败，界面从此改不动任何角色。
