# ADR-0089：反馈小域——面向平台的单向消息、两态、不做工单流

- 状态：Accepted（2026-10-28）
- 日期：2026-10-28
- 领域：帮助中心 / 学员与平台之间的单向消息（**新域**）
- 票：spec #1935 草稿 08（#2070）+ Web 票 12（#2074）
- 判据物：`backend/internal/feedback/`、`backend/internal/api/feedback_contract_test.go`、`frontend/src/pages/admin/FeedbackManage.vue`

## 背景

帮助中心此前只有 FAQ（`GET /api/faq` 只读整页）。学员遇到「课程看不了 / 积分少了 / 想提建议」**没有任何落点**：

- **论坛**是公开内容面——发出去是给别人看的，还要过治理（删帖、举报处置）。把「我这边出故障了」发到广场上，是让所有学员围观一次客服工单；
- **站内信**是平台→学员的**下发通道**，学员没有回写入口；给它加回写会把「谁在读」和「谁在答」压进同一张表；
- **内容精选**是可编排的编辑内容，与「某个人遇到的问题」不是一类东西；
- **举报**是内容治理的入口（举报职位/帖子），判据是「这条内容违规」，不是「这个功能坏了」。

原型 `帮助中心.png` 有「反馈消息 / 反馈历史 / 在线客服」，报告 §8 Q21 裁定：反馈立小域，在线客服 = 跳现有 AI 助手入口（零新算法，另票）。另有一条非功能动因：小程序教育类目送审要求**客服可达**——没有反馈通道，投诉就没有落点。

## 决策

1. **单一实体、两态**：新表 `feedback`，状态只有 `pending` / `handled`，只记 `handled_at`（与处理人 `handled_by`）。**没有**流转历史、没有回复线程、没有工单号、没有优先级、没有 SLA。
2. **三个动作、四个端点**：
   - 学员 `POST /api/feedback`（提交）、`GET /api/feedback`（本人历史，分页）；
   - 管理端 `GET /api/admin/feedback?status=`（列表，可按状态筛）、`POST /api/admin/feedback/{id}/handle`（标记已处理）。
3. **标记已处理是幂等的**：已处理的行再点一次，返回同一行、200、不改 `handled_at`。管理端列表里最容易被连点的就是这一列，报错只会让人以为操作失败。
4. **内容 = 文字 + 图片 + 联系方式**：文字必填（1–1000 字，去空白后判空）；图片 0–3 张；联系方式**可空且不强制格式**——学员可能写手机、微信号、QQ、邮箱，甚至「晚上八点后打」。格式校验会把真实可用的联系方式拦在门外，「可空」与「不校验格式」是同一件事的两面。
5. **图片复用论坛图片上传通道**（`POST /api/forum/upload-image`，前缀 `images/forum/`，同一套类型/大小校验；通道与类型表见 ADR-0066），**不新建通道、不新建前缀**。提交时按 ADR-0066 决策 5 的**可迁移那三条**校验：本站前缀（防外链）、扩展名在上传白名单内（读服务端铸造的 URL，不读客户端自报的文件名）、文件在存储侧真实存在；另加一条本域自有的「同一次提交内去重」。
  **投稿的第三校验（「同一 URL 未被任何投稿登记过」）在这里有意不迁**：它承重的前提是投稿附件**按用户分区**（`contributions/<uid>/`，引用即归属），而 `images/forum/` 不是按用户分区的目录——照抄会造出一条「任何人复用别人已用过的图」都判红的判据，而那条判据在本域的后果只是几行重复图片，不是归属被洗白。
6. **图片生命周期挂进既有回收（本域唯一的跨域耦合）**：反馈图与论坛图同前缀，因此**论坛悬空图片清理的引用集必须把反馈行算进去**——那轮清理每 6 小时跑一次、删的是 24h 后仍未被引用的文件；漏了这一格，反馈图片会在一天后变成裂图，而且**没有任何报警**（清理是静默成功的）。实现处注释与 sweep 配置处各留一句。
7. **两条能力键**：`feedback.submit`（学员）/ `feedback.manage`（管理员，进受保护角色能力全集）。不复用 `faq.read`：在 `/feedback` 上用「读」的能力键做写动作，会让能力名与它保护的动作脱钩。
8. **边界写死**：不建工单流 / 回复线程 / 状态机流转 / 通知下发；不改论坛、站内信、内容精选的既有语义；反馈不进全局搜索、不进内容精选、不进举报队列、不影响任何既有读面。

## 备选

- **直接上工单表（分配 / 优先级 / 流转 / SLA）** —— 拒绝。本期没有处置人、没有 SLA 承诺；建了就是一堆没人填的列，还会诱导「把反馈当任务派」的用法。
- **站内信双向化（学员可回复）** —— 拒绝。站内信的下发语义是它被各处复用的原因（通知、扣罚、投递）；一旦可回写，每条通知都要回答「这是不是一条会话」。
- **反馈发进论坛的某个私密板块** —— 拒绝。论坛的全部可见性判据都建立在公开面上，私密板块等于再立一套可见性判据，与「小域」的规模不匹配。
- **图片另建前缀 + 自己的上传端点** —— 拒绝。票面明确「不新建通道」；同前缀 + 引用集扩展的代价（一处引用源）远小于再养一条上传链路（校验、类型表、清理、监控各一份）。
- **状态加第三态（处理中）** —— 拒绝。三态以上必须有人定义「谁能进、何时进」，本期没有处置人。

## 后果

- 新增 `feedback` 表（迁移 000046）与 `internal/feedback` 域包；管理端多一个列表页（能力 `feedback.manage`），学员面两条路由挂 `feedback.submit`。
- 论坛悬空图片清理的引用集多一个来源（`model.Feedback`）。**这是必须的**，不是顺手加的：反馈图与论坛图同前缀。
- 反馈不产生通知、不产生积分、不影响任何既有读面；删学员账号时反馈随 `ON DELETE CASCADE` 一并消失（与站内信同口径）。
- 将来若要「平台回复学员」，那是一条**新的**下发决策（走站内信还是走反馈会话），不在本 ADR 的射程内——本 ADR 只裁定「收得到、看得到、标得掉」。
