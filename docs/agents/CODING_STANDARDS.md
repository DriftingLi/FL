# 编码规范（judgement 类）

本文件收「做起来要判断、没法交给机器判」的规范；能写成确定性检查的放 [`checks.md`](checks.md)，不在这里写第二遍。读者：实施会话，以及评审（code-review 技能的 Standards 轴）。来路：票 #2346（retro #2317）。

## 规则 1：新增守护 / 机检前，先查「不立守护」裁定

**触发**：准备新增任何会判红的东西——CI 步骤、守卫脚本、lint 规则、预检硬判据、测试断言。

**动作**：先在仓内查是否已有「不立守护 / 不设阈值 / 刻意不锁」的已裁定结论，四处都看：

1. `docs/design/` 下的裁定 / 结论记录；
2. `docs/adr/`；
3. `docs/agents/` 下记录的不锁结论；
4. 相关票的正文与结论（`gh` 不可用的会话里用票链接或 `deck_issue_get` 读票面与评论；读不到票面——认证失败、额度见底等——不等于「没有裁定」）。

命中则遵守裁定：不补门、不写第二份实现；认为裁定该翻案，先在票里提出、另行裁定，不在新增守护时顺手绕过。

**reviewer 的判法**：diff 里新增了门 / 机检 / 硬判据，且命中上述裁定 ⇒ 判 standards 违规，引用裁定、指出应回退；未命中则放行。

**为什么是判断类**：机检要自建一套与实现并行的判定逻辑，等于造第二份实现——收益一次性、成本持续；而「该不该立」取决于上下文（裁定当时的边界是否变了），机器判不了，只能人在 diff 里读。

**首个实例**：票 [#2317](https://github.com/DriftingLi/FL/issues/2317) 的「兜底边口径该不该立机检」边界分析，维护者裁定**不立机检**，三条候选判据均不落成门；裁定与理由的仓内单一真源是 [`docs/design/20261107-兜底边口径机检判据边界裁定.md`](../design/20261107-兜底边口径机检判据边界裁定.md)，本文件不复述。

## 规则 2：本文件只收判据，不接确定性检查

能写成 lint / typecheck / test / CI 断言的，放 [`checks.md`](checks.md) 与脚本里。本文件留给人 / agent 在评审时读，不产出任何门禁。

## 新增规则的写法

一条规则至少写清：触发条件（什么时候要想到它）、动作（查什么、命中后怎么办）、为什么判断类（为什么不交给机检）。有实例就挂票号，不复制实例正文——复制品会漂移，原处为准。
