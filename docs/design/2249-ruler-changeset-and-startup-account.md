## 6. 测不到 / 未证实

1. **「平均套件」的启动开销没测。** 只用 62 行 / 2 用例的轻量套件测固定成本；真实套件的固定 + 可变成本不线性可加（jest 的 transform 缓存命中率随套件变），所以 §3 的「89 s 上界」是**粗糙上界**，不是预测。
2. **没有重算 39 个历史改动集的平均子集。** #2019 时代是 80–81 套件、平均 30.8/81（38.0%）；本轮现测 106 套件、单文件档 22.6%–29.2%。**比例降了，但绝对值从 ~31 个套件变成了 24–31 个**——两个数不能直接对比「变好还是变坏」，因为套件总数也变了。
3. **b′ 名单的 21 个是否都还必要没验证。** 本笔记只量化了它把最小子集从 1–8 抬到 24 的价格（§0 第 4 条），**没有做「逐个关掉看红不红」的实验**（那要改 `behavior-suite-deps.mjs`，违反本票「不改被测物」）。
4. **形态 A 的「powershell 层」没有单独剥离。** 真实链路是 `powershell → dev-finish.ps1 → cmd → npm → jest`，本笔记的 A 形态省掉了 `dev-finish.ps1` 那一层（直接用 `cmd → npm`）。**所以 841 ms 是 npm 层的下界**，真实链路还要加 pwsh 脚本启动（未测）。
5. **跨机器不可移植。** 本机的 `Get-NetTCPConnection` 单次 1.5–2.5 s（见配套笔记）与 node 的进程启动都在同一台机器上测得；换机器（尤其 Linux/macOS）这张表全部作废。
