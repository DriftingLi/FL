先给结论。「真机验证」在本仓不是一个门，是三件可分别省略的东西，省略成本完全不同：

- **①a 真机逐页取证：可以省。** 当前「小程序优先窗口」内它本来就不跑，省略的实际增量是改写移动端 ADR-0040 的退出前置（32 页欠账）。它的历史空转率极高（近 20 个触及运行时面的合并 PR 里 5 个声明真机门、0 个留可核验产物），真实损失小于名义损失，前提是省下来的义务转移到 §3.4 的发版冒烟上。
- **hx:run 日常真机运行：不能省。** 它不是门，是 App 端唯一的反馈通道。uni-app x 标准基座只打 `arm64-v8a`，本机 AVD 是 x86，微信开发者工具只跑 mp-weixin 端。省掉它等于闭眼写 `.uvue`。
- **①b 能力面人工签收：不能省。** 指纹要人把手指按上去，机械上无替代（移动端 `docs/adr/0008-移动端验收门与证据.md`:892-898）。

外部对照支持同一分法：微信小程序云测在 mp-weixin 端有云真机替代；uni-automator 与 Android 模拟器都覆盖不到 uni-app x 的 App 原生端；DCloud 官方「真机自动化」路线本身就跑在真机上。调研的 7 个主流开源项目里，每 PR 跑真机设备农场的只有 React Native 一个；Flutter 的真机全部在 postsubmit。「省略真机、靠灰度加监控兜底」在大用户量项目里常见，在与本仓同规模的项目里未找到公开先例。

## 3. 分层影响

### 3.1 ①a 逐页取证：可以省，省掉的是「发现机会」而不是「日常回归」

会失去什么（真机独有失败模式）：

- 移动端 `docs/adr/0008-移动端验收门与证据.md`:189 对 ② 门的非等价声明：`content://` 上传、生物识别、第三方 SDK 回调、真机性能 / ANR 四类在微信开发者工具门上结构性测不出来。
- 0008:868（#883 spike 实测）记三例实害：`content://` 上传 602001、证件 level NPE、生物识别强转崩溃；开发者工具 console 报 `checkIsSupportSoterAuthentication:fail ... 请使用真机进行开发`。
- 最强论据是 #1389：移动端 `docs/adr/0030-refresh令牌的通道归属与族判定口径.md` 原写「本端不得假设 body 通道一定被走到」，真机 logcat 读数定案 App-Android 容器不维持 cookie jar，原句就地作废并标注「（#1389 反转，原句作废）」。这是真机读数改写架构结论的实例。省略真机后，这类发现要么推迟到发版冒烟，要么由线上用户暴露。

会省下什么（①a 自身的空转账）：

- 0008:72 全量逐个核对最近 20 个触及 `training-app/**` 且改 `*.uvue`/`*.uts` 的合并 PR：14 个声明 HBuilderX 编译门，5 个声明真机门，留下可核验产物的是 0 个。这套门 2026-09-13 立起来正是为了治这个。
- `docs/design/1494-mobile-dev-wallclock-audit.md` §2（掐表实测，2026-10-03）：一次 ①a 以 `index 导航未在 420 秒内落定` 结束、零截图；另一次 `PASS=0 FAIL=0 SKIP=1`，零产出。
- `docs/agents/ledger.md` 真机相关条目：#8 adb 解析三份 json 漂移（坏的那份只在真机露出来）、#9 全帧 hash 判据被 MIUI 实时网速钉死（后改 0.5% 差异像素）、#13 真运行会话常驻攥住项目目录、#14 `.ci-verify/` 随 `git worktree remove` 一起消失（判据输入永久丢失）、#23 #1713 的 25 个真机取证文件（6.5 MB）濒临失联。
- 量化底数（现测）：`docs/verification/` 共入库 90 个文件，`device/` 目录只有 4 个（`device/1116/*.png`），是各证据面里最少的；近 90 天 `training-app/` 提交行 397、唯一 `.uvue`/`.uts` 改动文件 261（近 30 天 151）；自 2026-08-01 起 commit message 含「真机」142 条。

结论：①a 历史上接近纸面门，省略的真实损失小于名义损失。省它的前提是那四类失败有下游承接，即 §3.4 的发版冒烟。省略 ①a 又不保留发版冒烟，等于把四类失败直接推给线上用户。

省之后要改什么：0040 决策 1（窗口内完全不跑）可以原样保留；要改的是退出前置（32 页欠账）与窗口退出后的常态节奏（0016 裁定 5「一次分支收口跑一次」），需要一份移动端新 ADR 把 ①a 正式降级为「发版前一次」。

### 3.2 hx:run：不能省，App 端没有替代载体

- 基座 arm64-only：移动端 `docs/adr/0030` 记（#1389 现测）uni-app x 标准基座 `android_base.apk` 内 47 个 `.so` 全为 arm64-v8a、无 x86/x86_64，而开发机两个 AVD 均为 `abi.type = x86`。模拟器路线结构性走不通。
- 微信开发者工具只跑 mp-weixin 端，看不到 App 侧 `.uvue`（编译为 Kotlin、原生 UI）的渲染与交互。
- 所以观察 App 端行为的唯一手段是真机。hx:run 不是门，省掉它不会触发任何红灯，但等于闭眼开发：近 90 天 261 个改动文件的反馈来源从「编译即见」变成「等发版冒烟集中暴露」。0040 自己给集中暴露记了账：「窗口内真机问题（真机独有交互、样式像素）不暴露，全部推迟到退出后集中爆发，退出批需预留返工缓冲。」
- 如果省略的动机是省每次 4-5 分钟的迭代（`docs/design/mobile-workflow-friction-survey.md`：设备侧一次视觉满意点约 235 秒，编译 66 + 装机 78 + 导航 83 + 截图比对），正确的杠杆是自动化替代人眼看（uni-automator `remote: true` 真机自动化，见 §4.1），不是砍通道本身。

### 3.3 ①b 能力面人工签收：保留（用户口径），且不用动它

- 0008:892-898：①a 不替代 ①b，指纹要人把手指按上去。
- 四类能力面触发（指纹、运行时权限弹窗、真机上传、厂商 ROM 交互）与 §3.1 的失败模式四类重合。Android 模拟器的虚拟指纹（官方表述见 §4.3）只模拟标准 `BiometricPrompt` 路径，测不了微信 Soter（开发者工具直接报 fail）、TEE 与厂商 ROM 交互。本仓的生物识别包络是快捷登录的核心路径（移动端 `docs/adr/0004-生物识别门控.md`，移动端编号体系）。
- 现状：0040 决策 5 已经把能力面 PR 推迟到退出后，这是「推迟」不是「省略」。保留 ①b 意味着这条不用改。
- 缺口：①b 的实际命中频率（多久命中一次能力面）仓内无记录，保留它的成本无法量化，见 §7。

## 4. 外部对照：官方能力边界与同类实践

以下 4.1-4.4 全部为 2026-10-23 现抓官方文档原文，页面文本存 `.scratch/research/*.txt`（不入库，本文件引行号处可复核）。

### 4.1 DCloud uni-automator

来源：https://uniapp.dcloud.net.cn/worktile/auto/quick-start.html 、 https://uniapp.dcloud.net.cn/worktile/auto/api.html

- 支持 uni-app (x) 项目自动化测试（quick-start:229-238，含「标准的 uni-app x 项目测试工程目录」）。API 能力：运行、跳转页面、触发点击、获取页面元素状态、截图（quick-start:185-189）。
- 平台差异表（quick-start:190-211）：App √（iOS 仅支持模拟器）、H5 √、微信小程序 √；支付宝、百度、抖音、飞书、QQ、快应用、快手、京东小程序均 ×。
- Android 真机自动化经 `env.js` 的 `remote: true` 开启（quick-start:507、603，注释「是否真机自动化测试」）。iOS 真机不支持设备截图 API（api:1149「iOS 仅支持模拟器，iOS 真机不支持该方法」）。
- 设备级 API 在真机上不完整：`program.device.setScreenOrientation` 仅支持 Android 模拟器和 iOS 模拟器，不支持 Android 真机、iOS 真机及 HarmonyOS（api:1360）。
- 微信端选元素受限：分包页面需延迟约 7 秒以上（quick-start:636）、element 不能跨组件选择（658）、暂不支持父子选择器（713）。
- 结论：uni-automator 能把 ①a 的「导航 + 截图 + 元素断言」脚本化，是省 hx:run 人眼时间的正确杠杆；但 App 端唯一可靠载体仍是真机（基座 arm64 限制对本仓同样成立）。它是「把真机验证自动化」，不是「省略真机的替代品」。它也解不了 ①b：脚本能点按钮，不能替人按手指。

### 4.2 微信侧

来源：https://developers.weixin.qq.com/miniprogram/dev/devtools/auto/automator.html 、 .../auto/remote.html 、 .../minitest/autotest.html

- Automator 模块本体「提供了启动及连接开发者工具的方法」（automator:216），经 `cli auto` 命令行开启自动化端口（246-250），默认载体是开发者工具模拟器。
- 官方另有「真机自动化」：`miniProgram.remote()` 扫码启动真机调试，后续测试脚本在真机上执行（remote.html:216-229，要求基础库 2.7.3 及以上）。
- 小程序云测（MiniTest）是云真机农场：智能化 Monkey（自研智能探索算法、零代码冒烟）、录制回放（开发者工具录制、云测真机回放）、自定义测试（真机跑测，官方原文「无需用户部署和维护真机环境」）、图片对比（满足 5 个相同基准条件自动与基准图对比）。
- 结论：mp-weixin 端的「真机验证」已有官方云替代，本仓窗口内把 ② 升为每 PR 主门正是押在这个边界上。但以上全部够不到 uni-app x 的 App 原生端（App 端不跑在微信里）。小程序侧兜底强、App 侧兜底缺，是本仓的不对称。

### 4.3 Android 官方模拟器与 adb 边界

来源：https://developer.android.com/studio/run/emulator-extended-controls 、 https://developer.android.com/tools/adb

- 模拟器扩展控件含 Fingerprint 面板，官方原文：「This control can simulate 10 different fingerprint scans. You can use it to test fingerprint integration in your app.」（extcontrols:842-845，API 22 及以下与 Wear OS 禁用）。标准 `BiometricPrompt` 集成在模拟器上可测。
- 但本仓生物识别链走微信 Soter 与厂商框架（开发者工具报 `checkIsSupportSoterAuthentication:fail`），虚拟指纹覆盖不了 Soter、TEE 与厂商 ROM 交互。
- `adb shell pm grant` 官方表述「Grant a permission to an app」，API 23+ 可授予 manifest 声明的任意权限（adb:1967-1970）。运行时权限弹窗可程序化绕过；「绕过弹窗」不等于「测到弹窗行为」，测弹窗行为要点系统 UI，而本机真机现测 `INJECT_EVENTS` 被厂商 ROM 拒（移动端 `docs/adr/0030`，#1389），adb 事件注入路线在本机走不通。
- 模拟器在本仓整体不可达：基座 arm64-only 而 AVD x86（§3.2）。

### 4.4 Play pre-launch 与 Firebase Test Lab

来源：https://firebase.google.com/docs/test-lab/android/test-lab-play

- 官方表述：上传到 Play 后自动跑 pre-launch report，在「a wide range of devices running different versions of Android」上测，报告用于定位 crashes、display issues 与 security 问题；pre-launch report 由 Robo test 驱动，Robo test 可指定设备、语言、Android 版本与更长时长，「more customizable than the pre-launch report」（ftl-play:144-155）。
- Robo 是探索式测试：不带业务脚本、不登录、不理解业务语义。抓得到崩溃与显示类问题，抓不到业务回归（本仓核心路径：登录续期、上传、快捷登录、论坛）。
- FTL 设备池含虚拟与实体设备：官方设备清单页 https://firebase.google.com/docs/test-lab/android/available-testing-devices 存在，本次抓取只拿到页面入口（JS 壳），虚拟/实体之分的原句未核实，标二手未核实。
- 灰度发布（Expo `eas update --rollout-percentage`，见 §4.5）是发布后的收敛手段，不替代合并前的验证。

归纳：

- 每 PR 跑真机：7 个项目里只有 React Native 一个，且限内部 PR。
- 每 PR 跑 emulator instrumented / e2e：Now in Android、Element X、React Native；Wikipedia 的 instrumented 是手动触发。
- CI 完全不跑设备测试：Signal（JVM + 截图）、Bitwarden（连单测都注释掉）。
- 真机农场出现在 postsubmit（Flutter）或 nightly 云端（Element X 传 BrowserStack），不在 PR 门。
- Expo 的官方兜底表述是灰度：「A rollout allows you to roll out a change to a portion of your users to catch bugs or other issues before releasing that change to all your users」（docs.expo.dev/eas-update/rollouts/）。
- 发布前人工设备验证的公开表述：7 个仓库均未找到（CONTRIBUTING 只写「thoroughly tested」一类）。
- 「同规模团队公开表述不跑真机、靠灰度 + 崩溃监控兜底」的项目：未找到，不编。

本仓定位：3-5 人团队、单台真机、无云设备农场预算。最接近的可比形态是 Wikipedia / Element X 模式（PR 门 JVM + 小程序/emulator，设备测试手动或 nightly 触发），而不是 Signal / Bitwarden 的「CI 完全不碰设备」（它们用户基数大、崩溃成本结构不同）。
