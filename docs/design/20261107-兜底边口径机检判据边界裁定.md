## 结论先行

## 1. 先勘清「边」是什么（判据能不能立住的前提）

现测 `scripts/behavior-suite-deps.mjs` 产出 reason 的形态有**两类**，混在一起谈会判错：

**第一类 · 全局边**（`globalEdges(changed)` 产出，命中即触发全跑或按名单纳入）—— 恒 **3 条**：

| `edge` | 命中条件 | 现语义 |
| --- | --- | --- |
| `gate-script` | 改 `.github/**` 或 `scripts/**.(mjs\|js\|ps1)` | 全跑 |
| `suite-set` | 改 `utils/*.test.js` | **只纳入读套件集合者**（#2312 起不再全跑） |
| `page-set` | 改 `pages.json` / `manifest.json` | 全跑 |

**第二类 · 常驻标记**（`select(map, changed, opts)` 内的 `add()`，**不是 globalEdge**）：

- `direct:<路径>`、`import-closure:<路径>`、`dir:<目录>`、`bprime-always:结构信号(...)`

⚠️ **勘误（原候选表述有错，是本票的硬产出）**：原候选把 `bprime-always` 算作「兜底边」。实测**不成立** —— `bprime-always` 从不作为 `edge:` 出现，它由 `opts.bprimeAlways !== false` 控制在 `select()` 里 `add()` 打标；脚本的 `edge:` 集**只有 3 个**。若机检按「`edge:` 字符串集」比对文档，会把 bprime 误判成漏项 ⇒ **判据必须显式区分「全局边」与「常驻标记」两类**。

现测定位（快照，HEAD `6c37587e`；行号会漂，持久锚点用函数名 / 小节名）：

- `globalEdges`：`behavior-suite-deps.mjs:337`，三条 `edge:` 分别在 `:345` / `:358` / `:370`，`:375 return reasons`
- `select`：`:490`；`direct` `:503`、`import-closure` `:506`、`dir` `:514`、`bprime-always` `:524`（`if (opts.bprimeAlways !== false)` 在 `:522`）
- `dev-loop.md` 的落点小节 = **「本地收口走行为腿子集（#2034 立，ADR-0046 步骤 3 的唯一入口）」**（`dev-loop.md:306`），引用按该仓约定引小节名、不引行号

## 2. 三个候选判据的实测评估（含误红风险）

### 判据 A · 集合相等（文档兜底边 token 集 == 脚本 `edge:` 集）

- **技术可行性**：✅ 现能判绿。脚本 `edge:` 集 = `{gate-script, suite-set, page-set}`；`dev-loop.md` 的兜底边列举 = 同 3 个、顺序一致。
- **但它有一个已存在的真实缺口**：`dev-loop.md` 的 reason 枚举**漏 `dir:`**（`:315` 只列 `direct:` / `import-closure:` / `bprime-always:` / 兜底边三条，而 `:322` 又提到 `dir:` ⇒ 同一节内部口径不齐）。⇒ A 的第一个动作是**修文档**，不是立规则 —— 它判的是「文档表述与代码一致」，**不是**「行为对不对」。
- **误红风险：中**。文档合法演进（新增一条全局边）⇒ 机检先红、每次都要有人补文档 / 走豁免。按 ADR-0053 总成本尺，是**持续税**。

### 判据 B · 窄口径（只判「`suite-set:` 不再全跑」这句在位）

- **技术可行性**：✅ `dev-loop.md` 有稳定锚点「**`suite-set:` 自 #2312 起不再全跑**」（`:320`）。
- **价值：窄**。**误红风险：低**（散文措辞一改就红，仍需豁免）。

### 判据 C · A + 豁免机制（文档侧可声明「计划中的边」）

- **技术可行性**：需设计豁免格式，**成本最高**。**误红风险：低**（豁免吸收演进），但引入新文档语法 = **新漂移面**。

## 3. 裁定与三条理由

**不立判据 A 的硬机检；候选 1 按「窄口径 + 不门化」落地或干脆不立 —— 维护者最终选「干脆不立」。**

1. **它在造第二份实现的镜像**：`dev-loop.md` 自己写着「判定住在工具里，本仓没有第二份实现」；机检「文档列的边 == 代码的边」恰恰与之相悖。本仓对「同一件事两份真源」历来判红（见 `jestSplitContract.test.js` 注释）。
2. **成本持续、收益一次性**：漂移是低频事件（#2312 那次靠手动 grep 发现，事后未再漂）；硬规则要每次演进都跟一次。
3. **真正该守的行为判据已经有守护了**：「别把 `suite-set` 改回全跑」（改后子集仍非全量）由 `utils/behaviorSubsetBehavior.test.js` 的 `M2b` / `M2c` 覆盖，不需要新机检。

**豁免机制形态**：无需设计 —— 未选 C、未立硬规则、无误红面需要吸收。

**若未来复议（不执行）**：只走 B 窄口径、**不门化**（`preflight-pr.ps1` 的 notes 或独立脚本提示，不判红），落点选移动端 `scripts/` 层（与 `check-contract-read.mjs` 同层，先例见 `ci.yml` 与 `.github/scripts/lib/lint-issue-references.mjs`），并**先修 `dev-loop.md` reason 枚举漏 `dir:` 那处**。

## 4. 明确不做（无论怎么裁）

- 不新增 CI 门 / 不动 ruleset（候选 1 最大的风险就是「把软成本换成会判红的硬规则」）。
- 不把 `bprime-always` 归入「兜底边」（它不是 globalEdge，见 §1 勘误）。
- 不写任何历史收益数字进代码或断言（套件数分母在漂：审计 103 / 旧树 109 / 现测 107）。
