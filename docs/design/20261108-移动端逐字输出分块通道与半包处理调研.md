## 结论先行

**一句话**：三端都能走同一条增量通道——`uni.request({ enableChunked: true, responseType: 'arraybuffer' })` + `RequestTask.onChunkReceived`（回调恒为 `ArrayBuffer` 字节块），配一个「字节块序列 → 事件序列」的**可测纯函数解析器**处理半包/粘包，能力缺失时降级回现行整包路径；`plus.net.XMLHttpRequest` 在真·uni-app x 下不可用（官方明文「uni-app x不支持plus」）；`done.content` 权威全文（#2310）在增量通道下**仍成立且更必要**，`status` 事件必须新增回调才能在增量通道里消费。后端协议、SSE 帧形、计费路径都不用改。

**四类判据，别混着引用**（分类表照 `docs/design/20261106-移动端长请求超时上限调研.md:13-19`，本票按其要求补「推断」一类）：

| 类型 | 内容 |
| --- | --- |
| **文档事实**（官方明文） | 微信 `wx.request` 的 `enableChunked`（最低基础库 2.20.2）/ `responseType`（默认 text，合法值 text、arraybuffer）；`RequestTask.onChunkReceived`（2.20.1，`res.data: ArrayBuffer`）；微信「后台 5 s `fail interrupted`」；DCloud uni-app x `onChunkReceived` 兼容版本表；DCloud「流式响应」要求 arraybuffer + 三方库解码；DCloud「uni-app x不支持plus」；SSE/Encoding/RFC 规范原文；DCloud TextDecoder 兼容表 |

## 五问逐一回答

### Q1｜App Android/iOS 有没有增量收包能力？

**结论**：**有**，且是同一条 uni-app x 官方通道 `enableChunked` + `onChunkReceived`（回调 `ArrayBuffer`）；`plus.net.XMLHttpRequest` 在 uni-app x 下被官方明确否定；原生层可行但不选。

- 【文档事实】DCloud `request.html` `onChunkReceived` 兼容性表（本次直接复取全表）：**Web 4.71 / 微信小程序 4.41 / 支付宝小程序 5.31 / Android 4.71 / iOS 4.71 / HarmonyOS 4.71**；`RequestTaskOnChunkReceivedListenerResult` 唯一属性 `data` 类型 `ArrayBuffer`（必填）。`responseType` 与 `data` 的 ArrayBuffer 支持：app-android 从 4.51、app-ios 从 4.61（`request.html` 参数表 / RequestSuccess.data）。
- 【源码事实】Android `dcloudio/uni-api/alpha/.../utssdk/app-android/NetworkManager.uts:1`（从 `../../interface.uts` 导入 UTS 接口）→ 真·uni-app x；`:213` `call.enqueue(new SimpleCallback(listener, task, param.enableChunked ?? false, ...))`；`:538-546` 原文 `let rawStream = response.body()!.byteStream()!; const enableChunked = this.enableChunked && response.header("Transfer-Encoding") == "chunked";`，命中 chunked 才走 `processStreamWithOkio`，否则 `readInputStreamAsBytes`（`:576-620`，2048 字节循环读攒整个 body）。`:628-745` `processStreamWithOkio`：生产者 Okio 每轮 `new ByteArray(8192)` 读，主线程消费者 `CHECK_INTERVAL = 100ms` 把共享缓冲整段取出，`:725-729` `ArrayBuffer.fromByteBuffer(ByteBuffer.wrap(bufferData))` 后 `chunkListener({ data: arrayBuffer })`。**⇒ Android 的 chunk 边界 = 100 ms 聚合窗口内累积的字节，不是 SSE 帧、更不是 UTF-8 字符边界。**
- 【源码事实】iOS `.../app-ios/NetworkManager.uts:19` `import { URLSessionDataDelegate, URLSession, ... Data } from 'Foundation'`、`:115` `class NetworkManager implements URLSessionDataDelegate`；`:138` `this.enableChunked = param.enableChunked ?? false`；`:149-158` `URLSessionConfiguration.default` + `dataTask(with:)`；`:391-405` `urlSession(... didReceive data: Data)` → `task.chunkReceivedListeners.forEach(... { data: ArrayBuffer.fromData(data) } ...)`。**⇒ iOS 增量 = 原生 URLSession 每次 `didReceive` 的 `Data` 转 `ArrayBuffer` 回调**，边界由底层送达决定，同样不保证帧/字符对齐。
- 【文档事实，经 `20261106:102` 转引】DCloud 文档说明 iOS `onChunkReceived`「基于原生 URLSession 实现，需要服务端采用流式响应（chunked 或 text/event-stream）」。
- 【推断（源码 + RFC）】Android 的 `enableChunked` 分支**依赖 `Transfer-Encoding: chunked` 响应头**：RFC 9113 §8.2.2（`https://www.rfc-editor.org/rfc/rfc9113.txt:2556`）把 `Transfer-Encoding` 列为 connection-specific，HTTP/2 `MUST NOT generate`；微信 `wx.request.md:601` 又明文「除声明了 `enableChunked` 后会走 HTTP1 以外，均会自动开启 HTTP2/HTTP3」⇒ **三端一致走 HTTP/1.1 是必要前置**，否则 Android 静默退回整包读路径、收不到 chunk。
- 【源码事实 + 推断】后端是否真的发 chunked：`handler.go:412-423` 的 `writeSSEHeaders` 只设 `Content-Type/Cache-Control/Connection/X-Accel-Buffering` 并 `WriteHeader(200)`，**未设 `Content-Length`**；Go `net/http/server.go:1607-1626` 在「无 Content-Length + HTTP/1.1」时 `cw.chunking = true`、`setHeader.transferEncoding = "chunked"` ⇒ 推断 Gin 落 net/http 自动 chunked。**线上 Caddy + Gin 是否真带该头未抓包，只能真机实测**（见「未找到一手来源」#7）。
- 【文档事实】`plus` 不可用见 B 判据（`uniapptox.html:142`）。C（原生层）依据：`https://doc.dcloud.net.cn/uni-app-x/` 首页「uni-app x 不会限制任何原生API的调用」，但不选（见「被否方案」）。

### Q2｜mp-weixin 端 `enableChunked` 是否必须配 arraybuffer / `responseType`？分包边界有无保证？小程序无 TextEncoder 时如何解码 ArrayBuffer？

**结论**：微信官方把 `enableChunked` 与 `responseType` 定义为**两个独立参数**，未写「必须配 arraybuffer」的强绑定；但 `onChunkReceived` 回调**恒为 `ArrayBuffer`** 而非文本，DCloud uni-app x 官方「流式响应」明文要求「同时设置响应体格式为 arraybuffer」；chunk 边界**没有任何帧/UTF-8 字符对齐保证**；小程序端需引三方库解码，App 端 UTS 有内置 `TextDecoder` 但无 stream 选项的一手证据。

- 【文档事实】`https://developers.weixin.qq.com/miniprogram/dev/api/network/request/wx.request.md`：`:109-124` `responseType` string，默认 `text`，合法值 `text` / `arraybuffer`，最低 1.7.0；`:199-205` `enableChunked` boolean，默认 `false`，「开启 transfer-encoding chunked」，最低基础库 **2.20.2**；`:585-587` 返回 `RequestTask`（1.4.0）；`:601` `enableChunked` 会走 HTTP1（高性能模式说明）；`:51` `timeout` 可在 `app.json` 或调用级配置。两参数在官方文档里**各自独立、无依赖说明**。
- 【文档事实】`https://developers.weixin.qq.com/miniprogram/dev/api/network/request/RequestTask.onChunkReceived.md`：全文「基础库 2.20.1 开始支持」「监听 Transfer-Encoding Chunk Received 事件。当接收到新的chunk时触发」，参数 `res.data | ArrayBuffer | 返回的chunk buffer`。
- 【文档事实】DCloud `request.html`「流式响应」段原文：`使用uni.request，把客户端的prompt通过POST的方式发送到LLM服务器，同时设置响应体格式为arraybuffer` / `客户端监听onChunkReceived事件，流式接收arraybuffer数据` / `客户端通过TextEncoder解码出文本，一般是markdown格式。（注意小程序自身没有TextEncoder，需要再通过三方库解码）`。**注意**：DCloud 原文写「TextEncoder 解码」，解码器实为 TextDecoder，属官方文档笔误；其结论「小程序自身没有 → 需三方库解码」是本问的直接一手依据。
- 【推断 + 只能真机实测】**「必须配 arraybuffer」不是微信一手文档的明文约束**，是 DCloud 实现指南的明文要求。微信侧不配 `arraybuffer` 时 `success` 的 `res.data` 形态、以及 chunk 回调是否仍给 `ArrayBuffer`，微信文档未写 ⇒ 只能真机实测（见「未找到一手来源」#1）。
- 【规范事实】chunk 边界无保证：RFC 9112 §7.1（`https://www.rfc-editor.org/rfc/rfc9112.txt:1054-1066`）`chunked-body = *chunk last-chunk trailer-section CRLF`、`chunk = chunk-size [chunk-ext] CRLF chunk-data CRLF`、`chunk-data = 1*OCTET`（**纯字节序列，与内容语义无关**）；`:1071`「HTTP/1.1 does not define any means to limit the size of a chunked response」。SSE 规范（`https://html.spec.whatwg.org/multipage/server-sent-events.html:374`）「Streams must be decoded using the UTF-8 decode algorithm」；Encoding §8.1.1（`https://encoding.spec.whatwg.org/#utf-8-decoder:3684-3837`）UTF-8 decoder 用 `UTF-8 bytes seen / bytes needed` 状态缓存不完整多字节序列，`do not flush`（`:2722`）标志 ⇒ 规范层本就设计为「一个码点可跨多次 feed」。**⇒ 一个 chunk 完全可能含多帧（粘包）、半帧、或切在 UTF-8 多字节字符中间**（【推断】，由「chunk 是字节序列 + UTF-8 是多字节 + 无任何对齐承诺」推出；具体平台行为只能真机实测，微信/DCloud 文档都未承诺）。
- 【文档事实】小程序解码：DCloud 明文「小程序自身没有TextEncoder，需要再通过三方库解码」。uni-app x **App 端**有内置 `TextDecoder`：`https://doc.dcloud.net.cn/uni-app-x/uts/buildin-object-api/textdecoder.html` 兼容表「Web √ / Android 4.31 / iOS 4.71 / HarmonyOS 4.71」，`decode(input)` 三个重载（`ArrayBuffer` / `DataView` / `TypedArray`）返回 `string`，无效数据用 `U+FFFD` 替换，**无 `{stream:true}` / options 参数**。⇒ mp-weixin 端（非 UTS 编译目标）无内置解码器、需三方库；App 端虽有 `TextDecoder`，但跨块不完整序列仍需解析器自己缓存（【推断】，见「未找到一手来源」#4）。
- 【文档事实】`https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.md:54`「建议服务器返回值使用 **UTF-8** 编码」；与本仓后端 `sendEvent` 写 `string(payload)`（`handler.go:474-476`）一致。

### Q3｜半包/粘包怎么处理：可测纯函数解析器设计要点（不写实现代码）

**结论**：解析器必须是**字节级、有状态、可重入**的纯函数，分「UTF-8 流式解码 → 行切分 → 字段累积 → 空行派发 → 事件映射」五层；末帧无空行按 SSE 规范**不派发**；现行 `parseStreamSSE` 的「末尾兜底派发」不能沿用。

**规范/源码依据**：

- 【规范事实】`html.spec.whatwg.org/multipage/server-sent-events.html`：`:340-355` ABNF `end-of-line = ( cr lf / cr / lf )`；`:87/:357` 恒 UTF-8；`:374-377` 用 UTF-8 decode algorithm、剥离一个前导 BOM；`:379-382`「CRLF 对 / 不跟在 CR 后的单个 LF / 不跟 LF 前的单个 CR」三种都是行结束；`:393` 空行 Dispatch；`:394` 冒号开头行忽略；`:399` processField；`:416` `data` 字段追加值再追加一个 LF；`:438-439` 派发时去掉末尾一个 LF；`:407`「file ends in the middle of an event, before the final empty line, the **incomplete event is not dispatched**」；`:498`「the last still has to end with a blank line, the **end of the stream is not enough**」；`:525`「The last block is discarded because it is not followed by a blank line」。`:359-365` 另提示「line buffering with lines defined to end with a single LF is safe, block buffering or line buffering with different expected line endings can cause delays」。
- 【规范事实】`encoding.spec.whatwg.org/#utf-8-decoder`：`:3707` 到 end-of-queue 且 `bytes needed ≠ 0` ⇒ 返回 error；`:3837` `bytes seen ≠ bytes needed` ⇒ 继续等、不产出。
- 【源码事实】本仓后端帧形：`handler.go:473-477` `sendEvent` 每帧固定 `"event: " + event + "\n" + "data: " + payload + "\n\n"` 并 `Flush()` ⇒ **单 `event:` 行 + 单 `data:` 行 + 空行**，LF 行结束，无 CRLF、无 bare CR、无多行 data。`:489-495` `status`、`:500-504` `message`、`:515-527` `sources`/`usage`、`:528-549` `done`，`:507-513` `error`。
- 【源码事实】现行 `api/aiAssistant.uts:542-569` `parseStreamSSE`：`text.split('\n')` + `line.trim()`，`:553` 空行派发，`:563-567` **末尾 `if (event.length > 0)` 无空行也派发一次**（与 SSE 规范相反）；`:548` `.trim()` 会吞掉 CRLF 里的 CR、把 bare CR 当普通字符。

**设计要点（输入：字节块序列；输出：事件序列 + 终止信号；不写实现代码）**：

1. **形态**：对外暴露 `feed(chunkBytes) -> Event[]` 与 `finish() -> { events, terminated, incomplete }`。内部只持有 4 组状态：UTF-8 解码器余量、行缓冲（含「上一块以 CR 结尾」挂起标志）、当前 `event` / `data` 缓冲、是否已见终止帧。`.uts` 纯函数模块，不碰 `uni.*`、不碰时间、不发请求 ⇒ 可直接进既有的行为腿 harness。
2. **字节 → 解码**：先过 UTF-8 流式解码器，块尾不完整的多字节序列**保留到下一块**，不能按字符边界切、不能丢。`finish()` 时若仍有 `bytes needed ≠ 0`，按 Encoding `:3707` 判为错误/替换字符，不静默拼出半个字。BOM 只在整个流首剥离一次（SSE `:376-377`）。
3. **CR 跨块（CRLF 与 LF 混用）**：块尾遇 `CR` 不能立即断行，要挂起；下一块首字节是 `LF` 则合并为一个行结束，否则按「单独 CR」断行并把该字节回推行缓冲。`LF` 只有在「不跟在 CR 后」时才单独断行（SSE `:379-382`）。⇒ 任何 `CRLF` / `LF` / `CR` 混用、以及 `\r\n` 被切在两个 chunk 之间，都必须得到同样的行序列。
4. **跨块的 `data:` 行**：字段级累积基于**完整行**，`data:` 行可跨任意多块，只有见到完整行结束才 processField；`event:` 与 `data:` 按到达顺序累积；一帧内多条 `data:` 行用 LF 拼接（`:416`）、派发时去掉末尾一个 LF（`:438-439`）；`:394` 冒号开头行忽略、未知字段按 `:399` 忽略。
5. **帧边界 = 空行**：只有空行才派发（`:393`）。一个 chunk 含多帧就连续派发多个事件（粘包）；半帧就继续缓冲（半包）。派发后重置 `event/data` 缓冲。
6. **末帧没有空行**：按规范**不派发**（`:407/:498/:525`）。`finish()` 返回 `incomplete = true` 交给上层走「回答未完整返回」收尾，**绝不能**把半个 `done`/`message` 当权威帧 —— 这正是现行 `parseStreamSSE:563-567` 兜底会犯的错，断流时它可能把半帧 `done` 派发出去、错误触发 #2310 的全文替换或提前清等待态。
7. **事件映射**：`message`→`onMessage(content)`、`sources`→`onSources`、`status`→`onStatus`、`usage`→（预留）、`error`→`onError` 且 `terminated=true`、`done`→`onDone(payload)` 且 `terminated=true`；坏 `data` 帧按「没有载荷」处理、不中断流（沿用 `:606-618`）。`done` 的 `data` 可为字符串 `"null"`（`:606-609`）。
8. **可测不变量（核心）**：**同一字节流无论怎样切分成 chunk 序列，`feed` 串接产出的事件序列必须一致**（含跨块 UTF-8 三/四字节、跨块 `\r\n`、一 chunk 多帧、末帧无空行）。这是把「半包/粘包」变成可回归用例的关键；用规格 `:122-129` 定的「手机端 .uts 纯函数行为测试层」承载，仿 `utils/aiDoneContentBehavior.test.js:20-23` 的真执行串法。
9. **边界防护**：单行长度设上限（防 OOM / 超长坏帧）；`finish()` 幂等；不持有跨请求的全局状态（每次 `sendStream` 新建解析器实例，401 重发必须换新实例 —— 见 Q4）。

### Q5｜`done.content` 权威全文（#2310）在增量通道下是否仍成立？`status` 事件要不要同步消费？

**结论**：**`done.content` 仍成立且更必要**（增量只改「`message` 何时到」，不改「累积增量 vs 归一后全文」的判据）；**`status` 要在增量通道里同步消费**，但现行回调形状没有 `onStatus`、事件分派也没有 `status` 分支，必须新增出口。

- 【源码事实】服务端判据 `handler.go:497-504` `var streamed strings.Builder` + `fullContent, usage, err := h.svc.StreamChat(..., func(content string) { streamed.WriteString(content); sendEvent("message", ...) })`；`:531-538` 注释「`content` 只在『终端权威全文 ≠ 已推增量』时出现，目前唯一来源是诊断配图归一」，代码 `if fullContent != "" && fullContent != streamed.String() { finalContent = fullContent }`；`:539-549` 组装 `donePayload` 并 `sendEvent("done", donePayload)`。⇒ **判据的两端都是「已推给浏览器的增量」与「归一后全文」，与这些增量是整包一次到、还是分块逐字到无关**。
- 【源码事实】客户端 `useAiChat.uts:214-230` `onDone` 无条件「`data['content']` 非空就 `assistantMsg.content = full` 整体替换」（#2310），随后 `thinking=false`；`api/aiAssistant.uts:506-510` 回调注释同口径；`utils/aiDoneContentBehavior.test.js:6-9` 注「客户端口径是无条件的『有 content 就整体替换累积正文』」，`:143-171` 五条行为用例（done 带 content 整体替换 / 纯图轮无条件替换 / 只有 meta 保留累积 / data=null 容空 / 空串不替换）。规格决策 15（`:101`）「上游的最终全文是权威，流式增量只为观感」。
- 【推断】增量通道下 `message` 更早、累积链更长，且跨块解码/半包本身就可能引入累积差异 ⇒ 全文替换的必要性**不降反升**；`done` 缺席时仍保留累积（`20261105` 能力盘点 `:106`）。**#2310 不变式原样保留，不得因「已经有逐字观感」而弱化。**
- 【源码事实 + 文档事实】`status` 要消费：`handler.go:491-495` 注释「上游 status 立刻下沉成 SSE 事件：v2 在首个 delta 之前发的『正在检索…』要马上到前端，**不能等 Stream 返回（那时内容已经开始流了）**」，`ctx = WithDiagnosisStatusSink(ctx, func(text string) { sendEvent("status", map[string]string{"text": text}) })`。`20261105` 能力盘点 `:355` 说「`status` 无实时价值」的**前提是整包到达**（一次性解析时 `status` 与 `message` 同时可见）；增量通道下 `status` 是首帧之前的独立事件，正好对应「等待态 / 正在检索」徽章。**⇒ 建议在增量通道同步消费 `status`。**
- 【源码事实】现状**消费不了**：`StreamChatCallbacks`（`api/aiAssistant.uts:500-512`）只有 `onMessage / onSources / onError / onDone`，无 `onStatus`；`handleStreamSSEEvent`（`:572-625`）只分派 `message / sources / error / done`，**无 `status` 分支** ⇒ `status` 帧当前被静默忽略。执行票必须补 `onStatus`（或等价状态出口）与 `status` 分支，否则「增量通道消费 status」无从落地。
- 【源码事实】徽章 / 耗时在 `done.meta`（`handler.go:489-490` `WithDiagnosisMeta`、`:528-548` `payload["meta"] = meta`，票 2245 决策 5），现行 `onDone` 只取 `content`（`useAiChat.uts:218-225`）不取 `meta`；规格 Testing Decisions（`:122-129`）已把「徽章/耗时映射」列进主 seam。⇒ 增量通道要不要补 `meta` 消费由执行票定，本票只标出落点。

## 选定方案与理由

**选**：`uni.request({ enableChunked: true, responseType: 'arraybuffer', ... })` + `RequestTask.onChunkReceived` 作为**唯一增量通道**，三端统一；字节块交给新增的「可测纯函数解析器」产出事件；**现行整包路径保留为能力缺失/异常时的降级**；`StreamChatCallbacks` 增 `onStatus`，`handleStreamSSEEvent` 增 `status` 分支；`done.content` 替换与等待态收尾沿用现行实现。

**理由**：

1. 【文档事实 + 源码事实】三端一手来源一致给 `ArrayBuffer` 字节块（微信 `RequestTask.onChunkReceived.md`、DCloud `request.html`、`uni-api` alpha Android/iOS `NetworkManager.uts`），无需为每端写不同通道。
2. 【源码事实】后端已具备前置条件：`handler.go:473-477` 每帧 `\n\n` 结尾且 `Flush()`、`:412-423` 不设 `Content-Length` ⇒ Go `net/http` 自动 chunked（`server.go:1618-1621`）；`writeSSEHeaders` 已设 `X-Accel-Buffering: no` / `Cache-Control: no-cache`。**后端零改动**。
3. 【文档事实】DCloud `request.html`「流式响应」段就是这套组合的官方示例（POST + arraybuffer + onChunkReceived + 三方库解码 + 流式渲染）。
4. 【源码事实】不动原生插件、不动后端协议、不动计费路径；新增面集中在客户端 API 层 + 一个纯函数模块，可用既有 `utils/utsHarness` / 行为腿回归。
5. 【推断】收益是「首 token 时间 / 打字机观感」，**不是**提超时上限（`20261106:126` 明确「别把 enableChunked 当提上限手段」）；超时仍靠现行 `AI_REQUEST_TIMEOUT = 330000` 与 `fail` 分支。

**必要前置**：三端一致走 HTTP/1.1（微信 `wx.request.md:601` 已保证 `enableChunked` 下走 HTTP1；Android 判断依赖 `Transfer-Encoding: chunked` 头，RFC 9113 `:2556` 禁止 HTTP/2 带该头）⇒ 生产链路实际协议【只能真机实测】。

## 半包 / 粘包解析器设计要点

见 **Q3** 的 9 条要点（字节级 UTF-8 流式解码、CR 跨块挂起、跨块 `data:` 行、空行派发、末帧无空行不派发、可测「任意切分事件序列一致」不变量、坏帧容错、终止帧、边界防护）。此处只补三点与选型的耦合：
