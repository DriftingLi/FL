# 20261031 shadcn/ui 机制借鉴调研：Registry 与 base×style 落到 frontend/

- **调研问题**：shadcn/ui 的 registry 与 base×style 两套机制，哪些在 `frontend/`（Vue 3 + Element Plus + Tailwind 4）里成立、哪些不成立；「搬机制不搬组件」的边界画在哪。
- **一手来源（外部）**：`shadcn-ui/ui` 仓库 `main` 分支，2026-10-31 抓取——`README.md`、`apps/v4/registry/README.md`、`apps/v4/registry/bases.ts`、`apps/v4/registry/__blocks__.json`、`packages/registry/README.md`、`packages/shadcn/package.json`、`skills/shadcn/SKILL.md`、changelog `2026-07-base-ui-default.mdx` / `2026-10-ai-elements.mdx`。
- **本仓取证**：一律「路径 + 行号」。计数为 2026-10-31 实测：`frontend/src` 174 个 `.vue`、`components/ui/` 36 件、`design-tokens.css` 160 条自定义属性、`element-overrides.css` 140 条 `--el-*`、`tailwind.css` 52 个 `@theme` 键、无 `components.json`。
- **口径纪律**：外部事实逐条带来源；本仓规则不抄原文，只引小节名与行号（正文在 `docs/agents/ui-conventions.md`）；「值得引入」必须给可验收的判据，给不出就写进第 8 节。

## 1 结论先行

1. **拆开看，只有两样值得搬：registry 的「字段面」（一件组件该声明什么）与「给 agent 的查询面」。** 其余三项——registry 协议（寻址/解析/安装）、base×style 矩阵、preset 短码——在本仓**没有消费者**，见第 5 节判定表。
2. **本仓已经有一个 registry，只是方向相反，别搞反。** shadcn 是「代码 → 生成 registry JSON」，本仓是「文档 → 运行时派生」，且**明确拒绝落一份手维护的 JSON**：`scripts/check-ui-intent.mjs:10-11` 原文是「这里不落一份手维护的 JSON …… 落盘就会有人手改，那就是本票要收掉的漂移源」。任何「加一份 `registry.json` 当单一真源」的方案，在评审处就会被这条既有裁定挡下。
3. **真正的缺口很小且具体：一条收敛映射被写了三遍，而登记表里没有它。** `el-x → UiY` 同时存在于 `scripts/check-el-controls.mjs:30-41`（数组）、同文件 `:31-40`（逐行注释）、同文件 `:99-102`（footer 文案）；`docs/agents/ui-conventions.md` 的意图登记表只有「唯一形态」与「存量计数」，**没有这一列**。于是 `check-el-controls`（黑名单）与 `check-ui-intent`（白名单）各持一半事实，加一个封装件要改两处 + 一段文案。
4. **观感层是 1×1，不是 3×8，而且「style 轴」已经被机械守住——这部分已经不欠 shadcn 什么。** 本仓 base = Element Plus（唯一），style = `design-tokens.css` + `tailwind.css` 的 `@theme` 桥 + `element-overrides.css`（三件职责不同），作用域变体一份（`valuation-tokens.css` 在 `.valuation-root` 内）。shadcn 靠「组件不写死颜色」的约定来保证 style 可换，本仓靠守卫：`check-ui-intent.mjs:18-19` 的规则②直接判 `border-radius` / `box-shadow` 的纯字面量，`check-bare-hex.sh` 判裸 hex。**约定 vs 机械判据，本仓这条更强。**
5. **组件层一件都不用搬。** 36 个封装件是 Vue + EP 的薄封装（`UiButton.vue` 全文 87 行，无 variants 库、无 `cva`）；shadcn 是 React + Radix/Base UI。注意它的多 base 也不是白来的——每个 base 的组件同样手写一遍（`apps/v4/registry/README.md` 明说 shared surfaces 要在两个 base 间保持同步），省下来的只是 base×style 的**组合生成**。换 base 在本仓等于重写 174 个 `.vue` + 重做 140 条 EP 覆盖，成本与收益不成比例。

**一句话建议**：只做两件事——**P0** 把收敛映射并入意图登记表，让两个守卫同源（消掉三写）；**P1** 给 36 件封装件做一个查询面（`node scripts/ui-docs.mjs <名字>`），替代 agent 每次通读 351 行文档。**P2**（MCP / 每件一页生成物）先实测 token 成本差再决定。其余明确不做，理由写在第 6 节，免得半年后有人重开。

## 3 shadcn 侧：把「shadcn/ui」拆成四层

外界常把 shadcn/ui 当成一个组件库，读源码会发现它是四件事捆在一起，**可拆、可只取其中一层**。

### 3.1 分发层：源码内联（copy-in）

组件以源码形式写进用户项目，不是运行时依赖——SKILL.md 原话：「Components are added as source code to the user's project via the CLI」。收益是「代码归你，改不用 fork」，代价是「升级要自己合并」。

### 3.2 协议层：registry（寻址 → 解析 → 安装）

一件组件 = 一条 registry item，带 `name` / `type` / `title` / `description` / `dependencies` / `files` / `cssVars` / `categories` / `meta` 这些字段（字段面取证：`apps/v4/registry/bases.ts` 的 `registry:style` 条目、`__blocks__.json` 的 `name/description/categories`、`packages/registry/README.md` 的 `resolveRegistryItems` 返回 `files/dependencies/cssVars`）。

寻址有四种形态：命名空间 `@shadcn/button`、URL、本地文件、**GitHub 仓库 `owner/repo/item`**（`packages/registry/README.md`「Fetch items」）。安装端 `addRegistryItems` 负责写文件、装依赖、灌 `envVars`，`overwrite: true` 才盖已有文件。

**注意它的生成方向**：仓库里的 `bases/base/`、`bases/radix/` 是手写的源，`public/r/*`、`styles/<style>/ui/*`、`__index__.tsx` 全是构建产物（`apps/v4/registry/README.md`「Source of truth」与「Generated output」两节把这条边界写得很死）。也就是说 **JSON 是产物，不是真源**。

### 3.3 观感层：base × style（贵轴与便宜轴）

矩阵 = 3 个 base（`base` = Base UI、`aria` = React Aria、`radix` = Radix，`bases.ts` 三条） × 8 个 style token（`nova` `vega` `maia` `lyra` `mira` `luma` `sera` `rhea`，`registry/styles/style-*.css` 八个文件，每个约 78 KB）。

两轴的**成本不对称**，这点最值得记：

| 轴 | 谁写的 | 加一个取值的成本 |
| --- | --- | --- |
| base（交互原语） | 手写。`apps/v4/registry/README.md` 只点两个手写 base（`bases/base/`、`bases/radix/`），而 `bases.ts` 另有一条 `aria`（React Aria）——**两处口径不一致**，本文按 `bases.ts` 计三个；无论哪个数，组件源都是手写、靠「shared surfaces 需在两个 base 间保持同步」这条约定维系 | 高：等于重写一遍组件 |
| style（视觉令牌） | 一份 CSS（`style-*.css`），组合由构建生成 | 低：加一个文件，交叉组合自动出 |

**所以「3 × 8」不是 24 套手写组件，是 3 套手写 × 8 份 CSS 再交叉生成。** 这个洞察决定了本仓该抄哪一半（见 4.3）。

### 3.4 附带层：给 agent 的查询面

- `skills/shadcn/SKILL.md` + `rules/*.md`：一份可执行的规则集（forms / composition / chat / icons / styling / base-vs-radix）。
- `shadcn mcp`：MCP server（4.23.0 已升 MCP TS SDK v2）。
- 文档页可输出 Markdown：changelog 原话「Every page is also available as Markdown, so you can point your coding agent at it」。
- `npx shadcn@latest info --json` 把项目上下文（aliases / base / style / tailwindVersion…）注入 agent。

## 4 本仓侧：逐层对照

### 4.1 分发层 —— 已有，且比它更严

`components/ui/` 36 件就是我们的「源码内联」：业务页面不得裸用 EP 控件（ADR-0035，`ui-conventions.md` 的「封装层」词条）。差别在于 shadcn 的 copy-in 是**跨仓**（从 registry 抄进你的项目），我们的是**同仓分层**（封装层 ↔ 业务层），没有「装进来」这个动作。

**判定：不引入。** 引入 copy-in 协议只会给「本来就是自己的代码」加一层搬运。

### 4.2 协议层 —— 有一个「反向 registry」

`scripts/lib/ui-intent-registry.mjs` 把 `ui-conventions.md` 的「意图登记表」三张表解析成 `native` / `pending` / `children` / `wrapperOf` 四个集合（`:89-134`），`check-ui-intent.mjs` 拿它当白名单判「模板里出现了未登记的 `el-*`」。

但字段面很薄，对比 shadcn 的 item 字段：

| shadcn item 字段 | 本仓现状 | 缺口 |
| --- | --- | --- |
| `name` | 有（`UiXxx` / `el-xxx`） | — |
| `type` | 有（native / pending / child，由表结构隐含） | — |
| `dependencies` | 无（EP 是全局依赖） | 无需求 |
| `files` | 无 | 可从组件目录反推，暂无需求 |
| `categories` | 有（意图，如「命令动作」「模态确认」） | — |
| `docs` | **无** | **这里有洞**：每件的用法只在组件 JSDoc 与 351 行正文里 |
| 替代关系（`el-x → UiY`） | **无** | **这里有洞**，见下 |

**第一个洞是实打实的**：`check-el-controls.mjs` 之所以还留着一份硬编码清单，就是因为 `wrapperOf` 只从「存量单元格里出现 `el-*`」的行派生（`ui-intent-registry.mjs:107-113`），而多数已收敛行的存量只写计数（如「命令动作 | … | `UiButton` | 326」），派生不出 `el-button → UiButton`。于是同一条映射在 `check-el-controls.mjs` 里存在三份（`:30-41` 数组、`:31-40` 注释、`:99-102` footer 文案）。

**判定：字段面值得补（P0），协议不引入。** 本仓只有一个应用、一个 registry 消费者，寻址 / 解析 / 安装三件都没有对象。

### 4.3 观感层 —— 1×1 双层 + 一个作用域变体

| shadcn | 本仓对应物 | 取证 |
| --- | --- | --- |
| base（交互原语） | Element Plus，**唯一** | `frontend/package.json` 只有 `element-plus`，无第二个 UI 原语依赖 |
| style（视觉令牌） | `design-tokens.css`（160 条）+ `tailwind.css` 的 `@theme` 桥（52 键）+ `element-overrides.css`（140 条 `--el-*`） | 三件职责不同：令牌 / 桥接 / 覆盖 |
| 作用域变体 | `valuation-tokens.css` 在 `.valuation-root` 内遮蔽品牌色 | `design-tokens.css:7-15` 的命名空间边界注释 |
| 组件不写死颜色 | 已有，且有守卫 | `check-ui-intent.mjs:18-19` 规则②（档位字面量）、`check-bare-hex.sh`（裸 hex） |
| `@theme inline` 桥接 | 同样的机制，本仓独立踩到同一个坑 | `tailwind.css:68-73`：「`@theme` 的键不能与源变量同名，否则 `--x: var(--x)` 构成自引用循环」 |

**已有的部分不要重做。** 本仓这条链比 shadcn 多一层守卫、少一层生成，方向是对的。

**但「便宜轴」在本仓并不便宜，这是唯一值得抄的地方。** `element-overrides.css:16-35` 里 success / warning / danger 的 7 档阶梯是**显式 hex**（如 `--el-color-success-light-3: #6EE7B7`），原因写在 `:10-14`：「项目 token 只有主色 + light + strong 三档，凑不满 EP 的完整阶梯」。这意味着**加第二套观感要再抄一遍这 140 条**——shadcn 的 style 轴之所以便宜，是因为它的组件只引用语义变量，令牌文件是唯一变量。

> 收敛这 140 条属于 token 存量治理（`docs/design/1880-token-audit.md` 的邻域），不在本文的机制判定里，只作为「为什么 style 轴值得保持单文件」的证据。

### 4.4 agent 面 —— 一份 351 行文档 + 7 条守卫

| 资产 | 现状 | 对 agent 的可读性 |
| --- | --- | --- |
| `docs/agents/ui-conventions.md` | 351 行，含视觉基调 / 词汇表 / 意图登记表 / 档位表 / 四条 Tailwind 边界 / 已知缺口 | 一次通读成本高；问「确认框用什么」要读完整节 |
| `check-el-controls.mjs` / `check-ui-intent.mjs` / `check-icons.mjs` / `check-font-scale.mjs` / `check-a11y.mjs` / `check-async-section.mjs` / `check-bare-hex.sh` | 7 条可执行判据，各自带自检 | **只能判红，不能回答「那该用什么」** |
| `check-ui-intent.mjs --emit-registry <file>` | 已存在，但「只写不读，仅供排查」（`:11-12`） | 有查询面的一半能力，被有意关掉 |

**判定：这是缺口最大的一层，也是收益最高的一层（P1）。**

## 5 判定表：机制 × 落点

| shadcn 机制 | 它解决的问题 | 本仓对应物 | 判定 |
| --- | --- | --- | --- |
| 源码内联（copy-in） | 代码归用户，改不用 fork | `components/ui/**` 36 件 + ADR-0035 禁令 | **已有，且更严** |
| registry 协议（寻址/解析/安装） | 跨仓分发与组合 | 单仓单应用，无消费者 | **不适用** |
| registry item 字段面 | 一件组件声明它是什么、替代谁、文档在哪 | 意图登记表（缺「替代关系」「文档」两列） | **值得引入 → P0** |
| base × style 双轴 | 换原语库与换观感正交 | 1×1（EP × 一套 token）+ 一个作用域变体 | **矩阵不适用**；「style 单文件」原则已有 |
| style 令牌单文件承载观感 | 加一套观感只加一个文件 | `design-tokens.css` + 桥 + 覆盖（三件），EP 七档仍是显式 hex | **原则已有，执行有缺口**（见 4.3） |
| preset 短码（`a2r6bw`） | 一键复现 base+style+font+icon | 无（品牌唯一，一色一意） | **不适用** |
| 生成物提交（`public/r`、`__index__.tsx`） | 构建期生成、运行期只读 | 反向：文档 → 运行时派生，**拒绝落 JSON** | **方向相反，沿用本仓** |
| `add --dry-run` / `--diff` 合并 | 上游更新时保留本地改动 | 无（EP 升级靠人眼发现覆盖漂移） | **弱需求，暂不建** |
| skill / MCP / docs-as-md | 给 agent 一个查询面 | 351 行文档 + 只能判红的守卫 | **值得引入 → P1/P2** |
| registry 目录与健康监控 | 生态治理（谁的 registry 活着） | 无 | **不适用** |

## 6 「搬机制不搬组件」的边界

### 6.1 不搬的六样东西（各自有硬理由，不是「暂时不做」）

| 对象 | 为什么不能搬 |
| --- | --- |
| React 组件源码（`bases/*/ui/**`） | 运行时与模板语法都不同；本仓 174 个 `.vue` 的业务面已按 36 个封装件收口，换实现等于重写 |
| Radix / Base UI / React Aria | 它们是 shadcn 的 base 轴取值；本仓 base 是 EP，换 base = 重写封装层 + 重做 140 条覆盖 |
| 8 个 style（`nova`…`rhea`） | 品牌一色一意（石墨青），对比度锁在 `contrast.spec.ts`；引入第二套 look 会与 ADR-0080 字号七档、ADR-0083 容器档位表直接冲突 |
| `shadcn` CLI / `components.json` | 它假定「组件来自外部，装进你的项目」；本仓没有「装」这个动作 |
| registry 协议实现（`@shadcn/registry`） | 寻址与安装面在本仓零消费者；依赖它等于为一个不存在的需求引一条 Node 依赖链 |
| 「手写 JSON 当单一真源」 | **已被本仓否过**：`check-ui-intent.mjs:5-12` 明确「落盘就会有人手改，那就是本票要收掉的漂移源」 |

### 6.2 什么算「机制」（可以搬，但必须变形成本仓形态）

| shadcn 的做法 | 本仓形态 | 变形点 |
| --- | --- | --- |
| 一件组件在 registry 里声明 `name/type/docs/替代关系` | 在**意图登记表**里加一列（或加一张「收敛控件 / 封装件」表） | 源仍是 markdown，不落 JSON |
| `npx shadcn docs <component>` 取文档 URL | `node scripts/ui-docs.mjs <UiXxx\|el-x\|意图词>` 就地打印 | 输出到终端，不生成站点 |
| `info --json` 注入项目上下文 | `--emit-registry` 已有，改为可读（加 `--query`） | 从「只供排查」升为「可被消费」 |
| skill 把规则喂给 agent | 复用现有 skill 通道，指向查询命令 | 不新写一份规则正文（会与文档双写） |

## 7 建议动作

### P0（低风险，一个 PR）：收敛映射并入登记表，两个守卫同源

**做什么**

1. 在「意图登记表」小节内新增一张表（`parseTables` 按表头认表，新增一张不影响现有三张）：

   ```
   | 收敛控件 | 封装件 | 守卫 |
   | --- | --- | --- |
   | el-button | UiButton | check-el-controls |
   ```

2. `lib/ui-intent-registry.mjs` 增加第四个派生面 `converged: Map<'el-x', 'UiY'>`（复用现成的 `tableOf`）。
3. `check-el-controls.mjs` 的 `GUARDED_CONTROLS` 改为从 `getRegistry().converged` 派生；footer 文案由同一份数据渲染，删掉 `:31-40` 的逐行注释与 `:99-102` 的手写文案。

**为什么值得做**：一条事实现在有 3 份写在同一文件里、第 4 份半藏在登记表；加一个封装件要改两处代码 + 一段文案，且两份清单已经不同源（10 条守卫 vs 登记表 30+ 行）。这正是 #1982 想消灭的形态，只清了一半。

**验收判据**

- 删掉登记表里的 `el-switch` 行 → `node scripts/check-el-controls.mjs --all` 必须对含 `<el-switch>` 的文件报红（证明映射真被读到，不是残留硬编码）。
- `node scripts/check-ui-intent.mjs --all` 与 `--emit-registry` 输出不变（回归）。
- `check-ui-intent.test.mjs` / `check-el-controls.test.mjs` 全绿；若自检里断言了 `counts.tables === 3`，同步改。

**已知约束（改之前必读）**

- `parseTables` 按表头认表、**按列位取值**（`ui-intent-registry.mjs:100-106`），加列只能加在末尾；改列序会静默错配。
- 新表的表头首格不能与现有三张（`意图` / `件` / `子件`）重名，否则 `tableOf` 会取错。

### P1（中）：给封装件做查询面，替代通读 351 行

**做什么**：`scripts/ui-docs.mjs`，三种入参——封装件名（`UiDialog`）、EP 控件名（`el-tabs`）、意图词（`确认`/`抽屉`）——输出一屏内信息：意图 + 三轴、唯一形态、存量与待迁、所属守卫、组件 props（从 `<script setup>` 的 `defineProps` 与 JSDoc 抽取）、同级替代（「这个不是 `UiDialog` 的场合用 `useConfirm`」）。

**为什么不生成站点**：本仓是内部全栈仓，没有对外文档需求；生成 `docs/ui/*.md` 会与 `ui-conventions.md` 形成双写，而双写正是本仓反复收口的东西。**查询面而不是文档面**，是这个建议的关键。

**验收判据**

- 一次真实任务（如「给举报列表加一个二次确认」）中，agent 只调用查询命令即可完成选型，不读 `ui-conventions.md` 全文。
- 查询输出与登记表不漂移：脚本从派生面取数，不另存一份映射。

### P2（待实测）：MCP / 每件一页，先算成本再决定

按 `docs/agents/checks.md` 的成本量尺（#1705 口径，实付 token）跑对照：同一任务「读 351 行文档」vs「调一次查询」。若差值不显著（比如 < 20%），**不做 MCP**——多一个常驻进程换不到收益。**没有实测数据前不立项。**

## 8 纸上判不出的项

1. **查询面是否真能替代通读**：agent 是「按需查」还是「先通读再动手」，取决于模型行为，纸面推不出；P1 的验收判据就是为此设的。
2. **EP 升级时 `--diff` 式合并的真实收益**：要等一次 EP minor 升级、看封装层实际被破坏几件才知道。现在建这套工具是纯投机。
3. **MCP 的宿主可行性**：本仓 agent 环境已有 skill 通道，MCP 是否多此一举，取决于宿主支持面——属环境事实，不属设计判断。
4. **140 条 `--el-*` 显式 hex 的收敛成本**：属 `1880-token-audit` 的邻域，需逐条判「能不能由 EP 自己算（`--el-color-x-light-N` 是否可由主色派生）」，纸上判不出，得实测一档。
