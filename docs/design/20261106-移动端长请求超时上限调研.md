# 移动端长请求超时上限调研（uni.request 提至 300 s 是否可行）

- 日期：2026-11-06
- 范围：`training-app/叉车维修培训学员端跨端应用/`（uni-app x，mp-weixin + App Android/iOS）
- 关联：`docs/design/20261105-诊断接口能力盘点与联调确认.md` §6.1 / §8 G5（那里只确认了「客户端 120 s < 服务端 300 s」，没回答平台侧上限，本文补这一格）
- 结论的取证方式：微信官方文档 4 页、DCloud uni-app x 官方文档、**DCloud 官方源码 `dcloudio/uni-api`（`alpha` 分支）**、OkHttp 官方源码 javadoc、Apple 官方文档 3 页、1 篇社区实测（2025-09）。全部链接见文末「来源」。
- 本次**未改任何代码**。

## 结论先行

**一句话**：`timeout: 300000` 在 **App 两端（Android/iOS）可行且有余量**——因为 uni-app x 把 `timeout` 落到 OkHttp 的 `readTimeout` / `URLRequest.timeoutInterval`，**语义是「读空闲」而不是「总时长」**，服务端 SSE 持续 flush 时字节不断到达即不断续命；但在 **mp-weixin 端不能从文档保证**——微信文档只写「默认 60000、单位 ms」，**既没写上限也没写语义是总时长还是空闲**，且**「切后台 5 s 未完成即 `fail interrupted`」是比 timeout 更硬、且与 timeout 取值无关的平台上限**（锁屏、切到车间别的 App 直接必挂）。

分三类，别混着引用：

| 类型 | 内容 |
| --- | --- |
| **文档事实**（官方文档明文） | 微信 `wx.request` 默认 60000 ms、可用 `networkTimeout.request` 或调用级 `timeout` 覆盖、**文档未设上限**；微信小程序切后台 **5 s** 内未结束的网络请求回调 `fail interrupted`；iOS `URLRequest.timeoutInterval` 默认 60 s 且是「idle」语义；iOS `timeoutIntervalForResource` 默认 **7 天**（总时长闸门不会先杀）；OkHttp `readTimeout` 是「individual read IO operations」、`callTimeout` 才是总时长（默认 0 = 不限） |
| **源码事实**（读官方实现得出，强于博客、弱于文档承诺） | uni-app x Android 只设 `connectTimeout/readTimeout/writeTimeout`、**从不设 `callTimeout`**，并**强制 HTTP/1.1**；iOS 只设 `URLRequest.timeoutInterval`，**未改会话级 `timeoutIntervalForRequest/ForResource`**；两端**非 chunked 路径也在 socket 层增量读**（Android 2048 字节循环 read） |
| **只能真机实测**（文档/源码都没有答案） | mp-weixin 的 `timeout` 到底是总时长还是空闲、是否真被某个更短的硬上限截断（社区只报了 chunked 模式下的异常，见 §4）；以及锁屏/后台这两种「非前台」场景下 300 s 是否还活着（§3） |

## 1. 微信小程序：`timeout` 能设多大，有没有硬上限

**文档层面：能设任意毫秒，没有写上限。**

- 默认 60 s，两层可配：全局 `app.json` 的 `networkTimeout.request`（number，默认 **60000**，「单位：毫秒」），或调用级 `wx.request({ timeout })`，「接口调用的 timeout 配置优先级高于 app.json 中的配置」。两页都**只写默认值，不写上限**。
  - https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html
  - https://developers.weixin.qq.com/miniprogram/dev/reference/configuration/app.html
- `wx.request` 参数表：`timeout` number、非必填、「超时时间，单位为毫秒。默认值为 60000」，最低基础库 **2.10.0**。同样**无上限说明**。
  - https://developers.weixin.qq.com/miniprogram/dev/api/network/request/wx.request.html

**文档层面查不到的两件事（本文不给结论，只标缺口）**：

1. **`timeout` 是总时长还是读空闲？** 微信文档从没定义；`fail` 回调只给 `errMsg/errno/exception`，看不出语义。这一条直接决定「300 s 整包」成立与否 —— 总时长语义下必须 ≥300 s 且零余量，空闲语义下只要事件有流动就够。
2. **有没有更短的硬上限？** 官方文档没有任何关于「超过 N 秒必断」的表述。

**实测证据（可信度：中）**：一篇 2025-09-12 的掘金文章「微信小程序 wx.request enableChunked 模式下 timeout 失效问题」给出四端实测（`enableChunked: true` + `timeout: 10 分钟` + SSE 响应头）：微信开发者工具 Stable 1.06.2503300 ❌ 任意值无效；iOS 微信 8.0.61 ❌ 任意值无效；**Android 微信 8.0.61：> 60000 ms ✅ 生效、< 60000 ms ❌ 无效**；Windows 微信 4.0.6.21 ❌ 任意值无效。作者归因为「安卓微信 60 秒硬编码阈值 / 其余端完全忽略 timeout」，但**没有给出任何官方 issue 链接**，属于单作者博客 —— 只能当「微信客户端实现可能不遵守文档」的线索，不能当判据。
- https://juejin.cn/post/7548717557530591272

仓内查到的只能是旁证：一篇 2020-08-25 的腾讯云社区转载博客演示了把 `networkTimeout.request` 写成 `1000000`（≈16 分钟）的写法，但**没有任何验证或原理说明**，可信度低，最多说明「社区确实有人这么配」。
- https://cloud.tencent.com/developer/article/1685013

> 想找微信官方社区里的「60 s 被断」原帖，两条候选（`.../community/develop/doc/000888301483a862bd4e0492251000`、`.../community/develop/doc/0002e0fc558a20ef4d4e0cfc05bc00`）用 curl 只拿到约 7 KB 的反爬壳，**未取得正文，不引用**。

## 2. uni-app x 里 `timeout` 怎么落地（小程序端 / App 端）

**文档层面**（`https://doc.dcloud.net.cn/uni-app-x/api/request.html`，页面标注「上次更新 2026/9/20」）：`timeout` number 默认 **60000**，描述只有「超时时间，单位 ms」，**没有上限、没有任何「平台语义不同」的说明**；`enableChunked`「开启 transfer-encoding chunked」；`RequestTask.onChunkReceived` 兼容性 Web 4.71 / 微信小程序 4.41 / 支付宝 5.31 / Android 4.71 / iOS 4.71。错误码里 `errCode 5 = 接口超时`、`600003` 网络中断、`602001` request 系统错误。

**小程序端**：uni-app x 不重新实现网络栈，`uni.request` 就是 `wx.request` 的包装（参数同名、错误码同名、`enableChunked`/`onChunkReceived` 同名且小程序侧兼容版本 4.41 对应基础库 2.20.x 的时代），所以 §1 的全部不确定性原样继承 —— 这一条是**推断**（DCloud 文档没写「透传」这个词），但同名参数 + 同名事件 + 无独立实现，可以认为等价。

**App 端**：读官方源码（`github.com/dcloudio/uni-api`，分支 `alpha`，`uni_modules/uni-network/utssdk/`）比读文档有用：

- Android `app-android/network/NetworkManager.uts:220-223`：
  ```kotlin
  const timeout : Long = param.timeout != null ? param.timeout!.toLong() : 60000;
  clientBuilder.connectTimeout(timeout, TimeUnit.MILLISECONDS);
  clientBuilder.readTimeout(timeout, TimeUnit.MILLISECONDS);
  clientBuilder.writeTimeout(timeout, TimeUnit.MILLISECONDS);
  ```
  紧接一行 `clientBuilder.protocols(Collections.singletonList(Protocol.HTTP_1_1));` —— **只设了 connect/read/write，从不设 `callTimeout`（总时长）；且强制 HTTP/1.1**。
- iOS `app-ios/network/NetworkManager.uts:185-187`：
  ```swift
  let timeout = param.timeout == null ? 120000 : param.timeout;
  let timeoutInterval = new Double(timeout!) / 1000;
  let request = new URLRequest(url = url!, cachePolicy: ..., timeoutInterval: timeoutInterval);
  ```
  会话是 `URLSessionConfiguration.default`（`:150-155`），**没有改 `timeoutIntervalForRequest` / `timeoutIntervalForResource`**。顺带一个文档与实现的出入：**iOS 不传 timeout 时源码默认 120000，而文档写 60000**。

所以链路是 `uni.request.timeout` → 小程序：`wx.request.timeout`（语义不明）→ App：OkHttp `readTimeout` / `URLRequest.timeoutInterval`（都是空闲语义）。

## 3. App 端：总时长还是读空闲？300 s 会不会被系统杀

**是读空闲，不是总时长 —— 这一条有官方 javadoc 原文。**

- OkHttp `readTimeout`：「The read timeout is applied to both the TCP socket and for individual read IO operations including on Source of the Response. The default value is 10 seconds.」；`callTimeout`：「The call timeout spans the entire call: resolving DNS, connecting, writing the request body, server processing, and reading the response body… The default value is 0 which imposes no timeout.」—— uni-app x 设的是前者、没设后者（§2 源码）。
  - https://raw.githubusercontent.com/square/okhttp/master/okhttp/src/commonJvmAndroid/kotlin/okhttp3/OkHttpClient.kt
- Apple `URLRequest.timeoutInterval`：「If during a connection attempt the request remains idle for longer than the timeout interval, the request is considered to have timed out. The default timeout interval is 60 seconds.」→ 明确 **idle**。
  - https://developer.apple.com/tutorials/data/documentation/foundation/urlrequest/timeoutinterval.json
- Apple `URLSessionConfiguration.timeoutIntervalForResource`：「how long… to wait for an entire resource to transfer before giving up… default value is 7 days」→ 真正的总时长闸门默认 7 天，**不会**在 300 s 处先杀；uni-app x 也没改它，等于保持 7 天。
  - https://developer.apple.com/tutorials/data/documentation/foundation/urlsessionconfiguration/timeoutintervalforresource.json

**推论（源码 + 服务端行为共同支撑，非文档承诺）**：本链路 `handler.go` 在 `EnsureSessionOwned` 通过后**立刻** `writeSSEHeaders(c)`（`backend/internal/aiassistant/handler.go:471`），`sendEvent` 每次 `WriteString` 都 `Flush()`（`:477`），上游 status 也会立刻下沉成 `status` 事件（`:487-490`）。也就是说 **响应头在 t≈0 就到客户端**，空闲计时在 headers 处就重置了一次；之后只要每个 `event:` 之间、以及首个事件之前的**静默间隙** < timeout，App 端就不会判超时。**真正被 timeout 约束的量是「最长静默间隙」，不是 300 s 总时长** —— 这一条对设计的影响比「把 120000 改成 300000」本身大得多（见 §6）。

**锁屏 / 省电**：

- iOS 文档明说进后台后应用在数秒内被 **suspend**：「That method has five seconds to perform any tasks and return. Shortly after that method returns, the system puts your app into the suspended state.」（该段讲的是 `beginBackgroundTask` 的时限，非普通请求，但结论一致：**普通 App 进后台不保证网络继续**）
  - https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time
- Android 侧没有找到「300 s 前台长请求会被系统杀」的一手文档；**未找到一手来源**。可以确定的只有：进程被冻结/杀后请求必然以网络错误（`600003`/`602001`）结束，与 timeout 取值无关。
- 这与 §1 微信「切后台 5 s 即 `fail interrupted`」是同一类问题的不同强度：**锁屏/切后台是超时参数管不到的失效面**，任何 timeout 取值都救不了。缓解手段只能是不让屏幕熄：`uni.setKeepScreenOn`（`https://doc.dcloud.net.cn/uni-app-x/api/screen-brightness.html`，微信小程序 4.41 / Android 5.08 / iOS 5.08 起）。

## 4. `enableChunked` + `onChunkReceived` 的超时语义是否不同

**文档：没有回答。** 微信 `RequestTask.onChunkReceived`（基础库 **2.20.1** 起，「监听 Transfer-Encoding Chunk Received 事件。当接收到新的 chunk 时触发」，回调 `res.data: ArrayBuffer`）页面**一个字都没提 timeout**；DCloud 的 `onChunkReceived` 文档同样没有。
- https://developers.weixin.qq.com/miniprogram/dev/api/network/request/RequestTask.onChunkReceived.html

**源码：App 端 chunked 与非 chunked 的「读」是同一条路，差别只在要不要把增量抛给监听者。** Android `NetworkManager.uts:538-543`：

```kotlin
let rawStream = response.body()!.byteStream()!;
const enableChunked = this.enableChunked && response.header("Transfer-Encoding") == "chunked";
```

非 chunked 走 `readInputStreamAsBytes`（2048 字节一轮 `read()` 累积进 `ByteArrayOutputStream`），chunked 走 `processStreamWithOkio`。两者都在 socket 层持续 `read`，而 `readTimeout` 是「individual read IO operations」级别的（§3），**所以开不开 chunked 都不改变 readTimeout 的续命行为** —— 至少 Android 上是这样。iOS 的 `onChunkReceived` 由 DCloud 文档说明「基于原生 URLSession 实现，需要服务端采用流式响应（chunked 或 `text/event-stream`）」，其底层同样是持续接收，空闲语义不变。

**两条只有在方案里才显形的坑（源码事实）**：

1. 微信侧 `enableChunked` 会让请求**退回 HTTP/1.1**（`wx.request` 的 `useHighPerformanceMode` 说明：「除声明了 `enableChunked` 后会走 HTTP1 以外，均会自动开启 HTTP2/HTTP3」）—— 用 chunked 换流式，等于放弃 HTTP/2/3。
2. Android 判断「是否 chunked」用的是 `response.header("Transfer-Encoding") == "chunked"`：**HTTP/2 没有这个头**。目前 uni-app x 在 Android 强制 HTTP/1.1（§2），所以没事；但一旦这层被改掉或中间设备把响应转成 HTTP/2，`onChunkReceived` 会静默收不到任何 chunk（不报错、只是没有增量）。做方案评估时要记住这个隐藏依赖。
3. 社区实测（§1）恰恰是**在 chunked 模式**下发现 iOS/devtools/Windows 的 `timeout` 失效 —— 也就是说「开 chunked 解决长请求」在微信端不是加法，可能是减法（它改变的是传输编码与 HTTP 版本，不提供任何超时豁免）。

## 5. `text/event-stream` 的缓冲 / 响应体大小限制

**未找到一手来源。** 微信 `wx.request` 文档、`responseType` 说明、`onChunkReceived` 页面、uni-app x `request` 文档，**都没有写响应体大小上限或 `text/event-stream` 的特殊限制**。

能确定的只有实现层的事实：

- **客户端侧没有「流式消费」，只有「整包攒完再回调」**：本仓现行用法（未开 `enableChunked`、`responseType` 默认 text）在 Android 上就是 `readInputStreamAsBytes` 把整个 body 攒进内存，iOS 上就是 URLSession 把数据全收完再回调。所以「整包」这个词是准确的：**在回调之前，业务层拿不到半个 token**。
- 因此实际约束不是「文档限制」而是**内存与端上缓冲**：300 s 的 markdown 回答按经验不过几十 KB~几百 KB，远不到任何端的危险区；**但这是估算，不是取证结论**。
- 服务端侧要保证不被中间层攒包：`writeSSEHeaders` 已设 `X-Accel-Buffering: no` + `Cache-Control: no-cache`，且每次写后 `Flush()`，Caddy `reverse_proxy` 也未配缓冲（见 §6.1 既有结论）。

## 6. 对「把 120000 改成 300000」的处置建议

分端给结论，别一刀切：

1. **App 端：改 300000 是安全的，但不是因为它「必须」300000。** 语义既然是空闲，那么只要服务端事件有流动，120 s 也够；改成 300000 实际放宽的是「最长静默间隙」。真正该做的是**给静默间隙加服务端心跳/占位事件**（例如上游首 token 前的 `status` 已有，但长推理阶段可能没有），把间隙压到远小于任何 timeout —— 这比把客户端数字调大更省事、且对两端同时生效。
2. **mp-weixin 端：改 300000 既不能从文档保证生效，也不能解决真正的杀手。** 文档允许任意毫秒，但语义未定义；社区实测显示在不同端 `timeout` 被忽略。更硬的是**切后台 5 s → `fail interrupted`**（前台锁屏同样触发），这一条与 timeout 取值完全无关，无法用参数解决。可行的减压只有两条：`uni.setKeepScreenOn(true)` 保持前台常亮（微信小程序 4.41+），以及缩短单次请求的期望时长。
3. **别把 enableChunked 当「提上限」的手段**：它不提供任何超时豁免（§4），在微信端还会退到 HTTP/1.1，且带来半包解析成本。

## 7. 若不成立，传输方案候选

| 候选 | 一句话取舍 |
| --- | --- |
| **A. `enableChunked` + `onChunkReceived`（打字机 + 增量续命）** | 体验最好、也是最接近「真流式」的做法，但**它不提高任何上限**：微信端要自己做半包解析（chunk 边界可能在 UTF-8 多字节字符中间，且**小程序没有 `TextEncoder`**，DCloud 文档明确要求引三方库解码），App 端 Android 还依赖 `Transfer-Encoding: chunked` 头（HTTP/2 下失效）。收益是 UX 与「首个 token 时间」，不是超时。 |
| **B. 任务化 + 轮询** | 把长回答变成「提交任务 → 拿 task_id → 轮询/短连接取增量」，单请求时长降到秒级，**彻底绕开两端的一切超时与后台限制**（包括微信 5 s 后台规则，因为每跳都很短）。代价是后端要加任务态与幂等、客户端要加轮询状态机，且服务端 300 s 的上游闸门仍在那里（只是不再由客户端连接承担）。 |
| **C. 降级：保持较长 timeout，但接受「300 s 内被判死」** | 改动最小（只改 `AI_REQUEST_TIMEOUT`），App 端大概率够用、微信端听天由命；配合「超时后提示稍后重试 / 走非流式历史查询」。适合先止血，不适合当长期方案。 |
| **D. 收敛回答长度与上限** | 把服务端 300 s 与客户端 timeout 一起下调（例如 90~120 s），让超时成为产品级 SLA 而不是工程缺陷；代价是长诊断可能被截断，需要 `done` 事件里带「已截断」标记。 |

## 8. 真机验证最小判据

**一条可执行的验证**（在现网或预发，不写代码即可做）：

1. 用终端拿 token 与一条**已知会跑很久**的提问（或临时把一个测试端点的上游拖慢），先确认服务端 SSE 的**首个事件时间**与**最长静默间隙**：
   ```bash
   curl -N -H "Content-Type: application/json" -H "Authorization: Bearer <token>" \
     -d '{"feature_key":"fault_consult","messages":[{"role":"user","content":"<长诊断问题>"}]}' \
     https://api.gdyidao.cn/api/ai-assistant/chat \
     | while IFS= read -r line; do printf '%s %s\n' "$(date +%s)" "$line"; done | tee sse-timing.log
   ```
   把每行前面打上时间戳后，算三个数：`t_headers`（第一个字节）、`t_first_event`、`max_gap`（相邻事件最大间隔）。这三个数决定后面怎么判。
2. 把 `AI_REQUEST_TIMEOUT` 临时改成 300000（**验证后必须改回或按结论定稿**），出 mp-weixin 包与 Android/iOS 包，在**前台亮屏**状态下各跑同一条提问，屏幕录像或打日志记 `success/fail` 与 `errMsg`。
3. 再跑一遍**锁屏 / 切到别的 App 30 s 后切回**的用例。

**通过判据（三条全中才算「300 s 整包可行」）**：

- 前台亮屏：mp-weixin 与 App 都拿到 `success`，且耗时 > 120 s（证明确实跨过了旧值，不是刚好跑得快）；
- 前台亮屏：`max_gap` 明显小于 300000（例如 < 60 s）——否则即使这次过了，也只是运气，应回到 §6 第 1 条去加心跳；
- 锁屏/切后台：**预期失败**。失败时 `errMsg` 若是微信的 `request:fail interrupted`（→ 平台 5 s 规则，与 timeout 无关，判据成立但方案不成立）、App 端若是 `600003/602001`（→ 系统挂起了进程），则如实记录为「超时参数不可覆盖的失效面」，不要据此调大 timeout。

**不通过判据**：前台亮屏下耗时 < 120 s 就 `fail`，或 `errMsg` 含 timeout/`errCode 5` 而 `max_gap` 远小于 timeout —— 说明客户端用的不是空闲语义（或微信侧另有更短上限），此时 §7 的 B（任务化）应作为主方案。
