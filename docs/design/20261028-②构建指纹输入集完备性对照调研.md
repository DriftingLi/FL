# ② 构建指纹输入集完备性对照（#2048 判据①）

日期：2026-10-28 · 来源票：https://github.com/DriftingLi/FL/issues/2048 · 一手源：本仓 D:\FL 现测（无外部资料）

## 问题

判据库 scripts/lib/mp-weixin-build-fingerprint.ps1 的输入集（cache key）是否覆盖「影响 mp-weixin 产物的来源全集」？有缺口 = 改动过的东西被判「未变」⇒ 复用旧产物、门照样绿 ⇒ **fail-open**。

## 现测口径（三条硬事实）

1. **键只有三组件，全等才命中**：inputs（项目根递归哈希，排除清单见 mp-weixin-build-fingerprint.ps1:93-95）/ product（产物目录哈希，:103）/ hbuilderx（版本令牌，:111）；任一算不出 ⇒ 重建（:19「判不出 = 重建，绝不猜命中」）。
2. **产物合法性与 appid 断言在 -SkipBuild 的两条分支之外**，指纹命中跳过构建时照样执行：scripts/mp-weixin-check.ps1:1767（合法性）+ :1784（appid）。⇒ 「门参数 -AppId 变了」这一维度由断言兜住，不是指纹的缺口。
3. **指纹只在真构建、且上述两道断言都过了之后才落盘**：mp-weixin-check.ps1:1795。⇒ 坏产物不会被写成基线。

## 结论

- 票面假设成立，但**缺口不在票面枚举的「源码 / 配置 / 静态资源 / uni_modules」那一侧**（那一侧实测完备），而在两处**非文件型来源**：构建命令（G1）与编译器本体（G2）。
- 二者都是**结构性判定**（判据库根本不读那些路径），**未做端到端实测**：本树当前无产物、无 .mp-weixin-build-fingerprint.json（unpackage/dist/build/mp-weixin 不存在）。

## 判据② 复现的两条路（成本与结论强度不同）

- **轻量（无需真机）**：扩 utils/mpWeixinBuildFingerprintBehavior.test.js 夹具，加「排除面但影响产物的文件变（夹具内 scripts/x.ps1）⇒ 现实现仍命中」——把 G1 机械复现成一条必红用例（现状必绿 ⇒ 反证缺口）。G2 同理：假安装根给「同目录名 + 同 cli.exe 字节」，改 plugins/ 下假编译器 ⇒ 仍命中。
- **重（端到端）**：真跑 ② 门两次（中间改 publish 参数），看 AUTO_SKIP_BUILD 日志行（mp-weixin-check.ps1:977）是否照样出现。只有这条能给「门照样放行」的直接证据。

## 收口选项（不在此替维护者定）

现有守护 …Behavior.test.js:89 把「排除面文件新增 ⇒ 仍命中」当**必不红**断言钉住 ⇒ 收口会反转这条断言的方向（至少对影响产物的那部分排除面）。这是**改判据**、不是加判据，须先与票面边界「不改 ② 门语义与触发判据」对齐。
