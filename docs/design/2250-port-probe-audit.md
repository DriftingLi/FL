## 0. 置顶结论

**结论行（供 A-4 引用）：四核心场景 ①②③④ 的「可连 / 有监听」布尔结论并非全一致——② 的通配 `::` 绑定存在一个 v6-only 子形态（Listen 表说有监听、而 `127.0.0.1` 试连超时），按票面判据「任一不一致 ⇒ 混判据」，因此 A-4 走混判据：循环内 TcpClient 快筛 + 预算末端 1 次 Listen 表收口。**

支撑这个结论的三件事，按分量排：

1. **② 有一处布尔级不一致，而且正是「换基元会变坏」的方向**。`bind=[::]:47220` 在 `IPV6_V6ONLY=1` 时，`Get-NetTCPConnection -State Listen -LocalPort` 返回 `count=1 addrs=:::47220`（旧基元判「就绪」），而门里现成的 `Test-MpWeixinTcpConnect`（固定连 `127.0.0.1`）连续两次读成 `TIMEOUT 2008/1999 ms`（新基元判「未就绪」）。**直接替换会让「v6-only 通配监听」从「就绪」翻成「等满整笔预算然后报 port-not-listening」**——正是 #2235 要消灭的那种假红/白烧形态。表与码见 §2 第 3、4 行。
2. **①②③④ 在双栈与专绑形态下确实等价**（§2 第 1、2、5、6 行）：专绑 `127.0.0.1` 与双栈 `[::]` 两种最可能出现的形态，两基元的布尔结论逐次相符，且 ④ 收摊后两基元同步转「无」。所以混判据不是「不知道谁对」，而是**已知新基元会在一个子形态上误判**，必须留一道收口。
3. **混判据的收口方向是对的、且不引入新风险**：末端那 1 次 Listen 表＝**今天门的行为**，所以混判据的最坏情形是「和现在一样慢」，最好情形是「前 N-1 轮几乎免费」，不存在比现状更差的取值。

**一句话给 A-4**：不能直替（② 有 v6-only 反例）；走混判据＝循环内 `TcpClient` 快筛 + 预算末端 1 次 `Get-NetTCPConnection` 收口。

## 2. 六格矩阵（n=2，每格三读数）

> 读法：「一致」= 两基元的**布尔结论**相符（能连上 ⇔ 表里有监听）；错误类型与耗时只作登记，不作判据。监听进程由探针自己起（`New-Object System.Net.Sockets.Socket` + `Bind` + `Listen`），④ 的监听方是独立子进程。

### ① 127.0.0.1 专绑监听 — `bind=127.0.0.1:47120`

| n | TcpClient | 耗时 | 同刻 Listen 表 | 一致 |
|---|---|---|---|---|
| 1 | **OK** | 8 ms | `count=1` `127.0.0.1:47120`（表 2451 ms） | ✔ |
| 2 | **OK** | 0 ms | `count=1` `127.0.0.1:47120`（表 2470 ms） | ✔ |

两个方向都对得上：能连 ⇔ 表里有。**这是两基元"应该"成立的基线格。**

### ② 通配 `::` 绑定 — `bind=[::]:47220`，一次换一个端口试两个子形态

| 子形态 | n | TcpClient(`127.0.0.1`) | 耗时 | 同刻 Listen 表 | 同刻连 `::1` | 一致 |
|---|---|---|---|---|---|---|
| 双栈（`IPV6_V6ONLY=0`） | 1 | **OK** | 1 ms | `count=1` `:::47220`（2656 ms） | OK 1 ms | ✔ |
| 双栈（`IPV6_V6ONLY=0`） | 2 | **OK** | 0 ms | `count=1` `:::47220`（2443 ms） | OK 0 ms | ✔ |
| **v6-only（`IPV6_V6ONLY=1`）** | 1 | **TIMEOUT** | 2008 ms | `count=1` `:::47220`（2428 ms） | **OK 1 ms** | **✘** |
| **v6-only（`IPV6_V6ONLY=1`）** | 2 | **TIMEOUT** | 1999 ms | `count=1` `:::47220`（2489 ms） | **OK 1 ms** | **✘** |

**这一格就是结论的全部重量所在。** 同一个端口，服务确实在监听（表说 `:::47220`，且 `::1` 上 1 ms 就连上），但 (a) 因为硬编码 `127.0.0.1` 而在 v6-only 形态下**连不上也判不出**——它只能等到预算耗尽报 `false`。而 (a) 的返回值是**布尔**、不含错误类型，调用方无法区分「真的没人听」与「听了但不在 v4 上」。

### ③ 无人监听 — 端口 1（系统保留、确认无监听）

| n | TcpClient（门预算 2000 ms） | 耗时 | 同刻 Listen 表 | 宽松预算 5000 ms 复读 | 一致 |
|---|---|---|---|---|---|
| 1 | **TIMEOUT** | 2001 ms | `count=0`（2296 ms） | **REFUSED** 2027 ms | ✔（布尔） |
| 2 | **TIMEOUT** | 2009 ms | `count=0`（1588 ms） | **REFUSED** 2015 ms | ✔（布尔） |

两基元的布尔结论相符（都判"没有"），但**错误类型在 2000 ms 预算这条刀锋上会翻转**：同一次拒绝，预算 2000 ms 读到 `TIMEOUT`、预算 5000 ms 读到 `REFUSED`（2027/2015 ms 才拒绝完）。这条差异的成因与影响见 §3 第二、三条——它**不是**基元语义差异，但它是「2000 ms 这个默认值在本机贴边」的硬证据。

### ④ 进程退出后收摊竞态 — 监听方是独立子进程（`127.0.0.1:47420`，监听 1.5 s 后 `Dispose` 退出）

先取对照基线（子进程仍在听），再在子进程退出后的四个时点各取 n=2：

| 时点 | n | TcpClient | 耗时 | 同刻 Listen 表 | 一致 |
|---|---|---|---|---|---|
| 子进程在听（对照） | 1 | **OK** | 0 ms | `count=1` `127.0.0.1:47420`（1508 ms） | ✔ |
| 子进程在听（对照） | 2 | **TIMEOUT** | 1997 ms | `count=0`（1812 ms） | ✔（此读已落在退出之后，见下） |
| post-exit @0 ms | 1 / 2 | **TIMEOUT** / **TIMEOUT** | 2001 / 2002 ms | `count=0` / `count=0`（2728 / 2192 ms） | ✔ / ✔ |
| post-exit @300 ms | 1 / 2 | **TIMEOUT** / **TIMEOUT** | 2009 / 2007 ms | `count=0` / `count=0`（2164 / 2234 ms） | ✔ / ✔ |
| post-exit @1200 ms | 1 / 2 | **TIMEOUT** / **TIMEOUT** | 2000 / 2011 ms | `count=0` / `count=0`（2095 / 2218 ms） | ✔ / ✔ |
| post-exit @3000 ms | 1 / 2 | **TIMEOUT** / **TIMEOUT** | 2008 / 2009 ms | `count=0` / `count=0`（2031 / 2403 ms） | ✔ / ✔ |

对照基线第 2 次读成 `TIMEOUT / count=0` 不是异常：子进程只监听 1.5 s，而每轮「试连 + 查表」在 4 路负载下要 ~2–4 s，第 2 轮起就落在退出之后了。这条我保留原读数**不重测**——它恰好演示了"收摊瞬间两基元同步转无"，是 ④ 想测的东西本身。

另用一个**非门基元**的快读器（`IPGlobalProperties.GetActiveTcpListeners()`，全表 25 ms 级）在退出后 300 ms 内密集采 13 次：`firstZeroAtMs=20`、`lastNonZeroAtMs`（无，即从第一次采样起就已经是 0）。⇒ **监听槽位在进程退出后 20 ms 内就消失**，而两个门原生的探法各自都要 ~2.0 s 才给出同一个结论。这条不用于判据，只用于说明「竞态窗口远小于探测粒度」——**④ 不构成新的不一致来源**。

### ⑤ backlog 满（listen 不 accept）— `backlog=1`、`127.0.0.1:47520`

真件造出来了：`Listen(1)` 后不 `Accept`，用保留连接把队列灌满，**第 2 条保留连接就连不上**（`fillers=1`）。此后本格读数：

| n | TcpClient | 耗时 | 同刻 Listen 表 | 一致 |
|---|---|---|---|---|
| 1 | **TIMEOUT** | 2003 ms | `count=1` `127.0.0.1:47520`（1999 ms） | ✔ |
| 2 | **TIMEOUT** | 2006 ms | `count=1` `127.0.0.1:47520`（1843 ms） | ✔ |

「一致」在这里的读法要小心：**两基元同时说"有人在听"、同时说"连不上"**——表说有监听（对，确实在听）、试连超时（对，队列满了接不进来）。这不是矛盾，是两种探法**各自如实描述了同一事实的不同侧面**：Listen 表只看绑定，试连还额外承担了「服务是否接受连接」这一层信息。对门的语义（端口出现 ⇒ 值得进入下一道协议级闸门）来说，两者给出同一结论。

### ⑥ 防火墙静默丢包 — **未证实**（`127.0.0.1:47620`）

**为什么造不出真件**：静默丢包要用 `New-NetFirewallRule -Action Block` 或 wfp 过滤器在 `127.0.0.1` 上丢包，两者都要管理员权限；而票面对本格的原话是「本机造不出真件是已预知的，就地标未证实，**不要为了凑格去改系统防火墙**」。所以没有尝试改防火墙，只留了「监听在且连接通」的对照基线：

| n | TcpClient | 耗时 | 同刻 Listen 表 | 判定 |
|---|---|---|---|---|
| 1 | OK | 0 ms | `count=1` `127.0.0.1:47620`（1676 ms） | 未证实 |
| 2 | OK | 0 ms | `count=1` `127.0.0.1:47620`（1475 ms） | 未证实 |

**这一格仍然说明了事**：静默丢包形态下 Listen 表**必然**报有监听（绑定没变），若试连也变成「超时」，两基元就会在这一格分裂成「表说有、试连说没有」——与 ②v6-only **同一方向的伪分歧**。这格虽未证实，但它与 ② 的已证实反例指向同一类风险，**加强而非削弱**混判据的结论。

## 3. 三处差异的定性（哪条是判据、哪条不是）

1. **耗时读数一律不作判据。** 本次 Listen 表单次 1475–3501 ms（票面基线 3.0~4.5 s），TcpClient 命中格 0–8 ms、未命中格 1997–2011 ms——全部在 4 路并发下测得，不能用于「谁更快」的跨次比较，也不能用于「替换能省多少」。**A-2 的判决只用布尔一致性**。
2. **③④ 的 `TIMEOUT` vs `REFUSED` 是本机拒绝路径 ~2.0 s 的刀锋效应，不是基元语义差异。** 交叉验证（同一次会话内，无监听端口、n=2）：
   - .NET `TcpClient.ConnectAsync`：`127.0.0.1 → THROW:ConnectionRefused 2083 ms`、`::1 → 2036 ms`、局域网地址 `192.168.132.1 → 2044 ms`；
   - python `socket.connect`（阻塞、5 s 超时）：`ConnectionRefusedError 2037 / 2031 ms`；
   - **node 原生 `net.connect` 同端口：`ECONNREFUSED 7 / 4 ms`**。

   node 走的是另一套栈，4–7 ms 就拿到了同一个 `ECONNREFUSED`。⇒ 拒绝本身在协议层是**即时**的；那 ~2.0 s 发生在 **.NET/Winsock 侧**（本机装有 Kaspersky + 腾讯电脑管家系统防护 + Windows Defender 三套安全软件，过滤驱动是最可疑的一环——**这是候选成因，未证实**，未做拔驱动对照）。**结论：门的默认预算 2000 ms 恰恰贴在这条延迟的边沿上**，所以 ③④ 的错误类型读数在「预算 2000」与「预算 5000」之间会翻转，而**布尔结论不变**。
3. **②v6-only 的差异是语义级、可复现、且方向明确。** 它不依赖耗时、不依赖负载：表说 `count=1`、`::1` 1 ms 可连、`127.0.0.1` 连不上。**这一条是唯一的判决依据。**

## 4. 落到 A-4 的形态

票面两个分支里，本次落在**第二个**：

| 分支 | 触发条件 | 本次是否成立 | 落地形态 |
|---|---|---|---|
| 直替 | ①②③④ 全一致 | **否**（② 有 v6-only 反例） | — |
| **混判据** | 任一不一致 | **是** | 循环内 `TcpClient` 快筛（命中即早退、几乎零成本）+ **预算末端 1 次 `Get-NetTCPConnection` 收口裁决** |

为什么混判据这个具体形状能吃掉 ② 的反例：末端那次 Listen 表**就是今天门的行为**——表说 `count≥1` 就照旧认为「端口出来了」并交给协议级就绪闸门（`MP_WEIXIN_READY` / `Tool.getInfo`，ADR-0008 钉的唯一 readiness 判据）。于是：
- v6-only 通配监听 ⇒ 快筛 1999 ms 后判否，**末端表判是** ⇒ 与今天一致，**不新增假红**；
- 常规形态（① 专绑、② 双栈、④ 已收摊）⇒ 快筛在 0–8 ms 命中或直接判否，末端那次表照跑一次收敛；
- 最坏情形＝「和现在一样慢」（每个预算末端仍付一次表查询），最好情形＝「前面 N-1 轮几乎免费」。

**残留风险（留给 A-1/A-4 落地时处理，不在本票射程）**：`$task.Wait($TimeoutMs)` 超时后**不取消**底层 `ConnectAsync`，在循环里反复调用会留下短暂存在的挂起连接（每次一次）。本次探针在 4 路负载下未见句柄耗尽或端口级副作用，但循环形态下应按 A-1 的墙钟预算把它压到「每预算轮一次」的量级，别在 1 s sleep 的循环里裸跑 180 次。

## 5. 测不到 / 未证实

1. **⑥ 防火墙静默丢包**：本机造不出真件（需管理员改防火墙，票面禁止）。仅有对照基线，判定「未证实」。
2. **~2.0 s 拒绝延迟的成因**：只做到「.NET/python 都慢、node 快」，指向 .NET/Winsock + 安全软件过滤驱动；**没有做拔驱动/关防护的对照实验**（那会改动系统状态，超出票面边界）。
3. **微信开发者工具真实自动化端口的绑定形态**（是 `127.0.0.1` 专绑、`[::]` 双栈还是 v6-only）：本次是**构造**六种形态，没有在 IDE 真跑时抓它的监听行。② 的反例因此是「存在这种形态且会被误判」，不是「IDE 就是这个形态」——但正因为不确定，混判据才是稳的选择。
4. **跨机器可移植性**：#2250 的判决基于这台机器。其他机器上拒绝延迟可能不是 2.0 s（node 的 4–7 ms 说明协议层本可以很快）。这不影响 §0 的结论（它只依赖布尔一致性），但影响「末端一次表查询有多贵」的账。
