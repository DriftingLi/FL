## 4. 外部对照：官方能力边界与同类实践

### 4.1 微信官方工具链的分工口径

CLI/automator 文档开头即写「若需在不依赖开发者工具场景（如自身业务工程流水线）进行小程序上传、预览，推荐使用 miniprogram-ci」（https://developers.weixin.qq.com/miniprogram/dev/devtools/cli.html ）——官方给 CI 的定位是**编译 + 上传/预览，不是运行时验证**；运行时验证的官方 CI 通道是云测真机（§4.3）。

miniprogram-automator（https://developers.weixin.qq.com/miniprogram/dev/devtools/auto/automator.html ）硬限制：`automator.launch` 需本机安装开发者工具，`cliPath` 默认探测仅 Mac/Win 两处、**无 Linux**；前置「安全设置中已开启 CLI/HTTP 调用」且登录态必须存在（`ticket` 可借用其它机器已登录身份）；连接走 `cli --auto <project_root> --auto-port 9420` + `automator.connect({wsEndpoint})`；**文档无 headless 字样 = 无官方无头模式**。CLI 的 `login` 为二维码扫码，CI 无法自动登录，`islogin` 只能查态。佐证脆弱性：miniprogram-automator 的 GitHub 仓库已消失（wechat-miniprogram org 无此仓库，npm repository.url 指向腾讯内网 git.code.oa.com；latest 0.13.0、2026-10-15 仍有维护）——issue 热度无一手来源，本文不引。Linux 运行开发者工具仅非官方移植（https://github.com/msojocs/wechat-web-devtools-linux ，免责声明「for learning and communication purposes only」、作者自述不保证各版本可用）。未找到官方禁止 CI 使用的条款，也未找到官方承诺 CI 可用的条款。

### 4.2 miniprogram-ci 能力边界（不能替 ② 的运行时面）

https://developers.weixin.qq.com/miniprogram/dev/devtools/ci.html ：「从微信开发者工具中抽离的关于小程序/小游戏项目代码的编译模块」，能力 = upload（开发版）/preview（二维码真机预览）/packNpm/云函数上传/getDevSourceMap；需公众平台「代码上传密钥」+ IP 白名单；robot 1~30。**验证层级 = 编译打包 + 上传鉴权，返回仅包体积信息，无任何运行时/渲染验证能力。** 本仓已两次裁定「用 miniprogram-ci 替 ② 门」不可行（1494:91、1657:119：官方 CI 能力清单不含无头运行时 console/异常判定）——勿再提**整体替代**；但「ci 承担构建/预览层、云测承担运行时层」的分层替代不是被否的那个方案，见 §6。

### 4.3 云测 MiniTest：官方唯一的流水线运行时通道

https://developers.weixin.qq.com/miniprogram/dev/devtools/minitest/ （官方测试团队 + WeTest 云真机）：智能化 Monkey、录制回放（开发者工具录制→云真机回放）、自定义 Minium 脚本、AI 自定义测试、启动/运行时性能、体验评分、质检、压测、图片对比。限制：Monkey「不支持输入、上传图片等复杂操作；无法校验页面逻辑」（autotest.html）；跑测框架是 **Minium（Python）而非 miniprogram-automator**——本仓门资产（JS/automator 形态）需改写；每台测试机至少扣 10 分钟时长；免费额度每周 150 分钟（仅用例执行时间）+ 每项目一次性额外 150 分钟（minium.html：云测免真机环境、虚拟测试账号避免个人微信号被判定黑产、DevOps HTTPS 接口提交任务、失败重跑）。**CI 衔接官方路径**（preview_test.html）：miniprogram-ci `preview`（robot 1-10）生成开发中预览版 → 云测提测选「开发中版本」+ 对应开发者账号 → 云真机跑用例。姊妹篇 §6.5 已建议「② 门取证接入微信小程序云测」，与本节独立收敛到同一条路线。

### 4.4 审核 + 灰度兜底：成立但责任在开发期

《常见拒绝情形》3.3.1/3.3.2/3.3.3：不可运行/崩溃/闪退/按钮无响应、本身或拖垮微信客户端崩溃、严重 Bug（无法返回退出/卡顿严重）均拒绝；3.3.4 有账号体系须提供测试号（https://developers.weixin.qq.com/miniprogram/product/reject.html ）。发布支持全量/分阶段（灰度）两种模式（https://developers.weixin.qq.com/miniprogram/dev/framework/quickstart/release.html ）。**但审核 = 提审时的人工检查，不是每 PR 门**；官方原文「请严格测试版本之后，再提交审核，过多的审核不通过，可能会影响后续的时间」——靠审核兜底意味着崩溃最晚在提审才暴露且消耗审核信用。

### 4.5 DCloud 对 uni-app x 小程序端的口径

- 支持面：HBuilderX 4.41+ 编译微信小程序、5.31+ 支付宝；「仅支持微信/支付宝小程序，其他主流小程序陆续适配」（https://doc.dcloud.net.cn/uni-app-x/mp/ ，2026-10-9 更新）。兼容性表格逐功能×逐平台维护 √/x/起始版本号，微信列大量功能为 x（https://doc.dcloud.net.cn/uni-app-x/tutorial/compatibility.html ）。

## 6. 建议口径（调研不改门，供裁定）

1. **不支持完全删除**：#1670 反例 + 0043 决策 3 冲突 + 约 25 条契约锁 + 删后无兜底通道，代价全面高于收益。
2. **首选「保留 + 成本 fix」**：改动面最小、不动判据、不碰 0043，能拿回台账估算的大部分墙钟。若墙钟仍不可接受，再走「降频为按批/发版前」——它需要一份新 ADR 修订 0043 决策 3，且 ② 在仓内没有批次形态先例，语义要从 0016 现抄。
3. **若一定要删运行时层**：前置条件是 build-only 检查（`cli publish mp-weixin` + `mp-weixin-product.ps1`）已建成并挂进 ④/CI——否则 (a)(b1) 两格一并丢掉，这是全表唯一「删了且无法用现成资产补」的部分。
4. **发版节奏的运行时兜底（全部官方文档化）**：miniprogram-ci `preview` → 云测「开发中版本」提测（每周免费 150 分钟；现有 automator 思路需改写为 Minium Python，Monkey 覆盖不了输入/上传场景）→ 真机冒烟 → 分阶段发布（灰度）控险。与姊妹篇 §6.5 建议收敛。
5. 被否方案重申：「用 miniprogram-ci **整体替代** ②」两次裁定不可行（1494:91、1657:119），理由经外部一手核实成立（无运行时验证能力）；本建议 3/4 是「ci 承担构建/预览层 + 云测承担运行时层」的分层形态，与被否方案不同，勿混。
6. **已裁定（2026-10-23 晚，用户裁定 C1）**：**保留 ②「每个运行时面 PR 必跑」、不修订 ADR-0043、不降频**，只修两个工具缺陷（票 A「② 结果行按页如实报告」/ 票 B「直达循环按页面语义分相」）。裁定依据 = §7.1 两轮实验读数（`--expect-page` 机制实测成立 ⇒ 取证面可复活）。**本文件 §6.1-6.5 的三种省略方案（完全删除 / 降频 / build-only 替代运行时层）均未被采纳**；6.2 的「保留 + 成本 fix」与 6.3 的 build-only 检查不属于本次裁定范围，仍留作独立议题。

### 7.1 实验补记（2026-10-23 晚，两轮真跑；证伪本节第二条缺口的前半）

**起因**：用户裁定链 B（证据改诚实）→ B1（先实测 `--expect-page` 再定 B）→ C1（§6.6）。目的只有一个：把「② 的取证面是一层还是两层」从推测变成读数。

**跑法纪律**：两轮都**不带 `-PostToIssue`** ⇒ 未贴任何评论；跑完工作树干净，`dist` 的 `app.json` 首项已还原 `pages/index/index`（`Switch-DistAppJsonFirstPage` 用毕还原，ADR-0038 决策 2）。探针走 `--expect-page`（ADR-0038 决策 1：首项换页 + plain 冷启动，**不调导航 API**）。

**Run1**（全量构建 ≈5min，exit 0）：`-Pages 'pages/login/login' -Auth off`
- `direct-page pages/login/login reached=True errors=0 exceptions=0 logs=0 shot=login.png elapsed=4s` ← **仓内第一条直达成功读数**（此前全 `docs/verification` 对 `--expect-page` 成功形态 grep = 0 命中）
- 同组 `pages/index/index` miss：落地 `pages/dashboard/dashboard`。成因 = IDE storage 残留已登录会话 + index 页「已登录无条件 reLaunch dashboard」业务不变量，而 `-Auth off` 恰好关掉 guest 盖帽 ⇒ **实验参数伪影，不是机制失败**（Run2 复验）。
- `direct-total pages=2 accepted=2 elapsed=119s`
- **缺陷一在此坐实**：结果行只声明一个 `navigation=` 字段，且 `scripts/mp-weixin-check.ps1`:1906-1911 的 `$missReason` 取**首个** miss；:1932-1935 遂把整组写成 `navigation=skip(reason=direct-page-unsupported)` ⇒ login 页那条 ok 只在 `Write-Log` 日志行里存活，对门与证据读者不可见。三种结果行形状（:626-650 的 pass/gateFailed/envBlocked）没有「部分成功」形态。

**Run2**（`-SkipBuild` ≈4.5min，exit 1）：`-Pages 'pages/login/login' -SkipBuild -Auth auto`
- index **过**：guest 盖帽 `MP_WEIXIN_AUTH {"ok":true,"status":"cleared",...}` ⇒ `direct-page pages/index/index reached=True shot=index.png elapsed=4s`。**证明 Run1 的 index miss 确系参数伪影**。
- login **落地判据过**（`pageStack=["pages/login/login"]`、`navigation.status=ok`）**但截图炸**：`error:"timeout waiting for automator response"`、`shots=[]`、断言 `currentPageScreenshot=false` ⇒ 门 exit 1。auth 注入本身成功（`status=injected ... http=200 biz=200`）。
- **缺陷二在此坐实**：`:1845-1856` 只按 `$isEntry` 分相——入口页给 guest、其余页**一律**注 auth。登录/注册类**游客页**作为非入口页被注进已登录会话，页面在截图窗口内自行跳转，automator 静默直至超时 ⇒ 「两相序」对游客页一族是一刀切错误。
- `direct-total pages=2 accepted=2 elapsed=273s`

**结论（三条）**
1. **`--expect-page` 机制可行**：两个不同页各拿到一次 `reached=True`，耗时 4s/页（direct 循环本身 119–273s，成本主要在构建与会话就绪）。「② 取证面只有一层」的判断作废。
2. **「取证面已死」是误判**：导航 API 那一路（(c) 的 reLaunch/navigateTo）确实恒败，但**冷启动直达这一路活着**——被缺陷一（成功读数被整组 skip 吞掉）与缺陷二（游客页被注会话）联手遮蔽。
3. **C1 成立**：取证面既然活着，「省略 ②」的收益就不该建立在「反正没取证」这个假前提上；保留门 + 修两个缺陷是正确处置（§6.6）。

**证据 provenance（诚实标注）**：本轮读数取自会话内两个后台作业输出（`pwsh-9f56334227af4f45` exit 0 / `pwsh-729665ea43604604` exit 1）；`.ci-verify` 的 ② 门日志随后续门跑被覆盖，**仓内无持久日志可复核**——故把读数写进本文与两张缺陷票正文，作为可引用的存档。复现命令即上两行参数组合（`-Auth off` 那轮需先清 IDE storage 会话，否则复现到的是参数伪影而非机制失败）。

### 7.2 修复落地与复测读数（2026-10-23 夜，两个缺陷均已合入 master）

§7.1 坐实的两处缺陷各自成票、各自带真跑证据合入（用户裁定 C1 的执行结果）：

| 缺陷 | 票 / PR | 改法 | 复测读数 |
| --- | --- | --- | --- |
| 一：一页 miss 吞掉整组成功读数 | #1816 / PR [#1830](https://github.com/DriftingLi/FL/pull/1830) | `navigation` 由单字段扩成四形态（`ok` / `partial(ok=<N>,skip=<M>)` / `skip(reason)` / `n/a`）+ `navigation.pages[]` 页级数组；形态声明进计划 `directPages.navigationShapes` | 修后同场景：`navigation=partial(ok=1,skip=1)` + `navigation=PARTIAL ok=1 skip=1 skippedSteps=pages/login/login`；同码另一次两页全达成 ⇒ `navigation=ok`、`shots=2` |
| 二：非入口游客页被注 auth 会话 | #1817 / PR [#1836](https://github.com/DriftingLi/FL/pull/1836) | 分相判据由「是否入口页」改为「入口页 ∪ 游客页族」，清单在计划 `directPages.guestPhase.routes` 声明；落地到别处时页级 reason 记 `landed-elsewhere(<落地页>)` | 修后两页都走 guest 相：`auth-inject(guest(login))` → `direct-page pages/login/login reached=True … elapsed=4s`，结果行 `navigation=ok`、`shots=2`、`direct-total pages=2 accepted=2 elapsed=109s`；截图入库 `docs/verification/mp-weixin/1817/{index-after,login-after}.jpg` |

**第三条缺陷（修的过程中才照出来，属读取层而非探针层）**：`Get-Prop` 用 `$Object.PSObject.Properties[Name]` 取值，而计划是真源、是 `[ordered]@{}` —— **`[ordered]` 的键不是 PSObject 属性**，故 `Get-Prop $guestPhase 'routes'` 静默回 `$null`，`$guestRoutes` 恒空，`$isGuestPage` 只剩入口页为真。首跑读数（提交 `a2044de4`）就是它的落点：index 走 guest、login 却拿到 `MP_WEIXIN_AUTH {"status":"injected"…}` 后 `reached=False`。

这条的教训比缺陷本身重要：**契约守护只扫源码文本时，「配置读不到」是全绿的**——计划里 `guestPhase.routes` 写得再清楚，29 条契约判据照样通过。故处置是「修读取层 + 把不变量写进守护」：`Get-Prop` 增 `IDictionary` 分支，C27 增断言 `$Object -is [System.Collections.IDictionary]` 并配变异反例（把该分支替换成 `$false` 必被检出）。

**环境教训（复测成本的真凶，非门设计问题）**：`cli quit` / `cli close` 在 **IDE 未运行**时会自启一个无项目实例占住 43005，随后 `devtools-open` 120s 超时 ⇒ 门判 `env-blocked`（`reason=automation-not-ready`、`sdk-version-missing`），看起来像「工具坏了」。可用开工前态：IDE 进程 0 个、端口 9420/43005 全空、`WeChatAppEx`/`Weixin` 容器进程 0 个、`hx-busy` 锁目录不存在；IDE 本体一律 `cli quit` 收（ADR-0008 红线：不得 `Stop-Process` 替代 `quit`），**容器残留**才可 `Stop-Process`。

**成本读数（供 §6 的成本议题用）**：`-SkipBuild` 一轮（会话就绪 + 两页直达 + 入库 + 评论文案）实测 ≈3 分钟，其中 `direct-total` 段 109–141s、单页直达 4s、会话就绪 8–12s、guest 盖帽 10–12s。全量构建那一轮 ≈5–6 分钟。⇒ ② 的墙钟大头是**构建与会话就绪**，不是探针本身；§6.2 的「build-only 检查」若成立仍有可观收益。

**现存缺口（诚实标注）**：本仓 `POST /repos/{owner}/{repo}/commits/{sha}/comments` 在 2026-10-23 晚连续返回 `404 Not Found`（对 HEAD、修复提交、master head、`-f body` 变体、带头探测均同；同 token 对空仓同端点返回 422 ⇒ 端点可达，非网络问题），而 #1770 定的「证据主键 = commit 评论」正依赖它 ⇒ 本轮 ② 证据实际落在**仓内产物** `docs/verification/mp-weixin/<票号>/*.jpg` + 票/PR 评论展示副本上。这是待独立复核的工具链问题，不影响 §7.1/§7.2 的机制结论。
