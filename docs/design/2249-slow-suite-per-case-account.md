## 0. 置顶结论

**结论行（供 A-1 引用）：假设② 部分成立、方向指错——「端口永不监听、付满 180 轮预算」这一形态在本机只占 22.9 s（不是主构成），真正的主构成是「成功路径上每一次 quit 都要等上一页那个分离监听器自然老死」，单次代价实测 64.0 s（60 s 生命期）与 124.9 s（120 s 生命期），而两个慢套件的逐用例耗时正好是这两个数的整数倍。**

支撑这个结论的四件事，按分量排：

1. **「付满预算」形态反而是最便宜的用例。** ResultLine 套件的五个用例里，四个都要真跑门；唯一「端口永不监听」形态（`环境受阻·端口直接 emit`）只花 **22 927 ms**，而三个「端口会监听」形态各花 **130 684 / 131 691 / 135 219 ms**。**差别不在轮询预算，而在端口会不会真的起来**——端口起不来时 `Wait-MpWeixinAutoPortReleased` 第一轮就读到 `count=0` 直接返回，一秒钟都不付。
2. **逐用例耗时是「单次 quit 代价 × 小整数」的乘法闭合，且乘数是可读出来的。** 单次 quit 代价由复刻探针实测：监听器活 60 s ⇒ `Wait-MpWeixinAutoPortReleased` 跑 **19 轮 / 63 969 ms**；活 120 s ⇒ **38 轮 / 124 892 ms**。于是：
   - ResultLine（60 s 生命期夹具）通过分支 135 219 ms ≈ **2 × 64 s**（128 s）+ 门自身 ~7 s；
   - ResultLine 探针前缀分支 130 684 ms、门未过分支 131 691 ms，同量级同解释；
   - AuthSkip（120 s 生命期夹具）注入成功 377 842 ms ≈ **3 × 125 s**（375 s）+ ~3 s；
   - AuthSkip 注入失败 253 578 ms ≈ **2 × 125 s**（250 s）+ ~3.5 s。
   四个用例、两套生命期、两个不同的乘数，全部落在 1–2 % 内——**这不是巧合能解释的**。
3. **门自己打的分阶段秒数把「钱花在哪儿」钉死在 `auto-probe` 段，且每页 ≈123.5 s。** AuthSkip 注入成功那一轮的 `.ci-verify/mp-weixin.log`：`automation start→end 20:44:00→20:44:13`（13 s）、`auto-probe start→end 20:44:13→20:48:20`（**247 s**）、`STAGE_SUMMARY stages=2 total=260s`、`direct-total pages=2 accepted=2 elapsed=247s`。**247 / 2 页 = 123.5 s/页**。而同一行的 `MP_WEIXIN_RESULT … ready=0s`、每个就绪闸门自报 `elapsedMs:300` ⇒ **这 123.5 s 一分钟都不在就绪判定上**，全在 `direct-coldstart` 的 quit / open / auto 三段。
4. **单次查询本身就贵到能把「轮」变成「天」。** `Get-NetTCPConnection -State Listen -LocalPort <p>` 本机 n=5（含新起 pwsh）：**4411 / 4815 / 4124 / 4299 / 4183 ms**；同进程连查 10 次：**3671 / 2195 / 2733 / 2326 / 2200 / 2021 / 2059 / 1549 / 1555 / 1573 ms**（`total=21902 ms`）。⇒ 稳定态 ≈1.55–2.2 s/次。**任何「循环 N 轮」的预算，实际成本都是 N × 1.5–2.5 s，不是 N 秒。** 这是假设②里**唯一成立**的部分。

**一句话给 A-1**：迭代次数预算确实要换成墙钟预算（§0 第 4 条成立），但**它不是主因**——主因是「等分离监听器老死」这一段本身就按生命期收费，A-1 换计量语义**不会**把这两个套件从 631 s 降到 300 s 以内；要真的降，得让 quit 之后**立刻**确认端口已释放，而不是等生命期。

## 3. 机理复刻：单次 quit 到底要付多少（n=1，逐轮全留）

真跑里不能插桩（会改被测物），所以把门里那段循环**逐字复刻**到仓外探针。逐字原文（`scripts/mp-weixin-check.ps1:1353-1362`）：

```powershell
function Wait-MpWeixinAutoPortReleased {
    param([int]$Port = 0, [int]$BudgetSeconds = 60)
    $held = 0
    while ($held -lt $BudgetSeconds) {
        if (@(Get-NetTCPConnection -State Listen -LocalPort $Port -ErrorAction SilentlyContinue).Count -eq 0) { return $true }
        Start-Sleep -Seconds 1
        $held++
    }
    return $false
}
```

## 4. 落到的形态：假设②的判词与 #2235 收益账的重算

票面把两个分支写成了「成立 ⇒ A-1 降 50%+」「不成立 ⇒ 重算收益账」。本次落在**后者**，但要分三块说清：

| 子命题 | 判词 | 依据 |
|---|---|---|
| 「端口轮询以迭代次数为预算，实际成本 = 轮数 × 单次查询，远超声称秒数」 | **成立** | §0 第 4 条：单次 1.5–2.5 s；60 轮 ⇒ 64.0 s / 124.9 s（§3） |
| 「慢套件的主构成 = 端口永不监听、付满整笔预算」 | **不成立** | 该形态用例只花 22.9 s（§2.1 第 4 行），是最便宜的一个 |
| 「慢套件的主构成 = 成功路径上每次 quit 等分离监听器老死」 | **成立**（本笔记的替代假设） | 四个用例 × 两套生命期的乘法闭合（§0 第 2 条）+ 门自身 `[STAGE]` 分账（§0 第 3 条）+ 三个对照套件的反向证据（§2.3） |

**#2235 的收益账要这么重算（三条具体改动）**：

1. **A-1 的验收判据要从「慢套件 secs 降 ≥50%」改成「单次 quit 的墙钟不再随监听器生命期线性增长」。** 现在的 ≥50% 判据相对 ADR-0042 基线（483~496 s）写死；本机实测已是 421 s（本来就已经「降」了 13%），若把 A-1 落地后的目标定在 ≤250 s，**依据必须换成「3 × 125 s ⇒ 3 × ? s」**，不能沿用票面的百分比。建议改成：`InjectSkip` 套件 ≤ 400 s、`ResultLine` 套件 ≤ 250 s（即「每次 quit 从 125 s 压到 40 s 以下」）。
2. **A-1 单独落地降不到票面承诺。** 换计量语义（Stopwatch 对预算）只让**每轮**从「1 s sleep + 1.5–2.5 s 查询」变成「至少 1 s」——但 §3 说明这段循环**根本没跑满轮数**（19/38 轮就早退），所以「轮数 × 单次查询」这个乘数在成功路径上不是主项；主项是**监听器自己的生命期**。**A-1 能吃掉的是失败路径与 v6-only 这类边角，吃不掉主项。** 若要让主项也降，必须另立一件事：quit 之后**主动探测**（`TcpClient` 试连，见 #2250 的混判据）来提前判定「这个端口已经没人了」，而不是死等 Listen 表变空。
3. **票面的「预算注入封存」触发值要改口径。** 现写「单 mpWeixin 套件仍 >5 min」。本机 `ResultLine` 421 s = 7.0 min、`AuthSkip` 631.5 s = 10.5 min，**两个都已经超了**——但票面把它当成「A-1 之后仍 >5 min 才触发」的兜底。按实测，这两个套件在**任何**A-1 落地前就已经越过这条线，封存条件应当**立即生效**而不是等待触发。

**一句话给下游**：把 A-1 的立项理由从「付满预算」改成「预算语义不可测」，把「≥50% 降幅」改成「单次 quit ≤40 s」，并**另开一件**治理「quit 后死等监听器生命期」——否则三条目标线（尤其含 mpWeixin 子集 ≤12 min）在 A-1 落地后仍然守不住。

## 5. 测不到 / 未证实

1. **每次真是「几次 quit-poll」没有插桩计数。** §0 第 2 条的乘数 2 与 3 来自读代码路径（`Invoke-DevToolsQuitAndPoll` 在 pre-flight 与每次冷启动处各调一次）与页数，不是运行时计数。要钉死需要在门里加计数输出——那会改结果行字段集，违反 A-1 的「字段集零改动」硬约束，所以本笔记只做算术闭合，不做插桩证明。
2. **`--verbose` 的单用例耗时含 jest 边界开销**。用 135 219 / 64 000 反推的乘数不可能是整数，多出来的 5–8 s 归给门自身开销（门打 `automation 13 s` 之类）——**没有逐段拆开**。
3. **真实微信开发者工具的 quit 行为没测到。** 夹具里的监听器是「`auto` 动词派生、`quit` 后靠自灭」的桩；真实 IDE 的 `cli quit` 是否真的会带走自动化服务的监听端口、多久带走，本笔记没有数据（#1695 记录过「假 CLI 的 quit 不会真退真实 IDE」这一环境耦合）。
4. **1056 s / 952.9 s 的原始出处仍不明。** 票面数字与仓内任何文档、任何套件名都对不上；本笔记推断它是「用阻塞式探针测出的假象」或「按 180 秒预算外推」，**这是推断，未证实**。
5. **单路基线只保证了「没有其他子代理」，不保证「没有其他进程」。** 本机常驻 workbuddy / Ollama / 微信开发者工具各一，读数抖动见 §3.1 的 queryMs 区间（1.5–3.2 s）。
