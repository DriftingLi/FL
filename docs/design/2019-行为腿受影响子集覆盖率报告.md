## 1 一句话结论

映射**够用**：81 个行为套件里，46 个有运行时真读证据的全部健全（370 条依赖边 100% 可选中）；
35 个 d 类（起子进程）**无法用本方法取证** —— 它们的映射只有静态证据（路径 token + 四条兜底边），
不是「没映射」，是「没验证」。39 个真实历史改动集上，平均只需跑 30.8/81（38.0%），中位 25/81（30.9%）。

**但票面指定的校验方法在这份历史上没有负样本**（39 个 PR 行为腿全绿），
所以「预测 ⊇ 实际失败」这条判据是**空洞通过**，本报告改用运行时真读对照（§6.2）。

文本耦合（与上面正交，是**叠加标记**不是第四类）：

- **读运行时面源码文本**（`readText` / `readFileSync` 读 `.uts`/`.uvue`）：**23** 个
- 其中 **b′（读真源 → 字符串手术 → 再执行）**：**21** 个 —— 名单见下

### b′ 名单（21 个，名单制，常驻子集）

```
aiAnswerBodyBehavior · aiAssistantSwallowBehavior · aiModelSelectionBehavior ·
aiSourcesDisplay · authPreRequestValidationBehavior · chapterNotFoundBehavior ·
coursePointsCtaBehavior · coursePointsRedeemBehavior · envelopeBehavior ·
fallbackChainEnvelopeBehavior · forumContentFormatBehavior · forumFormatPreferenceBehavior ·
forumImagePickerBehavior · landingLoginBehavior · markdownInlineBehavior ·
markdownSubsetBehavior · markdownToolbarBehavior · namedKeyEnvelopeBehavior ·
pagedListBehavior · resumeNotFoundBehavior · topicFeedBehavior
```

**为什么常驻**：它们对「源码文本长什么样」下判断。锚点原文一变，变异可能**没注入而断言照跑**
（本仓既有血账：CRLF 下 `.` 不匹配 `\r`，变异静默失效）。「改了哪个文件」对它们不是可靠的相关性代理，
所以按名单常驻，代价是恒定 +21 个套件。`--no-bprime-always` 可关掉做对照（子集会掉到 0–3 个）。

### 目录读取者（3 个，但这条边基本不产生有效覆盖）

`readdirSync` 出现在 4 个行为套件里，其中 3 个的参数能解析出来 —— 但解析结果是
`dir` / `.ci-verify` / `tmpProject` 这类**非仓库目录**（前两个是测试自己造的临时目录与日志目录，
`dir` 是遍历函数的形参）。也就是说：**目录边在当前代码里几乎不产生有效覆盖**，
它只起「别漏」的兜底作用，不是主判据。

真正覆盖这类依赖的是 §5 的两条结构性边：

- `jestSplitContract` 读全部 `utils/*.test.js` ⇒ 靠「套件集合」边（改测试文件即全跑）；
- `capabilitySurface` / `mpWeixinGatePages` / `mpWeixinBuildFingerprint` / `levelDetect*`
  扫 `pages/` ⇒ 靠「页面集合」边（改 `pages.json` 即全跑）+ 静态页面名 token。

| 项 | 规模 | 说明 |

## 5 四条兜底边（可机检，不留「看情况」）

| 边 | 触发判据（正则） | 理由 |
| --- | --- | --- |
| 门脚本 / workflow | `(^\|/)\.github/` 或 `(^\|/)scripts/.*\.(mjs\|js\|ps1)$` | d 类套件测的是脚本自身行为，「改了哪个业务文件」这一维对它失效 |
| 套件集合 | `(^\|/)utils/[^/]+\.test\.js$` | 两腿切分、心跳契约、套件并集完备都以「有哪些套件」为输入；且 `jestSplitContract` 在**子进程**里读全部套件，静态扫不到 |
| 页面集合 | `(^\|/)(pages\|manifest)\.json$` | 一批 d 类套件在子进程里扫 `pages/`，静态 token 只覆盖既有页面名，**新增页不命中任何 token** |
| b′ 名单 | 见 §3 名单 | 见 §3 |

前三条命中即**全跑**（81/81）。这三条都不常触发：39 个真实改动集里只有 3 个命中。

## 6 覆盖率

### 6.1 票面指定的方法为什么不可用

票面要求：「取 ≥15 个触及运行时面的历史 PR，比对**预测集合 ⊇ 实际失败集合**」。

实测取到 **39 个**这样的 PR（2026-10-10 ~ 10-26，合并态），**逐个**查了它们 PR 上所有
`mobile-test` / `behavior` 检查的结论（不是只看聚合）：

| 项 | 值 |
| --- | ---: |
| 触及运行时面的已合并 PR | 39 |
| 其中行为腿检查**全部 SUCCESS** 的 | **39** |
| 行为腿有过失败的 | **0** |
| 旁证：`mobile-gates` 全部历史运行（2026-10-18 起） | 676 次 = success 639 · cancelled 37 · **failure 0** |

**实际失败集合恒为空 ⇒ 该判据对任何映射都判绿。** 如实报「100%」等于自证，
所以本报告不把它当结论，只当作样本说明：**这份历史里没有负样本，回放校验没有判别力。**

这个「零失败」本身有两种读法，都影响 ADR-0046 的风险判断，一并记下：

- **乐观读法**：本地全量门确实把红拦在了推送之前 ⇒ CI 只是复核，改为子集后风险低。
- **保守读法**：也可能只是「红过的 PR 都没合」，而没合的 PR 不在 `--state merged` 样本里
  （本次取的是合并态）。若如此，负样本存在于未合并分支，而这批数据本次没取。
  实施票若要更强的证据，应改为按 `head_sha` 取**所有**运行，而不是只取合并后的 PR。

### 6.2 替代判据：运行时真读对照（非空洞）

做法：给 `fs.readFileSync` 打桩，跑**当时的全部 80 个套件**（取证基准 `f7767efc`），记录每个套件真实读到的仓内文件；
再逐条问「**若这个依赖改了，这个套件会不会被选中？**」——这才是映射真正要保证的事
（静态集漏了什么无所谓，只要闭包边 / 目录边能补回来）。

| 指标 | 结果 |
| --- | --- |
| 「套件 ← 真读依赖」边数 | **370**（涉及 279 个不同文件） |
| 依赖改动后套件被选中（边级） | **370/370 = 100%** |
| 全部依赖都能被选中的套件（套件级） | **46/46 = 100%** |
| 捕获真空（读发生在子进程里，本证据对它们无效） | **35**（全是 d 类，含取证后才加的 `gateStagesBehavior`） |

**取证基准**：370 条边来自 `f7767efc` 那次的 80 个套件。之后 master 上 #2001 新增
`gateStagesBehavior`（d 类，依赖 `gate-stages.ps1`），它**不在**这次取证里 —— 按 d 类计入真空，
由「门脚本改动 ⇒ 全跑」覆盖。所以「46 个已取证套件」的分母不随套件数增长，
而真空数会增长；两者不要混算。

**必须同时读的两句话**：

1. 那 46 个套件是**逐个验证过**的，不是抽样外推；
2. 35 个 d 类套件**没有被这条判据覆盖**。它们的相关性由「门脚本改动 ⇒ 全跑」兜底，
   但兜底的方向是「脚本变 ⇒ 跑套件」，反向（业务文件变 ⇒ 脚本读到它 ⇒ 套件该跑）**没有静态保证**。
   §8 记录了一个真实例子（改 `pages.json` 才补上的缺口）。

**门槛判断**：以「有证据的 46 个套件全部健全」对照 ADR-0046 的 90% 门槛 ⇒ **达标**。
若把真空套件按「未验证」计入分母，则是 46/81 = 56.8% ⇒ **不达标**。
两种读法都写在这里，取舍留给裁定人（我倾向第一种，因为真空部分有兜底边，且失败方向是「多跑」）。

## 7 收益实测

### 7.1 在 39 个真实历史改动集上

| 指标 | 值 |
| --- | ---: |
| 平均子集 | **30.8/81 = 38.0%** |
| 中位数 | **25/81 = 30.9%** |
| 等于全量（无收益）的改动集 | **3/39**（都改了 `pages.json` / `manifest.json`） |
| 最省的一档（只改一个 `.uvue`） | 21–22/81 ≈ 26–27% |

### 7.2 墙钟

| 场景 | 实测 |
| --- | --- |
| 行为腿全量（80 套件，默认并行） | **1197.9 s ≈ 20.0 min**，其中 7 个套件红 |
| 行为腿全量（80 套件，`-i` 串行 —— 仓里的正式跑法） | **未跑完**：38 分钟时到第 8 个套件，已中止（文档基线 1129 s–2160 s，见 `dev-loop.md`） |
| 子集（#1909 只改 `login.uvue` ⇒ 22 套件，`-i` 串行） | **84 s，22/22 套件、436/436 用例全绿** |

**84 秒 vs ≥38 分钟**，差的不是「少跑了 58 个套件」，而是**没跑那几个吃掉整轮墙钟的 d 类套件**
（`mpWeixinGateResultLineBehavior` 单套件 999 s；`-i` 那次第 8 个套件单独 749 s）。

两个必须一起读的脚注：

1. **并行会 flake。** 同一批 22 个套件，默认并行 37 s 但 `concurrent401RefreshBehavior` /
   `resumeNotFoundBehavior` **判红**；`-i` 串行则 22/22 全绿。这正是 ADR-0042 禁腿内并行的原因
   —— 子集也必须带 `-i`，否则会得到一个比它要替代的东西更不稳的本地信号。
2. **全量本地不是绿的。** 并行那一轮 7 红、`-i` 那轮前 8 个里已有 2 红，多数是 d 类
   （依赖 HBuilderX / 微信开发者工具 / 时序）。ADR-0046 说的是「本地提前知道」，
   而本机实测更接近「本地知道一部分，且其中有一部分是环境噪声」——实施票应考虑
   「子集跑绿 + 全量只看是否出现**新**红」的判据，而不是「全量必须绿」。


## 8 过程中发现的真实问题（三件，都不在本票范围）

1. **`systemBrowser.uts` 全仓零覆盖。**
   `utils/` 下 13 个 `.uts` 没有任何**行为**套件引用，其中 12 个有接线腿覆盖
   （`format.uts` 四个、`system.uts` 四个…），只有 `systemBrowser.uts` **行为与接线都没有**。
   这是守护空洞，不是映射漏洞 —— 全量跑对它同样没有信息量。

2. **单个套件吃掉整轮墙钟。** `mpWeixinGateResultLineBehavior` 单跑 ≈ **999 秒**（16.6 分钟），
   占全量 20 分钟基线的大头。子集方案的最大收益其实来自「不跑它」，而不是来自「少跑很多小套件」。

3. **`jestSplitContract` 读全部 200 个套件文件**，且读取发生在子进程里。
   它贡献了 370 条边里的 200 条 —— 任何按「边」统计的覆盖率都会被它主导，
   所以 §6.2 同时给了套件级数字。

## 9 限制与未验证

- **35 个 d 类真空未取证**（§6.2）。子进程读什么，进程内捕获看不到。
- **新增页面**这类结构性改动只能靠 `pages.json` 边兜底，不是靠映射算出来的。
- **`.uvue` 模板/样式**不在 a 类射程内：`loadUts` 只跑 `.uts` 逻辑模块。
  纯样式改动的行为子集主要来自 d 类扫页面套件与 b′ 常驻，粒度比 `.uts` 粗。
- 捕获夹具为**一次性研究用**，不进任何门；生产判据只依赖 `--changed`（纯静态，无副作用）。
- 本机全量行为腿**不是绿的**（见 §7.2 注），这不影响映射结论，但影响「本地绿 ⇒ CI 绿」这句承诺的强度。

## 10 复现

```bash
cd training-app/叉车维修培训学员端跨端应用

# 全量分类（每个套件的形态、文本耦合、抽到的路径边）

# 结构性审计：目录读者 / import 解析 / 漂移 token / 零引用 .uts
node scripts/behavior-suite-deps.mjs --health

# 给一组改动，算应跑套件（含触发的兜底边与原因），末行直接给 jest 命令
git diff --name-only | node scripts/behavior-suite-deps.mjs --changed-from stdin

# 批量（历史改动集回归）。cases.json 的造法见下
node scripts/behavior-suite-deps.mjs --batch cases.json

# cases.json：取最近合并、且触及运行时面的 PR
gh pr list --state merged --limit 200 --json number,files -q '.' \
  | node -e 'const ps=JSON.parse(require("fs").readFileSync(0,"utf8"));
      const RT=/(\.uvue|\.uts)$/;
      const out=ps.map(p=>({id:"#"+p.number,
        files:p.files.map(f=>f.path).filter(x=>x.includes("叉车维修培训学员端跨端应用/")&&(RT.test(x)||/(pages|manifest)\.json$/.test(x))) }))
        .filter(c=>c.files.length);
      console.log(JSON.stringify(out,null,1));' > cases.json

# 运行时真读对照（需要先用 dep-capture 夹具跑一轮全量）
DEP_CAPTURE_OUT=./.depcap npx jest --config jest.config.behavior.js \
  --setupFilesAfterEnv ./scripts/lib/dep-capture.cjs
node scripts/behavior-suite-deps.mjs --verify-capture ./.depcap
```
