## 二、响应式现状（复测）

首版票面的「24 个 / 6 条 media query」是测错的：检索式 `@media \(max-width` 漏掉了 `@media screen and (max-width: …)`。复测：

| 手段 | 数量 | 文件 |
| --- | --- | --- |
| CSS `@media` | **26 条** | 21 个 `.vue`（+1 条在 `valuation-tokens.css`） |
| JS `matchMedia` | 1 处 | `ChatPageShell` |
| Tailwind 断点工具类 | 41 处 | 18 个文件（`sm:` / `md:`，无 `lg:` / `xl:`） |
| **并集** | — | **39 / 172 个组件（22.7%）** |

断点分布：`768px` ×16、`480px` ×4、`767px` ×3、`560px` ×1、`900px` ×1、`1024px` ×1。

## 三、静态布局约束

| 指标 | 实测 | 含义 |
| --- | --- | --- |
| `min-width` 声明 | 20 处（多数 `min-width: 0`） | flex 收缩修正，不是布局约束 |
| 固定像素宽 | 73 处（含 `max-width` 命中，需按类名复核） | 固定宽度写在页面里 |
| `grid-template-columns: repeat(N)` | 5 处（2 列 ×3、4 列 ×2） | **没有成体系的栅格** |
| `overflow-x: auto/scroll` | 5 处 / 5 文件 | **没有成体系的横滚兜底** |
| `el-table` | 197 处 | 宽表在窄屏无统一塌陷口径 |

结论：现状不是"响应式做得差"，而是**没有响应式体系**——断点集中在 768、手段两套并存、宽表靠 Element Plus 自身行为。

## 四、渲染面量测（阶段 1a，进行中）

### 环境（2026-10-26 起）

- 依赖：`docker compose up -d postgres redis`（`forklift-pg` / `forklift-redis`）；
- 后端：`PORT=18080 go run ./cmd/server`，健康检查 `/api/health` 返回 ok；
- 前端：`npm run dev`（:5173），vite 代理 `/api` → `127.0.0.1:18080`；
- 量测：Edge headless + CDP（`Page.navigate` + `Emulation.setDeviceMetricsOverride`），读 `documentElement.scrollWidth` 与「右边缘越界的最宽元素」。

### 账号

| 角色 | 账号 | 说明 |
| --- | --- | --- |
| 管理员 | `admin` / `admin123` | 走 **`/api/auth/admin-login`**；默认创建时 **role_id 为空**（无能力集，首屏落到 `/admin/no-access`），已补 `admin.role_id = 1`（超级管理员）；`admin_role_capability` 当前 0 行，说明超管能力不依赖该表 |
| 学员 | `student` / `student123` | 走 **`/api/auth/login`**；需绑定证件：已设 `hrwai_users.current_credential_id = 1`，否则落到 `/training/onboarding/credential` |
| 讲师 | `tutor` / `tutor123` | 走 **`/api/auth/tutor-login`** —— 用 `/api/auth/login` 会得到「账号或密码错误」（**端点不对，不是账号不对**；2026-10-26 踩过一次）。UI 上 `mentor.localhost/login` 默认就是讲师档，直接登录即可 |
| 招聘者 | — | 走 **`/api/auth/recruiter-login`**；**无默认账号**（`EnsureDefaultUsers` 只建 admin / tutor / student），需由超管 `POST /api/admin/recruiters` 创建 |

### 首轮结果（`/login`、`/admin/dashboard`、`/admin/profile-review`、`/training/tutor` × 1440 / 1280 / 1024 / 900 / 768 / 560 / 375）

- **页面级横向溢出：0 例**。所有被测路由在 375px 下 `scrollWidth` 均 ≤ 视口宽 + 1。
- 375px 下管理端看板**实测可用**：侧栏收成图标条、统计卡 2×2 堆叠、内容单列（见 `docs/verification/web/1937/admin-dashboard-375.png`）。
- 窄屏退化来自 `SidebarLayout` 的 `@media (max-width: 768px)`（侧栏折叠）与卡片栅格的自适应，**不是**页面级断点。

### 由此修正一个判断

第三节写的「没有响应式体系」**说过头了**：外壳（侧栏 / 顶栏）与部分页面确实有窄屏退化，只是**覆盖面窄、且不统一** —— 26 条 `@media` 里 16 条是 768、其余是零散单页补丁；表格类页面的窄屏行为（列被裁 / 内部横滚）没有统一口径。审计要回答的是「哪些页面必须适配、适配到什么程度」，而不是「有没有适配」。

### 第二轮（9 路由 × 5 宽度，含表格密集页与 recruit 族）

账号补齐：**招聘者由超管创建**（`POST /admin/recruiters`）→ `recruiter/recruiter123`，recruit 族可测。

量测口径加了三项：表格内部滚动（`.el-scrollbar__wrap--h` 的 `scrollWidth / clientWidth`）、内容被裁元素数（`overflow-x: hidden` 且内容溢出）、页面级溢出。

**结果**：

| 族 | 被测路由 | 页面级溢出 | 375 下表现 |
| --- | --- | --- | --- |
| auth | `/login` | 无 | 正常单列 |
| training | `/training`、`/courses`、`/favorites` | 无 | 卡片堆叠 |
| tutor | `/training/tutor` | 无 | 卡片堆叠 |
| recruit | `/recruit`、`/recruit/resumes` | 无 | 卡片堆叠（无表格） |
| manage | `/admin/hrwai-users`、`/profile-review`、`/statistics` | 无 | **表格内部横滚**：表体 `scrollWidth/clientWidth` = **1230/319（3.9×）**、810/301、660/271 |

**关键发现：页面不溢出，是表体自己在滚。** `el-table` 的 `.el-scrollbar__wrap--h` 在 ≤1024 就出现横向滚动（1440 时 `/profile-review` 与 `/statistics` 尚不滚），且表格右侧固定「操作」列在 375 下压住内容（见 `docs/verification/web/1937/admin-hrwai-users-375.png`：只剩 ID / UID / 操作 三列可见，UID 折行）。

**结论（供 1c 裁定用）**：五个族的「最小可用宽度」都是 **375px 不崩**，但**表格族的可用性在 375 下依赖横滚**，而「横滚还是降列」正是 1c 要拍的那条。

## 五、断点 × 折叠动作表（1b）

只收现有实现，不发明断点。

| 断点 / 条件 | 触发点 | 动作 | 覆盖面 |
| --- | --- | --- | --- |
| `≤768px` | `SidebarLayout` 的 `@media` | 侧栏收成图标条、顶栏紧凑 | 全部走该外壳的页面（学员 / 讲师 / 管理 / 招聘） |
| `≤768px` | 15 条零散 `@media`（各页各写） | 局部微调：内边距、字号、隐藏次要信息 | 21 个文件，互不统一 |
| 任意宽度 | `el-table` 内部 `.el-scrollbar__wrap--h` | 表体横向滚动；右侧固定列常驻 | 197 处表格 |
| `≤480px` | `html` 的 rem 基准（ADR-0080 决策 4） | 字号基准 16 → 14 → 13，**结构不变** | 全站 |
| 无断点 | 卡片栅格（flex/grid wrap） | 自动换行 / 堆叠 | 学员端与看板类页面 |

读法：**唯一成体系的是外壳折叠与表体横滚**；其余是各页补丁与"栅格自然换行"。字号那条是全局缩放，不构成布局折叠。

## 八、补测（深色 / 饱满态 / 打印）

### 深色主题

6 条路由 × 3 个宽度（1440 / 768 / 375）= **18 个组合**，`documentElement.dataset.theme === 'dark'` 均生效，页面级溢出 **0 例**。表格行为与浅色一致（同为 3.9× 表体横滚）。

### 饱满态

用超管 API 种了 25 个学员（`POST /admin/hrwai-users`），列表默认 10 行/页。`/admin/hrwai-users` 有 **10 列**：

| 宽度 | 表体内容宽 / 容器宽 | 备注 |
| --- | --- | --- |
| 1440 | 1230 / 1106 | 已开始横滚 |
| 1024 | 1230 / 690 | |
| 768 | 1230 / 706 | |
| 375 | **1230 / 313（3.9×）** | 表头同步横滚；单元格文本被裁（`cell el-tooltip` 的 171/194 vs 158/138） |

结论：**列定义决定内容宽，行数只增高** —— 饱满态不改变 3.9× 的倍率，但放大了"内容被裁、要看 tooltip"的可感知度。

> 口径更正：表体横滚容器不是 `.el-table__body-wrapper`（它的 `scrollWidth == clientWidth`，会被误读成"不滚"），而是 `.el-scrollbar__wrap`（类名随状态变化，空表时是 `--h`、满表时是 `--hidden-default`）。下次量表格必须扫这个节点。

### 打印

`Emulation.setEmulatedMedia({ media: 'print' })` 下，`/admin/dashboard` 与 `/admin/hrwai-users` 的顶栏 `display: grid`、侧栏 `display: flex` —— **外壳照印**，与 Known Gaps 里「全库 `@media print` 0 条」一致。

### 对三份裁定的影响

均**不改变方向**：0084/0086 的倍率不变（列宽由列定义决定），0085 的学员端深色无异常。三份 ADR 的「证据边界」可以据此更新为「已补测深色与饱满态」。
