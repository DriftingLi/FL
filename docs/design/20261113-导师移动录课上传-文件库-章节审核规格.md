# 第一部分 · 规格

## Problem Statement

导师今天录不了一节课。录课视频是数百 MB 到 GB 级的长任务，而现有上传是单发 multipart、视频上限 200MB——移动网络一断就全废；移动端根本没有导师面，Web 导师端也不适合扛着手机录课。

导师也管不了自己的文件。上传的文件挂死在某个章节上（`chapter_file` 归属），没有「我的文件」这个面：录完的视频必须当场绑定章节，传错章节就得删了重来，想先录后挂做不到。

更要命的是章节没有任何审核门。讲师改章节正文或换章节文件**改完即对学员生效**——写错一个参数、传错一个附件，学员直接学到错的。本仓题库、投稿、资料三台审核状态机各管各的，唯独面向学员教学主线的章节内容是裸奔的。

## Solution

三块，一次定清：

1. **分片断点续传上传契约（载体无关）**：init 会话 → 分片 PUT → complete 拼装，断点可续、会话可 abort；单文件上限提到 2GB，专为录课长视频设计。契约不依赖任何移动端载体决策，Web 导师端与未来移动端走同一套。
2. **导师个人文件库**：上传先落导师自己的文件库（预览/改名/删除都在库上做），挂接到章节才随章送审——「先录后挂」成为常态路径；配额双臂防膨胀，删除随引用走绝不产生教学内容悬空。
3. **章节内容/文件先审后发审核机制**：照题库三态机同构（草稿 → 待审 → 已发布），整章一个审核单元、提交即冻结快照；已过审内容旧版保留、过审原子切换；管理员即审核者；存量一次性豁免。

## User Stories

1. 作为导师，我希望在手机上录完课就能开始上传，以便不被大文件单发失败逼回电脑前。
2. 作为导师，我希望上传到一半断网后能接着传，以便不重头再来。
3. 作为导师，我希望录完的视频先落在我的文件库里，以便录的时候不必先想好挂哪一章。
4. 作为导师，我希望在库里看到我传过的所有文件并预览/改名/删除，以便管理我的教学资产。
5. 作为导师，我希望把库里的文件挂到某个章节上，以便组织课程结构。
6. 作为导师，我希望保存章节改动不立即对学员可见，以便写到满意再提交审核。
7. 作为导师，我希望被驳回时看到驳回理由，以便知道改什么。
8. 作为导师，我希望提交审核后还能继续改草稿准备下一版，以便不被审核卡住编辑。
9. 作为学员，我希望只看到已过审的章节内容，以便学到的都是把过关的。
10. 作为学员，我希望导师修改已过审章节期间旧版照常可读，以便我的学习流不被编辑动作打断。
11. 作为管理员，我希望在审核队列里看到待审章节的冻结快照并批量过审/驳回，以便高效把关。
12. 作为管理员，我希望自己改章节直接生效，以便不被自己审自己空转。

## Implementation Decisions

### 块 A · 分片断点续传上传契约（载体无关）

- **A1 三段契约**：`init`（创建上传会话，登记归属导师与预期大小/类型）→ 分片 `PUT`（按序号上传分片）→ `complete`（服务端拼装落存储、产出文件实体）。另设显式 `abort`（放弃并清理半成品）。
- **A2 分片参数**：单片 5–8 MiB（R2/S3 最小片 5 MiB 为下限；上限由服务端读超时窗口决定，见附录 2）；除末片外各片等大，末片无下限；分片总数 ≤10,000。2GB 单文件 ≈400 片，远低于上限。
- **A3 会话生命周期**：未完成会话 7 天自动 abort（对象存储 lifecycle 语义）；客户端可随时显式 abort。
- **A4 业务上限与类型**：单文件 ≤**2GB**；格式白名单沿既有类型表四档全收（video / document / ppt / image），类型表仍是唯一事实源。
- **A5 落库**：complete 成功即产出**文件库行**（块 B），键命名沿既有 `<name>_<毫秒时间戳>.<ext>` 契约。
- **A6 共存不迁移**：既有 10 个单发 multipart 端点原样保留，不迁移到分片契约；录课大视频与文件库走分片，小文件（头像、插图等）继续单发。
- **A7 移动端接口位（载体无关）**：移动端录制产生的文件一律走本契约上传；录制侧约束（编码、单段时长、分段录制策略）随 [导师移动端载体选型 #2490](https://github.com/DriftingLi/FL/issues/2490) 在移动端独立 ADR 体系定，本规格不预设。
- **A8 断点续传语义**：客户端持久化「会话 id + 已完成分片清单」；中断/重启后凭会话 id 续传缺失分片；服务端以会话状态为准，重复分片幂等覆盖。

### 块 B · 导师个人文件库

- **B1 实体**：导师文件行，脱离章节文件表独立存在，归属单一导师；命名沿既有文件命名契约（A5）。
- **B2 单挂挂接**：文件行带章节归属字段，空＝在库未挂；挂接到章节后随该章节送审（块 C 的文件挂接清单即引用它）；**取消挂接回库**（回到未挂状态）。不做多挂引用计数（罕见场景 YAGNI，真需要时加性放开）。
- **B3 配额双臂**：每导师 **≤300 个文件、≤100GB 总量**，单文件 ≤2GB；任一臂超限即拒绝新上传并明示当前用量。数字为软值，可在实施时按运营数据调整。
- **B4 生命周期**：库内有行文件**永不静默 TTL 回收**（配额是显式可见约束，导师可自行清理）；仅「上传完成但未落库行」的真孤儿沿既有 orphan_sweep 机制 24 小时回收。
- **B5 删除随引用走**：被章节引用的文件（含在审快照引用、已发布槽引用）库侧**不可删除、不可替换**；被换挂/解挂后回库变未挂方可删。绝不产生章节侧悬空引用。
- **B6 替换在章节侧**：「换文件」是章节侧的换挂动作（挂新文件、旧文件回库），不是库侧的替换动作。
- **B7 管理面（Web 导师端 + 移动端同语义）**：文件列表（按类型/时间/挂接状态筛选）、预览（沿既有三查看器预览链路）、改名、删除、挂接/解挂。
- **B8 移动端接口位**：录制上传完成后文件以「未挂」状态入库，导师稍后在文件库或章节编辑面挂接。

### 块 C · 章节内容/文件先审后发审核机制

- **C1 状态机**：**三态 `draft / pending / published` + `reject_reason` 字段**，驳回＝回 `draft` 并记录驳回理由（无独立 rejected 态）；状态机独立命名，不与题库/投稿/资料三台状态机混称（「审核」是过载词）。枚举值沿小写字符串代码先例，新建章节默认 `draft`。
- **C2 编辑流程**：保存只落草稿（仅编辑面可见），**显式「提交审核」动作**才进队列（题库提交动作同构）；被驳回的草稿改完再提。
- **C3 审核单元**：**整章一个审核单元**——章节正文 + 章节文件挂接清单一起提交、一起过审，学员永远只见一致版本。
- **C4 冻结快照**：提交审核即冻结一份「在审版本」（正文 + 文件挂接清单快照）；审核期间讲师改的是**下一版草稿**、不影响在审内容（消除「审的和过的不是同一份」）；过审 → 冻结快照**原子切换**到已发布槽；驳回 → 弃快照。版本语义三份：working 草稿 / 在审快照 / 已发布槽；确切表结构（快照表 vs 槽列组合）由实施按读路径代价定，语义不得偏离。
- **C5 旧版保留**：已过审章节被改动触发重审期间，**旧版照常可见**；新版过审后原子切换。
- **C6 新章外显**：从未过审的章节在学员侧**完全不出现**——列表、计数、搜索、直连 id 一律按不存在处理（404 不泄漏存在性，与 ADR-0058 不变式同构）。
- **C7 管理员写面**：管理员（＝审核者）编辑章节**直接生效、不进队列**（自审空转）；配改前确认框 + 审计留痕兜手滑。
- **C8 审核者与约束**：仅管理员可审；**单 pending 约束**——同一章节同时只允许一个在审快照，重复提交拒绝（状态前置哨兵同构）。
- **C9 审核队列（管理端）**：按提交时间排序的待审列表 + 在审快照详情预览 + **批量过审 / 批量驳回**（批量驳回统一理由，先例同构）。
- **C10 通知**：过审/驳回发站内信 typed event（`review_status` payload，typed event constructor 先例同构）。
- **C11 学员可见谓词**：章节可见 ＝ 课程可见（`status=1` ∧ 已挂载）∧ 章节存在已发布槽；三个读面（课程详情/章节详情/章节附件投递）同一谓词。
- **C12 存量豁免**：上线时存量章节一次性视为已过审（置已发布槽），机制只管其后的新增与改动；存量巡检另行安排，不在本机制内。
- **C13 文件挂接与审核的关系**：挂上章节才随章送审（B2）；在审快照与已发布槽引用的文件视同挂接中（B5），库侧不可删。

### 各端需求面（概要，实施票再细化）

- **Web 导师端**：文件库管理页（B7）；章节编辑改造为「保存草稿 / 提交审核」两动作 + 审核状态与驳回理由展示（C2/C1）。
- **管理端**：章节审核队列（C9）；管理员编辑章节的改前确认（C7）。
- **移动端**：录制 + 分片上传（块 A）+ 文件库管理 + 章节挂接；载体与录制 UI 归 [#2490](https://github.com/DriftingLi/FL/issues/2490)，本规格只约束契约与语义。
- **学员端**：无新功能；可见性谓词收紧（C6/C11）自动生效。

## 2. 分片契约关键数字（调研实测/官方口径）

完整证据与来源链接见 [docs/design/20261113-分片上传契约调研.md](20261113-分片上传契约调研.md)。要点：

- 分片 5–8 MiB：R2/S3 强制最小片 5 MiB；**Go `http.Server` 60 秒读超时**是唯一硬约束（`backend/cmd/server/main.go:176-181`），1 Mbps 上行 5 MiB≈42s、8 MiB≈67s。
- 分片数 ≤10,000（R2/S3 同值）；单片 5 MiB–5 GiB，末片无下限、除末片外等大；未完成会话 7 天自动 abort（可配 lifecycle）。
- 反代面：EdgeOne 单请求默认 800MB（分片天然绕开）、Caddy 无 body 限制、gin 无 MaxBytesReader。
- uni-app x：无内建分片/续传/后台传输；`FileSystemManager` `position`+`length` 切片循环发送可行（官方告诫一次性读 ≤16M）；`uni.uploadFile` 单次＝一个 multipart POST、默认超时 120s、UploadTask 仅 `abort`/`onProgressUpdate`。
- 10 个既有单发端点原样共存（仅 tutor 章节上传涉视频档）。
- 三项需实测：弱网 5 MiB 是否落 60s 窗、uni-app x 大 buffer 内存、EdgeOne 实配上限。
