## 0. 置顶结论（三笔可省的账，每笔都有时间戳）

1. **② 微信开发者工具门是最大黑洞，而且大头是「白烧」不是「慢」。** 3 张票共 **12 次调用，9 次以失败/超时收场**（#1443 连烧 5 次，每次 `reason=sdk-version-missing`；#1422 烧 2 次，`devtools-open/close 超过 120 秒未返回`）。失败轮实测 **9–26 分钟/次**（相邻 mtime 间隔），而脚本文档口径写的是「成功 ≈4.5 min」——**"4.5 分钟"是最好情况，不是预期值**。三票 ② 段合计：#1422 ≈36 min、#1443 ≈86 min、#1467 3 次跑。
   **成因（2026-10-03 二订，撤回第一版的因果链）**：这 9 次白烧**全部落在「开发者工具会话不就绪」这一族**（`sdk-version-missing` / `page-stack-not-answering` / `devtools-open|close 超过 120 秒未返回`），而门自己**已经**带两道前置断言并且是硬失败：产物合法性 `exit 1`（`mp-weixin-check.ps1:1125-1138`）、产物 appid 与期望不一致 `exit 1`（`:1141-1149`，且注释明说 `--appid` 不改产物、产物一律取自 `manifest.json` 的 `mp-weixin.appid`，缺则落 `touristappid`）——**这两道都发生在开工具之前**，所以"产物坏了"那一族本来就很便宜。第一版把 `manifest 回写 → touristappid → sdk-version-missing` 串成一条链是**错的**：#1422 那次 15:20 的失败是在**通过**了 appid 断言之后才发生在 `MP_WEIXIN_READY` 上的（证据：`1422-wx-check.log` 头部有 `[publish-mp-weixin]`、失败行是就绪闸门）。脚本自载的成因是**坑位 6**：`auto → 端口` 段绑到「没加载项目的新 IDE 实例」⇒ `Tool.getInfo` 缺 SDKVersion、`App.getPageStack` 永不应答（`:61,166,581,710`；`docs/adr/0008:257`），**对策已是「close→open→auto 整段重试 `-AutoAttempts`（默认 3）」** ⇒ 一次调用＝最多 3 轮白等，这正是 9–26 min/次的来源。
   ⚠️ 一条被我**高估了**的线索（一订原话是「现成 fail-loud 判据被忽略 ⇒ 36 min」，不成立）：#1422 的 `wx-doctor`（15:12:27）确实输出「环境**未就绪**（2 层 FAIL）：`dist app.json = False`、`产物 appid = ''`（期望 `wx38c3e31b16a7ced0`）」，9 分钟后仍去跑 ②；但 15:20 那次**开头就重新 publish 了**，appid 断言因此被满足、真正的失败发生在后面的就绪闸门 ⇒ **doctor 报的是「产物层」、被那次 publish 自愈了，它挡不住的是「会话就绪层」**。所以 doctor 前置这条只值「产物坏了」那一族失败（本批样本 1 次），**不值那 36 min**——36 min 的账要记在会话不就绪 + 整段重试上。
2. **「sha 一变就重跑整道门」是不必要的，校验器早在 2026-09-12 就放宽了。** 取证据点：#1443 在 01:20:30 又跑了一次**完整 ④c**（publish 53 s + kotlinc 全模块，01:23:24 结束 ≈2.9 min），只为把 ④ 门评论绑到新 sha `c3adc58`；而 `git diff --name-only 4438dcf c3adc58` 只有一个文件——`docs/verification/mp-weixin/1444/current-after.jpg`（零运行时面）。按现行判据（`.github/workflows/pr-evidence.yml:137-146`：证据 commit 是 head 祖先**且**其间无运行时面改动 ⇒ 仍算绑上），**这次重跑与重贴都不必**。#1467 同理：merge 提交 `27e68a9` 带进来的只有 `#1468/#1470` 的 Go 域搬包 + 本分支 ② 截图，②（16:25:31）与 ④c（16:30:13）仍各重跑一次绑 `7f405fe` ⇒ ≈7.5 min 白付。
   机制：`kotlin-all-check.ps1` / `mp-weixin-check.ps1` 的参数表里**没有**「复用已有结论、只重贴」这条路径（`-PostToPr` = 整道门重跑；`kotlin-all-check.ps1` 全文 grep `祖先|ancestor|compareCommits|运行时面` **0 命中**）⇒ **校验器的放宽口径没有传导到取门脚本**，默认动作就退化成「重跑」。
3. **PR 开早了，就把门变成重复劳动。** #1443 的 PR #1444：`13:11:17Z` 实现提交 → `13:12:22Z`（本地 21:12）**开 PR**，此时 ④c/①/② 一道没跑完；随后 4 次 push（`0f9dcf9`＝**④c 实测红修**、`4438dcf`＝①a 取证、`c3adc58`＝② 截图），门一路跑到次日 `01:23`，`17:32:05Z`（本地 01:32）合并——**PR 生命周期 4h20m，其中取证尾段 131 min**。#1471（#1467）也是开 PR 后 15 分钟才贴第一条证据，最终**未合并即关闭**（17:29），issue 判 `wontfix`（20:01），改立 #1478。`docs/agents/release.md:18-20`「一件做完并验完再开 PR」防的正是这个形态。

**一条候选成因（现值可核，但因果未证实——别当结论）**：`sdk-version-missing` 字面是「工具没给出 `SDKVersion`」。除了脚本自载的「绑到没加载项目的新 IDE 实例」（上面坑位 6），本机还有一处可疑现值：**build 产物的调试基础库版本为空**。三处现值如下——

| 位置 | 现值 | 读法 |
|---|---|---|
| `training-app/…/manifest.json`（`mp-weixin` 段） | **无 `libVersion` 字段**（只有 `:14 "appid": "wx38c3e31b16a7ced0"`） | HBuilderX publish 从这里生成配置，缺字段就写空 |
| `training-app/…/unpackage/dist/build/mp-weixin/project.config.json:15` | `"libVersion": ""`（`:16 appid` 正常） | ② 门 publish 的就是 **build** 这份（`1422-wx-check.log` 的 `dist = …\unpackage\dist\build\mp-weixin`） |
| build 目录 `project*.json` 清单 | **只有 `project.config.json`，没有 `project.private.config.json`**；而 **dev** 产物那份私有配置里写着 `"libVersion": "development"` | 工具打开 build 项目时**没有私有覆盖**可把基础库补上 |

⇒ **同一工程，dev 产物有基础库、build 产物没有；② 门拿的正是 build 产物**——这是「值得现测一次」的线索，**不是结论**：本批 9 次失败没有任何一次留下「基础库缺失 vs IDE 实例未加载项目」的区分证据（两者的表象都是 `SDKVersion=(缺失)`），而 `docs/adr/0008:257` 与 `mp-weixin-check.ps1:61,166` 把这一族归给后者并给出了对策。若现测证实是前者，修法才轮到「给 `manifest.json` 写 `libVersion`」——注意 `manifest.json` 是三份运行时面 json 之一、受「不提交 / 会被回写脏改」纪律约束（`AGENTS.md:325`、`docs/adr/0008:275-278`），改它要连同该纪律一起裁定，不是顺手加一行。

顺带一条**性价比**提醒（不是耗时问题，是收益问题）：三票里 ② 门**成功的 3 次全部带 `navigation=SKIP（reason=navigation-api-unsupported）`**，12 次调用**没有一次**真正跑成逐页导航＋每页截图。也就是说花 20–90 min 换到的结论只是「入口页 console 无 error/exception + 1 张当前页截图」（`mp-weixin-check.ps1:118-122` 的非等价声明）。
