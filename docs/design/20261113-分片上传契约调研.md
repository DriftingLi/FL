## 0. 一句话结论

**三段形态在四面上全部可行，没有硬阻断**：R2/S3 原生 multipart（≤10,000 片、单片 5 MiB–5 GiB、总 ≤5 TiB，未完成会话 7 天自动回收）可直接承载分片；反代链上唯一的硬约束是 **Go `http.Server` 的 60 秒读超时**（每个分片 PUT 必须在 60s 内传完 body，⇒ 分片取 **5–8 MiB 量级**）；uni-app x 的 `uni.uploadFile` 无内建分片/续传/后台传输，但文件系统 API 足以自行切片、循环发送、按分片序号续传；既有 10 个单发 multipart 端点全部可原样保留、与分片会话端点共存。

## 1. 背景

导师端将通过移动端（uni-app x）录制课程视频并上传，量级数百 MB~GB。已定决策：上传采用「分片 + 断点续传」的**载体无关契约**（init 会话 / 分片 PUT / complete 拼装三段形态），载体选型另票决策。仓内现状：存储抽象 `backend/internal/storage/storage.go`（LocalStorage / R2Storage 两实现）、上传闸门 `backend/internal/filestore/file_store.go`（video 档 200MB 上限）、既有上传端点均为单发 multipart（一次请求读完整个文件进内存）。本调研回答四个问题并给出可直接写进契约的数字。

## 2. 问题 1：R2/S3 multipart 能力与 Storage 抽象扩展面

### 结论

1. **R2 的 S3 兼容 multipart 能力完备**：CreateMultipartUpload / UploadPart / CompleteMultipartUpload / AbortMultipartUpload / ListParts 五操作齐全，分片可并行上传、可断点续传（枚举已收分片后补传）；未完成的 multipart 会话**默认 7 天自动 abort**（可配 lifecycle 自定义）。
2. 仓内 `R2Storage` 用的 `aws-sdk-go-v2/service/s3` 客户端（`backend/internal/storage/r2.go:15`）**本身就带全套 multipart 操作**，不需要换 SDK；扩展面在 `Storage` 接口——现接口只有整对象 `Save(ctx, key, content []byte, contentType)`（`backend/internal/storage/storage.go:34-35`，**[]byte 一次性进内存**，GB 级不可用），需要新增 multipart 一族方法（或独立 seam）。
3. LocalStorage 模拟分片语义可行：本地暂存目录按 `upload_id` 存分片文件，complete 按 partNumber 升序顺序拼装成最终文件，abort 删暂存目录；孤儿会话回收可直接复用仓内既有悬空回收单点（`backend/internal/filestore/orphan_sweep.go:17-40`，`OrphanSweepConfig{TTL}` + `RunOrphanSweep`，ADR-0027 C2）。

### Storage 扩展面（事实推导，形态归 spec）

- 新增方法族（R2 侧一一对应 S3 操作）：`CreateMultipart(key, contentType) (uploadID, err)`、`UploadPart(uploadID, partNumber, r io.Reader)`、`CompleteMultipart(uploadID, parts)`、`AbortMultipart(uploadID)`、`ListParts(uploadID)`（断点续传查询口）。也可以拆独立接口不动 `Storage`——两种都只动存储 seam，不碰业务端点。
- **流式口是硬需求**：现有 `Save([]byte)` 与 `ReadMultipartFile`（整读内存）对 GB 级不可行；分片上传本身每片只有 5–8 MiB，走内存没问题，但**本地 complete 拼装与 R2 单发回退**都需要 `io.Reader`/`io.Copy` 形态的落盘口。
- LocalStorage 模拟：`<UploadFolder>/.staging/<upload_id>/part_<n>` 暂存 → complete 时按 partNumber 升序拼接到最终 key → `Abort` 删目录 → 孤儿 `<upload_id>` 按 TTL 回收（挂 `RunOrphanSweep` 同型守护，TTL 可对齐 R2 的 7 天或更短）。这与 R2 语义完全同构（R2 侧不落暂存、由服务端持分片）。

## 3. 问题 2：反代/部署面约束与分片大小量级

### 结论

生产请求链是 **客户端 → 腾讯 EdgeOne 边缘 → Caddy（`frontend/Caddyfile`）→ Go 后端**。逐跳约束：

1. **EdgeOne**：单请求上传体默认上限 **800 MB**（超限回 413），可调可关（企业版/标准版）——对分片（5–8 MiB/片）完全不构成约束，但说明**单发 GB 级上传在当前生产链上直接被 413**，分片化是必须项而非优化项。
2. **Caddy**：`frontend/Caddyfile` 全文无 `request_body`/`max_size` 配置（只有 `reverse_proxy`/`encode` 等），即 **Caddy 默认不限请求体大小**，不构成约束。部署面 `backend/internal/deploy/`（`topology.go`/`caddy_delivery_gen.go`）只管卷与投递头，也无 body 限制。
3. **Go `http.Server` 是唯一硬约束**：`ReadTimeout: 60s / WriteTimeout: 60s`（`backend/cmd/server/main.go:176-181`）——ReadTimeout 覆盖「读完请求头 + body」，**每个分片 PUT 的 body 必须在 60s 内传完**。gin 层无 `MaxBytesReader`（grep 全仓无命中）。
4. ⇒ **分片大小取 5–8 MiB 量级**：按 60s 读窗反推，1 Mbps 上行 60s ≈ 7.5 MiB；5 MiB 在 1 Mbps 下约 42s 可传完、8 MiB 约 67s（超窗）。弱网（≤0.5 Mbps）下 5 MiB 也会超 60s——要么服务端为分片路由放宽读超时，要么客户端自适应降片（**取值定稿需实测**，见 §7）。

### 证据表

| 事实 | 数值/形态 | 来源 |
|---|---|---|
| 生产反代链含 EdgeOne | Caddyfile 注释：「命中回源鉴权 token 的请求（EdgeOne 回源）」+ `EO-Connecting-IP` 处理 | `frontend/Caddyfile:24-38` |
| EdgeOne 单请求上传上限 | 默认开启、上限 **800MB**，超限 413；企业版/标准版可调/可关 | [腾讯云 · 最大上传大小](https://www.tencentcloud.com/zh/document/product/1145/46172) |

## 4. 问题 3：uni-app x 侧上传 API 能力（只报事实）

### 结论

1. **`uni.uploadFile` 是「一次调用 = 一个 multipart/form-data POST」**，参数面 `url / filePath（或 files 数组）/ name / header / formData / timeout`，**默认超时 120,000 ms**；返回 `UploadTask`，方法只有 `abort()`（中断）与 `onProgressUpdate()`（进度百分比 + `totalBytesSent`/`totalBytesExpectedToSend`）。**官方文档未声明单请求大小上限**。
2. **无内建分片、无断点续传、无后台传输**：API 索引「网络」类只有 概述/request/upload-file/download-file/get-network-type/network-status-change/websocket/connectEventSource——没有分片上传、后台传输任务、断点恢复类 API。分片发送只能在应用层实现：**循环调用 `uni.uploadFile` 每次送一片**，断点状态（已传分片序号）由应用自行持久化、与服务端 init 会话核对。
3. **文件切片读取可行**：`uni.getFileSystemManager()` 的读接口支持 `position`（起始位置，传正整数时文件指针不动、从该位置读）与按 `length` 读的形态（fd 读 `readSync` 明示 `length` 要读字节数），读回 `ArrayBuffer` + `bytesRead`；官方同时告诫**一次性读大文件建议 ≤16 MiB**——恰好贴合 5–8 MiB 分片方案。
4. 仓库移动端现状：`api/contribution.uts:98-100` 就是单发形态（`uploadFile('/contributions/upload-file', filePath, 'file', …, timeout: 120000)`），可作为分片循环的封装参照。

### 分片发送的可行形态（事实推导，载体决策不在本票）

FileSystemManager 读 `position+length` 切出 5–8 MiB 的 `ArrayBuffer` →（需要时 `writeFile` 成临时片文件）→ `uni.uploadFile` 的 `files: [{uri, name}]` 送一片 → 循环 + 按服务端 `init` 返回的已收分片清单跳过已传片。进度直接用 `onProgressUpdate` 汇总。这条链每一环都有上表官方 API 支撑；**是否这样实现由载体票决策**。

## 5. 问题 4：既有单发 multipart 端点清单与共存口径

### 结论

全仓共 **10 个**单发 multipart 上传端点（grep `FormFile(` 与路由注册交叉核对），全部走 `filestore` 闸门（类型表白名单 + 分档大小上限）。**只有 2 个端点可能碰到视频量级**（tutor 章节上传 200MB video 档、投稿上传 20MB/文件含 mp4），其余全是图片/PDF 档，单发完全够用。共存口径（事实依据）：

## 6. 对 spec 的输入（可直接写进契约的数字/形态）

1. **分片大小：5–8 MiB 量级**（建议 5 MiB 起步）。两个边界来源：① 若载体是 R2 直传 multipart，S3/R2 强制**单片 ≥5 MiB**（末片除外）（[R2 · Upload objects](https://developers.cloudflare.com/r2/objects/upload-objects/)）；② 服务端 `ReadTimeout=60s` 限定「每片必须在 60s 内传完」（`backend/cmd/server/main.go:179`），1 Mbps 上行下 5 MiB≈42s / 8 MiB≈67s。
2. **分片数上限：≤10,000**（与 R2/S3 同值；5 MiB×10,000 ≈ 49 GiB，对 GB 级录课余量充足）。
3. **总大小上限**：R2 硬上限对象 5 TiB / multi-part 4.995 TiB（[R2 · Limits](https://developers.cloudflare.com/r2/platform/limits/)）；业务上限待 spec 定，**须覆盖现行 video 200MB 档**（`file_store.go:29-33`）。
4. **三段语义对齐 S3**：init → 会话 id（= uploadId）；chunk PUT 带 partNumber（1–10,000），**同 partNumber 重传幂等覆盖**（S3 UploadPart 语义）；complete 提交 partNumber+校验值清单、服务端**按 partNumber 升序拼装**（CompleteMultipartUpload 语义）；abort 回收（AbortMultipartUpload 语义）。
5. **断点续传查询口**：会话状态返回「已收分片清单」（= ListParts 语义，S3 单页 ≤1,000 片、可分页）；客户端据清单跳片补传。
6. **会话 TTL / 孤儿回收：7 天**（R2 未完成 multipart 默认 7 天自动 abort，[R2 · Upload objects](https://developers.cloudflare.com/r2/objects/upload-objects/)）；本地暂存同 TTL，回收守护复用 `RunOrphanSweep` 形态（`backend/internal/filestore/orphan_sweep.go:37-84`）。
7. **响应信封**：统一 `{code, message, data}`、HTTP 状态与 code 同值（`backend/pkg/response/response.go:13-15`）；仓内既有先例只豁免 Vditor 形状（`vditor_upload.go`），分片端点应走统一信封。
8. **每片一次 HTTP 请求**（uni-app x 侧 `uni.uploadFile` 单请求形态，无内建批量），客户端并发度可由 `onProgressUpdate` + abort 兜底（[uni-app x · uni.uploadFile](https://doc.dcloud.net.cn/uni-app-x/api/upload-file.html)）。

## 7. 未决 / 需实测

1. **弱网下 5 MiB 能否落在 60s 读窗内**：0.5 Mbps 上行 5 MiB≈84s 超窗——要么分片路由放宽 `ReadTimeout`（仓内有 SetWriteDeadline 越过全局超时的先例，`backend/internal/aiassistant/handler.go:407-408`），要么客户端按测速自适应片大小。**取值定稿需真机弱网实测**。
2. **EdgeOne 站点实际「最大上传大小」配置值**：默认 800MB，但控制台可调/可关——仓内看不到控制台现值，需运维确认（对分片方案无影响，对「是否保留单发大文件回退」有影响）。
3. **uni-app x `FileSystemManager.read` 的 `length` 逐平台行为**（position/length 组合、bytesRead 语义）与 **>5 MiB ArrayBuffer 分配的真机内存表现**——官方只给了「建议一次性读 ≤16M」告诫，需真机实测一次。
4. **uni.uploadFile 平台侧隐含大小限制**（官方文档未声明）：App-Android 目标下需真机试一片大 buffer；**mp-weixin 目标若保留**，wx.uploadFile 的平台限制需另查微信官方文档。
5. **complete 拼装 GB 级对象的落盘形态**：`FileStore.Save([]byte)` + 60s 内部 ctx（`file_store.go:87`）对 GB 级内存/耗时都紧张——是否给存储 seam 加流式 Save/本地直接拼装落盘，属 spec 的接口扩展面决策。
6. **断点状态的持久化位置**（客户端本地 vs 服务端会话核对优先）与「换设备续传」是否在范围内——需求口径未定，属 spec/载体票。
