# 20261026 uni-app x 官方自动化测试选型调研

- **调研问题**：官方 uni-automation-test 路线（Node 侧 Jest 驱动真机/小程序 + 截图基准图回归）与本仓移动端现有自建验收门（② 微信开发者工具截图门 + ③ 契约门两腿 Jest）相比，取舍是什么。
- **起点文章**（二手来源，2026-09-19 发布）：《uni-app x 自动化测试指南：页面截图对比测试与 Jest 体系解析》，https://blog.gitcode.com/c310be9f30458aa2c87b70f1da910bc2.html
- **一手来源**：dcloudio/uni-app 仓库 `src/自动化测试说明.md` 及配套测试文件（GitHub raw 直取，GitCode 镜像 https://gitcode.com/gh_mirrors/un/uni-app ）、DCloud 官方文档 automation 章节（uniapp.dcloud.io / doc.dcloud.net.cn）、本仓移动端 ADR 与门脚本。
- **口径纪律**：每条事实带来源；查不到一手来源的明确标注；不编造 URL 与 API。本仓文件引用一律「路径 + 小节名」，不抄规则原文。

## 1. 结论先行

1. **官方开源侧只有「截图保存」，没有「截图对比」。** 博客通篇当作主线的「页面截图对比测试」，在一手源码里是两个不同的 Jest 匹配器：`pages.test.js` 实际调用的 `toSaveImageSnapshot` **只写文件、不比较**——`fs.writeFileSync` 无条件覆盖旧基准图、恒返回 `pass=true`（仅 IO 异常才算失败）（`src/jest-setup.js:89-134`）；真正具备「不存在则生成基准、不匹配则判红产 diff 图」语义的是同文件里配置的 `toMatchImageSnapshot`（jest-image-snapshot，`customDiffDir = __snapshot__/diff`）（`src/jest-setup.js:8-18`），但截图测试流没有用它。**对比与基准图管理发生在 DCloud 内部测试平台（未开源）**——「在测试平台删除基准图」这句在官方 `src/自动化测试说明.md:10` 有出处，平台侧的对比逻辑未找到任何一手来源。⇒ 本仓若走这条路，拿到的只是采集层，**对比层要自建**。
2. **本仓 2026-09-19 已经实测过这条路线并裁定清退**，不是空白选型：移动端 ADR-0020《端到端测试通道裁决落锁与装配清退》记录了整套 `@dcloudio/uni-automator` 装配（jest.config.js / env.js / 示例用例 / 4 个 devDeps）因「配置承诺了不存在的能力」被整体删除；更早的 PR #1136 裁决「微信小程序通道只能做 page 级断言、不能做流程验证」（ADR-0020 §②、§③）。重启官方路线 = **重开已关闭的裁决** + 按 ADR-0020 附 C 逐条现测三条环境前提（插件在位 / 版本握手对齐 / adb 在 PATH）。
3. **官方 API 对 uni-app x 的支持面有明确的能力空洞，博客没有点出来。** 官方 api.md 平台差异矩阵里 uni-app x 列存在一排不支持（`element.trigger` / `swipeTo` / `moveTo` / `slideTo`、`program.mockUniMethod` 等均标 x；`page.callMethod` 与 `element.callMethod` 在 uni-app x 仅支持一个参数；Android 端 `page.data` 暂不支持取 defineExpose 暴露的 ref 数据）——对「用 Element 交互替代截图断言」的设想是硬约束。
4. **截图基准漂移是双方共同难题，本仓反而有实测标定数据、官方平台侧是黑盒。** 本仓像素比对阈值 0.5% 是同帧实测标定（噪声上方 ~45×、真变化下方 ~200×，ADR-0008「画面稳定判据必须宽容比较」节），跨天基线实测 0.919% 假红（ADR-0043 决策 5 引 `docs/agents/dev-loop.md:352` 血账），故 ADR-0043 决策 5 明确「阈值不许移植、跨发版阈值待第二次发版实测标定」；官方测试平台用什么阈值、怎么判基准漂移——未开源，不可评估。
5. **CI 集成面官方路线不占优。** dcloudio/uni-app 仓库**没有** `.github/workflows`（GitHub API 查询 404），官方示例仓库无公开 CI 配置，文档里的「推荐 CI 自动运行」只是建议；而本仓已实测托管 runner 上两道运行时门卡在**账号登录态**（DCloud `Please Login in!` / 微信 `islogin` ENOENT，ADR-0008「2026-10-16 实测回写」、ADR-0041 决策 1）——官方路线的真机链路同样只能本机跑，CI 面相对现有 ② 门**无增量**。

**一句话建议**：不替换 ②③ 门；官方路线当前唯一值得保留的兴趣点是「App 端（Android 真机）program.screenshot + Element 交互」作为 ①a 发版冒烟的**采集层候选**，但它必须先以 `/prototype` 实测回答第 6 节列出的问题，且不得绕过 ADR-0020（E2E 通道裁决）与 ADR-0043（①a 降级常态化）的现行裁定。

## 2. 调研问题与范围

**选型问题**（一句话）：在 ADR-0043 把 ② 升为常态主门、①a 降为发版前一次的格局下，官方 uni-automation-test 能否、是否值得补进本仓验收门体系，替代或叠加 ②（微信开发者工具截图门）与 ③（契约门两腿 Jest）。

### 3.4 §3 截图基准图的保存与测试平台管理（**关键失真所在**）

博客主张三段，逐段核对：

| 博客主张 | 一手核对 | 判定 |
| --- | --- | --- |
| 基准图存 `__image_snapshots__`，可用环境变量 `saveImageSnapshotDir` 覆盖 | `jest-setup.js:102-109`：`SNAPSHOTS_DIR = "__image_snapshots__"`，`process.env.saveImageSnapshotDir` 优先 | ✅ 属实 |
| diff 目录为 `__snapshot__/diff` | `jest-setup.js:6,14`：`customDiffDir = path.join(saveImageSnapshotDir /* 默认 __snapshot__ */, "diff")`——**该目录属于 `toMatchImageSnapshot`（对比匹配器），不属于 `toSaveImageSnapshot`** | ⚠️ 事实对、归属被博客混同 |
| 「基准图不存在则自动生成；不匹配则测试失败并生成 diff 图」「不在测试平台删旧基准图，Jest 会在对比时判失败产 diff 图」 | `jest-setup.js:89-134`：`toSaveImageSnapshot` 只做 `fs.writeFileSync(filePath, Buffer.from(received,"base64"))`，**无条件覆盖旧基准图、无比较、`pass` 恒为 true**（仅写文件抛异常才 false）。`pages.test.js` 用的正是它 ⇒ **开源测试流本地不可能判失败、不可能产 diff 图** | ❌ **失真** |
| 「页面变更→在测试平台删除基准图→Jest 重新生成」 | 「需要在测试平台删除基准图」在 `src/自动化测试说明.md:10` 有原文出处；但「测试平台」是什么、对比在哪发生——**官方文档 grep 确认通篇无「基准图/测试平台/jest-image-snapshot」字样**，平台侧无任何一手来源 | ⚠️ 出处有、机制未开源 |

## 4. 博客与一手来源的出入

**失真（博客说法与一手源码矛盾）**

1. **「Jest 会在对比时判失败产 diff 图」不成立于开源侧**：`toSaveImageSnapshot` 恒覆盖、恒 pass（`jest-setup.js:118-128`），`pages.test.js` 全部截图断言走它 ⇒ 纯本地跑这套测试**永远全绿**。判失败与 diff 生成只发生在 DCloud 内部测试平台（未开源）。这是全篇最要紧的一处失真：照博客理解去评估「官方截图回归的严格性」会高估。
2. **把 `toMatchImageSnapshot` 的语义安在了 `toSaveImageSnapshot` 上**：「不存在自动生成 / 不匹配判红产 diff」是 jest-image-snapshot 匹配器的行为；diff 目录 `__snapshot__/diff` 也是 `toMatchImageSnapshot` 的配置（`jest-setup.js:9-15`）。博客未区分两者。

**语焉不详（有出处但机制不完整）**

1. **「测试平台」全程黑盒**：只有 `自动化测试说明.md:10` 一句「需要在测试平台删除基准图」；平台是什么（DCloud 商业测试平台）、对比阈值、机型差异处理、基准图版本管理——全部无一手来源。
2. **基准漂移与机型差异只字未提**：官方材料对「同一页面在不同设备/不同时间的截图差异如何容忍」没有任何公开说明。
3. **`page.data` 的 defineExpose 支持口径打架**：api.md 平台矩阵写「Android 端暂不支持」，quick-start 更新记录写「HBuilderX 4.13 起支持」——两处并存，博客任选一边都没引。

**单边内容**

- **博客有、一手无**：第 3.4 节表格里的对比失败/diff 机制描述（仅平台侧可能成立，无来源）。
- **一手有、博客无**：① `element.trigger`/`swipeTo`/`moveTo`/`slideTo` 等在 **uni-app x = 不支持**的矩阵格子；② `callMethod` 在 uni-app x 单参数限制；③ dcloudio/uni-app 无公开 CI 配置；④ `jest.setTimeout(50000)` 等小项。①② 对 uni-app x 项目（本仓）恰是决定性的。

| **元素定位 API 能力** | Element API 丰富（$/$$/text/attribute/tap/input/scrollTo…），但 **uni-app x 列有整排不支持**（trigger/swipeTo/moveTo/slideTo 等），`callMethod` 单参数，Android defineExpose ref 数据受限（api.md 平台矩阵） | ② 门实测：`page.$('.class')` + `text()` 可用（ADR-0008 2026-09-18 复测，verdict `class-selector-usable-tap-flow-unproven`）；`mp.reLaunch`/`mp.navigateTo` 恒 `Uncaught [object Object]` ⇒ 导航组诚实 SKIP（ADR-0008「小程序门」）；③ 门行为腿用 `utils/utsHarness.js` 真执行 .uts 绕开设备 | 官方 Element 在 uni-app x 上的能力**纸面就不完整**，「用交互断言替代截图断言」的前提不成立；本仓 ② 的导航缺陷是 miniprogram-automator 侧的，官方 uni-automator App 侧能否避免——未实测（第 6 节） |

| **与 ②③ 的重叠/替换关系（ADR-0043 语境）** | 提供「逐页截图回归 + 元素交互」整套采集；② 门的截图（`.ci-verify/*.png`）与之重叠；③ 门（契约测试）与之正交 | ADR-0043：② 升为每个运行时面 PR 的常态主门，①a 降为发版前一次；ADR-0020：E2E 通道已裁决不做并清退装配，「别再重开这个问题」（spec §②）；③ 门判据 = 改坏被测物会不会红（classify-guards.mjs 行为/接线二分） | **不构成替换**：官方路线覆盖的是 ①a（发版冒烟）的采集面，且 ADR-0043 刚把这一面降频；引入它 = 重开 ADR-0020 裁决，程序成本明确。③ 门是纯逻辑契约层，官方路线完全不触碰 |
| **迁移成本** | 需按 ADR-0020 附 C 重启配方逐条现测三前提：插件在位（本机 HBuilderX 5.23 已内置 `hbuilderx-for-uniapp-test` 5.2.1，ADR-0020 附 A）、版本握手对齐（`@dcloudio/uni-automator@2.0.0` 与 HBuilderX 树内 `3.0.0-*` 的 `.automator/*.json` 精确相等要求——ADR-0020 附 B 判「配置齐全表象下的必然失败点」，npm 上该包已带 `deprecated: error version`）、adb 挂 PATH；另有 Windows 侧已知缺陷：其编译步骤 spawn `npm.cmd` 无 shell ⇒ EINVAL（ADR-0008 2026-09-18 修订第 6 条）、HBuilderX CLI 失败退出码恒 0 必须解析 stdout（ADR-0008「CLI 勘误」） | 现状零迁移：②③ 门、判据校验器、证据流均已运行数月，守护测试成体系 | **迁移成本高且回报未证**：ADR-0020 当时的实测结论是「预期回报很低」——元素级/导航级断言在当时组合下不可用，而那恰是 E2E 唯一能提供的东西（ADR-0020 附 C5）。App 侧链路（adbkit）未测过，是唯一未被该结论覆盖的面 |

## 6. 纸上判不出的项（需 `/prototype` 实测）

以下各项**纸面辩论到此为止**，不做推断性结论：

1. **App 端（Android 真机）`program.reLaunch`/`navigateTo`/`Page.waitFor`/`Element` 的实际可用性**：ADR-0020 的「恒 `Uncaught [object Object]`」实测对象是**微信通道**（miniprogram-automator + 开发者工具）；官方 uni-automator 的 App 通道（adbkit + uniappx 基座）在本机从未跑过（`unpackage/**/.automator` 全树 0 命中，ADR-0020 附 A）。这是官方路线唯一可能提供增量的面，必须实测。
2. **版本握手能否解开**：ADR-0020 附 C 建议用 HBuilderX「初始化测试环境」让插件补配对版本运行时——该路径能否让 `.automator/*.json` 与 `uni-automator` 版本对齐，未测。
3. **截图基准在真机的漂移率**：同一 APK、同一页面、跨天/跨电量/跨温度的像素差分布——决定自建对比层（若接 jest-image-snapshot）的阈值，本仓只有 ①a 侧的 0.5%/0.919% 数据（同帧/跨天，ADR-0043 决策 5），App 自动化截图流未标定过。
4. **`page.data`/defineExpose 在当前 HBuilderX 版本（本机 5.23/5.24）uni-app x Android 上的真实支持度**（api.md 与 quick-start 更新记录口径打架，见 3.6）。
5. **整套链路的耗时账**：官方示例 `BATCH_SIZE=20` 分批 + testTimeout 30-50s，在本仓页面规模（pages.json 页数）下一轮截图回归要多久、能否塞进「发版前一次」的预算——只能实测。
6. **云上集成**：受 ADR-0041 决策 1（账号登录态结构性不可解）约束，纸面判断为不可行；若要推翻需在托管 runner 重做探针实验，成本与收益均待议。
