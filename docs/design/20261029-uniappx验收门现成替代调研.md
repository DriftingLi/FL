## 1. 两处前提错误（这两条比答案更值钱）

**后果**：`@dcloudio/hbuilderx-cli` 的三道版本门槛（`uni-launch` 5.0+、`uni-test` 4.87+、`uni-logcat` 4.87+）**本机全部满足**。问卷 A2 问"门槛是硬要求还是建议"这件事，价值下降为"确认破坏性变更"，而不再是"能否用"。

### 1.2 官方测试环境里有 `jest-image-snapshot`，不是"只有保存"

`plugins/hbuilderx-for-uniapp-test/src/environment/package.json`（`hbuilderx-for-uniapp-test-lib` v3.0.0，官方测试环境依赖清单）原文：

```json
"dependencies": {
    "@playwright/test": "^1.58.1",
    "playwright": "^1.58.1",
    "adbkit": "^2.11.1",
    "cross-env": "^7.0.3",
    "jest": "^27.0.4",
    "jest-environment-node": "^27.4.4",
    "jest-image-snapshot": "6.1.0",
    "node-simctl": "^6.4.1",
    "minidev": "2.2.5"
}
```

且 `changelog.md` 有对应条目：「更新 测试环境依赖，**增加 jest-image-snapshot**」（0.3.0 版）。

**这意味着什么**：`jest-image-snapshot` 是 pixelmatch + SSIM 内核的业界标准截图断言器（首跑自动落基线、`--ci` 下差异即红、`failureThreshold`/`threshold` 可调、可选 `diffDir` 出对比图）。**这正是你们自建的 0.5% 阈值 + 基准图管理那一层的现成替代**，而且是官方自己装进测试环境的。

**但必须区分两件事，不能混为一谈**：

- `toSaveImageSnapshot` / `toMatchImageSnapshot` 是 **uni-automator 的 API 面**；
- `jest-image-snapshot` 是**通用 matcher**（`expect(buffer).toMatchImageSnapshot()`）。

ADR-0044 当初的判据是"`toSaveImageSnapshot` 无条件覆盖、恒 pass"——这条可能对**那个具体 API**成立，但由此推出"官方没有对比能力"是**把 API 面的缺陷放大成了能力面的缺失**。准确的说法是：**官方给的是"截图 + 通用 matcher"，基线策略与阈值口径要自己定**——也就是你们已经写好的那部分判据，仍然要写，但底层 diff 引擎不用再自己维护。

## 3. 官方通道不是 headless（B1/B2 的真正答案）

这是本次调研最有决策价值的一条。`src/HBuilderXCli.js` 里：

- `:217` `let workspaceFolder = await hx.workspace.getWorkspaceFolder(projectPath);`
- `:219-220` `if (workspaceFolder == null) { … "[自动化测试] 无法获取到项目信息，请确认项目已拖入到HBuilderX中" }`

也就是：**`cli uniapp.test` 要求该项目已经作为工作区被 HBuilderX 打开**，它跑在 HBuilderX 插件宿主里，不是独立进程。

与本仓已有调研互相印证（不重复，只引用）：`docs/design/20261028-HBuilderX-cli-publish仅编译原语参数面调研.md` 已记「官方多处明写**执行命令前，请先启动 HBuilderX**，`cli --help` 亦然」⇒ 前提里隐含的"不占 HBuilderX 单实例"= **不成立**。

**推论**：走官方通道**不会**让编译/测试搬进无桌面容器；单实例排队这条铁律不变。B1 的问题因此收窄为**只剩一句真需要问**：「有没有非交互登录 / headless runner 的官方路线」。

## 6. 对决策的净影响（我的看法）

1. **"官方路线已被排除"这条需要重开**。ADR-0044 的排除理由建立在"只有保存没有对比"上，而官方测试环境依赖里就有 `jest-image-snapshot`。不必立刻推翻 0044（它当时实测清退过整套装配，那部分结论仍然有效），但**它的判据面选错了**——问的是 API 行为，没看环境依赖。这与清算文档 §3 记的同一个病（判据面选窄会稳定给出"干净"的错答案）是同源的第三次。
2. **能省的是"写驱动"，不是"排队"**。`cli uniapp.test` 替掉的是 2,461 行的 GUI 驱动与切页脚本；单实例、开发者工具依赖、真机占用一样没省。按清算表的账，这对应 D2 一整块 + D1 的切页部分，**是这次唯一一处"能减掉四位数行数"的机会**。
3. **截图 diff 引擎可以立刻降级为"用现成的"**：`jest-image-snapshot` 或 odiff，替换你们自写的比对与裁切工具（747 行一次性工具 + 阈值标定）。**阈值口径仍得自己定**——跨天 0.919% 假红不是 diff 引擎的锅，是"什么时候允许重落基线"的规则没定。
4. **一个必须先做的前置实验（不到半天）**：在本机 5.26 上对**一个已有页面**初始化官方测试环境（产生 `env.js` + `jest.config.js`），跑 `cli uniapp.test app-android` 与 `mp-weixin` 各一次，只看两件事——① uvue 页面能否被 `reLaunch` 到、元素能否选中；② 多设备弹窗是否会卡住脚本。这两条一票决定 A4/D1/D2 是否能落地。**在拿到这两个读数前，不要改任何门。**
