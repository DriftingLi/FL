## 票面订正（三）：「客户端补上限 = 与后端一致」只对 ASCII 严格成立

PR #1316 的 spec 轴评审复核后端唯一规则源后所得（PR 正文「诚实边界」第 8 条同记），单独回报一次，因为它改变本票「一致」这个词的读法。

**本票口径**：客户端补 `> 20` 上限之后，预请求校验即与后端规则源一致、21-32 位不再打到后端才拿 400。

**现测（`backend/internal/service/password_write.go:34-37`，逐字）**：

```go
func validatePasswordLength(password string) error {
	if len(password) < 6 || len(password) > 20 {
		return errors.New("密码长度需为 6-20 位")
	}
```

`len(string)` 在 Go 里是**字节数**，而客户端 `.length` 是 **UTF-16 码元数**。⇒ 两边数的单位不同：

- 7 个汉字 = 客户端 7 个码元（放行）= 后端 21 字节（400）⇒ 「21 位本地就拦、不打后端」在含非 ASCII 的口令上**不成立**；
- 反方向不存在误杀：码元数 > 20 ⇒ 字节数必 > 20，两页都会拦 ⇒ 只会「放过该拦的」，不会「拦掉该放的」。

**本票不因此改修法**：客户端要精确对齐就得自己数字节（`unescape(encodeURIComponent(p)).length` 一类），那属于把后端单位口径抄进客户端，风险与本票「客户端只多拦一次」的定位不符 ⇒ 按 #1286 那条「采用后端口径要单独裁」的同族纪律处理。

**守护侧的连带如实记**：新增的行为守护 `utils/authPreRequestValidationBehavior.test.js` 的区间样本全用 `'a'.repeat(n)`（纯 ASCII），**抓不到**上面这一类偏差 —— 它证的是 ASCII 下的区间两侧。

缺口在规则源那一侧（「6-20 位」到底指字节、码元还是字符），不在移动端射程：

- 若裁**字节** = 现状（`len()`），则客户端文案「位」应改成明确单位或改判字节；
- 若裁**字符** = 后端应改用 `utf8.RuneCountInString`，则本票客户端这一档才是完整一致。
